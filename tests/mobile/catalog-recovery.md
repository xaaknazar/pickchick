# Восстановление заказа при недоступном каталоге

Сохранённый TEST-сеанс проверяется независимо от загрузки меню. Чтение истории
не создаёт новую сессию; ошибочный ответ означает неизвестное состояние, а не пустой
список заказов. Последние полученные заказы остаются в памяти при последующем сбое.
После холодного запуска без связи показывается объяснение и повторная проверка;
локальная история не выдаётся за свежие серверные данные.

Создание новой корзины требует завершённого восстановления и свежего подтверждения
TEST-capability вместе с каталогом. Ранее сохранённый запрос можно восстановить
с прежней идентичностью/ключом. Открытие уже созданного заказа не зависит от меню.

Проверки 6 сентября 2026:

- 32 mobile unit-теста прошли, включая четыре новые проверки границы чтения:
  сохранённый заказ при сбое каталога, недоступный read без потери intent,
  отсутствие скрытой регистрации при открытии истории и истёкшая идентичность.
- TypeScript, ESLint и Expo web export прошли.
- `browser_catalog_recovery.py` прошёл на локальном export: сохранённый unknown-заказ
  при недоступном каталоге, cold reload со сбоем orders, ручное восстановление,
  переход к прежнему unknown из checkout без POST и правдивый retry доступности M11.

В браузерной регрессии все `/v1/**` перехвачены. Использованы только явно обозначенные
фикстуры; реальных заказов на VPS создано **0**. Это проверка интерфейса
при отказах сети, отдельно от ранее выполненного настоящего HTTPS journey.

Запуск после локального Expo web export и SPA-сервера:

```sh
MOBILE_RECOVERY_URL=http://127.0.0.1:4182 \
  .local/design-venv/bin/python tests/mobile/browser_catalog_recovery.py
node --test tests/mobile/*.test.mjs
```

M10 теперь доступен из сообщения о фактической смене версии меню; это сообщение
не скрывается при успешном ответе. M11 доступен из ошибки загрузки и после retry
показывает фактическое подтверждение/неизвестность, а не постоянный текст о закрытии.
