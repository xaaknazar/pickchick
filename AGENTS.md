# PickChick — постоянные правила разработки

## Источник плана

Канонический репозиторий: https://github.com/xaaknazar/pickchick.
Актуальный план находится в `docs/01-technical-spec.md` — `docs/07-sources.md`;
начинать с `README.md` и `docs/project-status.md`.
ZIP v1 и его распакованная копия — исторические снимки, не источник текущих требований.

Заказчик поручил разрабатывать проект поэтапно по этому плану и сохранять
в GitHub все изменения проекта. Срок — четыре календарных месяца,
включая тестирование и внедрение. Дата T0 пока не зафиксирована.

## Порядок работы

- Перед изменениями прочитать текущий этап, рабочее дерево, затронутые разделы ТЗ
  и критерии приёмки. Сохранять чужие незакоммиченные изменения.
- Выполнять законченные, проверяемые этапы. Обновлять `docs/project-status.md`:
  что реализовано, что проверено, что не начато и какие зависимости остались.
- Решения пользователя имеют приоритет. При изменении архитектуры/объёма
  обновить соответствующий документ и записать причину; не менять план молча.
- Требования и возможности Kaspi, ККМ, Яндекса не выдумывать. Симулятор
  и sandbox не выдавать за подтверждённую production-интеграцию.
- Не отправлять сообщения поставщикам и другим людям без прямого поручения.

## Данные и инварианты

- Деньги хранить в целых минимальных единицах, финансовые эффекты — в PostgreSQL.
- Redis не является единственной копией заказа, платежа, чека или бонусной операции.
- Подтверждение оплаты получать от доверенного банковского/терминального адаптера.
- Использовать идемпотентные операции и durable outbox/inbox.
- Cloud и edge имеют явное владение агрегатами. Не применять last-write-wins
  к деньгам, остаткам, выдаче и бонусам.
- Касса/кухня/табло должны работать через локальный узел при потере WAN;
  доступность банка и законного фискального режима проверять отдельно.
- Не сохранять в репозитории токены, пароли, ключи, production-дампы,
  реальные телефоны клиентов и платёжные реквизиты.

## GitHub и проверки

- Для новых этапов разработки создавать короткие ветки `codex/<task>`.
  Публиковать проверяемые коммиты и ветки в канонический репозиторий;
  проходить PR/CI, когда они настроены. Не использовать force-push в общие ветки.
- Перед коммитом проверять staged diff и отсутствие секретов. Не добавлять
  посторонние пользовательские файлы и локальные копии архивов.
- Запускать проверки, соответствующие изменениям. Не заявлять, что тесты,
  интеграции или развёртывание прошли, если это не подтверждено результатом.
- После завершённого этапа отправлять коммиты в GitHub и сверять удалённый SHA.
  Если push не прошёл, сообщить об этом и сохранить локальную работу.
- Общие contracts, миграции и дизайн-токены изменять согласованно.
  Одновременные задачи выполнять в разных ветках/рабочих копиях.

## Отчёт пользователю

Сообщать результат этапа, проверки, ссылку на коммит/PR и следующий этап.
Не обозначать настройку GitHub как готовность backend, CI, банковских API
или рабочего ресторана.

## Перенос дизайна

- В текстах интерфейсов использовать обычный дефис `-` вместо длинных тире,
  включая диапазоны и обозначения пустых значений, по решению владельца.
- Для мобильного приложения визуальный источник — `design/reference-source/mobile-v2.html.txt`
  и исходные материалы заказчика. Не заменять его нашей интерпретацией в галерее.
- Сверять реальные скриншоты первичных экранов с оригиналом: композиция, размеры,
  типографика, изображения, фиксированные действия. Проверка переходов между
  всеми страницами не является доказательством визуального соответствия.
- На витрине фонового видео нет кнопки паузы по прямому решению заказчика.
  Системное сокращение анимации, пауза при уходе в фон и статичная обложка сохраняются.
