# Синтетический TEST-каталог и заказы

Это общий серверный сценарий для проверки mobile/kiosk → кухня → табло.
Он не представляет продажи, банковские подтверждения, ККМ или бонусные операции.
`TEST_ORDER_FLOW_ENABLED` разрешён только в local/test/staging.

## Совместимость выпуска

Без query-параметра `/v1/test/*` возвращает точный формат `mockup-v0.2`, который
понимает установленная сборка iOS 3. Новый клиент передаёт
`?catalog_version=mockup-v0.3` во всех TEST-запросах. Каталог v0.2 сохраняет прежние
11 товаров и цены; v0.3 содержит 24 позиции исходного дизайна.
Версия корзины выбирает серверный расчёт независимо от формата ответа.
В ответе v0.3 старые заказы сохраняют старый снимок; клиент читает union схем.

Снимки PostgreSQL не переписываются. При ответе старому клиенту новый снимок
проецируется в старый формат: выбранный состав добавляется в название, цена
содержит доплаты, `id` строки содержит её уникальный `line_id`. Это исключает
совпадающие ключи двух вариантов одного блюда на старом экране кухни.
Модификаторы остаются читаемыми и в заданиях кухни.

## Новый состав

Корзина передаёт только `product_id`, `quantity` и
`selections: [{ group_id, option_id, quantity }]`. Допустимы разные варианты
одного SKU, максимум 11 строк / 20 единиц в строке. Дубли одного варианта и
одной опции, неизвестные/недоступные опции, превышение лимитов и чужая цена
отклоняются. Сервер проверяет сумму выбранных количеств по min/max каждой группы.

`testLineId()` — чистая общая функция идентичности варианта, экспортирована из
`@pickchick/test-order-flow/contracts`. Без выбора она возвращает product ID;
порядок выбранных опций не меняет идентичность. Снимок фиксирует исходную цену,
итоговую цену единицы, названия/доплаты/количества выбора и данные базовой порции на момент
расчёта. Полный справочник возможных опций в строки заказов не копируется: он
остаётся в каталоге. Это ограничивает объём истории на мобильном клиенте. Смена справочника не меняет старый заказ.
`payment_method` — `kaspi` или `card`, по умолчанию `kaspi`; это только выбранный
макет способа оплаты. Подтверждение остаётся явно `simulated_approved`.

Перед новым API нужна миграция `005_cloud_test_modifier_task_titles.sql`,
расширяющая текст кухонного задания до 4 000 символов. Старые данные не меняются.
Readiness требует 004, 005 и 006, когда включён TEST-контур.

## Бессрочный TEST-доступ

По поручению владельца от 7 сентября миграция 006 переводит все неотозванные
TEST-ключи и customer-сеансы в PostgreSQL `infinity`, сохраняя ID, hash токена,
роль, канал и историю. Новые ключи выдаются без срока. Отзыв проверяется на каждом
запросе; реальные staff/OTP-сессии этого решения не наследуют.

API передаёт `expires_at: "9999-12-31T23:59:59.999Z"` как совместимый ISO-маркер
для уже опубликованных strict-клиентов. Это не дата окончания серверного доступа:
БД хранит настоящую бесконечность. Драйвер возвращает число `Infinity`, которое
явно сериализуется; null, extra fields и строка `infinity` в JSON не вводятся.
Однократное `sessions/continue` обновляет старую локальную дату, в том числе при
открытом заказе бессрочного actor, не меняя заказ или результат оплаты.

40 расчётов и 20 заказов ограничивают последние 24 часа каждого сеанса, а не его
полную историю. Для выдачи новых сеансов сохранены 100 за два часа (неотозванных)
и 200 за UTC-сутки; старые бессрочные сеансы не занимают пожизненные слоты.
До 20 неотозванных служебных ключей, 20 незавершённых заказов на customer
и 2 000 на TEST-стенде. Customer получает до 20 полных снимков с приоритетом
всех незавершённых перед недавней историей; manager — до 2 000 с тем же
приоритетом. БД сохраняет всю историю, постраничный просмотр старых записей
пока не реализован. Так постоянная история не превышает лимит mobile 4 в 2 MB.
Quote по-прежнему годна пять минут. Автоочистка не удаляет бессрочный
неотозванный доступ; удаляются только записи с конечным сроком, истёкшим более
семи дней назад, либо отозванные более семи дней назад, с TEST-каскадами.
Хранение активной бессрочной истории требует контроля размера БД и явной политики
архивации на следующем этапе; молчаливой потери доступа ради освобождения квоты нет.

## Происхождение наполнения

Единственный датасет: `src/complete-catalog.ts`, также доступен мобильному
предпросмотру через чистый export `@pickchick/test-order-flow/complete-catalog`.
Источник — `design/reference-source/mobile-v2.html.txt`, SHA-256
`63ed692aaf314b3161870efb22a8680e1db679e62e7d1fd169c2626d04e42eb5`.
Все 24 описания, цены и КБЖУ перенесены из него; КБЖУ указаны на базовую порцию,
не прошли ресторанную проверку и не учитывают выбранные дополнительные продукты.
Пустые аллергены означают отсутствие подтверждённых данных, а не их отсутствие
в блюде. `ingredients` содержит исходное описание, а не исчерпывающую техкарту.

Исправлены технически испорченные ID исходника. Количество обязательных соусов
и напитков взято из письменного состава: например, два напитка у дуо и 32 соуса
у набора 100 фингерсов. У наборов на компанию нет отсутствующих в составе напитков.
Исходный общий UI ошибочно предлагал всем наборам по одному соусу и напитку.
Дополнительный платный тост начинает с нуля; бесплатный включённый напиток выбран
по умолчанию. Доплата за лимонад появляется только после его явного выбора.

Четыре варианта размера соуса сохранены как в мокапе: 60 мл, 0,3 л, 0,4 л,
0,5 л; его множители КБЖУ 1 / 5 / 6,7 / 8,3 также оставлены. Исходное описание
острого соуса при этом говорит о 60/180/300 г. Это известная несогласованность
демонстрационных данных; до реальных продаж ресторан должен утвердить размеры,
единицы и техкарты. Для воды и Piko оригинальные изображения отсутствуют,
используется идентификатор явной общей иллюстрации `generic-drink`.

ETA повторяет оценку мокапа: максимум базового времени категорий плюс
`(количество единиц − 1) × 1,2`, с округлением вверх и ограничением 120 минут.
Это не измерение текущей загруженности кухни. Полный редактор каталога в
бэк-офисе, публикации по точкам и производственные компоненты остаются в roadmap;
этот этап даёт единый API-датасет и неизменяемый выбранный состав заказа.
