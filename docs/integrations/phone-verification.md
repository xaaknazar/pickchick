# Подтверждение номера PickChick: подключение провайдеров

7 сентября 2026. Владелец предоставил API-доступ Mobizon. Ключ сохранён в
приватной конфигурации на VPS и проверен с IP сервера через read-only API.
`user/getOwnBalance` и `alphaname/list` ответили успешно; зарегистрированных
отправителей пока нет. Тариф, подпись/OTP-шаблон и бюджет ещё не подтверждены.
Реальная отправка кодов и регистрация пользователя пока не включены.
[Протокол подключения без секретов и баланса](../operations/deployments/2026-09-07-mobizon-account.md).

## Предлагаемый выбор

Начать с SMS через Mobizon; Telegram Gateway добавить как добровольно выбранный
альтернативный канал, сохранив SMS для пользователей без Telegram. WhatsApp
подключать через официальный Business Platform после onboarding. Это рекомендация
разработки, а не утверждённый заказ или оплаченная услуга.

| Канал            | Подключение                                                                          | Что учитывать                                                           |
| ---------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| SMS / Mobizon    | Аккаунт, договор/тариф, ключ API, зарегистрированный отправитель и OTP-шаблон        | Доставка на конкретные SIM Казахстана ещё должна пройти проверку        |
| Telegram Gateway | Gateway business account, токен, баланс, согласие на этот канал                      | Получатель должен иметь Telegram, зарегистрированный на введённый номер |
| WhatsApp         | Meta business portfolio, WABA, служебный номер, API access и authentication template | Допуск аккаунта и итоговый тариф проверяются при onboarding             |

Основания: [Mobizon API](https://mobizon.kz/help/api-docs/sms-api),
[Telegram verification tutorial](https://core.telegram.org/gateway/verification-tutorial),
[официальный пример Meta authentication template](https://www.postman.com/meta/whatsapp-business-platform/request/6vkv46u/create-authentication-template-w-otp-copy-code-button).

## Стоимость и сроки, которые надо учесть до выбора

На публичной странице Mobizon для персонального отправителя и начального
тарифного уровня указаны следующие цены, KZT с НДС:

| Оператор      | Имя отправителя в месяц |                           Сообщение |
| ------------- | ----------------------: | ----------------------------------: |
| Beeline       |                17 400 ₸ |                             17,80 ₸ |
| Kcell         |                14 500 ₸ |                             16,60 ₸ |
| Altel / Tele2 |                20 800 ₸ | 10,40 ₸ по верификационному шаблону |

Итого для имени на всех трёх направлениях — **52 700 ₸/месяц** плюс SMS.
Для Beeline общая подпись не подходит; регистрация персональной может занять
до 30 дней. Шаблон/категория, накопленный тариф, сегменты и возможная классификация
международного трафика влияют на цену. Это публичные условия, не коммерческое
предложение конкретному аккаунту PickChick. [Mobizon: тарифы](https://mobizon.kz/prices).

Telegram публично указывает **$0.01 за доставленный код**; финальную цену и
региональные условия нужно сверить в кабинете. Проверка `checkSendAbility` при
успехе уже платная: при последующей отправке надо использовать её `request_id`,
чтобы не оплатить второй запрос. [Описание сервиса](https://core.telegram.org/gateway),
[API](https://core.telegram.org/gateway/api#checksendability),
[условия](https://telegram.org/tos/gateway).

У WhatsApp цена зависит от рынка получателя и категории доставленного сообщения;
точную ставку для Казахстана здесь не фиксируем без актуального тарифа аккаунта
и комиссии выбранного посредника. [WhatsApp pricing](https://whatsappbusiness.com/products/platform-pricing/).

### Расчёт для 5 000 пользователей в месяц

Расчёт по скриншоту владельца и публичному тарифному плану 2 на 7 сентября 2026. Подпись включена на всех трёх направлениях: 52 700 ₸/месяц. Один код
занимает один оплачиваемый сегмент; для Altel/Tele2 действует утверждённая
верификационная категория. Микс операторов пока неизвестен. Для примера взяты
Beeline 40%, Kcell 30%, Altel/Tele2 30% — это допущение, не доли рынка или
статистика PickChick. Средняя цена SMS: 0,4 × 17,80 + 0,3 × 16,60 + 0,3 × 10,40
= 15,22 ₸.

| Отправлено SMS за месяц |      SMS |  Подпись |     Итого |
| ----------------------: | -------: | -------: | --------: |
|                       0 |      0 ₸ | 52 700 ₸ |  52 700 ₸ |
|                     500 |  7 610 ₸ | 52 700 ₸ |  60 310 ₸ |
|                   5 000 | 76 100 ₸ | 52 700 ₸ | 128 800 ₸ |

Формула: 52 700 + 17,80 × N_Beeline + 16,60 × N_Kcell + 10,40 × N_AltelTele2.
При неизвестном миксе 5 000 SMS дают диапазон 104 700–141 700 ₸, при сохранении
подписи на всех трёх направлениях. Повторы и дополнительные сегменты увеличат
сумму. Это только SMS/подпись, без VPS и других расходов проекта; это оценка,
не разрешение пополнить счёт или оформить платную услугу. Условия конкретного
аккаунта ещё надо подтвердить. Пороги 500 тыс./1 млн. в шапке тарифа относятся
к накопленным пополнениям, не к числу пользователей. [Mobizon: тарифы](https://mobizon.kz/prices).

5 000 активных пользователей не равны 5 000 SMS ежемесячно. В первый месяц
5 000 новых пользователей с одним кодом на каждого дадут строку 5 000. Если в
следующем месяце возвращаются те же люди с сохранённым входом, SMS им не нужны:
остаётся фиксированная плата плюс коды новым пользователям и для восстановления
доступа. Если каждый месяц добавляются 5 000 новых пользователей, эти расходы
на SMS повторяются.

## Сохранение входа

Поручение владельца 7 сентября 2026: после первого OTP сохранять вход в личном
мобильном приложении без плановых повторных подтверждений. Обычные открытия,
обновления, перезапуски, смена месяца и длительная неактивность не запрашивают
код. Приложение автоматически обновляет короткий access token через отзывную
сессию устройства без календарного/idle-expiry; токен обновления хранится в
Keychain/Keystore и вращается. SMS-провайдер в обновлении сессии не участвует.

При offline/timeout/5xx сохранённый вход не удаляется. Защищённые операции
ждут успешной проверки сервером, интерфейс показывает проблему связи.
Параллельный refresh или потерянный ответ не должны разлогинивать пользователя.
Новый OTP нужен при новом устройстве, явном выходе, потере локального ключа
(в том числе после очистки данных/переустановки, если ключ утрачен) либо
защитном отзыве. Удаление аккаунта отзывает все его сессии. На публичном киоске
сохраняется обязательная очистка гостевого сеанса; staff-доступ не меняется.

Требования добавлены в MOB-01 и AC-36–38. Это план реализации real auth:
нынешний локальный demo-профиль уже восстанавливается из хранилища, но не
является подтверждённым серверным аккаунтом. Реальные сессии и новый вход
ещё нужно реализовать и проверить на устройствах; эта правка документации
не включает их в TestFlight.

## Что означает «через бота»

Обычный Telegram-бот не начинает диалог с произвольным введённым номером.
Пользователь сначала запускает бота; `request_contact` позволяет запросить контакт
в личном чате. Для подтверждения в PickChick пришлось бы связать одноразовый
challenge приложения с Telegram sender, убедиться, что контакт принадлежит ему,
и завершить серверную проверку. Пересланный контакт или текст с номером не являются
такой проверкой. [Telegram Bots](https://core.telegram.org/bots),
[KeyboardButton](https://core.telegram.org/bots/api#keyboardbutton).

Telegram Gateway выполняет доставку кода на аккаунт введённого номера отдельным
официальным API. Для WhatsApp будем оценивать официальный канал authentication
и условия конкретного поставщика, а не обещать надёжность неизвестного бота.
Название/ссылка на компанию из предложения владельца пока ожидаются.
[WhatsApp Business Messaging Policy](https://whatsappbusiness.com/policy/).

## Что уже есть в приложении и почему потребуется новая сборка

Mobile 4 использует локальный demo-код `123456`. Он не подтверждает номер и не
создаёт серверный customer. Номер остаётся на устройстве, TEST-заказы связаны с
отдельной anonymous identity. Бессрочные TEST-ключи не заменяют реальные OTP.

Опубликованный mobile 4 требует `phone_auth: false` в прежнем строгом
`/v1/capabilities`; смена на true сломает загрузку меню. Для нового входа нужен
отдельный контракт `/v1/auth/capabilities` либо новая версия capabilities.
Старый ответ должен остаться совместимым. Реальный вход будет в новой сборке,
с отдельным auth state и без автоматической привязки TEST-истории по введённому
неподтверждённому номеру. Текущие поля уже имеют подсказки для OTP autofill;
его работу проверим настоящими сообщениями на физических iPhone и Android.

## Подготовленный адаптер и проверка конфигурации

В `packages/phone-verification` находится серверный транспорт Mobizon. Он
выключен по умолчанию, принимает только канонический номер и шестизначный код,
отправляет параметры в HTTPS POST body на фиксированный API host. Redirects
запрещены; срок запроса — пять секунд, ответ ограничен 16 KiB. Ошибки не содержат
телефона, кода или API-ключа. Неопределённый результат не повторяется автоматически.
Транспорт не создаёт аккаунт и не генерирует/проверяет challenge сам.

Для нового окружения создать приватный `.local/phone-verification.env` из
`.env.phone.example` с правами 0600. Существующий заполненный файл не заменять
шаблоном. API-ключ уже размещён в приватной конфигурации; не переносить его в
example-файл. До регистрации подписи и завершения серверного входа оставить
`PHONE_DELIVERY_PROVIDER=disabled`. При последующем подключении заполнить точный
`MOBIZON_APPROVED_SENDER` и выбрать `PHONE_DELIVERY_PROVIDER=mobizon`.
Проверка конфигурации не отправляет запросы провайдеру и не списывает средства:

```sh
pnpm --filter @pickchick/phone-verification build
node --env-file=.local/phone-verification.env scripts/phone-verification-preflight.mjs
```

Она подтверждает только формат настроек. Действительность ключа, баланс,
регистрацию подписи, доставку и цену можно подтвердить только в кабинете и
контролируемой реальной проверкой. Переключение этой переменной само по себе
не включает телефонный вход в опубликованном API или mobile 4.

## Серверный процесс следующего этапа

1. Приложение показывает утверждённые условия и фиксирует версию согласия,
   принимает номер и выбранный доступный канал. Выбор маркетинговых сообщений
   хранится отдельно от необходимой проверки номера.
2. Сервер нормализует номер, создаёт криптографически случайный шестизначный
   код, challenge и срок три минуты. Номер хранится зашифрованно; lookup и код —
   через раздельные HMAC. Код, полный телефон и секрет провайдера не логируются.
3. PostgreSQL атомарно резервирует лимиты номера, устройства, IP и общий бюджет
   отправки до обращения к провайдеру. Не более пяти попыток на challenge,
   повторная отправка через 60 секунд; точные дневные лимиты согласуются с
   бюджетом. Нынешний Redis с `allkeys-lru` не должен быть единственным
   хранилищем этого бюджета: eviction/restart не может обнулять ограничения.
4. Адаптер передаёт код выбранному провайдеру. `accepted` означает принятие
   запроса, а не доставку или подтверждение номера. Timeout даёт `unknown`:
   автоматического повторного списания/отправки нет. Каналы не переключаются
   бесконтрольно и не оставляют несколько действующих кодов.
5. Сервер атомарно проверяет срок, попытки, challenge binding и код. Только
   после успешного одноразового потребления создаётся/подтверждается customer.
   Затем выдаются отдельные отзывные access/refresh-сессии с ротацией.
6. Новая мобильная сборка подключается к этому API. Для gateway нужны отдельные
   auth routes и заголовки реальных данных, доверенная обработка client IP;
   нынешняя пометка всех ответов `synthetic` для настоящего auth не подходит.
7. Перед включением проверяются отказ провайдера, неизвестная отправка,
   задержанный старый код, повтор, параллельные подтверждения, бюджет, отзыв,
   restart и отсутствие секретов в логах. После этого — реальные SIM всех
   операторов и физические устройства.

Customer/consent/session/OTP-домен, публичные auth routes и новая сборка — работа
следующего этапа после выбора подключения; наличие адаптера не закрывает MOB-01
и AC-01. Миграции customer не заменяются таблицами `test_actors`.

## Данные для подключения

- Статус аккаунта выбранного сервиса и контакт владельца кабинета; для неизвестного
  агрегатора — название/ссылка, официальный API и описание канала доставки.
- Для Mobizon: ID аккаунта, подтверждённые операторы/тариф, sender и OTP-шаблон.
  API-ключ размещается в защищённом server secret-файле; не в чате, Git или Expo.
- Утверждённый лимит расходов в день/месяц и номера тестовых устройств с операторами.
- Данные юридического лица, контакт поддержки и утверждённая версия текстов
  конфиденциальности/согласия; в текущей M33 ещё демонстрационная заглушка.

Рабочий короткий текст для регистрации шаблона: «PickChick: код {code}.
Никому не сообщайте.» Окончательная формулировка зависит от регистрации шаблона
у операторов. Документ можно использовать при оформлении кабинета;
сообщения поставщикам от имени владельца не отправлялись.

API-доступ Mobizon уже получен и проверен; повторно запрашивать этот ключ не
требуется. Следующая внешняя зависимость — зарегистрированная подпись и
операторский шаблон, затем согласованные лимиты расходов и тестовые устройства.
