Их назначение и актуальная регистрация в этом обследовании не проверены. Номер кассы служит идентификатором, не секретом авторизации. Предоставленный ранее ключ iiko не является ключом Webkassa.

## Две отдельные задачи

**Чтение уже выпущенных чеков.** Официальный API описывает получение чека по номеру. В кабинете Webkassa есть «Отчёты → История чеков», поиск и просмотр/повторная печать. Для подключения PickChick нужно получить разрешённый доступ к нужным кассам и проверить чтение одного существующего документа, затем сверить номер, сумму, дату, позиции и фискальные реквизиты. Копия существующего чека не должна создавать новую продажу. Массовый экспорт за период, доступность старых чеков, ограничения, пагинация и способ получения ссылки/QR требуют актуального API-контракта; наличие истории в UI их не подтверждает.

**Фискализация новых заказов.** PickChick передаёт данные расчёта в Webkassa, получает результат и сохраняет его в заказе. Webkassa обслуживает фискальный документ и связь с ОФД; подтверждение получения денег приходит от эквайера отдельно. Получение API-доступа ещё не означает техническую приёмку адаптера или разрешение переключить ресторан.

Источники: [официальное описание API](https://promo.webkassa.kz/integrations/api), [порядок интеграции](https://promo.webkassa.kz/tpost/7szx50s9y1-kak-integrirovatsya-s-webkassa), [история и повторная печать в FAQ](https://promo.webkassa.kz/questions). Публичные материалы проверены; закрытая Postman-коллекция и актуальная полная спецификация в кабинетах не получены.

Существующий ключ обслуживающего плагина может иметь ограничения по приложению/интегратору. Возможность его использования PickChick не подтверждена. Предпочтителен согласованный доступ собственной интеграции к уже зарегистрированным кассам. Покупка нового оборудования или регистрация новой боевой ККМ не объявляются обязательными: сначала проверить повторное использование действующих касс с Webkassa/ЦТО.

## Порядок подключения

1. Владелец или обслуживающий интегратор входит в существующий кабинет Webkassa. Сверяем две ККМ, их статус, юридическое лицо, ОФД и назначение. Пароли/ключи передаются через защищённое хранилище, не в переписку и не в мобильное приложение.
2. Запрашиваем актуальный комплект для интегратора: документацию, Postman, порядок API-авторизации и доступ к нашим существующим кассам. Уточняем права чтения истории, повторное получение результата после таймаута и разрешённость совместного доступа во время перехода. Секреты iiko для этого не использовать.
3. Для новых чеков проходим официальный тестовый маршрут Webkassa: тестовый кабинет, тестовая касса/API-KEY, разработка и совместная проверка с поставщиком, затем production-доступ. Это тестирование Webkassa, не регистрация разработчика iiko и не замена существующих боевых касс.
4. Сначала реализуем серверное чтение одного чека и его привязку к заказу. Для архива используем отдельную модель импортированного документа и проверенное соответствие заказу; не сопоставляем только по сумме/времени и не публикуем все чеки всем клиентам.
5. Добавляем адаптер к существующему fiscal intent/outbox в `packages/commerce-core`. Сохраняем снимок строк, налогов и сумм до вызова; секреты остаются на сервере. При потере ответа сверяем исходную операцию, а не повторяем продажу вслепую. API-поля и endpoints не придумываются до получения спецификации.
6. Проверяем sandbox: продажа, получение копии, повтор события оплаты, потерянный ответ, restart, возврат по исходным позициям, отказ печати и сверка итогов. Сценарии X/Z, частичных возвратов и работы при потере WAN уточняем по действующей версии API и испытываем отдельно.
7. Назначаем единственного исполнителя фискализации для каждого канала. Учитываем iiko, терминал и возможную автофискализацию эквайера. Прежний канал отключаем только при согласованном переключении; чтение истории не требует остановки iiko. Пилот новых чеков проводится после приёмки тестов и реквизитов.

Предлагаемый поток: подтверждённый расчёт → серверный fiscal intent PickChick → Webkassa → ОФД; результат → сохранённые реквизиты/ссылка чека → история заказа, касса или киоск. Формат ссылки/QR берём из документированного ответа, а не строим по догадке. Реальные продажи и возвраты для исследования не создавались.
