# Связь экранов с состоянием системы

Дата: 7 сентября 2026. Идентификаторы экранов — `design/prototype/screens.json`.
Мобильные строки описывают **состав проверяемой сборки 0.1.0 (4)**.
Факт публикации в TestFlight, ревизии VPS и окончательные результаты смотрите в
[состоянии проекта](../project-status.md); эта матрица фиксирует реализованное поведение.
Визуальный источник mobile — предоставленный оригинал
`design/reference-source/mobile-v2.html.txt`; галерея не заменяет его композицию.
Эта таблица отличает работающий интерфейс от просмотра дизайна. Полный объём ТЗ
сохраняется: отсутствие доступа к провайдеру не считается выполненной интеграцией.

**Сервер TEST** означает реализованный путь через общий `/v1/test` с сохранением
заказа в PostgreSQL. Каталог — версия серверного источника данных для тестирования.
Номер начинается с `T-`, платёж явно симулируется, кассового чека нет. Данные
не поступают в действующий ресторан. **Локально** означает состояние устройства.
**Недоступно** — экран имеет объяснение и переход назад, но успешная операция
не выдумывается. Просмотр каталога и заказов в галерее использует отдельное состояние;
тестовый телефонный профиль остаётся локальным и не является серверной регистрацией.

M13–M18 и M20–M22 в рабочем режиме используют общую карточку и фактическое состояние
заказа. Например, готовность показывается сразу после действия кухни, даже если
исходный маршрут был M17. Галерея сохраняет отдельный просмотр каждого дизайна.

Номер demo-профиля не выбирает серверный TEST-сеанс и не открывает историю другого
устройства. Выход удаляет локальный номер/ник, но сохраняет незавершённые тестовые
заказы. Реальные SMS, бонусы и платёжные реквизиты этим сценарием не задействуются.
[Как проверить сборку 4](../operations/mobile-beta-0.1.0.md).

очереди. Источник — `packages/test-order-flow/src/complete-catalog.ts`;
редактор этих данных в бэк-офисе ещё не реализован.

## Кухня, табло и управляющий

`/kitchen/prep` получает задания приготовления. `/kitchen/assembly` показывает
их зависимости, разрешает сборку после всех компонентов и подтверждает выдачу.
`/display` читает только номера и канал заказа; выданный заказ исчезает. Каждое
изменение подтверждается API с ролью, идемпотентным ключом и ожидаемой версией.
При ошибке сохраняется предыдущий список с временем последнего обновления.
Мобильный заказ v0.3 передаёт выбранные опции в названиях работ и составе; адаптер
совместимости позволяет прежним кухонным/управляющим клиентам читать эти заказы.
Неизменяемый серверный снимок при этом сохраняет исходные опции и метод оплаты.

`/manager` читает TEST-заказы, открывает состав, разрешает неизвестную симуляцию,
отменяет с причиной и подтверждает выдачу. Ссылки на склад, рецептуры, персонал
и другие страницы открывают отмеченные макеты; это ещё не работающий CRUD.
В частности, менять блюда, КБЖУ, цены и модификаторы через бэк-офис пока нельзя:
для этого требуется отдельный редактор каталога. Текущие изменения данных выполняются
через серверный источник и проверенный выпуск.
Windows POS имеет прежний локальный backend обычного неоплаченного заказа,
но её полноценный UI/edge-путь к двум станциям не завершён.

## Подтверждение связи

Приёмка состоит из отдельных доказательств: PostgreSQL/HTTP integration,
проверка Docker runtime с ограниченной ролью, HTTPS journey на VPS,
нажатия в браузерных клиентах и нативный iOS Release. Результаты записываются
в [состояние проекта](../project-status.md) и deployment record. Наличие страницы,
успешная сборка или цветной статус сами по себе не доказывают интеграцию.
