## Права

Гость читает меню; customer — свои заказы/кошелёк/согласия; kiosk — только текущий
сеанс и привязанный terminal; cashier — своя точка и разрешённые операции;
shift_manager — смена, стопы, возврат/переназначение по полномочиям; kitchen —
задания назначенных станций; display — read-only публичная проекция; accountant —
сверка/фискальные документы по роли; network manager — назначенные точки;
system admin — устройства/технический контур, без автоматического доступа ко всей
PII. Скрытая кнопка не заменяет серверную авторизацию.

Offline grant ограничен по времени. При истечении показать denied и связь с
управляющим; не выдавать бессрочную роль только из сохранённого UI. В прототипе
аккаунт не выбран и роли не реализованы: состояния открываются ревьюером явно.

## Состояния и восстановление

- **Loading:** сохранять геометрию/контекст; сначала skeleton, затем timeout с
  действием безопасного повтора чтения. Не оптимистично подтверждать деньги.
- **Empty:** различать ещё нет объектов и нет результата фильтра; дать создание
  только при праве. Чек «ещё не получен» не равен пустой истории.
- **Error:** понятное сообщение, сохранённый order/attempt ID, безопасное действие;
  внутренний stack/содержимое банковского ответа пользователю не показывать.
- **Conflict:** old/new version и diff; не перезаписывать изменения коллеги.
- **Offline/stale:** observedAt, источник и WAN/LAN/bank/KKM отдельно; будущий
  recovery включает прочтение актуального состояния и дедупликацию pending command.
- **Expired/limited:** новый challenge/QR только по правилам сервера; открытый
  экран не продлевает права или токен.
- **Payment unknown:** сохранить экран проверки после app restart. Новый
  payment attempt недоступен до финального ответа или разрешённого reconciliation.
- **QR claim:** телефон не аутентифицирует; wallet spend offline выключен,
  ожидаемое начисление не становится доступным до принятой ledger-операции.
- **Кухня:** повтор действия ждёт прежний результат. «Отложить»/перенести не
  меняет receivedAt; `done` компонента не включает `ready` заказа.
- **Display overflow:** 6 номеров на панель в контрольном макете, очередь целиком
  сохраняется. Проектный цикл страниц 8 с + номер страницы; reduced motion без
  сдвига. Порядок ready по времени готовности. Сотрудник выдачи — источник removal.
- **Idle kiosk:** проектно 90 с + предупреждение 15 с, сессия очищается; активная
  попытка банка остаётся на edge, дисплей возвращает lookup состояния без чужой PII.

## Источники данных и совместимость с backend

Фактически существующие API v0.3.0 покрывают основу меню, device pull/ACK и
локальные staff/quote/unpaid-order. Остальной UI проектирует будущие контракты;
он не доказывает, что OTP, Kaspi, fiscal/refunds, KDS или BO уже реализованы.

1. Общие tokens → ui-native/ui-web; визуальная компонента получает props.
2. Container читает state/query, отображает доступные сервером действия.
3. Изменение → command с idempotency key/expectedVersion → pending → accepted
   или rejected → новое чтение/событие. Timeout не интерпретируется как отказ банка.
4. Для cloud/edge разных владельцев не делать client-side last-write-wins.
5. Источник аналитики и observedAt обязателен. Показатели в B02/B18/B19/B30 —
   примеры структуры, не новая база учёта в браузере.

## Приёмка дизайн-итерации и следующий порядок

В этой версии: каждая запись каталога открывается отдельным route, у неё есть
purpose, requirement, следующий экран и состояния. Критические исключения имеют
собственные макеты. Интерактивный прототип не выполняет бизнес-операции.

Дальше по реализации: (1) проверить брендбук и одну реальную пиковую смену;
(2) согласовать два KDS, cash/terminal/KKM fallback и экономику; (3) перенести
компоненты mobile/киоск/POS в нужные runtime; (4) подключать реальные API по
готовности; (5) проверить local network permission, клавиатуру, VoiceOver/TalkBack,
200% text, принтер/терминал и две ориентации на реальном оборудовании.
Публичный HTTPS для мобильного staging отдельно: текущий SSH-only backend
не является endpoint для реального TestFlight приложения.

Полный KZ перевод, редактура юридических текстов, пользовательское тестирование,
тесты на физическом оборудовании и pixel-perfect соответствие отдельному
брендбуку ещё не выполнены. Эти ограничения не закрывать красивым прототипом.
