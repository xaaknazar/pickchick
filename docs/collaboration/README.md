# Совместная работа с двух Mac

По решению владельца от 23 сентября 2026 работа продолжается с обоих Mac.
GitHub хранит общий код, решения и передачу задач. Истории чатов Codex,
несохранённые файлы, локальные базы, секреты и процессы Metro автоматически
между компьютерами не переносятся.

## Две ветки с разным назначением

- `codex/shared-development` - общий текущий срез разработки. В нём должны
  оказаться все законченные этапы с обоих компьютеров. Это не production-релиз
  и не утверждение, что вся интеграция уже принята. `main` сохраняет отдельную
  роль принятой версии. Первоначальная база - PR #72, `bd72865`, с известными
  ошибками общей CI, перечисленными в [передаче контекста](handoff.md).
- `codex/work-coordination` - служебная ветка с одним `state.json`: занятые
  области, рабочие ветки, последние сохранённые коммиты, итоги и следующие шаги.
  Её не сливают в код и не открывают как рабочий checkout.

Завершённая задача не освобождает область, пока её коммит не включён в общий
срез. Непринятые локальные правки существуют только на том компьютере, где
сделаны: перед переключением на другой Mac нужен опубликованный checkpoint.

## Подготовка второго Mac

Клонировать канонический репозиторий, выбрать `codex/shared-development`,
прочитать `AGENTS.md` и этот файл. Для существующей копии сначала сохранить
её изменения; не применять reset/clean ради синхронизации. Не копировать
`.git` со старого компьютера: новый clone получает отдельную идентичность
рабочего места. Установить версии Node/pnpm из репозитория и зависимости.

Нужен обычный GitHub-доступ по HTTPS или SSH. Утилита использует существующую
настройку Git, не хранит токены. Git user.name/user.email должны быть настроены.
Для первой проверки достаточно Node, установка npm-зависимостей не требуется:

```sh
node scripts/project-sync.mjs sync
node scripts/project-sync.mjs status
```

При отсутствии сети или доступа команда заканчивается ошибкой. Кешированные
данные не объявляются актуальными. Работать автономно можно только в своей
уже занятой области; публиковать общий срез и выполнять deploy до повторной
синхронизации нельзя.

## Начало каждой задачи

1. В общей рабочей копии выполнить `pnpm project:sync` и `pnpm project:tasks`.
2. Прочитать свежие `AGENTS.md`, `docs/project-status.md`, журнал задач,
   [handoff.md](handoff.md) и актуальные открытые PR.
3. Создать отдельную ветку/рабочую копию от `origin/codex/shared-development`.
4. Занять область до правок, например:

```sh
node scripts/project-sync.mjs claim mobile-cards apps/mobile
```

ID задачи должен быть уникальным. Области - пути относительно корня; родитель
перекрывает вложенные пути. `apps/mobile` и `apps/mobile/src` конфликтуют,
`apps/mobile` и `apps/kitchen` допускают одновременную работу. `*` занимает
весь проект. Общие contracts, миграции, токены и общие документы тоже требуют
резервации. Добавить области своей задачи можно повторным `claim` с тем же ID.

Для внешних ресурсов используются области `@vps`, `@vps/roadmap`,
`@windows/cashier`, `@windows/kitchen`, `@release/ios`. Общий `@vps` конфликтует
со всеми его подразделами. Резервация не даёт дополнительных серверных прав
и не заменяет штатный deployment lock/CAS в runbook.

Если область занята - выбрать независимую задачу либо согласовать передачу.
Не отменять чужую резервацию по возрасту: время само по себе не означает,
что другой Mac закончил работу.

## Передача незавершённой работы другому Mac

Сохранить только относящиеся к задаче файлы, проверить diff/секреты, сделать
понятный checkpoint-коммит и push рабочей ветки. Не называть его готовым релизом.
Затем передать краткую сводку, включая неудавшиеся/не запущенные проверки:

```sh
node scripts/project-sync.mjs handoff mobile-cards "Что изменено и проверено" "Что продолжить и какие ограничения остались"
```

Другой Mac читает `status`, получает указанную ветку/коммит и выполняет
`claim` с тем же ID. Утилита не разрешает принять более старый коммит, чем
сохранённый при передаче. Пока задача ожидает передачи, её области остаются
занятыми. Если старый Mac недоступен, нужна явная согласованная передача
владельцем; автоматического перехвата активных задач нет.

## Завершение и объединение

1. Обновить статус проекта, решения и roadmap; до изменения общего файла
   добавить его в области своей задачи. Повторить `pnpm project:check`.
2. Проверить и опубликовать свою ветку, оформить PR с результатами проверок.
   Невыполненные проверки и известные проблемы базовой версии указать явно.
3. Получить свежую общую ветку и проверить изменения с другого Mac. Если она
   продвинулась, явно интегрировать её в свою рабочую ветку и повторить
   затронутые проверки. Автоматического merge/rebase утилита не делает.
4. После проверки diff и результатов включить законченный этап в общий срез
   обычным fast-forward push, без force. При параллельном обновлении Git
   отклонит push: получить новую вершину, согласовать и проверить объединение.
5. Выполнить:

```sh
node scripts/project-sync.mjs finish mobile-cards "Результат, проверки и ссылка на PR" "Следующий этап"
```

`finish` проверяет чистое дерево, совпадение локального HEAD с опубликованной
рабочей веткой и наличие этого коммита в общей ветке. Squash для интеграции в
общий срез не использовать: история должна сохранять проверяемую связь SHA.
Полностью зелёная CI и релизные критерии обязательны для принятия в `main`
и выпуска. Общий срез разработки с явно указанными базовыми проблемами
не объявляется принятым релизом.

## Что именно защищено

`check` получает свежие remote refs и обнаруживает отставание от общей или
собственной удалённой ветки. `sync` обновляет только текущую ветку из её
одноимённой remote-ветки через fast-forward; при локальных изменениях или
расхождении останавливается. Он не делает stash, reset, clean, merge конфликтов
или скрытый push файлов.

Журнал записывается отдельным commit-tree, не затрагивает index/HEAD/файлы
рабочей копии. Обычный fast-forward push предотвращает потерю одновременной
записи. При гонке выполняются повторное чтение и проверка пересечений.

Это рабочий протокол и проверяемый инструмент для агентов, а не запрет GitHub
на любые сторонние команды. Ручной обход, работа офлайн и непереданные изменения
могут нарушить согласованность. Не обещать мгновенную синхронизацию всех чатов
или постоянно одинаковые рабочие деревья при параллельной разработке.

Известные границы: второй Mac ещё должен получить репозиторий и пройти первый
`sync/status`; реальная одновременная работа двух физических Mac не принята.
Проверки воспроизводят два независимых clone и конкурентные записи на локальном
bare remote. Секреты, подписи Apple, навыки Codex и доступ к ресторанной LAN
настраиваются на каждом компьютере отдельно.
