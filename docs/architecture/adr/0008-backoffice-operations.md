# ADR 0008 - операционный бэк-офис

Дата: 8 сентября 2026. Статус: реализован локально, эксплуатационное внедрение ожидает проверки.

## Контекст

Владелец поручил реализовать все разделы присланного бэк-офиса и связать их с backend
и внутренними операциями. BO-01 содержал только редактор каталога. Исходный offline HTML
показывает демонстрационные числа и успешные уведомления без транзакций; перенос этих
уведомлений не выполняет требование. Полный объём §4.6 ТЗ сохраняется.

## Решение

Добавить `backoffice-core` в существующий модульный backend и миграцию cloud017.
Не вводить отдельный микросервис для каждого раздела. Cloud015 и cloud016 импортированы
как зависимости отмены неоплаченного заказа и наблюдения POS. Данные cloud и edge
сохраняют существующее владение; POS-проекция доступна для чтения.

Бэк-офис аутентифицирует личный токен управляющего каталога, но операционные полномочия
выдаются отдельно, для конкретной точки: manager или analyst. Выдача роли через
доверенный CLI оставляет неизменяемый журнал. Публичного маршрута выдачи прав нет.
Один SQL transaction включает проверку/блокировку прав, business command, audit и
идемпотентный receipt. Отзыв личного доступа препятствует новым операциям.

Склад хранит целые количества в g/ml/pcs и деньги в минимальных единицах KZT.
Документы, движения, опубликованные версии и аудит неизменяемы. Оценка списаний
средневзвешенная; последнее списание забирает остаток округления. Инвентаризация
записывает разницу. Производство переносит стоимость сырья в полуфабрикат атомарно.
Ревизии остатков предотвращают проведение по устаревшему состоянию.

При создании коммерческого заказа trigger фиксирует техкарты. Списание требует
наблюдаемого подтверждения производства/готовности/выдачи и запрещает второе списание.
Отсутствующие нормы, комбо и модификаторы блокируют автоматическое применение базового
рецепта. Меню-рецепт описывает одну порцию; полуфабрикат имеет явный выход партии.
Старые заказы без зафиксированной техкарты автоматически не пересчитываются.

Refund и cancellation используют существующий CommerceRepository внутри той же
транзакции, а не пишут альтернативные финансовые таблицы. Ответ `pending` не означает
успешный возврат; деньги меняют состояние по доверенному событию адаптера.
Ошибка записи BO-аудита откатывает также запрос возврата и его outbox.

Публикация промо/игры/плана станции отдельна от редактирования. Публичный content API
выдаёт только опубликованные промо и встроенные игровые переключатели с расписанием.
Mobile запрашивает их при открытии, раз в минуту и при возвращении в foreground.
Приложение не получает записи гостей, сотрудников или заказов через этот API.
Конфигурация не содержит исполняемого кода. Клиентское отключение игры - настройка UI,
не серверная защита наград. Награды пока строго нулевые.

## Альтернативы

- Копировать offline demo вместе с фиктивными успехами: не соответствует реальным операциям.
- Записывать возвраты напрямую из BO: нарушает владение финансовым агрегатом и идемпотентность.
- Автоматически применять cloud-план на кухне без edge receipt: нельзя подтвердить применение
  и безопасную смену маршрута. План сохраняется как подготовленная публикация.

## Последствия и незавершённый объём

Фактические возможности и оставшиеся работы перечислены в
[runbook](../../operations/backoffice-operations.md). Это завершённый проверяемый этап
BO-02, но не заявление о готовности всего §4.6 или ресторана. В частности, интеграции
провайдеров, доставка конфигурации на edge, полноценные кадровые/кассовые смены,
серверные награды, аналитические события и переключение всех клиентов на нейтральный
каталог сохраняются в плане. Экономика, аппаратное обеспечение и условия провайдеров
не выдумываются ради визуального заполнения раздела.

## Дополнение 24.10.2026: доставка плана станций на кассу

Альтернатива «применять cloud-план без receipt» по-прежнему отклонена. План станций доставляется
отдельным каналом по образцу menu-sync (ADR 0002): версия плана в облаке (cloud070), pull
кассой по ключу устройства, применение в одной транзакции edge (edge024) или отклонение с
причиной, durable receipt, статус в кабинете. Каждая версия - полный план, поэтому касса
получает только новейшую версию без ответа; версии только растут, повтор идемпотентен.
Подтверждённый план пока не меняет маршрутизацию заказов: это отдельное решение о кухне.
Флаг `BACKOFFICE_STATION_PLAN_DELIVERY_ENABLED`, по умолчанию выключен.
[Описание и выпуск](../../operations/stage2-2026-10-24/cfg.md).

## Дополнение 05.11.2026: переход 19.11 - роли, склад v2, отчёт продаж, начальные остатки

Контекст: 19.11.2026 ресторан уходит с iiko; кабинет нужен начальнику смены, бухгалтеру и
управляющему в первый же день (контракт `../cutover-2026-11-contracts.md`, §5.7, §5.10, CC-5..CC-8).
Каждое решение выключено флагом env API по умолчанию; без флагов ответы и права байт-в-байт
прежние (тесты на ключи ответа D0).

- **Роли поверх грантов.** `bo_access_grants` остаётся с двумя ролями (`manager` пишет,
  `analyst` читает). Начальник смены и бухгалтер - назначение (`bo_role_designations`, 074,
  только добавление, действует последняя запись) поверх гранта аналитика, только при
  `BACKOFFICE_ROLES_ENABLED`. Одна статическая матрица прав (`roles.ts`) проверяется в одной точке
  входа каждого раздела; поле `role` ответа прежнее, новые `effective_role`/`permissions[]` - только
  с флагом. Назначает только владелец базы (`backoffice-setup.mjs --designation`), HTTP-маршрута
  записи нет. Отклонено: новые значения роли гранта - сломали бы установленный кабинет и прежние
  проверки.
- **Чтение - один префикс `GET .../ops/<view>`.** Новые отчёты (`stock`, `sales`) - под одним
  путём для шлюза и прокси, запись - прежний `POST .../commands` с `request_id`, аудитом и
  блокировкой точки. Новых путей записи нет.
- **Отчёт продаж читает проекции, а не владеет продажами.** Касса - владелец продаж, оплат и
  возвратов (edge); облако хранит копию `cloud_pos_*` (073, поток `posSales`) и только читает её.
  Счёт - как в Z-отчёте кассы (отменённые продажи в продажах, отмена - возврат), чтобы цифры
  кабинета и смены совпадали построчно; «Без выручки» (питание, маркетинг) отдельно; все восемь
  способов оплаты раздельно (решение владельца 05.11). Нет таблиц или прав - отчёт по облачным
  каналам с `coverage.pos=false`, без ошибки. Отклонено: отдельный отчёт «Продажи кассы» (дубль,
  R6) и отчёт по `pos_order_sync_projection` (нет оплат по способам).
- **Начальные остатки - теми же командами, что кабинет.** `stock-opening-import.mjs` не пишет в
  базу напрямую: план с SHA-256 превращается в документы «Инвентаризация» по 100 строк с
  постоянными `request_id`; повтор после потери ответа не создаёт дублей, план, устаревший из-за
  чужих документов, не отправляется. Стоимость обязательна; у позиции с остатком - сначала
  отдельный документ обнуления, потому что подсчёт сохраняет текущую среднюю себестоимость.
