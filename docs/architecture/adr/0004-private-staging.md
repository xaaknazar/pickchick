# ADR 0004 — частный staging на существующем VPS

Статус: принято для инженерного стенда, 06.09.2026.

## Контекст

Заказчик передал существующий VPS для PickChick. Проверка по SSH выявила Ubuntu
24.04, 4 vCPU, 3914 MiB RAM, диск около 200 GB, Docker 29.7.2 и работающий
проект idrink с PostgreSQL 16 и Caddy на 80/443. ОС запрашивает перезагрузку.
Управление чужим приложением и его обновление не входят в этот этап.

## Решение

Выделить Compose project `pickchick-staging`: собственные сеть, том PostgreSQL
18, Redis и API. Суммарные лимиты постоянных контейнеров — 1408 MiB; это
ограничение памяти, не резерв и не подтверждение нагрузочной способности.
API слушает внутри контейнера, host mapping только `127.0.0.1:13100`.
БД и Redis не публикуют порты; сеть internal. Доступ разработчика — SSH-туннель.
HTTP внутри изолированной сети и туннеля допустим только для синтетического стенда.

Добавлен явный APP_ENV=staging только для cloud API, с проверкой имён сервисов,
схемы/имени БД и отдельных случайных паролей. Local/test ограничения сохраняются,
production и удалённый edge не включаются. PostgreSQL admin, schema owner и
runtime — разные роли; runtime не выдаёт устройства и не выполняет DDL.
Для row locks выделены UPDATE только на ключевые столбцы devices/credentials/branches.
Это не row-level security и не защита от администратора Docker-хоста.

Контейнер приложения работает без root, с read-only filesystem, no-new-privileges,
лимитами ресурсов и ротацией логов. Образ содержит собранный monorepo, включая
инструменты миграции и dev dependencies; минимизация runtime image — отдельная работа.
Образы базовых сервисов закреплены digest, приложение — SHA исходного коммита
и image ID в реестре развёртывания. CI проверяет сам образ и права runtime БД.

Отдельная ops-учётная запись входит в docker group: это административные права
на хост, а не изоляция от idrink. Прежний доступ владельца сохраняется.
Глобальные firewall/SSH policy, reboot и существующий proxy не меняются.

Копии pg_dump шифруются age по публичному ключу; приватный ключ хранится на
компьютере владельца. Ежедневная копия на том же VPS защищает от отдельных
логических ошибок, но не от потери сервера. Независимое хранилище в РК и
production WAL/PITR остаются обязательными до работы с реальными данными.

## Альтернативы и последствия

- Отдельный чистый VPS: лучше изоляция и возможность обслуживания; требует
  дополнительного ресурса. Предпочтителен для будущего production.
- Подключиться к действующему Caddy: возможно позднее, после выбора DNS и
  аутентификации staging; сейчас затрагивает другой сервис без необходимости.
- Открыть 3100 в интернет: отклонено, публичные auth/TLS и защита API не готовы.

Это продвижение инфраструктурного пункта 1Б.3 после получения VPS. Каталог,
оплаты, кухня и сроки roadmap не объявляются завершёнными. Физическое размещение
ЦОД/копий в РК подтверждается договором провайдера, а не SSH-баннером или IP.
