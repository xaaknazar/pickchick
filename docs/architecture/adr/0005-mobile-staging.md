# ADR 0005 — нативная мобильная beta и публичный каталог staging

Дата: 2026-09-06. Статус: принято в рамках поручения заказчика.

## Причина

После подготовки дизайна заказчик поручил перенести все мобильные страницы
в приложение, подключить VPS и выпустить PickChick в TestFlight. Заказчик
подтвердил отсутствие домена и доступов Kaspi/ККМ/SMS, а для первой сборки выбрал
отдельное приложение в существующей Apple Team Aknazar Kuanysh.

Это добавляет параллельную работу над клиентом к этапу 1Б.3. Полный четырёхмесячный
объём ТЗ и приёмка кассы/кухни/склада сохраняются. Выпуск beta не закрывает Gate B
и не является завершением экосистемы.

## Решение

- `apps/mobile`: React Native 0.86.3, React 19.2.3, Expo SDK 57.0.20 и Expo Router;
  совместимые версии закреплены в package.json/lockfile. Это нативные компоненты,
  без WebView с HTML-прототипом. Источник выбора —
  [Expo SDK 57](https://expo.dev/changelog/sdk-57) и фактический bundledNativeModules.
- Общие контракты и дизайн-токены используются из pnpm monorepo. Expo поддерживает
  [монорепозитории](https://docs.expo.dev/guides/monorepos/); отдельные native
  каталоги генерируются из app.json и не редактируются как второй источник правды.
- Jost/Manrope в нативных TTF поставляются закреплёнными пакетами Expo Google Fonts.
  Изображения, видео и логотип берутся из предоставленного мокапа. Генеративно
  изменённый логотип в приложение не включается. Стандартный Expo prebuild
  компилирует исходный логотип в непрозрачный App Store icon 1024×1024.
- `kz.pickchick.app`, Team `DAJTP6MC3Q`, версия 0.1.0, первый build 1. Это отдельная
  запись PickChick, не обновление Divergents или iDrink. Для загрузки используются
  локальная сборка Xcode, automatic signing и App Store Connect.
- Каталог клиента читается через разрешённые публичные GET по HTTPS. Фиксированный
  endpoint — `https://pickchick.185.129.51.103.nip.io`. Перед чтением меню проверяются
  staging/synthetic capabilities, затем runtime-схемы точек и меню. Неизвестный
  формат и включённые коммерческие функции отклоняются этой beta.
- По последующему поручению связать экраны добавлен отдельный TEST-путь
  [ADR 0006](0006-test-order-flow.md): серверные quote/заказы, ограниченный
  гостевой Bearer-сеанс, явная симуляция оплаты, две кухонные станции, табло
  и выдача. Он включается отдельным capability и не запускает операции ресторана.
- Публичный gateway — отдельный контейнер без секретов/БД/host ports. В общий
  Caddy добавлен отдельный hostname; существующий idrink проверен до и после.
  [Runbook](../../operations/public-staging-https.md) содержит границы и откат.
- Локальная корзина хранит идентификаторы и количества. При восстановлении цены
  берутся из соответствующего release меню; несовпавший release сбрасывает корзину.
  Суммы считаются целыми минимальными единицами. Цена на клиенте — предварительный
  итог, будущий checkout обязан получить серверный quote.
- Галерея всех 35 экранов показывает отмеченные примеры. Её корзина, профиль и
  результаты тренировочной игры изолированы от режима сервера. Ни один пример
  не создаёт заказ, SMS, оплату, чек, бонус или обращение в поддержку.

## Ограничения первой beta

Серверное меню синтетическое; коммерческий каталог и составы не утверждены.
Без провайдеров вход по SMS, платежи, фискализация и бонусные операции недоступны.
История реальных заказов и кошелёк не подменяются данными макета. Игра тренирует
взаимодействие локально, без наград. Полный перевод на казахский, уведомления,
удаление серверного аккаунта и реальные legal/support процессы требуют реализации.

Временный DNS зависит от nip.io; собственный домен понадобится до коммерческого
запуска. TLS и TestFlight не заменяют мониторинг, внешние backup, аппаратные WAN
испытания, Apple beta review и приёмку полного P0/P1.

## Проверка и переход

Требуются unit проверки денег/восстановления/отказов API, bundle export для
iOS/Android, проверка всех нативных экранов и запуск установленной iOS Release
без Metro. Отдельно подтверждаются подпись, загрузка Apple и обработка TestFlight.
Один успешный шаг не считается подтверждением последующего.

Далее: каталог с модификаторами/комбо и API клиента → OTP → quote/checkout и
банковские попытки → ККМ/admission/кухня → история/лояльность. Каждый шаг проходит
критерии ТЗ и включает серверные отказные сценарии, а не только интерфейс.
