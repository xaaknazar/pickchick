# ADR 0018: оплата киоска на отдельном терминале Kaspi Smart POS

Статус: принято 16.11.2026 (запрос владельца в треде «Подключить iPad-киоск с оплатой на
Kaspi-терминале»). Реализация: облако (commerce-core, API, миграция 080), приложение киоска,
показ источника заказа на кухне. Изменено 22.11.2026: HTTPS с закреплённым сертификатом
(решение 1).

## Контекст

- Киоск (apps/kiosk, iPad) говорит только с облаком; сейчас платит Kaspi QR на экране через мост
  (ADR-0012, provider `kaspi-qr`). Кухня принимает заказ киоска только после подтверждённой оплаты.
- У владельца второй терминал Kaspi Smart POS для iPad. Терминал отдаёт локальный API на порту
  8080 (конспект: docs/integrations/kaspi-smart-pos-api.md в ветке codex/kaspi-pos-1115). Наш
  Smart POS 3 (приложение 2.64.9) отвечал обычным HTTP без TLS (ADR-0017 п. 11 в той же ветке).
- Уточнение 22.11.2026 (касса, ветка claude/project-thread-ej7z1n, коммит 992d2a98): обычный HTTP
  терминал отдаёт только при выключенном переключателе «Защита интеграции» («Панель главного
  кассира»), и тогда `register` сразу отклоняется кодом 105. С включённой защитой порт 8080
  говорит только TLS с самоподписанным сертификатом (обычный HTTP обрывается), и `register` по
  HTTPS проходит после «Разрешить». Сборка киоска 25 умела только HTTP и поэтому не могла
  привязать терминал. Fetch React Native на iOS самоподписанный сертификат не принимает.
- ТЗ KIO-03: за киоском закрепляется terminal ID, предпочтительно отдельный терминал.

## Решение

1. **iPad сам ведёт терминал по LAN, по HTTPS с закреплённым сертификатом.** Терминал и iPad в
   одной частной сети; iPad вызывает `https://<IP терминала>:8080/v2/...`. Доверие - не цепочка
   сертификатов и не имя (адрес - IP), а SHA-256 листового сертификата (DER, строчный hex),
   закреплённый при первой привязке (доверие при первом подключении, как у оператора кассы):
   киоск сначала делает только TLS-рукопожатие (`probe`), берёт отпечаток предъявленного
   сертификата, сотрудник видит его первые и последние 8 знаков и подтверждает привязку
   «Разрешить» на терминале. Дальше каждый вызов идёт через нативный модуль
   `apps/kiosk/modules/kaspi-tls` (Swift, URLSession): доверие сервера принимается только при
   совпадении отпечатка, иначе соединение отменяется в рукопожатии, и ни один байт запроса
   (путь, токен) не уходит. Отпечаток хранится в SecureStore рядом с токенами и в облако не
   отправляется. Владелец держит «Защиту интеграции» включённой: при выключении терминал
   переходит на HTTP, и закреплённая связь перестаёт работать.
   Обычный HTTP (`http://<IP>:8080`, fetch) остаётся только для терминала, который на `probe`
   отвечает без TLS; сам по себе киоск с HTTPS на HTTP не переходит. Если по HTTP `register`
   отклонён кодом 105, сотрудник видит «включите «Защиту интеграции»». Точка-сервер и облако к
   терминалу не ходят. Токен терминала (`accessToken`, `refreshToken`, 24 ч) хранится только в
   SecureStore iPad и обновляется через `/v2/revoke` до истечения. В облако токен и отпечаток не
   отправляются никогда.
2. **Облако принимает итог, заверенный ключом киоска** (как `cashier_attested` у кассы, ADR-0015):
   новый провайдер `kaspi-pos` (метод `kaspi_terminal`) для киоска, отдельный от `kaspi-qr`.
   Деньги засчитываются только по `status=success` с `transactionId`, суммой, равной сумме
   попытки, и тем же `terminalId`, что привязан к этому киоску. Включается флагом
   `KIOSK_KASPI_TERMINAL_ENABLED=true` и учётной записью провайдера `kaspi-pos` точки.
3. **Привязка терминала к киоску видна в облаке**: iPad сообщает `terminalId`, `serialNum`,
   IP после успешного `register`; облако хранит последнюю привязку на устройство киоска.
   Один терминал - один киоск (повторная привязка того же terminalId к другому киоску отклоняется,
   пока старая не снята).
4. **Источник заказа на кухне**: на всех рабочих экранах кухни у заказа подпись источника:
   «Киоск», «Приложение», «Касса», для доставки - название агрегатора (уже есть «ДОСТАВКА ·
   Яндекс Еда …»). Табло для гостей не меняется.

## Контракт API (кроме существующих заголовков киоска `x-kiosk-device`, `x-kiosk-key`)

Все ответы `no-store`, ошибки в существующем формате kiosk-checkout.

- `GET /v1/kiosk-checkout/config` - в существующем ответе добавляется
  `kaspi_terminal: { enabled: boolean, terminal: null | { terminal_id, serial, host, linked_at } }`.
- `PUT /v1/kiosk-checkout/terminal` тело `{ terminal_id, serial, host }` (host - частный IPv4) -
  привязать/обновить терминал этого киоска. `DELETE /v1/kiosk-checkout/terminal` - снять.
  409 `KIOSK_TERMINAL_TAKEN`, если terminal_id привязан к другому активному киоску.
- `POST /v1/kiosk-checkout/orders/:id/payment` тело `{ method: 'kaspi_terminal', request_id }` -
  создаёт попытку оплаты провайдера `kaspi-pos` на точную сумму заказа. Ответ
  `{ attempt_id, amount_tenge, terminal_id, expires_at }`. 409 `KIOSK_TERMINAL_NOT_LINKED`,
  `KIOSK_TERMINAL_DISABLED`. Сумма - целые тенге (иначе 409 `KIOSK_TERMINAL_WHOLE_TENGE`).
- `POST /v1/kiosk-checkout/orders/:id/terminal-events` тело
  `{ attempt_id, kind: 'started' | 'result', process_id, terminal_id, status?: 'success' | 'fail' | 'unknown', sub_status?, transaction_id?, method?: 'qr' | 'card' | 'alaqan', amount_tenge?, message? }`.
  Идемпотентно по (`attempt_id`, `kind`, `process_id`); повтор с теми же данными - тот же ответ,
  с другими - 409. `result` + `success` → оплата засчитана, заказ уходит на кухню тем же путём,
  что и после QR. `fail` → попытка закрыта, можно начать новую. `unknown` → попытка остаётся
  «требует сверки» (существующие инциденты оплаты киоска, миграция 050), заказ на кухню не идёт.
  Ответ: состояние заказа как в `GET orders/:id`.
- Попытка без `result` дольше 15 минут становится инцидентом «требует сверки», не отказом.

## Поведение iPad

- Настройка терминала - в служебном меню киоска (после кода сотрудника): IP → `probe` (TLS:
  отпечаток сертификата; без TLS: `deviceinfo` по HTTP) → `deviceinfo` по тому же транспорту →
  `register?name=pickchick-kiosk-<6 символов>` (на экране киоска - начало и конец отпечатка) → на
  терминале «Разрешить» → токены и отпечаток в SecureStore → `PUT terminal` (только ID, серийный
  номер, IP).
- Поиск терминала по новому адресу (DHCP без резерва) для HTTPS-привязки спрашивает `deviceinfo`
  тоже с закреплённым отпечатком: устройство с другим сертификатом не отвечает вовсе, даже с
  теми же ID и серийным номером. «Проверить связь» при другом сертификате показывает «Терминал
  отвечает с другим сертификатом. Проверьте IP или привяжите заново.»; привязка не меняется.
- Привязки, сохранённые сборкой 25 (без отпечатка), читаются как HTTP-привязки.
- Оплата: экран «Оплатите на терминале - картой или Kaspi QR» с суммой; `POST payment` →
  `/v2/payment?amount=` → `started` → опрос `/v2/status` раз в секунду → `result`. Потеря связи
  после отправки `payment` никогда не повторяет оплату: только `status`, затем `actualize` не чаще
  раза в 10 с. processId и attempt_id сохраняются до отправки, чтобы после перезапуска приложения
  дочитать итог и сообщить его облаку.
- Если терминал не привязан или выключен в облаке, киоск показывает прежнюю оплату QR на экране.
- iOS: `NSAppTransportSecurity.NSAllowsLocalNetworking=true` и `NSLocalNetworkUsageDescription`;
  HTTPS идёт через локальный Expo-модуль `kaspi-tls` (autolinking из `apps/kiosk/modules`,
  входит в `expo prebuild` и CocoaPods). Для HTTPS нужен новый нативный билд iPad (26 и новее,
  TestFlight); в вебе и на Android модуля нет, HTTPS-вызов там ничего не отправляет.

## Риски

- Заверение итога киоском: украденный ключ киоска позволяет отметить заказ оплаченным без денег.
  Смягчение: ключ только в SecureStore, Single App Mode, сверка `transactionId` в отчётах Kaspi,
  отзыв устройства в «Устройствах». Возвраты через API не делаются (ручной возврат на терминале),
  «Только интеграция» на терминале не включать.
- Доверие при первом подключении: если при первой привязке по этому IP отвечает чужое устройство
  с TLS, закрепится его сертификат. Смягчение: сотрудник видит ID и серийный номер терминала и
  отпечаток, привязка требует «Разрешить» на самом терминале.
- Терминал сменил сертификат (сброс, переустановка приложения Kaspi): связь перестаёт работать
  до новой привязки («Отвязать» → «Подключить»). Оплата при этом не уходит.
- Токен терминала по Wi-Fi открытым текстом - только у HTTP-привязки (защита интеграции
  выключена), как у кассы (ADR-0017 п. 11).
- Фискальный чек по-прежнему отдельно (Webkassa не подключена).
