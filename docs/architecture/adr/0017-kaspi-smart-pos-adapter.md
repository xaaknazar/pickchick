# ADR-0017: касса отправляет сумму на Kaspi Smart POS (адаптер терминала на edge)

Статус: решение владельца 15.11.2026 («Начать сейчас», ветка проекта «Подключить Kaspi-терминал и
принтер чеков»). Продолжает [ADR-0015](0015-pos-sales-manual-fiscal.md): ручная отметка кассира
остаётся запасным путём. Описание API терминала - [kaspi-smart-pos-api.md](../../integrations/kaspi-smart-pos-api.md).

## Контекст

В P0 оплата терминалом отмечается со слов кассира (`kaspi_terminal`, `cashier_attested`). Владелец
хочет, как было в iiko: кассир нажимает «Отправить на терминал», сумма появляется на терминале,
после оплаты касса сама оформляет продажу и заказ уходит на кухню. У Kaspi Smart POS есть
официальный локальный API (HTTPS, порт 8080, `/v2/*`, токен на 24 часа). Его методы, статусы и
ошибки описаны по документации Kaspi; на нашем устройстве API ещё не проверен.

## Решение

1. **Адаптер живёт на edge** (сервер точки), а не в приложении кассы. Edge владеет оплатами, хранит
   токен терминала, держит одну операцию на терминал и переживает перезапуск кассы. Касса говорит
   только с edge, как и для остальных команд.
2. **Привязка терминала к кассе** - таблица `kaspi_pos_devices` (миграция 029): один активный
   терминал на кассу (`local_terminals`), частный IPv4 терминала, SHA-256 его TLS-сертификата
   (закрепление: сертификат выдан на `*.kaspipos.kz`, а мы ходим по IP, поэтому имя не проверяется,
   проверяется отпечаток), имя регистрации и токены. Привязывает и отвязывает только скрипт
   оператора `scripts/kaspi-terminal-setup.mjs` (`probe`, `register`, `status`, `unlink`) с
   owner-окружением: `register` вызывает `/v2/register`, кассир нажимает «Разрешить» на терминале.
   Рантайм edge читает привязку и сам обновляет токен (`/v2/revoke`) за 3 часа до истечения.
3. **Попытка оплаты** - таблица `kaspi_pos_attempts`. Сначала строка пишется в PostgreSQL
   (`created`), затем рантайм занимает её (`sending`) и вызывает `/v2/payment`. Состояния:

   | Состояние     | Значение                                                                                                       |
   | ------------- | -------------------------------------------------------------------------------------------------------------- |
   | `created`     | записана, на терминал ещё не отправлена                                                                        |
   | `sending`     | запрос на терминал уходит                                                                                      |
   | `send_failed` | терминал не получил или отказал до начала (нет связи, 106/107/108, токен) - денег не было, можно новую попытку |
   | `wait`        | терминал принял сумму (`processId`), ждём гостя                                                                |
   | `success`     | терминал подтвердил оплату (`transactionId`, способ qr/card/alaqan)                                            |
   | `fail`        | терминал ответил «не прошла» или кассир отменил на терминале                                                   |
   | `unknown`     | терминал не знает итога; edge вызывает `/v2/actualize` не чаще раза в 10 с                                     |
   | `lost`        | ответ на `/v2/payment` потерян после отправки: итог неизвестен и processId нет                                 |

   Одновременно у терминала не больше одной незавершённой попытки (уникальный индекс). Оплата
   никогда не повторяется сама: `unknown` разрешает только `actualize`, `lost` - только человек
   (смотрит историю на терминале и при оплате отмечает вручную, как в P0). Сумма - целые тенге.

4. **Опрос** ведёт касса: `GET pos/terminal-payments/{id}` раз в секунду; на каждом запросе edge
   (по одному запросу на попытку) спрашивает терминал `/v2/status` и записывает переход. Фонового
   цикла нет: если касса закрыта, попытка ждёт, терминал хранит операции 24 часа.
5. **Продажа по попытке.** Получив `success`, касса сразу отправляет обычный `POST pos/sales`, где
   часть `kaspi_terminal` несёт `attempt_id`. В той же транзакции edge проверяет: попытка этой
   кассы, этой котировки, `success`, сумма части равна сумме попытки, попытка ещё не использована;
   ставит `order_id` попытки и пишет часть с `attempt_id` и `reference` = номер операции Kaspi.
   Заказ, как и раньше, сразу допускается на кухню. Срок котировки для такой продажи не проверяется
   (он проверен при создании попытки), меню и стопы - проверяются. База повторяет проверки
   триггером, `attempt_id` уникален среди частей.
6. **Восстановление.** `GET pos/terminal-payments/open` отдаёт попытки этой кассы за 24 часа,
   которые не закончены или оплачены без заказа. Касса показывает их и даёт оформить продажу.
7. **Подтверждение в облаке.** CHECK 026 и облако 073 знают только `cashier_attested` для
   `kaspi_terminal`; в P0.5 значение не меняется, отличие - `attempt_id` на edge и номер операции
   Kaspi в `reference`. Отдельное значение `terminal_confirmed` в потоке `posSales` - этап 2 вместе
   с облачной миграцией (не раньше 19.11). Это занижение, а не завышение: продажа по попытке
   подтверждена терминалом, а помечена как более слабое подтверждение.
8. **Возврат** через терминал (`/v2/refund`) - этап 2. Сейчас возврат по терминалу, как в P0:
   кассир проводит его на терминале, касса записывает. Поэтому режим терминала «Только
   интеграция» не включать.
9. **Выключатель.** Без строки `kaspi_pos_devices` для кассы всё работает как в P0. Ответ
   `GET pos/config` получает последним ключом `kaspi_terminal_link` (true, если у кассы сессии
   есть активный терминал); касса без этого ключа считает его false. `unlink` возвращает ручной
   режим.
10. **Касса.** При `kaspi_terminal_link` экран «Kaspi терминал» показывает кнопку «Отправить
    сумму на терминал». Пока терминал решает, корзина, «Назад к заказу» и новое меню
    заблокированы, касса раз в секунду читает попытку. `success` сразу даёт журналируемый
    `POST pos/sales` с `attempt_id` по той же квоте (без пересчёта), и заказ уходит на кухню без
    нажатия. `fail`/`send_failed` - можно отправить ещё раз или выбрать другой способ. `lost` -
    касса больше ничего не отправляет и показывает ручную кнопку «Оплата на терминале прошла»
    после проверки экрана терминала. Смешанная оплата с терминалом пока ручная.

## Последствия и риски

- API проверен только по документации и на имитаторе в тестах; до проверки на настоящем терминале
  (оплаты по 100 ₸, отмена на терминале, обрыв Wi-Fi) режим включается только на тестовой кассе.
- Терминал и сервер точки должны быть в одной локальной сети, у терминала постоянный IP (резерв
  DHCP). Отпечаток сертификата меняется при замене сертификата терминала: тогда `probe` и
  повторный `register`.
- Токен хранится в базе edge (как и остальные данные точки), в репозиторий и логи не попадает.
- 029 - новая миграция edge: ставится оператором после 028 с копией базы, как 026-028.

## Приёмка

1. Юнит-тесты клиента терминала на имитаторе: закрепление сертификата, токен, все статусы,
   ошибки 106/107/108/401, обрыв до и после отправки.
2. Интеграционные тесты: попытка → `success` → продажа с `attempt_id` → кухня; повтор, чужая касса,
   другая сумма, повторное использование, `lost` и `unknown` не дают продажи; права рантайма.
3. На точке: `probe`/`register`, оплата 100 ₸ QR и картой, отмена на терминале, обрыв сети.

## Порядок включения на точке

1. Новый релиз сервера точки и инструментов копии базы (они уже знают schema029), затем свежая
   проверенная копия базы schema028.
2. Все службы edge остановлены: `node infra/windows/kaspi-pos-upgrade-db.mjs inspect <tools>
<app> <branch>`, затем то же с `apply`. Повторный `apply` отказывается.
3. Службы запущены. На терминале: «Защита интеграции» → «Настроить доступ», постоянный IP в
   роутере.
4. `node scripts/kaspi-terminal-setup.mjs probe --host <IP>` - отпечаток сертификата сверить с
   терминалом; `register --terminal <касса> --host <IP> --certificate-sha256 <отпечаток>` -
   подтвердить на терминале. Токен не печатается.
5. Касса подхватывает `kaspi_terminal_link` за 30 с. Первая проверка - оплата 100 ₸.
