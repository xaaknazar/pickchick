# ADR 0014: облачный кухонный канал для киоска и мобильного приложения

Статус: принято владельцем 2026-10-10; реализация не начата (этап S0 - только решения
и документы). Дата: 2026-10-10.

Подробная архитектура, этапы S0-S7, тесты и риски:
[cloud-kitchen-channel.md](../cloud-kitchen-channel.md).

## Причина

Сейчас любой заказ доходит до кухни только через кассовый edge. Киоск после оплаты
ждёт per-order admission (`edge.kitchen_admission_requested` в
`packages/commerce-core/src/repository.ts`), а мобильный checkout и киоск закрываются
кодом `AVAILABILITY_STALE`, если проекция кассы `cloud_branch_availability` старше
30 секунд (`packages/commerce-core/src/availability.ts`). Выключенная или отключённая
от WAN касса останавливает продажи iPad и приложения, хотя кухня и облако работают.
Владелец решил, что облачные каналы не должны зависеть от кассы.

## Решения владельца 2026-10-10

1. Касса (edge) и кухня по LAN сохраняются и работают без интернета. Текущий
   локальный порядок [ADR-0011](0011-kitchen-live-link.md) и
   [ADR-0013](0013-device-access.md) не отменяется.
2. Заказы киоска (iPad) и мобильного приложения дополнительно поступают на кухонные
   экраны напрямую через облако, независимо от кассы. Заказы агрегаторов (Яндекс)
   по-прежнему идут через кассу с подтверждением.
3. Номера заказов - отдельные диапазоны по каналам: касса 1-299, iPad 300-599,
   приложение 600-899. Сброс - при открытии смены (выбор владельца).
4. Стоп-лист при выключенной кассе: управляющий ставит стопы на сайте бэк-офиса,
   для iPad/приложения они действуют сразу. Облачный канал продаёт позицию, только
   если её нет в облачных стопах **и** нет в последних известных стопах кассы.
   Управляющий может снять устаревший кассовый стоп только для облачных каналов,
   с обязательной причиной и аудитом.
   **Уточнение владельца 2026-10-10:** управляющий может снять (unstop) кассовый стоп
   из бэк-офиса и для самой кассы. Снятие действует для iPad/приложения сразу; для
   кассы оно доставляется как удалённая стоп-команда по существующему пути
   `cloud_stop_commands` (cloud 048) -> `remote_stop_commands` (edge 019). Если касса
   offline, команда не истекает молча (сейчас TTL 120 секунд): она остаётся
   ожидающей и применяется при переподключении кассы с проверкой `expected_version`.
   Если касса за это время сама изменила стоп этой позиции, команда отклоняется и
   показывается управляющему как конфликт (без last-write-wins). Причина и аудит
   обязательны в обоих случаях.
5. Кухонные экраны аутентифицируются в облаке как устройство: код подключения из
   бэк-офиса, отзываемый; пароль повара не нужен. Действия аудируются по устройству
   и станции.
6. Gate оформления для облачных каналов: вместо свежести кассы (`AVAILABILITY_STALE`)
   проверяется `KITCHEN_OFFLINE` - хотя бы одна станция сборки и одна станция
   приготовления опрашивали облачную ленту за последние 30 секунд; плюс включённый
   приём заказов, часы работы и опубликованное меню.
7. Фискальные чеки заказов киоска/приложения при выключенной кассе - решение
   владельца 2026-10-10: облачный режим включается **пока без фискального чека**,
   схема чека добавляется позже. Это осознанно принятый владельцем риск; поведение
   ККМ/Kaspi не выдумывается. Заказы облачного режима помечаются как оформленные без
   фискального чека и попадают в отдельный список для последующей сверки, когда
   схема будет согласована с бухгалтером (см. раздел «Открытые вопросы»).

## Решение по нумерации (следствие решения 3)

- Событие открытия смены на кассе сбрасывает все три диапазона точки.
- Пока касса offline, облачные диапазоны продолжаются и по кругу переиспользуют
  номера внутри своего диапазона, пропуская номера активных (не выданных и не
  отменённых) заказов.
- Если все 300 номеров диапазона заняты активными заказами - оформление в этом
  канале отклоняется `NOT_READY` и создаётся алерт смене/поддержке.
- Позднее возможна опция: открытие смены управляющим из бэк-офиса, если касса
  выключена весь день. Сейчас не реализуется, фиксируется как кандидат.
- Касса переходит со сквозной последовательности `fulfillment_display_sequence`
  (`packages/edge-fulfillment/src/repository.ts`) на диапазон 1-299 со сбросом по
  смене. Текущее ограничение `display_number bigint UNIQUE` в
  `db/edge/migrations/005_edge_fulfillment.sql` и неизменяемость зарезервированного
  номера из `015_edge_reserved_order_number.sql` пересматриваются в edge 021.

## Архитектура (кратко)

- Режим точки `cloud_channels_owner` (`edge` | `cloud`) с монотонным `epoch`.
  Владелец выполнения фиксируется в заказе в момент подтверждения оплаты и далее не
  меняется; смена режима действует только на новые заказы.
- В режиме `cloud` для kiosk/mobile не создаётся `edge.kitchen_admission_requested`.
  Выполнение ведёт облачный агрегат `cloud_kitchen_orders`/`cloud_kitchen_tasks`
  с тем же набором команд, что edge (`start_task`, `complete_task`,
  `complete_station`, `confirm_stop`, `ready`, `handoff`, `confirm_cancel`),
  `expectedVersion` + `Idempotency-Key` + durable outbox.
- Чистая машина состояний выделяется в общий пакет из
  `packages/edge-fulfillment/src/model.ts` и проверок переходов в
  `packages/edge-fulfillment/src/repository.ts`; edge и cloud используют одну
  реализацию и общие тестовые векторы.
- Кухонный gateway получает второй upstream (облачный `/v1/kitchen/*`). Renderer
  объединяет ленты по `orderId` с полем `fulfillmentOwner`; действие уходит только
  владельцу заказа; индикатор связи показывается по каждому потоку; журнал
  незавершённых команд офлайн хранится отдельно для каждого владельца.
- Табло объединяет оба источника номеров.
- Протокол fulfillment transport 5: событие `cloud.channel_order_mirrored` ->
  read-only таблица edge `cloud_channel_orders` для отчётов/X-Z. Это зеркало не
  показывается на кухне второй раз и не создаёт заданий.
- Стопы облачных каналов - собственная таблица облака; кассовые стопы по-прежнему
  пишет только edge (`db/cloud/migrations/048_cloud_stop_commands.sql`), облако их
  не перезаписывает.
- Снятие кассового стопа из BO: облачный канал сразу использует override, касса
  получает команду unstop. Сейчас `cloud_stop_commands` имеет жёсткий
  `CHECK(expires_at = created_at + interval '120 seconds')`, переходит в `expired`,
  а ожидающее UNSTOP не учитывается в `availability.ts`, пока edge его не применил.
  Для unstop из BO TTL заменяется долговечным состоянием `pending` до переподключения
  кассы; применение на edge проверяет `expected_version`, расхождение даёт
  `conflict`, видимый управляющему. Состояние `no_open_shift` и правило «одна
  открытая команда на позицию» сохраняются; итоговую семантику (в том числе для
  STOP-команд) фиксирует S5.

## Альтернативы

- Оставить только edge и ускорить восстановление кассы: не выполняет решение
  владельца о независимости iPad/приложения.
- Перенести всё выполнение в облако: ломает работу кассы и кухни без WAN.
- Двусторонняя репликация заказов edge <-> cloud с last-write-wins: запрещена
  AGENTS.md и docs/03 для выдачи и денег.

## Последствия

- Два владельца выполнения в одной кухне: каждое действие направляется ровно одному
  владельцу, кухня обязана показывать, чья лента недоступна.
- Без WAN облачные заказы на кухне не видны и новые не принимаются (gate
  `KITCHEN_OFFLINE`); локальная касса продолжает работать.
- Облако становится писателем стопов облачных каналов - явное изменение таблицы
  владельцев docs/03 (раздел ниже).
- Отчёты/X-Z кассы включают облачные заказы только через зеркало протокола 5.

## Открытые вопросы

1. Фискальный чек kiosk/mobile при выключенной кассе: кто executor, допустим ли
   облачный API ККМ, отложенный чек и его срок. Вопрос к бухгалтеру и поставщику ККМ
   (docs/01 раздел 6.2). До ответа облачный режим работает без чека по решению
   владельца 2026-10-10 (решение 7), заказы копятся в списке для сверки.
2. Открытие смены из бэк-офиса при выключенной кассе (кандидат, не решение).
3. Перенос ролей станции между экранами (KDS-04) для облачной ленты.
