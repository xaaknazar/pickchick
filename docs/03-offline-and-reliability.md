# PickChick — автономная точка, синхронизация и переход с iiko

Версия 1.0 · ключевая часть архитектуры. Под «без интернета» понимается потеря WAN при сохранении питания и локальной сети. Другие аварии описаны отдельно.

**Уточнение владельца 14 сентября 2026:** для первой точки локальный узел и PostgreSQL
размещаются на кассовом моноблоке Windows 10 Pro; второй моноблок переключает
станции приготовления/сборки/выдачи. [ADR-0009](architecture/adr/0009-two-windows-workstations.md)
заменяет предложение отдельного Linux-сервера для этой установки. Требования
к сохранению данных, закрытому API, автономности и приёмке остаются прежними.

**Уточнение владельца 8 октября 2026, kiosk Kaspi QR:** коммерческий iPad в
текущем этапе создаёт заказ/платёжный intent в облачном PostgreSQL и получает QR
без ожидания per-order admission с кассового edge. Это явное исключение из общего
локального порядка ниже, а не перенос владения задним числом. Публикация меню,
актуальная доступность кухни, стопы, расписание и аккаунт проверяются до оплаты.
Доставка admission остаётся durable outbox; оплата не подделывает reservation,
номер заказа или кухонное принятие. После подтверждения банка заказ может быть
оплачен до доставки на кухню. iPad хранит гостя/заказ и показывает ожидание номера
без автоочистки, сотрудник разбирает задержку. После фактического admission
reconcile выпускает единственную kitchen-команду. При несовместимом/недоступном
edge доставка ожидает восстановления; без WAN новый облачный QR не создаётся.
Мобильные счета и POS сохраняют прежние правила. Решение и доказательства:
[kiosk-v3-launch.md](operations/kiosk-v3-launch.md).

## 1. Локальный узел

Каждая точка получает edge: сервис заказов, локальную PostgreSQL, меню/цены/правила, кухню, табло, локальный outbox/inbox и supervisor. Касса и киоск всегда оформляют локальные заказы через edge, в том числе при работающем интернете. Они не переключают владельца заказа между облаком и локальной БД при каждом обрыве связи.

Предпочтителен отдельный Linux mini-PC. Текущий сервер/моноблок iiko можно рассматривать после обследования мощности, ОС, лицензий, драйверов, дисков и портов. Нельзя считать, что установка нашего сервиса рядом с iiko безопасна без стенда; прямую запись в БД iiko не использовать.

Касса Windows обращается к edge по защищённому LAN API. Локальный Windows hardware service взаимодействует с ККМ, принтером и Smart POS по разрешённым SDK/протоколам. Бизнес-операция сохраняется на edge до вызова оборудования; состояние драйвера и terminal operation ID сохраняются для восстановления.

Нужны стабильные адреса оборудования, отдельный служебный VLAN от гостевого Wi-Fi, Ethernet для edge/кассы/стационарных устройств, управляемая Wi-Fi-сеть для iPad, основной интернет + LTE/5G-резерв и UPS для сетевого оборудования и edge. Принтер/ККМ учитывать по фактической мощности UPS. LAN не должна зависеть от доступности провайдера или внешнего DNS для каждого запроса.

HTTPS-сертификаты и локальное имя узла должны продолжать работать без WAN. Решение о private PKI/MDM или заранее выпущенном сертификате с локальным DNS принять на аппаратном стенде; отключать проверку TLS в клиентах нельзя. Обновление сертификатов производится заблаговременно и мониторится.

## 2. Владельцы данных

| Данные/действие | Единственный владелец записи | Реплики и поведение |
|---|---|---|
| Профиль, согласия, общий кошелёк | Центральный сервис | На edge минимум сведений; начисление по номеру — локальный claim |
| Каталог, базовые цены, программа лояльности | Центр | Edge активирует неизменяемую версию и подтверждает ACK |
| Ручной стоп точки, текущие резервы, остатки точки | Edge | Центр хранит проекцию; удалённое изменение — команда, применяемая edge |
| Локальный заказ POS/kiosk и его расчёт | Edge | Центр импортирует события, не редактирует независимую копию |
| Коммерческая часть mobile/Яндекс | Центр | Edge принимает execution request и ведёт выполнение |
| Производство и выдача любого заказа | Edge | Центр получает подтверждения, показывает клиенту проекцию |
| Kaspi-операция через Smart POS | Назначенный edge/hardware adapter | Центр наблюдает и сверяет, не повторяет её другим адаптером |
| Удалённая банковская оплата | Центр | Edge получает подтверждённое разрешение исполнения |
| Фискальный документ | Назначенный executor конкретной ККМ/операции | Другой узел может читать результат, но не создать второй чек |
| Номер выдачи | Единственный активный edge точки | Mobile сначала показывает UUID/подтверждение; короткий номер — после ACK edge |

**Не делать двустороннюю репликацию одинаковых изменяемых строк с last-write-wins.** Для заказа разделить агрегаты `order_commercial`, `order_fulfillment`, `payment`, `fiscal_document`: у каждого собственный владелец, version и поток событий. Если логически они показаны в одной строке `orders`, чужие поля обновляются только проекцией событий владельца. Поле `aggregate_type` входит в ключ последовательности. Источник локального заказа нельзя менять без явной процедуры передачи полномочий.

Например, отмена mobile — команда центра к edge: edge может принять её до приготовления либо вернуть «уже готовится». Центр не переписывает локальный `in_progress` на `cancelled` без согласования. Возврат денег может начаться по правилам поддержки, но статус кухни и факт списания сырья всё равно фиксируются отдельно.

## 3. Нормальный локальный заказ

1. Касса/киоск читает опубликованное меню edge, собирает корзину и отправляет команду с request ID.
2. Edge проверяет доступность, рассчитывает цены/модификаторы, фиксирует снимок, сохраняет заказ и outbox. Все рабочие шаги имеют долговечные состояния.
3. Если списываются Чики, edge получает центральный hold; при недоступном центре списание недоступно. Ввод телефона для будущего начисления не блокирует покупку.
4. Для наличных кассир подтверждает получение и сдачу. Для Smart POS edge резервирует терминал, создаёт session и вызывает адаптер. Таймаут API переводит операцию в unknown и запускает проверку, не вторую оплату.
5. Назначенный fiscal executor выпускает чек по утверждённому сценарию. Если ответа нет, он сначала ищет исходную операцию, а не создаёт новую с другим ID.
6. После подтверждённых предпосылок edge разрешает приготовление, назначает номер, создаёт задания A/B и события для табло/центра.
7. Повар и сборщик отмечают свои этапы. Выдача сотрудником создаёт основание начисления в центре.

Для пилота предложен осторожный gate: готовить после подтверждения оплаты и успешно выданного фискального документа, в том числе законного автономного чека. Если бизнес хочет готовить при краткой задержке фискального ответа, такую политику отдельно согласовать с бухгалтером/ККМ и зафиксировать пределы; не включать бесконечное «пробьём потом».

## 4. Мобильный заказ и гонка с отключением точки

Heartbeat полезен для отображения состояния, но не гарантирует приём: связь может исчезнуть через миллисекунду. Поэтому перед стартом банковской оплаты центр запрашивает у edge admission reservation для конкретного quote, состава и суммы. Edge долговечно резервирует доступность и возвращает reservation ID/версию.

Платёжный TTL и резерв согласовываются с фактическим провайдером. После открытия платёжной сессии резерв не освобождается только из-за клиентского таймера. При истечении ожидаемого времени он переходит в `pending_resolution`; контролируемый процесс проверяет банк и принимает release/execute/refund. Это исключает продажу последней порции второй раз, пока первая оплата ещё может завершиться.

После success центр надёжно отправляет `authorize_fulfillment`. Пока edge не подтвердил применение, статус — «Оплачено, подтверждаем заказ с рестораном». Если связи нет, работает очередь и алерт. Предложенные пороги: уведомление смене/поддержке через 30 секунд без ACK; через 2 минуты заказ требует ручного решения; фактические сроки согласовать с операциями и банком.

Возврат после потери связи нельзя запускать просто по таймеру: edge мог принять команду и начать готовить, а ACK потерялся. Требуются подтверждённая отмена на edge либо решение уполномоченного сотрудника с учётом неопределённости и запретом повторного приготовления после возврата. Все последующие команды несут версию/ID и проверяются на terminal business state.

Если точка недоступна до admission, новая мобильная оплата не открывается. Просмотр меню/истории остаётся доступным, заказ показывает «Точка временно не принимает заказы». После восстановления приём включается только после синхронизации активных заказов, стоп-листа и проверки готовности ККМ/кухни.

## 5. Матрица аварий

| Ситуация | Что продолжает работать | Ограничение/реакция |
|---|---|---|
| WAN точки отключён, LAN работает | Касса, киоск, кухня, табло, локальное меню и новые локальные заказы | Банк только при реальной независимой связи терминала и проверенном API; ККМ только в допустимом автономном режиме |
| Kaspi/эквайринг недоступен | Сбор корзины; наличные при работоспособной ККМ | Безнал не подтверждать; не считать клиентский скриншот доказательством |
| Центр/кошелёк недоступен | Локальные продажи/кухня | Новое начисление pending, списание общего баланса запрещено; нет актуальной сетевой аналитики |
| Redis недоступен | Сохранённые данные и критические DB-процессы, если реализован fallback | Кеш замедлится; часть уведомлений/OTP временно недоступна; восстановить очередь из outbox |
| PostgreSQL центра недоступна | Edge обслуживает свою точку | Mobile checkout/CRM недоступны; не пытаться хранить деньги только в Redis |
| Облачная ККМ недоступна для точки | Корзина и ранее принятая кухня | Без проверенной локальной альтернативы новые расчёты ограничить по утверждённому регламенту |
| ОФД недоступен, ККМ доступна | Только то, что разрешает конкретная зарегистрированная ККМ | ККМ сама формирует автономный признак; наша очередь не выдаёт его сама |
| Кассовое приложение закрыто | Edge, кухня, табло, киоск | POS после запуска читает состояние, не отправляет checkout повторно |
| Принтер без бумаги | Электронно выпущенный чек остаётся выпущенным | Алерт и повторная печать существующего чека; не новая фискальная операция |
| KDS A потерян | Другой экран и edge | Управляющий назначает A-задачи на B; все события сохраняются |
| iPad потерял Wi-Fi | Остальные устройства | На iPad нельзя завершить checkout из одного локального UI-кеша; восстановить связь/направить на кассу |
| LAN/роутер сломан | Только независимые устройства по собственным режимам | Общая очередь кухни недоступна; переключить запасной роутер/регламент точки |
| Edge выключился | Подтверждённые данные сохраняются на диске | Supervisor/UPS/restart; при гибели устройства — controlled recovery, без двух активных владельцев |
| Питания нет | Пока хватает реально рассчитанного UPS | Организованный останов; offline ПО не заменяет питание |
| Яндекс приходит в центр, точка недоступна | Центр может сохранить запрос, но не принять его за кухню | Приостановить приём/отказать по контракту; fallback через кабинет партнёра с ручной сверкой |

## 6. Протокол синхронизации

Обе стороны используют transactional outbox/inbox. Доставка — at least once; бизнес-эффект — однократный благодаря idempotency и ограничениям БД. Обещание «exactly once через WebSocket» не закладывать.

**Отправка:** выбрать доступные записи outbox в порядке producer sequence → отправить batch с version → получить ACK после commit получателя → отметить подтверждение. При падении после commit получателя повтор безопасен. Устаревшее событие не откатывает объект, пропущенное — запрашивается повторно.

**Приём:** аутентифицировать устройство/центр, проверить точку, схему, допустимый размер и sequence → сохранить inbox → применить доменную команду → сформировать ответ/outbox одним commit. Ошибочное сообщение получает explicit error/DLQ; ACK никогда не означает «мы проигнорировали заказ».

Backoff с jitter, ограничение batch/полосы, приоритеты: деньги/оплаты и отмены → активная кухня → продажи/склад → справочники → аналитика/медиа. Фотографии не должны блокировать оплату или выдачу. Несовместимую версию схемы помещать на разбор, не терять и не считать синхронизированной.

Чекпоинт обновляется только до максимального непрерывно обработанного sequence. Для snapshot: временно согласовать watermark, передать консистентное состояние с checksum, применить атомарно и продолжить поток после watermark. Snapshot не очищает локальный outbox неподтверждённых операций.

Предложение хранения: неподтверждённый outbox — до ACK/разбора, без TTL; подтверждённый replay-архив — 30 дней на edge с конфигурируемым лимитом диска. При заполнении диска не удалять неотправленные продажи: заранее предупреждать, затем останавливать новый приём до безопасного восстановления. Дедупликационные ключи финансовых операций сохранять по финансовой retention-policy.

При восстановлении WAN сначала обменяться версиями/очередями/активными неизвестными оплатами, затем согласовать доступность и разрешить mobile/Яндекс. Последние подтверждённые события могут быть старше текущего времени: UI показывает `last_synced_at` и локальные/сводные результаты отдельно.

## 7. Конфликты справочников и остатков

Центральная публикация меню — неизменяемый release. Edge проверяет checksum/совместимость, применяет атомарно и подтверждает activation. До ACK публичный checkout не использует для этой точки новые цены. Уже оплаченные заказы продолжают работать по своему снимку, даже если блюдо удалено из актуального меню.

Ручной стоп имеет приоритет над автоматическим снятием стопа. Бэк-офис может отправить команду «разрешить продажу», но удалённая команда не считается применённой, пока edge не проверил реальную доступность. Устаревшая цена/стоп-конфигурация не перезаписывает более новую только по времени сервера.

Во время WAN-аварии нет глобального точного остатка. Источник движения конкретного склада один — edge точки. Управляющий в центре видит время актуальности; правка остатков из центра оформляется документом-командой, которую принимает edge. Межточечное перемещение: отгрузка, товар в пути, приёмка; остатки обеих точек не меняются одной необеспеченной сетевой операцией.

## 8. Терминал, ККМ и неизвестный результат

Одна активная платёжная сессия на физический терминал. Durable lock связан с operation ID; освобождение не происходит только по TTL, если статус банка unknown. Последующий клиент видит занятость/проверку. Снятие блокировки вручную требует сверки terminal journal и причины.

Для каждого адаптера реализовать capability matrix: create/status/cancel/full refund/partial refund/reconciliation/idempotency. Возможность не предполагается по названию API. Если провайдер не поддерживает идемпотентность, наш adapter хранит intent до сетевого вызова, отправляет стабильный external reference при доступности и проверяет исходную операцию после таймаута. При невозможности установить результат — `needs_review`, а не бесконечный повтор списания/чека.

Один расчёт — одна назначенная ККМ. Failover фискализации не означает отправить тот же запрос в другую ККМ: сначала установить, выпущен ли исходный документ, и действовать по утверждённому регламенту. Для Яндекса заранее определить, кто обязан выпустить какой чек; наша система не должна автоматически дублировать чек агрегатора.

## 9. Backup и восстановление

Центр: регулярный full backup + непрерывное архивирование WAL для PITR, шифрование, отдельные credentials, копия в другом домене отказа в Казахстане. Предложение retention: ежедневные копии 30 дней, месячные 12 месяцев; окончательные сроки привязать к политике данных и стоимости. Реплика не заменяет backup: удаление/повреждение может реплицироваться.

Edge: локальная PostgreSQL с fsync/durable commit, backup на отдельный носитель/узел и отправка в центр при WAN; резервная копия конфигурации/сертификатов защищена. Обычный процессный crash после подтверждённого commit не теряет заказ. При физической потере единственного диска во время WAN-аварии RPO определяется последней доступной копией, а не центральным SLO.

Для повышенной гарантии — второй локальный узел с синхронной записью и защищённым failover. Не запускать automatic leader election из двух устройств без безопасного кворума/fencing. Стартовая управляемая процедура: изолировать старый edge → проверить последнюю копию/журнал → активировать новый epoch/certificate → переключить клиенты → сверить неизвестные платежи → открыть продажи.

Откат приложения не должен откатывать уже состоявшиеся деньги и события. При восстановлении БД сверять provider journal, неисполненные outbox и идентификаторы операций до включения повторных отправок. Каждый restore drill сохраняет время, проверенные заказы, суммы, потерянный интервал и ответственного.

## 10. Мониторинг и работа смены

Метрики: WAN heartbeat, edge last_seen/epoch, диск, DB latency, возраст старейшего outbox, ошибки синхронизации, mobile paid без edge ACK, неизвестные оплаты, очередь чеков, terminal busy, KDS lag, непринятые/поздние Яндекс-заказы, дубли webhook, расхождение wallet projection/ledger, отрицательные остатки, закрытие смены и crash-free sessions.

Каждый заказ связывается единым correlation ID по cloud/edge/банк/чек/кухня. Логи структурированные и маскируют PII; incident alert содержит order ID и ссылку для уполномоченного сотрудника. Метрики финансовых расхождений рассчитываются из БД, а не только из logs.

Предложенные первичные тревоги: edge отсутствует >15 секунд — закрыть новый online admission после истечения короткого eligibility окна; старейший финансовый outbox >30 секунд — предупреждение; paid без принятия >30 секунд — срочный разбор; неизвестный платёж >2 минут — задача смене; диск >70/85% — предупреждение/критический уровень. Настроить после измерения пилота, чтобы не перегрузить смену ложными сигналами.

Runbook «непонятная оплата»: найти заказ → проверить исходный operation ID в адаптере → дождаться/запросить состояние → не вводить второй раз сумму на терминале → подтвердить результат либо передать старшему → сверить чек. Runbook «нет WAN»: проверить индикаторы → перейти на разрешённые методы → продолжать локальную кухню → не обещать бонусное списание → после восстановления проверить очередь/сверку.

## 11. Переход с iiko

### 11.1. Обследование и перенос

Зафиксировать версии iiko/Windows, характеристики сервера, ККМ и терминала, драйверы, лицензии, принтеры, сеть, экранные плееры, договор Яндекса и фактический процесс смены. Экспортировать справочники разрешёнными механизмами: блюда, модификаторы, цены, техкарты, ингредиенты, единицы, налоговые группы и внешние ID.

Тестовый импорт проходит таблицу соответствий и сверку количества/сумм. Историю продаж можно оставить в доступном read-only архиве с согласованным сроком; полная миграция истории — отдельная задача. Если есть существующие бонусы, переносить сверенный начальный ledger с актом остатков и дедупликацией телефонов, а не произвольным полем balance.

### 11.2. Теневой режим

iiko остаётся владельцем действующих продаж/чеков. PickChick получает разрешённые копии/экспорты для сверки меню, маршрутов и отчётов без платёжных и фискальных побочных эффектов. Если нужного feed нет, использовать контрольные тестовые заказы и выгрузки; не объявлять автоматический shadow mode без доступа к интерфейсу iiko.

Два KDS не должны одновременно производить одну и ту же коммерческую продажу. В shadow environment отдельная маркировка, запрет реальной кухни и выдачи.

### 11.3. Пилот и переключение

1. На стенде пройти аппаратные тесты и возвраты; на точке обучить смену.
2. Выделить пилотное окно/канал; заранее определить единственного владельца каждого заказа и ККМ.
3. В момент смены владельца Яндекс получить согласованное переключение у партнёра; завершить/разнести текущие заказы, сохранить внешние ID и статусы. Не оставлять два активных обработчика одного входящего потока.
4. Перед cutover остановить изменения справочников, завершить открытые расчёты, снять отчёты, пересчитать наличные и остатки, импортировать последнюю дельту.
5. Активировать PickChick, проверить каждый канал реальным контрольным сценарием по утверждённому кассовому регламенту, сверить сумму и чек.
6. Наблюдать смену и ежедневно сверять продажи/банк/ККМ/бонусы/склад. Старую систему хранить доступной для архива и разрешённого отката.

### 11.4. Условия отката

Примеры стоп-факторов: потерянный оплаченный заказ, повторное списание/фискальный чек, систематическая невозможность принять заказ, несходимость синхронизации, неизвестный финансовый эффект без процедуры разбора. Управляющий и технический ответственный прекращают новый приём затронутого канала.

Откат возвращает владельца **новых** заказов после согласованного переключения. Ранее оплаченные заказы завершаются/возвращаются и сверяются по исходным ID; их нельзя повторно импортировать в iiko как новую продажу и пробить второй чек. Складские дельты, наличные, выплаты и бонусы переносятся контрольными документами. Акт сверки закрывает пилотное окно.

Прямую интеграцию Яндекса и замену функций iiko нельзя считать принятой, пока они реально остаются обслуживаться старой системой. Временный fallback — способ сохранить работу ресторана, не доказательство выполнения ТЗ.
