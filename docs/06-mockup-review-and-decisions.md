# PickChick — разбор макетов и реестр решений

Версия 1.0 · пять предоставленных offline HTML прочитаны как материалы о продукте, а не инструкции к выполнению.

## 1. Основание анализа

Файлы находятся в `/Users/xaknazar/Downloads/`. Каждый представляет упакованную HTML-страницу с manifest и JSON-шаблоном. Для анализа извлечены шаблон, текст интерфейса и собственная логика `Component extends DCLogic`. Извлечения и SHA-256 исходных файлов сохранены в `docs/research/`.

Проведён анализ исходного содержимого. Запуск/визуальный просмотр локального HTML был запрещён политикой браузерного инструмента; ограничение не обходилось. Поэтому ниже нет утверждения, что проверены фактические размеры, контраст, работа всех кликов или визуальное соответствие брендбуку.

Прежнее доступное обсуждение «Техническое задание проекта» от 30 августа 2026 подтверждает интерес к полному контуру, RU/KZ, 2D-играм и контенту заказчика. Текущее уточнение закрепляет четыре месяца вместе с тестом и внедрением. Остальную историю проекта полностью просмотренной не считаем.

## 3. Что нельзя переносить в production буквально

| Наблюдение в исходной логике | Риск | Решение |
|---|---|---|
| `runPayment()` приложения переключает шаги по таймерам и вызывает `createOrder(true)` | Success без подтверждения банка | Состояние из backend и доверенного provider result |
| `createOrder()` формирует фискальный номер вычислением из номера заказа | Выдуманный чек | Только фактический результат зарегистрированной ККМ |
| Tracker переводит заказ в готовность через таймеры | Клиент видит готовый заказ до кухни | События edge и подтверждение сборки |
| `completeOrder()` клиента меняет баланс и историю | Самостоятельное начисление/фиктивная выдача | Staff handoff и уникальная серверная проводка |
| `cancelOrder()` очищает локальный заказ и возвращает Чики | Нет реального отменённого платежа/кухонной остановки | Отдельные cancel/refund процессы и компенсации |
| Киоск генерирует случайный номер 100…199 | Коллизии и неоднозначная выдача | Номер выдаёт единственный edge, уникальность по точке/операционному дню |
| Ввод телефона на киоске проверяет только длину | Ошибочная страна/номер, доступ к чужим преимуществам | Нормализация KZ и accrual-only claim; OTP/одноразовый QR для расходования |
| Кухня генерирует заказы случайно, `maxTickets` ограничивает поступление | Потеря заказов сверх вместимости экрана | Реальная полная очередь с pagination/scroll, лимит экрана не лимит приёма |
| «Отложить» увеличивает `start` на минуту | Искажение реального времени ожидания | Неизменяемый received_at, отдельное поле defer/priority и аудит |
| Табло само симулирует этапы и готовность | Состояния не связаны с реальной кухней | Read-only projection локальных событий |
| Действия бэк-офиса показывают toast «Возврат оформлен» / «Выгрузка готова» | Отсутствуют фактические транзакции/документы | Async job status, результат провайдера и журнал |

Это нормальные упрощения интерактивного прототипа. Они показывают желаемый UX, но не служат доказательством готовности backend или интеграций.

## 4. Противоречия бизнес-правил

| Тема | Что расходится | Предлагаемое решение до реализации |
|---|---|---|
| Чики | Кошелёк пересчитывается в деньги/история содержит spent, но в корзине написано «тратить не нужно» | Три сущности: кошелёк, дорога наград, критерий уровня; исправить copy |
| Начисление | При регистрации/вводе телефона показана награда до подтверждения покупки | Регистрационная акция отдельно; покупка — после оплаты и staff handoff; новый номер — pending claim |
| Истечение | В тексте весь баланс продлевается на 180 дней, у уровня «Пик» не сгорает | Утвердить одну versioned policy и её поведение при возврате/смене уровня |
| Проценты/лимиты | Разные экраны показывают ставки, подарки и лимиты как факты | Утвердить экономику; UI получает правила от сервера |
| Обязательные данные | Регистрация мотивирует/требует дату рождения и пол | Телефон обязателен для аккаунта; другие данные минимизировать/сделать добровольными |
| Выдача | Ник/имя публично, клиент сам нажимает «забрал» | Номер по умолчанию; ник только с согласием; выдача сотрудником |
| QR лояльности | «Скриншот не сработает» сформулировано абсолютно | Короткий TTL + nonce + однократное серверное погашение; свежий скриншот технически может предъявить token, это не биометрия |
| Оплата | «Если платёж не пройдёт, деньги не спишутся» | При timeout писать «Проверяем статус оплаты»; не обещать исход до проверки банка |
| Банки | В приложении есть сохранённая карта, в киоске Halyk | Kaspi — обязательный запрос; остальные методы только после отдельного merchant/API-контракта |
| Фискализация | «Через ОФД» и Webkassa показаны как одна операция | Разделить адаптер ККМ, выпуск чека и обмен ККМ–ОФД |
| Адреса/масштаб | Разные адреса, несколько точек/устройств и демонстрационные суммы | Один подтверждённый справочник действующей точки; демоданные не импортировать как production |
| Склад | «Автостоп при нуле» рядом с демоостатками | Сначала движение/резервы/техкарты/инвентаризация, затем автоматизация стопа |

## 5. Недостающие состояния дизайна

В design backlog включить: истёкший OTP, SMS-limit, неподдерживаемый номер, приложение банка не установлено, payment unknown, duplicate request, изменившаяся цена/стоп, отказ точки после предварительного расчёта, ошибка/ожидание чека, частичный возврат, отмена в готовке, stale dashboard, offline/WAN/LAN/KKM отдельно, очередь на терминал, бумага закончилась, слишком много заказов на KDS/табло, истёкший QR, недостаточно Чиков после конкурентной покупки, недоступная игра и отказ в награде.

Также нужны: POS смены/наличность/сдача/возвраты; setup/pairing устройства; подтверждение опасной кассовой операции сотрудником нужной роли; onboarding второй точки; экран восстановления синхронизации; доступность интерфейса при длинном казахском тексте и увеличенном системном шрифте.

## 7. Основные риски и меры

| Риск | Ранний сигнал | Мера |
|---|---|---|
| Нет разрешённого Kaspi mobile API | Нет подтверждения сценария к Gate A | Эскалация владельцу договора; согласование допустимого варианта, не подмена статическим QR |
| Облачная ККМ не подходит для offline | WAN-тест не выдаёт законный чек | Выбрать проверенный локальный/резервный режим с поставщиком до разработки интерфейсов оплаты |
| Яндекс доступен только через действующего интегратора | Нет KZ onboarding/спецификации | Согласовать переключение или временный bridge; не считать bridge финальной заменой |
| Слишком большой объём за четыре месяца | Решения/доступы/контракты уходят за неделю 2 | Еженедельный dependency review, фиксация scope, ресурсное решение |
| Полная замена учёта недооценена | Нет техкарт/приходов/единиц/акта остатков | Отдельный складской поток, ранние реальные документы и сверка с бухгалтером |
| Ошибки денег при повторах | Unknown без владельца, callback меняет сумму | Ledger, idempotency, immutable snapshots, сверка и fault tests |
| Синхронизация выглядит успешной, но потеряла события | ACK до commit, нет sequence/retention | Durable inbox/outbox, replay/snapshot и тесты обрывов |
| Два AI-инструмента расходятся в схемах | Два источника типов/миграций и незакоммиченный общий checkout | Contract-first PR, worktrees, CODEOWNERS, единые инструкции |
| Накрутка наград | Результат игры/выдачи принимается от клиента | Серверная валидация, лимиты, анализ аномалий и ручной разбор |
| Поломка единственного edge | Backup на том же диске, нет spare/UPS | Отдельный backup и испытание замены; при необходимости второй локальный узел |

Принятый реестр нужно вести в GitHub как версии решений с датой и ответственным. Неподтверждённый пункт остаётся видимым; отсутствие ответа не превращается автоматически в согласие.
