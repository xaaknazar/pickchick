## Этап 1А — локальный исполняемый фундамент

Реализовано в ветке `codex/stage-1-foundation`:

- pnpm monorepo: API, edge, contracts, database, platform, test-fixtures.
- Node/TypeScript/NestJS и зависимости зафиксированы, lockfile включён в Git.
- Два PostgreSQL-контейнера с отдельными томами; локальный Redis cache.
- Миграции cloud/edge с lock, transaction, checksum и запретом смешивания схем.
- Организация, юрлицо, точки, устройства, каталог, цены, immutable версии меню;
  составные FK ограничивают принадлежность сущностей. Таблицы inbox/outbox
  подготовлены; работающий transport/worker пока не реализован.
- Центральные read-only endpoints точек/активного меню и локальное меню edge.
- Runtime Zod-контракты, генерируемые OpenAPI/event schema и проверка дрейфа.
- Health/readiness с раздельными состояниями БД/схемы/Redis, request ID,
  безопасные ответы ошибок и ограничение запуска на local/test/loopback.
- Синтетический seed; повторный запуск не создаёт дубликаты, приём заказов выключен.
- GitHub Actions workflow для build/types/lint/format/contracts, unit/integration
  tests на PostgreSQL и dependency audit; PR template и CODEOWNERS.
- [Инструкция запуска](operations/local-development.md) и [ADR](architecture/adr/0001-foundation.md).

Локально подтверждено:

- `pnpm check`: build, typecheck, lint, форматирование, 5 unit tests, contract drift.
- `pnpm test:integration`: 15 сценариев на реальной PostgreSQL и Nest HTTP.
- Повторный migrate/seed; fresh migrations, конкурентный runner, checksum drift,
  rollback DDL, ограничения организации/денег/снимков и дедупликация inbox.
- Меню edge читается после остановки cloud API и перезапуска edge; сбой Redis
  даёт degraded, сбой PostgreSQL — readiness 503, неверная branch binding — отказ.
- `pnpm audit --audit-level=high`: известных уязвимостей не найдено на момент проверки.

Публикация ветки, PR и результат удалённого CI фиксируются в GitHub.
Наличие workflow в коде само по себе не означает, что GitHub CI уже прошёл.

**Границы:** это завершённая первая инженерная часть этапа 1, не полный Gate A/B.
Нет OTP/RBAC/device enrollment, полноценного каталога с модификаторами/комбо,
checkout/заказа/кухни, фискализации, эквайринга или синхронизации между точками.
Прямой seed двух БД не является протоколом синхронизации; короткий restart-тест
не заменяет 8-часовую автономную приёмку. Клиентские приложения и production
развёртывание не созданы, branch protection в GitHub пока не настроен.

## Следующий этап 1Б

1. Контракты идентичности сотрудника/устройства и ограниченный локальный setup.
2. Публикация меню с подтверждением применения на edge через durable outbox/inbox.
3. Версии цен, модификаторы/комбо и серверный quote на тестовом каталоге.
4. Первый идемпотентный локальный заказ и события кухни; финансовые операции
   добавлять с отдельными состояниями и тестовыми адаптерами без ложного success.
5. Параллельно закрывать внешние решения Gate A, чтобы перейти к настоящим
   Kaspi/ККМ/Яндекс-интеграциям и сквозному Gate B.

## Внешние зависимости

Доступы Kaspi mobile и Smart POS; выбор и автономный режим зарегистрированной
ККМ; API Яндекс Еды Казахстан; характеристики оборудования точки; согласование
бонусной экономики и складских правил. Полный список —
[реестр решений](06-mockup-review-and-decisions.md).
