# PickChick — состояние проекта

## Текущий этап — серверные аккаунты, каталог и исполнение заказа

7 сентября 2026 заказчик поручил выполнить оставшуюся разработку по roadmap.
Фундамент сохранён в `codex/market-readiness-core`; следующий этап LAN-кухни
ведётся в `codex/local-kitchen-lan`. Реализованы следующие части:

- [Клиентские аккаунты](operations/customer-identity.md): OTP, зашифрованный профиль,
  согласия, постоянная сессия, отзыв и удаление; HTTP подключён к API. Expo может
  использовать этот серверный вход по явному флагу сборки, сохраняет доступ и
  восстанавливает потерянные ответы. Реальные SMS по-прежнему выключены.
- [Касса](operations/pos-client.md): рабочий web-клиент локального edge с ролями,
  меню, расчётом, неоплаченным заказом, отменой и журналом восстановления. Проверен
  с настоящими локальными PostgreSQL/HTTP, в том числе после потерянного ответа.
  Оплата, ККМ, смены и локальная кухня пока не подключены к этой кассе.
- [Коммерческое ядро](operations/commerce-core.md): неизменяемый расчёт, заказ,
  резерв допуска точки, фактические события оплаты, возвраты, фискальные состояния,
  сверка и outbox. Это внутренний домен: банковские адаптеры и HTTP checkout ещё
  не включены. Передача заказа в локальную кухню проверена прямым вызовом между
  временными cloud/edge БД; сетевой транспорт и worker ещё не подключены.
- [Локальное исполнение заказа](operations/edge-fulfillment.md): долговечный
  резерв допуска, закреплённый маршрут компонентов, задания приготовления и
  сборки, явные готовность/выдача и отмена, локальные права персонала,
  идемпотентные inbox/outbox. Добавлены [LAN HTTP API](operations/edge-fulfillment-http.md)
  с реальными правами персонала и [клиент кухни/табло](operations/lan-kitchen-client.md):
  приготовление, сборка, выдача, журнал потерянных команд, очереди и безопасные
  номера на табло. Клиент проверен через настоящий локальный API и PostgreSQL.
  Cloud↔edge transport/worker сейчас разрабатывается; POS ещё не подключён.
  Резерв допуска пока
  не резервирует склад или производственную мощность. Физический ресторанный
  цикл без WAN не принят.
- [Каталог для бэк-офиса](operations/catalog-admin.md): отдельные полномочия
  управляющего по точкам, 24 блюда исходного макета как черновик, редактирование,
  версии, явная публикация и аудит. Рабочий UI бэк-офиса связан с PostgreSQL:
  описания RU/KZ, КБЖУ, фото из макета, модификаторы, состав комбо, сохранение и
  публикация. Серверный расчёт проверяет опубликованную версию и сохраняет
  точный состав/цены в коммерческом заказе. Публикация не меняет старые TEST-цены
  и не разрешает автоматически реальные продажи; налоговые настройки задаются
  отдельно и требуют утверждения.
- [Серверные Чики](operations/loyalty-core.md): журнал начислений, резервы без
  перерасхода, возвраты и долг, партии и истечение. Внутренний домен прошёл
  25 проверок; он ещё не подключён к событиям выдачи, интерфейсу и игре.
  Бонусная программа автоматически не активируется: нужны утверждённые правила.

В общей рабочей копии прошли **128 PostgreSQL/HTTP-проверок, 28 commerce,
25 loyalty и 16 проверок эксплуатационных сценариев**. Следующий LAN-этап
добавил **12 HTTP-проверок**, расширил домен кухни до **22 проверок** и прошёл
**26 проверок клиента/gateway + 3 PostgreSQL/HTTP/browser-сценария**.
Все эти наборы повторно прошли в общей рабочей копии после интеграции.
Чтение KDS использует согласованный снимок без блокировок заказов; четыре
конкурентных сценария воспроизвели прежние ошибки и подтвердили исправление.
Эти результаты получены на временных данных, без реальных SMS, банковских
операций и чеков.

8 сентября в общей рабочей копии LAN-этапа прошли `pnpm check`, все **140**
сценариев `pnpm test:integration` и все 29 проверок `pnpm test:kitchen`.
Проверены реальные экраны 1280×800 / 1920×1080, потеря ответа после commit,
повтор той же команды после reload и отсутствие повторной выдачи.
Станция сборки видит все закреплённые за ней заказы, даже если у неё нет своей
задачи приготовления. [Протокол и снимки](../tests/operations/verification-lan-kitchen-2026-09-08.md).
Для этих сценариев добавлен отдельный пятый CI job. На физических устройствах
новый LAN-клиент ещё не установлен; сетевая доставка заказов из облака не принята.

В общем слое PostgreSQL исправлен [разрыв соединения внутри транзакции](../tests/operations/verification-database-disconnect-2026-09-07.md):
процесс получает контролируемую ошибку, повреждённое соединение удаляется из
pool. Автоматического повтора транзакции нет; потерянный ответ на COMMIT
по-прежнему требует сверки идемпотентной операции. Для использованного OTP
действует отдельный лимит пяти ошибочных восстановлений без повторной SMS
и без влияния чужого request ID на клиента.

[GitHub PR #20](https://github.com/xaaknazar/pickchick/pull/20) открыт как draft.
[CI выпуска](https://github.com/xaaknazar/pickchick/actions/runs/34151721514) прошёл
во всех четырёх jobs. `prepare` и `apply` на VPS завершены; проверены восстановление
свежей копии, миграции, права, сохранность прежних данных и соседних сервисов.
[Протокол выпуска](operations/deployments/2026-09-07-market-foundations.md).
Отдельная проверка public bundle под `umask 077` и
ограниченным Linux Caddy прошла [локально](../tests/operations/verification-public-bundle-permissions-2026-09-07.md).

На VPS API и web обновлены до **`7cd53b6`**. [Бэк-офис](https://pickchick.185.129.51.103.nip.io/backoffice/)
включён, доступ управляющего сохранён приватно, 24 блюда загружены как
неопубликованный черновик r1. Плановая очистка настроена; ручной и первый
автоматический запуски прошли. Реальные SMS/оплаты/чеки выключены. Доступные TestFlight-сборки
относятся к предыдущему выпуску. Закрытый киоск
не считается готовой постоянной установкой ресторана, а отдельные домены не
означают приёмку всей системы. Нагрузочная цель — до миллиона регистраций и
1 000 одновременно исполняемых заказов на нескольких точках — ещё не принята.
[Первый локальный baseline](operations/capacity-baseline.md) проверил миллион
синтетических identity-строк и 1 000 открытых заказов по десяти точкам без ошибок.
Он измеряет SQL/доменные транзакции и не заменяет испытания HTTP, доставки событий
и физических кухонь на выделенном стенде в Казахстане.
Kaspi, ККМ/ОФД, Яндекс, sender/бюджет SMS, утверждённые данные, оборудование и
пилот остаются в [реестре зависимостей](operations/launch-inputs.md).

  Один active edge на точку; приватный файл идентичности исключён из Git.
- Публикация следующей версии меню: immutable release, outbox и непрерывный
  producer sequence одной транзакцией; повтор по release UUID идемпотентен.
- Настоящие HTTP pull/ACK с авторизацией устройства по своей точке. Центр
  меняет активное меню только после подтверждения применения на edge.
- На edge: проверка hash/версии/последовательности, snapshot/activation/inbox/
  cursor/ACK outbox в одном commit. Worker с timeout, ограничением размера,
  повтором/backoff и восстановлением неподтверждённого ACK после restart.
- OpenAPI v0.2.0 и команды `device:setup`, `device:revoke`, `menu:publish`,
  `sync:once`, `sync:watch`; пример меню v2 и инструкция воспроизведения.
- [ADR 0002](architecture/adr/0002-device-menu-sync.md),
  [инструкция обмена](operations/menu-sync.md),
  [предложение VPS](operations/vps-plan.md) с проверенным публичным тарифом.

Локально прошли `pnpm check` (включая 7 unit tests) и 26 интеграционных тестов.
Новые сценарии используют отдельные временные схемы в двух PostgreSQL:
реальный HTTP worker, конкурентная публикация/доставка, rollback в середине
операции, потерянный ACK-ответ, offline/retry, hash/schema/gap, изоляция точки,
ротация/expiry/revoke, старый ACK после нового меню и malformed/oversized HTTP.
Вручную выполнены CLI setup, повторная публикация примера v2, `sync:once`
(`applied`, затем `idle`) и сравнение release/version обоих HTTP API.
Права файла ключа 600 и каталога 700 проверены без вывода секрета.
[PR №2](https://github.com/xaaknazar/pickchick/pull/2) принят в main после
подтверждения продолжения заказчиком. CI на `a0487b8` прошёл;
merge commit: `ed5ce66fd49d9b03b8eccd43d82f60975d33de1d`.

**Границы:** это первая часть этапа 1Б. Работает только localhost с тестовыми
данными. Публичный одноразовый enrollment, роли/вход сотрудников и OTP клиентов,

каталог с комбо/quote/заказы, мобильные интерфейсы и оплаты ещё не реализованы.
Короткие тесты restart не заменяют полный 8-часовой аппаратный WAN-тест.

На момент этапа 1Б.1 VPS ещё не был предоставлен. Был подготовлен staging-кандидат PS Cloud Basic-4

## Этап 1Б.2 — права персонала, базовый quote и локальный заказ

Реализовано в ветке `codex/stage-1b-local-orders`:

- Trusted local setup персонала и терминалов: cashier/shift_manager/kitchen,
  8-часовые сессии и grant, хранение хеша секрета, обновление сессии и отзыв.
  Каждая операция проверяет точку, active staff/terminal, срок и роль.
- Cashier создаёт/читает/отменяет свои неоплаченные заказы на своём терминале;
  manager управляет режимом приёма, ручным стопом и заказами точки. Кухонная
  роль не имеет доступа к этому POS API.
- Quote по активному меню: обычные SKU, количество, «в зале»/«с собой», BigInt,
  KZT, immutable snapshot и TTL 5 минут по часам БД. Клиентские цены запрещены.
- Idempotent POST заказа по quote UUID; повтор возвращает прежний результат,
  changed payload конфликтует. Unique quote → order; перепроверяются TTL,
  меню, режим точки и стопы. Создание/отмена, audit, outbox и command result
  фиксируются одной транзакцией; отдельный producer для коммерческих событий.
- Заказ имеет только `awaiting_payment` или `cancelled`, без состоявшейся
  оплаты/фискализации/готовки. Отмена требует expected version и причину;
  immutable quote сохраняет исходные цены после смены меню.
- API v0.3.0, миграция edge 004, CLI `staff:setup`, `staff:revoke`,
  `local:request`, синтетические примеры, [инструкция](operations/local-orders.md)
  и [ADR 0003](architecture/adr/0003-local-orders.md).

Проверки: 10 unit и 39 integration сценариев, включая реальный HTTP,
повтор/конкуренцию, права и чужую точку/терминал, expiry, stop/menu change,
rollback outbox, обновление сессии одновременно с checkout и restart edge
при отсутствии центрального HTTP API. Build/types/lint/format/contracts проходят;
результат CI связан с актуальным SHA PR этого этапа.

Ручной CLI smoke: setup manager/cashier → open → quote на 7180 ₸ по примеру v2
→ create → replay с тем же результатом → cancel → GET cancelled → close.
Исходный закрытый режим точки восстановлен. Файлы сессий имеют mode 600,
секреты в вывод и Git не включаются. Заказ smoke синтетический, оплаты нет.

**Границы:** backend только localhost; права выдаются trusted CLI на edge,
не центральной системой управления пользователями. Нет публичного входа/PIN/OTP,
комбо/модификаторов, скидок/Чиков, расписания, складского резерва, смен ККМ,
реальных денег/чеков, кухни/табло и доставки заказов в центр. Коммерческий outbox
сохранён, consumer не реализован. Полный Gate B и аппаратный WAN-тест не пройдены.
После этапа заказчик предоставил существующий VPS; инфраструктурная работа описана ниже.
