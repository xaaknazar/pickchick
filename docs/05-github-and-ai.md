# PickChick — один GitHub и совместная разработка с Fable / Astra

Уточнение владельца 23 сентября 2026: продолжать работу с двух Mac без потери
обновлений. Введены общая ветка разработки `codex/shared-development`, отдельный
журнал резерваций `codex/work-coordination` и команды проверки/передачи задач.
[Обязательный порядок и границы](collaboration/README.md). Общая ветка не
подменяет принятую main-версию и не означает автоматический deploy.


Версия 1.0 · схема организации работы. Для начальной публикации выбран приватный
репозиторий [xaaknazar/pickchick](https://github.com/xaaknazar/pickchick), подтверждены
действующие права записи. В этапе 1А добавлены monorepo, CI workflow и CODEOWNERS;
branch rules и среды production-развёртывания ещё не настроены. Выполнение и
фактические проверки отслеживаются в [состоянии проекта](project-status.md).

## 1. Что именно нужно объединить

По уточнению заказчика Fable 5.1 — модель Anthropic, Astra 6 — модель OpenAI для дизайна и других работ. Здесь эти названия обозначают выбранные AI-инструменты команды. Релизные номера, стоимость и доступность соответствующих API отдельно не подтверждались; архитектура продукта от них не зависит.

Fable может помогать писать backend/интеграции, Astra — проектировать интерфейсы, клиентский код, сценарии и проводить review. Но backend исполняется как TypeScript/Node.js, а интерфейсы — как приложения React/React Native. Называть сервер «написанным на Fable» технически недостаточно: модель — помощник разработчика, не runtime системы.

**Один private monorepo GitHub — источник правды для кода, контрактов, документации и решений.** AI-инструменты не видят автоматически чужую переписку или незакоммиченные изменения из другого checkout. Они видят то, что доступно в их рабочей копии или connector. Синхронизация обеспечивается commit/PR/fetch, общими документами и чёткими заданиями.

Production-серверам не нужен доступ к AI-моделям для приёма заказов. Если подписка AI закончится или сервис недоступен, ресторан должен продолжать работать.

## 2. Предлагаемый monorepo

```text
pickchick/
  apps/
    mobile/                   # iOS/Android
    kiosk/                    # отдельный iPad app
    pos/                      # Electron UI кассира
    kitchen/                  # KDS web
    display/                  # табло
    backoffice/               # управление
  services/
    api/                      # центральные NestJS-модули
    worker/                   # очереди и фоновые процессы
    edge/                     # сервис локальной точки
    hardware-bridge/          # Windows service/драйверы
  packages/
    contracts/                # OpenAPI/JSON Schema/events
    api-client/               # генерируемые SDK
    domain/                   # чистые типы и допустимые общие правила
    pricing/                  # детерминированный расчёт без доверия клиенту
    design-tokens/            # цвет, типографика, отступы, радиусы
    ui-web/                   # компоненты React web
    ui-native/                # компоненты React Native
    i18n/                     # ключи и RU/KZ
    observability/            # trace/log helpers без PII
    test-fixtures/            # синтетические данные
  db/
    cloud/migrations/
    edge/migrations/
  infra/
    cloud/
    edge/
    monitoring/
    backups/
  docs/
    product/
    architecture/adr/
    integrations/
    operations/
    decisions/
    handoffs/
  .github/
    workflows/
    ISSUE_TEMPLATE/
    PULL_REQUEST_TEMPLATE.md
    CODEOWNERS
  AGENTS.md
  CLAUDE.md
  package.json
  pnpm-workspace.yaml
  pnpm-lock.yaml
```

Структура задаёт целевой состав; в этапе 1А созданы services/api, services/edge и общие packages contracts/database/platform/test-fixtures. Остальные приложения и пакеты добавляются по мере реализации. Общие дизайн-токены не означают один UI на телефон, кассу и кухню: у них разные размеры, жесты и рабочие сценарии. Общие types не дают клиенту права самостоятельно подтверждать оплату или бонусы.

Для TypeScript-части предложены pnpm workspaces и один lockfile; сборочный orchestrator добавлять по необходимости. Для .NET bridge — отдельный воспроизводимый build внутри monorepo с общим release manifest. Использовать только зафиксированные зависимости, проверяемые CI.

## 3. Пошаговая настройка

1. Выбрать владельца GitHub organization, исходников и коммерческих аккаунтов по договору. Доступ разработчика не должен быть единственным способом восстановить проект.
2. Создать private repository `pickchick-platform` либо согласованное имя. Включить MFA для участников, минимальные роли и резервного администратора организации.
3. Установить branch rules для `main`: PR обязателен, проверки CI обязательны, запрет force-push и удаления, review владельца изменяемого домена. Доступность правил private repository проверить по выбранному GitHub plan. [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
4. Настроить CODEOWNERS: деньги/данные/edge принадлежат ответственному backend/tech lead; mobile/UI — владельцу клиента; infra — DevOps. Это маршрутизация review, а не гарантия качества сама по себе. [GitHub CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).
5. Создать `dev`, `staging`, `production` environments с разными credentials/БД/merchant test IDs. Secrets хранятся в защищённых хранилищах, `.env.example` содержит только имена и безопасные примеры.
6. Добавить общий проект задач: Backlog → Ready → In progress → Review → QA → Done. Поля: requirement ID, канал, точка/edge/cloud, owner, dependency, milestone, risk, acceptance evidence.
7. Зафиксировать OpenAPI, event schemas, ADR и дизайн-токены до параллельной реализации зависимых интерфейсов.
8. Подключить AI-инструменты только к назначенным working copies и задачам. Не передавать им production-доступы для обычной разработки.
9. Выполнить пробный PR: контракт → серверный handler → генерируемый SDK → UI → тест → staging. Проверить, что другая рабочая копия получает изменения через Git.
10. Добавить правила выпуска, миграций, подписанных сборок и восстановления; назначить ответственных за release.

## 4. Как двум AI-инструментам работать одновременно

На одну задачу — отдельная ветка и рабочий каталог через `git worktree`. Это поддерживаемый Git механизм для нескольких рабочих деревьев одного репозитория. См. [git-worktree](https://git-scm.com/docs/git-worktree).

Пример команд для будущего репозитория, выполнять после создания `main` и чистого исходного checkout:

```sh
git fetch origin
git worktree add ../pickchick-orders -b codex/PC-101-order-core origin/main
git worktree add ../pickchick-mobile -b codex/PC-102-mobile-checkout origin/main
```

Первый каталог открывает инструмент для backend-задачи, второй — для mobile-задачи. Изменения не смешиваются в общей рабочей директории. Ветки короткие: после небольшого завершённого изменения PR проходит review/CI и вливается. Не держать отдельную «вечную ветку Fable» и «вечную ветку Astra» четыре месяца.

Контракт меняется первым небольшим PR или согласованной зависимой веткой. Автор фиксирует причину, совместимость, пример запроса/ошибки и migration impact. После merge второй исполнитель делает fetch/rebase своей ветки и регенерирует SDK. Независимые миграции схемы нельзя принимать автоматически только потому, что Git не показал текстовый конфликт: нужен просмотр семантики и порядка применения.

Файлы lockfile, миграции, shared schemas и дизайн-токены меняет один назначенный исполнитель за раз либо отдельные согласованные PR. UI может разрабатываться по mock server, сгенерированному из контракта; mock-успех не переносится в production как «платёж прошёл».

Перед передачей задачи создать короткий handoff в `docs/handoffs/PC-101.md`: принятые решения, изменённые контракты, выполненные проверки, известные ограничения и следующий шаг. Не копировать туда все мысли модели и весь чат — только проверяемую информацию.

## 5. Общие инструкции AI-инструментам

Канонические инструкции закреплены в корневом `AGENTS.md`; `CLAUDE.md` ссылается на него. Это выбранная реализация общих правил, без третьей дублирующей копии. Они не должны содержать противоречащие друг другу версии архитектуры. Для другого клиента Anthropic явно передавать тот же файл в контекст.

Содержание правил:

- Архитектурные источники: ТЗ, ADR, OpenAPI и схема БД. Текущий prompt задачи не должен незаметно менять финансовые инварианты.
- Деньги — целые минимальные единицы; подтверждение оплаты — только bank/terminal adapter; клиентский redirect не даёт success.
- Заказы/чеки/бонусы — durable state + idempotency. Критические события не существуют только в Redis.
- Cloud и edge имеют явных владельцев полей/агрегатов. Нельзя добавлять last-write-wins для финансовых состояний.
- Нельзя встраивать реальные секреты, телефоны и production-дампы в код, fixtures, issues и prompts.
- Изменение контракта требует схемы, примеров, SDK и теста совместимости. Миграция требует upgrade-test.
- Сгенерированный код проверяется так же, как человеческий. Нельзя заявлять «тесты прошли», если они не запускались.
- Перед завершением — diff, релевантные проверки и краткая передача. Production-deploy выполняет установленный release pipeline.

Пример задачи AI-инструменту:

```text
Задача PC-101: реализовать идемпотентное создание заказа по quote.
Основание: ORD/Checkout из ТЗ, AC-04, OpenAPI v1.
Рабочая ветка: codex/PC-101-order-core.
Область: services/api/orders, db/cloud/migrations, tests/orders.
Вход: quote_id, quote_version, Idempotency-Key, authenticated customer.
Результат: сохранённые order/intent/hold/outbox в одной транзакции.
Приёмка: десять повторов дают один order; иной body с прежним ключом — 409;
конкурентные резервы не превышают доступный кошелёк.
Необходимый handoff: схема изменений, выполненные тесты и ограничения.
Если контракт противоречит ТЗ, зафиксировать конфликт до реализации зависимого шага.
```

Распределение «Fable пишет backend, Astra проверяет» полезно как второй взгляд, но две модели могут повторить одну ошибку. Финансовые инварианты доказываются тестами/сверкой, а бизнес-правила и выпуск принимает назначенный человек.

## 6. CI/CD

| Этап | Обязательная проверка | Выход |
|---|---|---|
| Pull request | Format/lint/types; unit/property tests затронутых доменов; schema/OpenAPI validation; secrets/dependency scan | Отчёт CI, reviewable diff |
| PR с данными/деньгами | PostgreSQL integration tests; миграция с предыдущей схемы; concurrency/replay; provider contract tests | Доказательства AC, блокировка merge при ошибке |
| Merge в main | Повторяемая сборка затронутых пакетов; контейнеры/Windows/mobile artifacts; release metadata | Неизменяемые версии/commit SHA |
| Staging | Автодеплой, миграция, smoke/E2E, тестовые интеграции и nightly аппаратные тесты по доступному стенду | Release candidate |
| Production | Назначенный release owner проверяет gate, backup/compatibility, включает небольшой канал/точку | Наблюдаемый rollout с возможность остановки |
| После выпуска | Smoke, financial reconciliation, queue/error monitoring | Подтверждённый выпуск или управляемый откат |

Не запускать destructive migrations автоматически с каждой сборкой. Сначала совместимое расширение schema, затем rollout приложений, очистка старого — отдельный релиз. Для edge проверять совместимость текущего и предыдущего поддерживаемого протокола с cloud; старое устройство получает понятное ограничение и обновление вне пиковой смены.

Сборка iOS требует поддерживаемого macOS/Xcode и подписей; выбрать локальный Mac runner или подходящий сервис сборки. Для Android/Windows — отдельные подписанные artifacts. Production-подписи недоступны PR из недоверенного контекста. EAS/внешний CI не должен получать базу клиентов; правила допустимости выгрузки кода/секретов фиксируются владельцем организации.

Обновление киоска/кассы/edge — вне активной оплаты, с проверкой очередей и совместимости. Новая версия сначала проходит стенд и одну точку. Нативные изменения mobile публикуются через магазины; обновления ресурсов/JS применяются только в рамках проверенной совместимости и правил платформы.

## 7. Definition of Done

Задача считается готовой, когда выполнен requirement, контракты совпадают, изменения схемы воспроизводимы, права проверены, релевантные автоматические/аппаратные тесты пройдены, ошибки видны в мониторинге, RU/KZ ключи присутствуют, документация/сценарий поддержки обновлены и PR принят. Для денег обязательны повтор запроса, неизвестный исход и компенсация.

Задача UI не готова, если работает только счастливый сценарий. Нужны empty/loading/error/offline/permission denied/payment unknown и восстановление после перезапуска. Для KDS — полный список заказов при переполнении экрана; для киоска — очистка персональных данных; для mobile — возврат из банковского приложения.

## 8. Обязательные артефакты проекта

По окончании проекта в организации должны быть: исходники и история PR; ADR; OpenAPI/event schemas; cloud/edge миграции; воспроизводимая инфраструктура; синтетические seeds; перечень зависимостей/лицензий; подписанные release artifacts; тестовые протоколы; инструкции кассира/повара/управляющего; runbooks аварий; схема сети; договорные API-спецификации в разрешённом месте; backup/restore инструкции; реестр аккаунтов и ответственных без секретов.

Вопрос «они видят код друг друга?» проверяется простым упражнением: первый инструмент делает PR изменения схемы → второй получает commit, обновляет SDK и проходит общий контрактный тест. Общий чат без такого процесса интеграцию не обеспечивает.
