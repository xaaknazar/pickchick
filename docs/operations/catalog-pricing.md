# Расчёт корзины по опубликованному каталогу

Состояние на 7 сентября 2026: пакет `@pickchick/catalog-pricing` рассчитывает
корзину на сервере по опубликованному снимку CMS. Это подготовленный доменный
компонент checkout: он не создаёт заказ, платёж, чек или HTTP-маршрут и не
включает продажу в точке. Старый `/v1/test` использует прежний каталог и цены.

## Вход и граница доверия

Клиент передаёт только версию, способ получения, SKU, количества и выбранные
идентификаторы опций. Пример структуры:

```json
{
  "catalog_version": 1,
  "service_mode": "takeaway",
  "items": [
    {
      "sku": "pick-combo",
      "quantity": 2,
      "selections": [{ "group_id": "drink", "option_id": "cola", "quantity": 1 }]
    }
  ]
}
```

Идентификаторы опций в примере иллюстративные: обязательный полный выбор
нужно брать из конкретной опубликованной версии. `selections: []` допустим
только при выполнении всех минимумов групп. Значения `default_quantity`
помогают интерфейсу предложить выбор, но не создают молчаливые заказы на сервере.
Неизвестные поля, в том числе клиентские цены, скидки, точка, канал и customer ID,
отклоняются строгой `CartInputSchema`.

Доверенный сервер передаёт `PricingScope`:
`{organizationId, branchId, customerId, channel}`. Каналы доменного расчёта —
`mobile` и `kiosk`; способ получения — `takeaway` или `dine_in`.
`customerId` может быть `null` для гостя. Проверка сессии, назначение точки
устройству и доступ пользователя остаются обязанностью вызывающего сервиса:
наличие UUID в этом типе само по себе не является авторизацией.

`new CatalogPricing(database).price(scope, cart)` делает один MVCC SELECT
из `branches`, `catalog_branch_heads`, `catalog_publications`. Он проверяет
совпадение организации и точки, читает только текущую публикацию и требует
`branches.ordering_enabled=true`. Ни черновик, ни TEST-цены не участвуют.
Версия корзины должна совпасть с прочитанной активной версией, иначе возвращается
`STALE_CATALOG`, без тихой замены суммы. Опубликованный снимок должен иметь
`content_reviewed=true` и совпадающий SHA-256 нормализованного JSON.

Чистая функция `priceCatalogSnapshot({reference, orderingEnabled, payload}, scope, cart)`
нужна для повторной проверки внутри транзакции commerce. Её `payload/reference`
должны приходить из доверенного репозитория. Передача произвольного JSON с
самостоятельно посчитанным hash не доказывает факт публикации.
`catalogPayloadHash` использует тот же порядок полей после `CatalogPayloadSchema.parse`,
что CMS при публикации; порядок ключей, возвращённый JSONB, не влияет на hash.

## Правила суммы и состава

- Суммы — строки целых минимальных единиц KZT. Вычисления выполняются через
  `BigInt`, с верхней границей `9_000_000_000_000_000` на цену, строку и корзину.
  Нулевой итог не выдаёт quote. Дробные и отрицательные количества/деньги запрещены.
- `unitPriceMinor = baseUnitPriceMinor + Σ(option.price_delta_minor × option.quantity)`.
  `grossMinor = unitPriceMinor × line.quantity`. Минимум/максимум группы относится
  к сумме количеств опций на одну порцию родителя. `max=1` задаёт взаимоисключающий
  выбор. Дополнительных правил несовместимости между группами в схеме нет.
- Базовая цена родителя **уже включает** фиксированные `combo_components`.
  Цена связанного SKU не прибавляется второй раз. `linked_product_id` у опции
  задаёт компонент производства; доплата определяется только `price_delta_minor`.
  Если оператор изменил цену связанного SKU, цена комбо от этого не меняется.
- Фиксированные вложенные комбо без модификаторов разворачиваются в компактный
  список конечных SKU. Количества одинаковых SKU суммируются; это количества
  **на одну порцию родителя**, для производства умножаемые на `line.quantity`.
  Родительская позиция не дублируется в `components`; у обычного блюда список пуст.
  Выбранные связанные опции тоже попадают в этот список.
- Настраиваемый вложенный компонент отклоняется как `AMBIGUOUS_COMPONENT`, даже
  если у его модификаторов есть defaults: вложенного контракта выбора пока нет.
  Недоступный родитель или фактически включённый компонент блокирует расчёт.
  Недоступная невыбранная опция не блокирует другую допустимую конфигурацию.
- Вход ограничен 200 строками, 1000 порций в строке, 40 выбранными опциями;
  количество опции — 1–40 с дополнительной границей из каталога.
  Один вариант нельзя прислать двумя строками: клиент должен объединить количество.
  Разные варианты одного SKU имеют разные детерминированные UUIDv8 `lineId`.
  Перестановка опций/строк не меняет расчёт, изменение количества не меняет line ID;
  смена версии каталога меняет line ID.
- Число конечных компонентов ограничено миллионом единиц на строку, без создания
  массива поштучных записей. JSON результата ограничен 1 MiB; превышение останавливает
  расчёт с `QUOTE_TOO_LARGE`, включая раннюю проверку накопленного размера строк.

Скидки во всех выдаваемых quotes равны нулю. Отдельная чистая `allocateDiscount`
проверяет заданную доверенным policy-модулем сумму и распределяет её методом
наибольших остатков, с детерминированным порядком `lineId` при равенстве остатков.
Она не вызывается расчётом и не является промоакцией или правилом лояльности.
Клиент не может передать ей скидку через API данного этапа — API отсутствует.

## Неизменяемый снимок для заказа

Экспорты схем находятся в `@pickchick/catalog-pricing/model`:
`PricedCatalogQuoteSchema`, `CatalogReferenceSchema`, `SelectedDetailsSchema`,
`CartInputSchema`. Результат содержит:

```text
catalogReference: organizationId, branchId, version, payloadHash, publishedAt
customerId, channel, serviceMode, currency, ttlSeconds=300
lines[]: lineId, productId, sku, title, description, quantity,
         baseUnitPriceMinor, modifiersUnitPriceMinor, unitPriceMinor,
         grossMinor, discountMinor="0", totalMinor, selectedDetails
subtotalMinor, discountMinor="0", totalMinor
```

`selectedDetails` хранит локализованные названия/описания, состав, порцию,
изображение, декларацию аллергенов, КБЖУ, выбранные группы/опции с ценой доплаты
и компактные компоненты. Невыбранные модификаторы не копируются в каждый заказ.
Результат отделён от входного объекта: последующее изменение каталога не меняет
полученный снимок. Долговременную неизменяемость обеспечит сохранение commerce;
этот пакет не записывает quote в БД и не выдаёт его идентификатор или expiry.

КБЖУ с `nutrition_status=unverified`, включая значения из макета, сохраняются
как исходная декларация, а `perServing/lineTotal` остаются `null`. Явная отметка
review каталога не превращает их в лабораторно подтверждённые значения.
Для `operator_entered` возможен арифметический пересчёт известного веса из
`per_100_g` или базовой порции; один явно заданный `nutrition_multiplier`
без связанного SKU масштабирует базовую декларацию. Округление до 0,001 —
формат отображения, не утверждение о точности измерений.
Несколько модификаторов или добавка без нутриентного контракта дают `null`
с причиной `modifier_nutrition_unknown`. Миллилитры не подменяют граммы.
Базовые КБЖУ комбо считаются декларацией всей базовой порции, компоненты
не суммируются повторно. `allergens` — именно декларация родительского блюда;
компоненты имеют собственные декларации. Полную проверку аллергенов добавок
без контракта не обещаем и пустой массив со статусом `unknown` не трактуем
как отсутствие аллергенов.

## Подключение commerce и ограничения

Для выдачи durable quote вызывающий commerce должен внутри своей транзакции
проверить текущую публикацию/точку, удержать соответствующую блокировку на время
выдачи, пересчитать вход чистой функцией и сравнить весь результат. Проверка
только Zod-формы входного `selectedDetails` не доказывает правильность суммы.
Сохранённый quote закрепляет старый снимок на срок действия; публикация новых
цен не должна менять уже выданные действующие предложения. Повтор команды с
прежним ключом идемпотентности должен возвращать прежний результат, а не новый quote.

Foundation `releaseId` нельзя подменять выдуманным UUID. Новый commerce bridge
отдельно сохраняет `catalogReference` и снимок выбора; его интеграция и миграция
не входят в этот пакет. Налогового кода, привязки SKU к ККМ и ставки в CMS нет:
нужен отдельный доверенный provisioning. При отсутствии этих настроек реальный
checkout остаётся закрытым. Не выбираем фиктивный `taxCode` и не подтверждаем
Kaspi/ККМ/бонусы результатом арифметического расчёта.

Схема CMS пока не задаёт расписание, цены по каналам, рецептурные остатки,
стоп-листы edge и резерв кухни. Расчёт соблюдает только существующий `available`
и `ordering_enabled`, не придумывает часы работы. Проверки этих дополнительных
условий и согласованность cloud/edge должны быть подключены до реальных продаж.
Это также не проверка производительности на тысячу одновременных заказов.

Миграций и конфигурационных переключателей в пакете нет. Для read-only wrapper
достаточно `SELECT` на `branches`, `catalog_branch_heads`, `catalog_publications`
и `USAGE` схемы; ему не нужны staff credentials, row locks, INSERT или UPDATE.
Commerce при атомарной выдаче отдельно потребует права для своего row lock.
Runtime-ошибки содержат только типовой код без payload, телефона и секретов.

## Проверки этапа

Локально в изолированной рабочей копии:

```sh
pnpm --filter @pickchick/catalog-pricing build
node --test tests/unit/catalog-pricing.test.mjs
node --env-file=.env --test --test-concurrency=1 tests/integration/catalog-pricing.test.mjs
```

Unit-проверки покрывают подмену денег, ошибочные числовые строки, варианты,
минимумы/эксклюзивность групп, linked SKU без двойного начисления, вложенные
компоненты, размер ответа, арифметические границы, копирование снимка, неизвестные
КБЖУ и точность распределения скидки. PostgreSQL-проверки используют временные
схемы: публикация 24 SKU через настоящий CMS, неизменность действующих цен при
редактировании, параллельная публикация/расчёт, scope, отключённая точка,
стоп-лист и отдельная роль с SELECT только трёх таблиц.
Провайдеры, реальные телефоны, платежи и VPS в проверках не участвуют.
