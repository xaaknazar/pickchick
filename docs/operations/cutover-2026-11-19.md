Правила для всех шагов:

- Всё новое выключено по умолчанию (§3). Слияние, деплой и установка ничего не включают; каждое
  включение - отдельный шаг со своей проверкой и своим откатом.
- Миграции аддитивны и не откатываются: откат - прежний рантайм или выключатель, схема остаётся
  (контракт §3.2 п. 4). Рантайм edge после первой оплаченной продажи на версию без продаж не
  откатывается (`pos-sales.md` §9 п. 3).
- Деньги - целые тиын. Адреса, UUID, пароли, токены и номера чеков - только из приватной
  карточки монтажа и защищённых файлов владельца, не из репозитория. Примеры ниже вымышленные.
- Любое отклонение от ожидаемой проверки - остановиться на этом шаге и выполнить его откат; не
  «чинить на ходу» чужой шаг.

### 7.2 Когда возвращаться на iiko

Решает владелец (Codex предлагает), не позже 30 минут от начала сбоя, чтобы уложиться в час:

- нельзя продавать ни на одной кассе PickChick, включая резервную на сервере, и причина не
  устранена за 15 минут;
- кухня не получает заказы ни на экранах KDS, ни после `kds-switch disable` на прежних станциях;
- сервер точки или его база недоступны, и восстановление по `edge-restore.md` не укладывается в
  час;
- деньги расходятся систематически: X-отчёт не сходится с ящиком или терминалом на нескольких
  продажах подряд по причине программы, а не ошибки ввода.

Не причина возвращаться на iiko: нет интернета; одна касса; принтер; один способ оплаты;
отказ облака; ошибка одного заказа (отмена или возврат с PIN).

### 7.3 Как вернуться на iiko за час

§7.1 и восстановление базы. Порядок - чтобы не было двойных чеков и потерянных заказов:

1. Зафиксировать время. Кассы заканчивают текущие продажи, новых в PickChick не начинают.
2. Деньги: на каждой кассе PickChick - номер Webkassa каждой продажи с политикой
   `manual_webkassa` введён (вкладка «Чеки Webkassa»), остаток - список в журнал смены;
   закрыть смены продаж (Z) с пересчётом; закрыть смену в Webkassa.
3. Кухня: заказы в работе доготовить и выдать в PickChick (не отменять и не вводить в iiko

4. `pos-sales-setup.mjs disable --reason "Откат на iiko 19.11"` (только после Z всех касс).

5. Агрегаторы: вернуть связку iiko с Яндекс Едой и Kwaaka/Glovo; заказы, уже введённые в

### 9.1 Припаркованное событие `posSales`: найти и освободить

Когда: `pos-sales-setup.mjs status` показывает `cloud.last_error` вида
`PARKED <CONFLICT|INVALID_EVENT|LOCAL_INVALID|TOO_LARGE> <event_id>`, а `pos_sales_outbox.pending`
не падает. Поток продаж кассы стоит перед этим событием, все следующие события ждут за ним;
касса продаёт как обычно, данные не теряются. Команда - из папки поставки RC-edge (пакет несёт
её с этой версии), с `<owner.env>` (§5), без сети; строки `pos_sale_outbox` руками (`UPDATE`) не
править.

1. Посмотреть, что стоит (только чтение, можно в любой момент):
   `node --env-file=<owner.env> infra/windows/pos-sales-sync-release.mjs status`
   → одна строка JSON, например (здесь разбита на строки для чтения; значения вымышленные):

   ```json
   {
     "event": "pos_sales_sync_status",
     "branch_id": "<uuid точки>",
     "checked_at": "2026-11-19T07:29:12.345Z",
     "owner": true,
     "sync": {
       "last_error": "PARKED INVALID_EVENT <event_id>",
       "last_supported_at": "2026-11-19T07:28:40.120Z"
     },
     "pending": 2,
     "parked_count": 1,
     "parked": [
       {
         "event_id": "<event_id>",
         "kind": "shift_report",
         "sequence": "1000000004",
         "state": "parked",
         "reason": "INVALID_EVENT",
         "attempts": 1,
         "occurred_at": "2026-11-19T07:20:01.002Z",
         "age_minutes": 9,
         "head": true,
         "waiting_behind": 1
       }
     ]
   }
   ```

   `parked` - припаркованные события по порядку (`kind` - `sale`, `void`, `refund`, `fiscal`,
   `shift_report`; `reason` - код отказа; `age_minutes` - возраст события; `head: true` - поток
   стоит именно на нём; `waiting_behind` - сколько событий ждёт за ним). `parked: []` при
   `PARKED` в `pos-sales-setup status` - событие уже освобождено и ждёт отправки (минута).
   `owner: false` - окружение не владельца, `release` откажет.

2. Освобождать **только после устранения причины** (иначе следующая попытка снова паркует то
   же событие - вреда нет, но и толку нет):
   - `INVALID_EVENT` у Z (`shift_report`) после восстановления базы кассы - только после
     ответа владельца облака `pos_sales_restored_z` с `state: accepted` или `duplicate` (§9.2);
   - `CONFLICT` или `INVALID_EVENT` у прочих событий - после исправления в облаке
     (`backoffice-cutover.md` «Остановленный поток» пп. 1-2: строка `pos_sale_rejected` в
     журнале API, исправленный рантайм API или данные облака). Отмену или возврат продажи
     потерянного отрезка после восстановления не освобождать без инженера: облако отклонит
     его снова, и это верно (второй возврат тех же денег);
   - `LOCAL_INVALID` или `TOO_LARGE` - только после установки исправленного рантайма кассы
     (разбор с полосой pos): событие нельзя отправить в том виде, в каком оно записано.
3. Освободить ровно это событие:
   `node --env-file=<owner.env> infra/windows/pos-sales-sync-release.mjs release --event <event_id> --reason "<причина 3-300 символов>" --actor "Codex"`
   → одна строка JSON на stdout, например (разбита на строки для чтения):

   ```json
   {
     "event": "pos_sales_sync_released",
     "branch_id": "<uuid точки>",
     "event_id": "<event_id>",
     "kind": "shift_report",
     "sequence": "1000000004",
     "occurred_at": "2026-11-19T07:20:01.002Z",
     "previous": {
       "state": "parked",
       "reason": "INVALID_EVENT",
       "last_error": "rejected:INVALID_EVENT",
       "attempts": 1,
       "sync_last_error": "PARKED INVALID_EVENT <event_id>"
     },
     "changed": { "outbox_last_error": null, "sync_last_error": null },
     "state": "pending",
     "reason": "Z смены через восстановление кассы принят владельцем облака",
     "actor": "Codex",
     "released_at": "2026-11-19T07:31:05.000Z"
   }
   ```

   **Эту строку целиком скопировать в журнал окна и в отчёт Codex** (время, команда,
   результат): другой записи действия оператора нет - в 026 нет таблицы аудита для неё, а
   заморозка DDL 10.11. Сама строка очереди показывает освобождение своими полями:
   `last_error` пуст, `acknowledged_at` пуст до доставки, `attempts` и байты события прежние;
   у `pos_sale_sync_state` пуст `last_error`, `updated_at` - время освобождения. `--actor` -
   метка роли (`"Codex"`, `"инженер"`), не имя и не телефон. Команда вызывает ту же функцию
   отправителя `retryPosSalesDelivery` (`packages/pos-order-sync/src/sales-worker.ts`), что и
   тесты полосы cloud.

4. Проверка через 1-2 минуты (служба `PickChickPosSync` смотрит на припаркованный поток раз в
   минуту): `pos-sales-sync-release.mjs status` → `parked: []`, `pending` падает до 0;
   `pos-sales-setup.mjs status` → `cloud.last_error` пуст. Снова `PARKED` с тем же
   `event_id` - причина не устранена: дальше не освобождать, звать инженера.

Повтор `release` того же события ничего не меняет и отказывает `NOT_PARKED`: `state: pending` -
уже освобождено и ждёт отправки, `state: delivered` - облако его подтвердило. Каждый отказ - одна
строка JSON `pos_sales_sync_release_refused` на stderr (`code`, `message`), код выхода 1, в базе
ничего не изменено:

| `code`           | Что значит                                                                                                                                              | Что делать                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `USAGE`          | не та команда или ключи: нужны ровно `status` или `release --event --reason --actor`, каждый ключ один раз                                              | набрать команду, как в п. 3                                                  |
| `EVENT_INVALID`  | `--event` не uuid                                                                                                                                       | взять `event_id` из `status`                                                 |
| `REASON_INVALID` | `--reason` короче 3 или длиннее 300 символов или в несколько строк                                                                                      | причина в одну строку, например `"Z смены через восстановление кассы 19.11"` |
| `ACTOR_INVALID`  | `--actor` не от 2 до 64 символов в одну строку                                                                                                          | `--actor "Codex"`                                                            |
| `OWNER_REQUIRED` | `EDGE_DATABASE_URL` из `<owner.env>` - не владелец `pickchick_edge_owner` на `127.0.0.1:55433/pickchick_edge`, нет `APP_ENV=local` или `EDGE_BRANCH_ID` | взять защищённое owner-окружение точки (§5); до подключения к базе           |
| `NOT_INSTALLED`  | на точке нет 026 (`pos_sale_outbox`)                                                                                                                    | освобождать нечего: поток `posSales` на этой базе не идёт                    |
| `NOT_OWNER`      | подключение не владельца `pos_sale_outbox` (например, роль службы `pickchick_pos_sync`)                                                                 | owner-окружение точки                                                        |
| `UNKNOWN_EVENT`  | такого события нет в очереди этой точки                                                                                                                 | сверить `event_id` с `status`                                                |
| `NOT_PARKED`     | событие не припарковано (`state`: `pending` - уже освобождено, `delivered` - доставлено)                                                                | ничего не делать; через минуту - п. 4                                        |

Строка `pos_sales_sync_release_failed` (`code: UNEXPECTED`, `error_code` - код базы или
подключения, без адресов и паролей): выполнить `status`. Если события больше нет в `parked`,
освобождение прошло - записать в журнал время, команду и вывод `status`; если оно там -
ничего не изменено, устранить ошибку подключения и повторить п. 3.

### 9.2 Z смены, открытой во время восстановления: порядок

1. Касса: `pos-sales-sync-release.mjs status` → в `parked` событие с `kind: shift_report`,

   восстановления» пп. 1-3 - выгрузка события `export-z.sql`, команда владельца облака

   `state: accepted` (или `duplicate`, если Z уже принят) сохранить для бухгалтера.
3. Касса (п. 4 того раздела): `pos-sales-sync-release.mjs release --event <event_id> --reason "Z смены через восстановление кассы принят владельцем облака" --actor "Codex"`

owner-подключением `127.0.0.1:55433` в контейнере не запускалась (проверка адреса и отказы до
