# Вход через Telegram Gateway - 26 сентября 2026

## Решение и фактическая готовность

Владелец выбрал Telegram Gateway сейчас и явный резерв SMS; WhatsApp остаётся
следующим каналом после регистрации Business Platform. Это коды на телефон,
зарегистрированный в Telegram, а не вход через произвольного Telegram-бота.

Реализованы транспорт, серверный контракт и мобильный выбор канала. Владелец
создал Gateway-аккаунт и сохранил токен в локальный защищённый файл. Один код
действительно отправлен на согласованный номер владельца; он подтвердил получение.
Это проверка доставки, а не сквозной вход в публичное приложение. Backend, публичный
gateway, миграция022 и новая mobile-сборка на VPS/TestFlight ещё не выпущены.

Секрет находится только в `.local/telegram-gateway.env` на первом Mac (0600,
ignored). Номер, токен, код и ответы с балансом не входят в репозиторий. Второй Mac
получает код и эту инструкцию через Git, секреты переносятся отдельно.

## Поведение

- `/v1/auth/config` сообщает только доступные `channels`. Telegram выбирается
  первым при наличии; неподключённые SMS и WhatsApp не показываются.
- `/v1/auth/otp/request` принимает `channel: telegram | sms`. Отсутствие поля
  означает прежний SMS, а не скрытую отправку в другой сервис. Форма ответа сохранена; новый запрос обязан содержать согласие
  `delivery_consent` по контракту этапа023. Старый клиент без него нужно обновить.
- Миграция `022_cloud_otp_channels.sql` сохраняет канал, провайдера и его ссылку
  на отправку. Readiness активного identity проверяет миграцию и новые столбцы.
- Канал входит в идентичность запроса. Повтор после потери ответа не отправляет
  новый код; сменить канал с тем же request_id нельзя. При новой отправке после
  общего cooldown прежний challenge теряет силу. Аккаунт остаётся одним.
- Лимиты телефона, IP и durable дневной бюджет общие для всех каналов. Таблица
  бюджета исторически называется `identity_sms_daily_budget`, но включает Telegram.
- Telegram получает собственный шестизначный код сервера с TTL180. Только проверка
  кода в PostgreSQL выдаёт сессию; факт доставки сам по себе не авторизует клиента.
- Таймаут5с включает зависший поток ответа; предел ответа16КиБ. Секрет передаётся
  только в Bearer-заголовке фиксированного HTTPS-адреса, redirect запрещён.
  Неопределённый ответ не вызывает автоматической повторной отправки или SMS.
- На mobile сохранены paste/autofill, доступный выбор канала, общий таймер,
  восстановление запроса после перезапуска. На маленьком экране содержимое
  прокручивается, основная кнопка остаётся доступной. Применены адресные рекомендации
  UI/UX Pro Max и Impeccable в существующем оформлении PickChick.

## Реальная проверка Telegram

Первый send вернул доставленное сообщение, но наш парсер первоначально назвал
ответ неопределённым. Диагностика без повторного send показала: Gateway возвращает
`phone_number` строкой цифр без `+`. Парсер исправлен: разрешены только два точных
представления исходного номера, с плюсом и без него. Добавлена регрессия, включая
нулевую стоимость собственного номера. Чужой номер/неверный формат не принимаются.

Проверка `checkVerificationStatus` с несуществующим request_id подтвердила доступ
к API без сообщения. Для подтверждённого номера владельца один `checkSendAbility`
вернул нулевую стоимость. Это исключение для собственного номера: такую проверку
нельзя считать бесплатной для произвольных клиентов. Preflight проекта вообще
не делает HTTP-запросов и сообщает `messages_sent: 0`, а не готовность аккаунта.

## Проверки

- Сборка всех28 workspace-пакетов; TypeScript mobile; OpenAPI соответствует исходникам.
- 49 адресных Node-проверок: transport/config, preflight, identity-контракты и mobile
  session; отдельно6 регрессий WhatsApp. Реальных отправок в этих тестах нет.
- 29 PostgreSQL-проверок: прежний вход/refresh, межканальная идемпотентность,
  cooldown, бюджет, смена действующего кода, restart и readiness без новых столбцов.
- Expo web export. Локальная визуальная проверка393×852 и320×568: номер,
  Telegram/SMS, экран кода, ручная смена канала и прокрутка. Применялись синтетические
  ответы через локальный service worker, без внешних отправок. Таймер и утрата
  ответа дополнительно проверены логическими/DB-тестами.
- Реальная доставка одного Telegram-кода подтверждена владельцем в чате.

Приёмка на физических iPhone/Android, мобильной сети и реальном account API ещё
не выполнена. Полная CI и выпуск отмечаются отдельно от локальных проверок.

## Настройка и следующий выпуск

Шаблон: `.env.phone.example`. Для Telegram-only задать
`PHONE_DELIVERY_PROVIDER=telegram_gateway`, `TELEGRAM_GATEWAY_TOKEN` и
`PHONE_SMS_FALLBACK_ENABLED=false`. SMS включать только после проверки Mobizon,
зарегистрированного отправителя и бюджета: `PHONE_SMS_FALLBACK_ENABLED=true` требует
валидных `MOBIZON_API_KEY` и `MOBIZON_APPROVED_SENDER`. Переключение остаётся ручным.

Существующие identity-настройки обязательны: `CUSTOMER_AUTH_ENABLED`, ключи,
утверждённые legal URL/версия согласий и лимит. Названия и порядок запуска см.
[customer-identity.md](customer-identity.md). Не переносить локальный env целиком
в публичные mobile-переменные. Токен предназначен только для backend.

До публичного запуска:

1. Утвердить документы/версию согласий и дневной бюджет; проверить средства
   Gateway для номеров клиентов. Успешный бесплатный self-test не доказывает баланс.
2. Пройти CI, зарезервировать VPS/API и публичный gateway, проверить фактический
   release020 и порядок ещё не выпущенных021/022, ACL и резервную копию.
3. Установить backend/migrations/routes с прежними release-lock/CAS-проверками,
   передать секрет защищённо, включить только готовые каналы.
4. Собрать mobile с `EXPO_PUBLIC_CUSTOMER_AUTH=server`; проверить сквозной вход,
   рестарт, повторный код, недоступный Telegram и logout на согласованных устройствах.
5. Не объединять автоматически демонстрационные профили/заказы с реальными
   аккаунтами. Отдельно проверить принадлежность заказов новому customer identity.
