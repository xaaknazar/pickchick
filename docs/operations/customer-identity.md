# Клиентский вход: PostgreSQL, OTP и постоянные сессии

Статус 7 сентября 2026: реализован отдельный серверный домен и HTTP-контроллер,
проверенный на синтетических данных во временных PostgreSQL-схемах. Это не
подтверждение доставки SMS, включения входа на VPS или выпуска нового mobile.
Телефонный транспорт Mobizon подключается через существующий адаптер;
настоящие сообщения в этих проверках не отправлялись.

## Граница интеграции

`@pickchick/customer-identity` экспортирует `CustomerIdentity`,
`createCustomerIdentityOptions`, `CUSTOMER_IDENTITY`, схемы входящих данных и
`CustomerSessionSchema` / `OtpResponseSchema`. Контроллер
`services/api/src/customer-auth-controller.ts` получает через Nest DI экземпляр:

```ts
new CustomerIdentity(pool, createCustomerIdentityOptions(environment), delivery);
// provider: { provide: CUSTOMER_IDENTITY, useValue: identity }
// controller: CustomerAuthController
```

Применяется миграция `007_cloud_customer_identity.sql` обычным проверяющим
контрольные суммы migrator. Она добавляет только `identity_*`; TEST actors,
историю заказов, деньги, кухню и существующие токены не меняет. Реальный профиль
не связывается автоматически с anonymous TEST-заказами по введённому телефону.
Миграция обратно не удаляется при откате API: старый API игнорирует новые таблицы.
Активные новые сессии требуют версии API, содержащей этот домен.

Требуется зарегистрировать контроллер/DI в API, зависимости и сборку пакета.
Существующий `/v1/capabilities` остаётся совместимым со старыми TestFlight
клиентами, ожидающими `phone_auth: false`. Готовность входа определяется отдельно.

## Конфигурация и включение

По умолчанию `CUSTOMER_AUTH_ENABLED=false`. Disabled-контур возвращает 503 для
операций входа и профиля и не обращается к БД или SMS-провайдеру. GET config
остаётся доступен и сообщает `enabled: false`.

Для явного включения необходимы:

| Переменная                       | Условие                                                                                  |
| -------------------------------- | ---------------------------------------------------------------------------------------- |
| `CUSTOMER_AUTH_ENABLED`          | Только `true` включает домен                                                             |
| `CUSTOMER_AUTH_CONSENT_VERSION`  | Идентификатор утверждённого комплекта условий и privacy, 1–100 ASCII букв/цифр/`._-`     |
| `CUSTOMER_AUTH_TERMS_URL`        | Утверждённый HTTPS URL условий без credentials, query и fragment                         |
| `CUSTOMER_AUTH_PRIVACY_URL`      | Утверждённый HTTPS URL privacy с теми же ограничениями                                   |
| `CUSTOMER_AUTH_DAILY_SMS_BUDGET` | Явный лимит 1–999999 резервирований SMS за UTC-день, не денежная сумма                   |
| `CUSTOMER_AUTH_LOOKUP_KEY`       | Независимый случайный ключ 32 байта, hex64, для поиска телефона и привязок устройства/IP |
| `CUSTOMER_AUTH_OTP_KEY`          | Другой случайный ключ 32 байта, hex64, для HMAC OTP и verify receipt                     |
| `CUSTOMER_AUTH_PII_KEY`          | Другой случайный ключ 32 байта, hex64, для AES-256-GCM телефона и профиля                |
| `CUSTOMER_AUTH_RECEIPT_KEY`      | Другой случайный ключ 32 байта, hex64, для AES-256-GCM ответов с токенами                |

Повторяющиеся/очевидные placeholder-ключи отклоняются; секреты и их значения не
включаются в ошибки. Ключи должны храниться отдельно от БД и её копий в
казахстанском секретном контуре. Замена ключа в `.env` не является процедурой
ротации: сначала требуется контролируемое повторное шифрование/индексирование
данных и проверенный план восстановления. Автоматическая ротация keyring пока
не реализована.

Нужны также действующие `PHONE_DELIVERY_PROVIDER=mobizon`, ключ Mobizon,
утверждённый sender и шаблон. Если delivery отключён, config возвращает false.
Строка версии и URL сами по себе не доказывают согласования юридических текстов
или рабочего маршрута SMS. Их утверждение и проверка доставки на казахстанских
SIM остаются условиями включения.

HTTP-хост должен устанавливать `Cache-Control: no-store`, ограничение размера
JSON и безопасное логирование. Контроллер использует Express `@Ip()`; при reverse
proxy доверять только известному ingress, исключить прямой обход API и проверить
подмену `X-Forwarded-For`. По умолчанию Express не доверяет этому заголовку.
Нельзя включать `trust proxy=true` для произвольной цепочки: это обходит IP-лимит.
Настройка ingress, публичные лимиты до Node и мониторинг бюджета входят в
интеграцию хоста, не в данный пакет.

## HTTP-контракт

Поля используют `snake_case`; лишние поля входящих объектов отклоняются.
`device_id` и `request_id` — UUID, созданные клиентом и сохранённые **до** запроса.

| Метод и путь                | Тело / ответ                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| GET `/v1/auth/config`       | `{enabled, consent_version, terms_url, privacy_url}`; при выключении все три значения null                               |
| POST `/v1/auth/otp/request` | `{phone, device_id, request_id}` → 202 `{challenge_id, expires_at, resend_at, delivery_status}`                          |
| POST `/v1/auth/otp/verify`  | `{challenge_id, code, device_id, request_id, consents:{terms_version, privacy_version, marketing_opt_in}}` → 200 session |
| POST `/v1/auth/refresh`     | `{refresh_token, device_id, request_id}` → 200 session                                                                   |
| POST `/v1/auth/logout`      | Bearer access → 200 `{ok:true}`                                                                                          |
| GET `/v1/customers/me`      | Bearer access → 200 `{customer}`                                                                                         |
| PATCH `/v1/customers/me`    | Bearer access, хотя бы одно из `{nickname?, birth_date?, gender?, marketing_opt_in?}` → 200 `{customer}`                 |
| DELETE `/v1/customers/me`   | Bearer access → 200 `{ok:true}`                                                                                          |

`session` содержит `access_token`, `refresh_token`, `access_expires_at`,
`session_id`, `customer`. Клиент:
`{id, phone, nickname, birth_date, gender, profile_completed_at, created_at}`.
Даты времени — ISO UTC; дата рождения — `YYYY-MM-DD` или null.
`gender` — `female`, `male` или null. Никнейм необязателен, обрезаются крайние
пробелы, максимум 32 Unicode code points; пустая строка явно очищает никнейм.
Дата рождения проверяется по календарю Алматы, от 1900 года до сегодняшнего дня.
Пустая дата/пол очищаются через null. Пропущенные PATCH-поля сохраняются; изменение
только marketing не отмечает заполнение профиля. Профиль обновляется атомарно.

Обе версии в `consents` должны точно совпасть с `consent_version`; принятие
условий/privacy подтверждается явно в UI после возможности прочитать документы.
Marketing — отдельный boolean, не предвыбранное обязательное согласие. Версии,
значения и серверное время согласий фиксируются транзакционно при успешном OTP;
изменения marketing добавляют новую запись. Ошибка записи откатывает весь запрос.

Общие безопасные ошибки: 400 `INVALID_REQUEST`, 401 `UNAUTHORIZED`, 409 `CONFLICT`,
429 `RATE_LIMITED`, 503 `SERVICE_UNAVAILABLE`. Контроллер передаёт только код;
глобальный фильтр добавляет стандартный trace ID. Телефон, код, токены и сырые
ответы провайдера не попадают в ошибки/логи. Ответ не сообщает, существовал ли
клиент до проверки телефона. HTTP 5xx/timeout — неизвестный результат, а не повод
удалить локальную сессию или автоматически выбрать demo-вход.

## OTP и SMS-бюджет

Номер нормализуется `libphonenumber-js/max` 1.13.12: Казахстан, валидный мобильный
диапазон, E.164. Ввод `8...` и `+7...` одного номера приводит к одному account.
Одного формального `+7` недостаточно; российские и городские номера отклоняются.
Метаданные диапазонов требуют обновления и проверки провайдером перед запуском.

Код создаётся `crypto.randomInt`, шесть цифр; в PostgreSQL хранится только HMAC с
контекстом challenge+device. Сравнение digest — timing-safe. Срок challenge 3
минуты; неверная проверка сохраняет попытку, максимум 5 даже при параллельных
запросах/перезапуске. Неподходящие consent/device не потребляют код. Новый явный
resend делает предыдущие неиспользованные challenge этого телефона недействительными.

Перед единственным вызовом доставки PostgreSQL резервирует:

- cooldown 60 секунд на телефон и устройство;
- телефон: 5 за скользящий час, 10 за 24 часа;
- устройство: 10 за час, 30 за 24 часа;
- доверенный IP: 30 за час, 100 за 24 часа; общий NAT не получает ограничение
  «одна SMS в минуту на всех посетителей»;
- явный глобальный лимит за UTC-день.

Глобальный advisory lock держится только во время короткого резервирования,
не во время HTTP к провайдеру. Бюджет — число попыток отправки; `rejected` и
`unknown` тоже тратят резерв, чтобы сбои не создавали неконтролируемый расход.
Нагрузочная приёмка миллиона профилей и замер contention этого лимитера ещё не
выполнены; горизонтальные API используют общий PostgreSQL lock/counter.

`delivery_status=submitted` не означает доставки/проверки номера. Timeout,
неизвестный ответ или crash после резерва оставляет `unknown`/`reserved` и никогда
не отправляется повторно фоновым worker. Клиент может ввести фактически полученный
код и при unknown. Явный resend после cooldown — новая отдельная попытка.

Повтор `otp/request` с тем же `request_id`+device+canonical phone возвращает тот
же challenge и не расходует бюджет. Если первая отправка ещё идёт, ответ unknown.
Иной телефон/устройство с занятым ключом — 409. После очистки challenge остаётся
только random request UUID и время очистки; такой старый запрос получает 409,
но никогда не отправляет SMS повторно. Клиент предлагает явную новую отправку.

## Постоянные сессии и потеря ответа

Access и refresh — независимые случайные 32-байтные opaque токены. В сессии только
SHA-256 digest; access действует 15 минут. У device session нет календарного или
idle expiry. Длительное отсутствие пользователя не требует плановой SMS.
Повтор OTP на том же телефоне/устройстве заменяет только эту сессию; на другом
устройстве используется тот же unique customer и его сохранённый профиль.

Verify атомарно поглощает challenge, сохраняет согласия, создаёт сессию и
зашифрованный ответ. Повтор после потерянного ответа требует тот же
challenge+code+device+request_id+consents, допускается до 24 часов, пока начальный
refresh этой сессии не вращён и сессия не отозвана. Это восстановление начального
входа, не произвольное повторное использование поглощённого OTP. Обновление версии
документов не отменяет exact-replay уже выданного receipt: восстанавливается
исходное согласие без принятия новой версии. Новая проверка требует актуальную
версию; повторное согласование изменений после входа — отдельный UI-процесс.

Refresh атомарно меняет access/refresh и сохраняет **ровно один** зашифрованный
receipt на сессию. Потерянный ответ можно получить с предыдущим refresh, тем же
request_id и device, только пока его successor остаётся текущим. Календарного
ограничения у этого последнего receipt нет: закрытое на сутки/месяц приложение
может восстановить последний ответ. Следующая ротация заменяет receipt, старое
поколение больше не принимается. Иной request_id с предыдущим token получает 409;
параллельные refresh не отзывают выигравшую легитимную сессию.

Customer внутри receipt — неизменяемый снимок момента выдачи; актуальный профиль
после восстановления читается через GET me. Receipt может вернуть уже истёкший access. Клиент сначала надёжно сохраняет его
successor refresh, затем создаёт новую ротацию с новым request_id. После получения
ответа нельзя повторно использовать тот же request_id уже с successor token.
Очередь refresh в mobile должна быть единственной на устройство; намерение
ротации сохраняется до сети, receipt — до удаления намерения.

Выход отзывает текущую сессию; `revokeSession(sessionId)` — команда для доверенного
административного слоя, без публичного HTTP route. Отзыв очищает access/refresh и
все recovery receipts. DELETE очищает телефон/профиль/согласия, удаляет сессии
всех устройств и оставляет random customer ID + время удаления. Условия
удаления будущих фискальных/финансовых документов этот модуль не определяет.
Повтор DELETE после потерянного ответа может получить 401: mobile не должен
объявлять успех до проверки исхода; отдельный deletion receipt пока не реализован.

## Очистка и эксплуатационные ограничения

`identity.cleanup(): Promise<void>` — команда владельца, которую хост должен
вызывать по расписанию. Она и `revokeSession(sessionId): Promise<void>`
доступны владельцу даже при выключенном публичном входе/SMS; HTTP-маршрутов
для этих административных команд нет. Она очищает истёкшие OTP payload/verify receipts; после 24 часов
удаляет challenge без активного verify receipt, сохраняя бессодержательный
request tombstone. Дневные счётчики старше 7 дней удаляются. Последний refresh
receipt активной сессии не очищается по времени. Нужны мониторинг запуска cleanup,
количества 429/unknown и расхода дневного лимита без PII.

При удалении account временные HMAC метаданные challenge для защиты от SMS-abuse
сохраняются до этой очистки, но связь с customer/session и прямые PII удалены.
Ни это техническое окно, ни сохранение минимальных tombstone не являются
утверждённой юридической политикой хранения. Правила удаления, backup/WAL,
согласий и сроков необходимо согласовать до обработки настоящих клиентов.

Нужны отдельная миграция и изолированный runtime DB role, backup/restore с
доступными вне БД ключами, ограничение доступа к encrypted receipts, применение
процедуры key rotation и проверка реального ingress. Модуль не выдаёт себя за
готовые payments, loyalty, production checkout или готовность всех AC-36–38:
перезапуск/обновление настоящего телефона и системное secure storage проверяются
на этапе mobile. SMS-provider sandbox/SIM acceptance остаётся отдельной проверкой.

## Проверки этого подэтапа

Синтетические unit/integration тесты проверяют нормализацию и календарь,
fail-closed config, сохранение попыток и budget при конкуренции, lost-response
request/verify/refresh, неизвестную доставку без повторов, 400 дней отсутствия
активности без SMS, bounded receipt, защитный отзыв, удаление, шифрование данных,
параллельный PATCH и rollback при ошибке записи, HTTP-контракт/no-store и
отклонение поддельного X-Forwarded-For при стандартном Express trust-proxy.

```sh
pnpm --filter @pickchick/customer-identity build
pnpm --filter @pickchick/api build
node --test tests/unit/customer-identity.test.mjs
node --env-file=.env --test --test-concurrency=1 tests/integration/customer-identity.test.mjs
```

Интеграционный harness создаёт случайные временные схемы local cloud/edge БД,
применяет миграции и удаляет только свои схемы. Delivery — внедрённая fake-функция;
реальные телефоны, провайдеры и VPS в тестах не используются.
