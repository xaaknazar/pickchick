# Локальная регистрация edge и доставка меню

Это стенд с искусственными данными. Нужны шаги
[первого запуска](local-development.md), включая новые миграции. Команды
выполняются из корня репозитория. HTTP API пока доступен только на localhost.

## Настройка устройства

Seed создал pending edge тестовой точки. Выдать ему ключ:

```sh
pnpm device:setup 10000000-0000-4000-8000-000000000004
```

Ключ сохраняется в `.local/edge-identity.json` (600), каталог `.local` (700).
Файл и каталог игнорируются Git. Команда сообщает только ID, срок и путь.
Не копировать ключ в текст команды, документацию или PR. Это trusted local
setup через БД, не публичный enrollment и не вход кассира по телефону.

Ротация на том же устройстве (предыдущий ключ перестаёт работать):

```sh
pnpm device:setup 10000000-0000-4000-8000-000000000004 --rotate
```

Worker перечитывает файл перед каждым циклом. Срок ключа — 30 дней.
Для отзыва конкретного устройства:

```sh
pnpm device:revoke DEVICE_UUID
```

Revoked устройство повторно не активируется. Локальное сохранённое меню
остаётся доступно, но центральный обмен отклоняется. Смена edge на новый
физический узел и восстановление утраченной БД требуют будущего snapshot/fencing
протокола, а не простого создания другого device ID.

## Публикация и подтверждение

1. Создать JSON по `MenuSnapshot` из OpenAPI: новый `release_id`, правильный
   `branch_id`, следующая целая `version`, `schema_version: 1`, `published_at`
   и `items`. После первого seed следующая версия — 2; далее брать следующую
   после последней опубликованной, включая ещё не подтверждённые версии.
   Пример для чистого seed — `examples/menu-v2.json`.
2. Опубликовать файл в центре:

```sh
pnpm menu:publish examples/menu-v2.json
```

Повтор неизменённого файла возвращает прежнее событие. Изменять опубликованный
UUID нельзя: для следующего меню нужны новый UUID и следующая версия.
Публикация пока не переключает активное центральное меню.

3. Запустить API и edge в отдельных терминалах, затем worker:

```sh
pnpm start:api
```

```sh
pnpm start:edge
```

```sh
pnpm sync:once
```

При успехе: `state: applied` (или `acknowledged` для ранее сохранённого ACK,
`idle` при отсутствии работы). Проверить одинаковые `release_id` через
`GET /v1/branches/{branchId}/menu` центра и `GET /edge/v1/menu` локального API.

Постоянный обмен до Ctrl+C:

```sh
pnpm sync:watch
```

По умолчанию центр — `http://127.0.0.1:3100`. Для другого локального порта
задать `EDGE_SYNC_ORIGIN`; удалённые URL, userinfo, path, query и redirects
отклоняются. Worker нуждается в EDGE_DATABASE_URL, EDGE_BRANCH_ID и приватном
файле идентичности; CLOUD_DATABASE_URL и Redis ему не нужны.

## Проверка отказов

Остановить cloud API: worker пишет безопасную ошибку, повторяет с backoff;
сохранённое меню edge продолжает читаться. Запустить cloud API — обмен
продолжается. Не удалять outbox/inbox/cursor вручную для исправления ошибки.

`pnpm test:integration` автоматически проверяет настоящий HTTP/PG обмен,
потерянный ACK-ответ, повтор, конкуренцию, rollback, границы точки, expiry,
rotation/revoke и ошибки последовательности. Тесты синхронизации создают
собственные временные схемы в двух локальных БД и удаляют только их.

Постоянный `menu_sync_failed`: проверить health, срок/привязку ключа,
выполненные миграции и обе очереди. Повреждённая схема/hash, пропуск sequence
или другая точка не подтверждаются и не пропускаются автоматически. Дашборд
ошибок, DLQ, алерты и snapshot recovery ещё не реализованы.
