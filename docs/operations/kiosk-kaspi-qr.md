# iPad kiosk: гостевой Kaspi QR

Дополнение 7 октября: владелец выбрал **оба способа, QR основной**. Реализованы
телефонный счёт, выбор метода и серверный запрет завершения незавершённой оплаты.
[Код, проверки и фактические условия включения](kiosk-payment-options.md).
Этот этап пока не включает банковские маршруты на VPS.

## Состояние 7 октября 2026

Подготовлен отдельный путь `kaspi-qr`, выключенный по умолчанию. На подключённый
iPad Air 13-inch M3 установлена отдельная development-сборка Kiosk 0.1.0 (1)
с коммерческим сценарием; 7 октября подтверждён запуск экрана настройки устройства.
Это ещё не привязка к серверу и не подтверждение банковской работоспособности.
Ранее выпущенная TestFlight-сборка продолжает использовать TEST-контур.
Новый сценарий: меню канала kiosk
из бэк-офиса, корзина, в зале / с собой, QR, подтверждённый номер заказа.
Регистрация гостя, телефон и игры не нужны.

Серверная цена/версия каталога, стоп-лист, часы ресторана, резервирование на
кухне и проверенный платёж остаются обязательными. Контрольный платёж
проводится только после согласования суммы владельцем; реальные заказы
этим изменением не создавались.

## Границы

- Существующий `kaspi-remote` обслуживает мобильные счета по телефону.
  QR использует отдельную запись payment account с provider `kaspi-qr`,
  принадлежащую тому же подтверждённому продавцу и точке.
- Это тот же неофициальный мост кассира, а не обещание официального API Kaspi.
  Ключи кассира доступны только серверу; ключ киоска хранится в SecureStore.
- QR возвращается только своему устройству/гостевой сессии. На сервере сначала
  фиксируется попытка, затем выполняется один create. Потеря ответа не разрешает
  второй create: состояние unknown требует сверки.
- 180 секунд отсчитываются от первого create; QR скрывается по истечении срока.
  Это не отмена банком. Продолжается проверка, включая позднюю оплату.
  В изученном API QR cancel отсутствует. Метод invoice cancel для QR не вызывается.
- Принятие оплаты использует существующие PostgreSQL inbox/ledger/outbox.
  Успех клиентской анимации/таймера/локального QR не создаёт платёж.
- При неопределённой оплате гостевой сеанс не очищается. Следующий гость допускается
  после подтверждённого результата; заказ продолжает жить на сервере и кухне.
- Типовой фискальный режим - required. Прежнее согласование пилота без Webkassa
  не заменяет настройку обязательного фискального режима для запуска точки.

## Банковский контракт: что ещё проверить

Закреплённый upstream `tapter-dev/kaspi-pos-automation@28c9167` поддерживает
`POST /api/qr/create {amount,latitude,longitude}` и
`GET /api/qr/status?qrOperationId=...`. Телефон не передаётся. Сохраняется
оригинальный QrToken, без преобразования в произвольный deeplink.

В upstream `src/polling.js` успех обозначен Processed, а `public/app.js` - Paid.
Подтверждённого примера полного status response нет. Текущий строгий адаптер
принимает только Processed с точными QrOperationId и Amount. Отсутствующие
поля, другое имя статуса или несовпадение суммы оставляют unknown, не оплату.
До включения для гостей необходимо на контрольном платеже проверить поля
реального ответа, expiry, терминальное состояние и доставку на кухню. При иной
форме ответа сначала доработать адаптер и его regression fixture, не ослаблять
проверку суммы/идентичности. В отчёт сохранять имена полей и обезличенный fixture,
не токены, QR реального счёта или данные покупателей.

2. Полная зелёная CI для точного source SHA. В существующую release-процедуру

   Создать штатную зашифрованную резервную копию, проверить восстановление,

3. Собрать bridge context `prepare-container.mjs UPSTREAM NEW_DIRECTORY --qr`.
   Включить `BRIDGE_QR=on` только на приватном мосте. QR route не делает

4. Создать отдельный `kaspi-qr` provider account в той же организации/точке/
   legal_entity. Зарегистрировать kiosk_devices и передать оператору приватный
   device ID/key безопасным каналом. В БД хранить только SHA-256 ключа. Не
   копировать ключи в Expo public env, URL, Git или публичный JSON.
5. Настроить API KIOSK_CHECKOUT_* и отдельный worker. Публикация каталога канала
   kiosk и её ACK локальным узлом обязательны. Gateway должен разрешать только
   перечисленные kiosk-checkout routes c ограничением частоты и тела; endpoint

6. Собрать отдельное приложение kz.pickchick.kiosk с
   EXPO_PUBLIC_KIOSK_COMMERCIAL=1. HTTPS origin закреплён в src/api.ts

   Применить ipad-kiosk-lockdown.md после приёмки.

## Переменные

API сохраняет существующие KIOSK_CHECKOUT_ENABLED, ORGANIZATION_ID, BRANCH_ID,
FISCAL_ACCOUNT_ID/FISCAL_POLICY, APPROVAL_REFERENCE, TAX_CODE, MAX_MINOR,
PII_KEY и часы работы. Добавлены:

- `KIOSK_CHECKOUT_PAYMENT_METHOD=kaspi_qr`;
- `KIOSK_KASPI_QR_ACCOUNT_ID` - отдельный provider account, не remote invoice.

Worker `node services/api/dist/kiosk-kaspi-qr-worker.js`:

- `KIOSK_KASPI_QR_ENABLED=true`, отдельный ACCOUNT_ID;
- `KIOSK_KASPI_QR_LATITUDE` / `KIOSK_KASPI_QR_LONGITUDE` - подтверждённые координаты
  точки, не координаты Mac и не случайные значения;
- приватные KASPI_BRIDGE_URL, KASPI_SESSION_TOKEN_SN, KASPI_SESSION_VTOKEN_SECRET,
  KASPI_SESSION_PROFILE_ID, cloud DATABASE_URL и обычные platform env.

Worker работает в приватном namespace моста, loopback; logs содержат только
счётчики/типы ошибок. При unknown_overdue необходима операторская сверка.
Повторная авторизация кассира или смена device.json не выполняются автоматически.

## Привязка iPad отдельным этапом

`infra/staging/release-kiosk-qr.py` готовит и устанавливает только API настройки
устройства и миграции 043/044. Он сохраняет все опубликованные файлы, включая

Маршруты гостевых заказов, платёжный аккаунт и QR worker остаются выключенными.
Это подготовка привязки, а не включение оплаты или меню на киоске.

Профиль допускает согласованный владельцем `deferred_pilot` без Webkassa;
он не создаёт фискального чека. Для режима `required` нужен реальный fiscal account.
Приватные настройки передаются через файл 0600, не через аргументы или журнал.
Выпуск требует точной зелёной CI, занятой области VPS, штатного lock,
зашифрованной копии с проверенным восстановлением и проверки старого API на 043/044.
`preflight` читает состояние, `prepare` создаёт неизменяемые артефакты,
`apply` меняет сервисы под maintenance; `rollback` требует исходного owner ID.

Откат сохраняет базу и новые данные. Если после открытия доступа появились новые
финансовые операции, точная проверка данных может остановить автоматический откат:
lock сохраняется, необходим разбор записей, восстановление старого дампа не выполняется.
23 адресные проверки охватывают миграции, права, environment, сохранность файлов,
heartbeat, анонимные finance-запросы и имитацию последовательности apply.
Реальная установка на VPS этими локальными проверками не подтверждается.

## Короткие данные настройки - 7 октября

По просьбе владельца форма принимает операторский ID (3-64 символа ASCII,
буквы, цифры, точка, дефис, подчёркивание) и ключ/пароль (12-128 символов).
Регистр ID значим. Старый формат UUID + 64hex продолжает работать.
Технический идентификатор устройства и случайный внутренний токен не сокращаются.

Новый `/enrollment/exchange` проверяет временный alias и возвращает ранее
выданные credentials только тому же requestId. iPad сохраняет requestId до
запроса, проверяет полученные credentials через `/enrollment/check`, затем
сохраняет их в SecureStore. Пароль оператора не сохраняется в приложении.
Потерянный ответ можно повторить; другой iPad/requestId использовать уже
привязанный alias не может. Alias действует 24 часа для первичной привязки;
после неё срок не ограничивает сохранённое устройство. Повторная первичная
настройка требует нового разрешения/alias, а не перезаписи активного устройства.

Миграция 044 хранит salted scrypt verifier и AES-GCM ciphertext внутреннего
токена, связанный с ID/организацией/точкой/alias через AAD. Отдельный приватный
`KIOSK_ENROLLMENT_KEY` обязателен для exchange. Пять ошибок блокируют alias
на 15 минут, счётчик сохраняется в PostgreSQL. Одновременная обработка scrypt
ограничена четырьмя запросами процесса. Ошибки не раскрывают наличие alias.
Runtime получает SELECT на обе таблицы и только UPDATE трёх служебных колонок
alias + UPDATE(lock_anchor) устройства для блокировки строки; менять ключ
или активность устройства runtime не может.

`scripts/provision-kiosk-enrollment.mjs` принимает только пути `--device`,
`--credentials`, `--encryption-key`, `--output-sql`. Входные файлы 0600,
ключ шифрования - 64hex в отдельном файле, credentials JSON содержит
`login`/`password`. SQL генерируется однократно 0600, без открытого пароля
и токена, выполняется owner-доступом после регистрации того же устройства.
При неопределённом результате повторяют тот же SQL: повторная генерация
с новой солью не подменяет существующий alias.

Проверены 59 клиентских сценариев, typecheck, 7 сценариев на изолированном
PostgreSQL (включая реальную роль с точными runtime grants), 23 release-теста.
Development-сборка 0.1.0 (2) с короткими полями собрана, установка и живой
вход отмечаются отдельно после полного CI нового исходного коммита.

### Предыдущая попытка установки и продолжение

Источник 89d7959 прошёл все 11 jobs Foundation CI 37580398576. В реальном
rollout получены зашифрованная копия и успешное изолированное восстановление,
применена 043. Guard ошибочно определял образ через отсутствующий environment
`RELEASE_SHA`; установка остановлена. Явный rollback завершён: API d6cd144,

окружение по-прежнему сравнивается целиком. Для нового исходного коммита после
сохранённой 043 используется `--previous-attempt-proof-dir` с исходными
