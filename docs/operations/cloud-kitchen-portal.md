# Облачные заказы на страницах кухни (портал, ADR-0014 S6)

Решение владельца 2026-10-10: заказы iPad-киоска и мобильного приложения, которые выполняет
облако (`fulfillmentOwner: "cloud"`), показываются на **существующих** страницах
`pickchick.kz/kitchen/prep`, `/kitchen/assembly` и `/display` (портал `infra/kitchen-portal`,
[ADR-0011](../architecture/adr/0011-kitchen-live-link.md)). Вход прежний, новой привязки для
поваров нет. Контракт API: [cloud-kitchen-s4.md](../architecture/cloud-kitchen-s4.md), раздел
«Контракт кухонного портала».

Статус: код и тесты в ветке `codex/cloud-kitchen-portal`; **в production не включено**, флаг
портала по умолчанию выключен, релиз на VPS не выполнялся.

## Как это работает

- Браузер, как и раньше, читает кассу через `/kitchen-live/<роль>/edge/v1/fulfillment/*`
  (туннель Windows). При включённом флаге он дополнительно читает облачную ленту через
  `/kitchen-live/<роль>/cloud/v1/fulfillment/*` - тот же контракт и те же проверки ответа.
- Сервер портала сам проверяет сессию страницы до любого запроса в облако:
  - повар: токен, `X-Staff-Session-ID` и терминал этой роли (как для кассы); сессию подтверждает
    касса (`GET /edge/v1/session`), портал помнит подтверждение в памяти до срока сессии и
    перепроверяет его каждые 30 секунд, пока касса на связи. Отказ кассы удаляет его сразу;
  - пока касса недоступна, уже подтверждённая сессия продолжает работать с облачной лентой;
    новая (не подтверждённая) - получает `503`, в облако запрос не уходит;
  - привязанное табло (ADR-0013, cookie экрана) читает номера по своей cookie без логина повара;
    точка cookie должна совпадать с точкой облачной записи.
- Ключ `pcks_...` для (точка, роль) берётся из защищённого `config.json` портала и уходит только
  в заголовке `Authorization` к API по внутренней сети. Ответы API пересобираются в форму ленты
  кассы (лишние поля отбрасываются), в HTML/JS/`config.json` уходит только флаг
  `cloudKitchen: true`. Тест проверяет, что ключ не появляется ни в одном ответе.
- Опрос облачной ленты делает только открытая страница (раз в 5 секунд, пока есть сессия) -
  это heartbeat станций для `KITCHEN_OFFLINE`. Станцию, которую ключ роли не обслуживает,
  портал не опрашивает в облаке (пустая лента, ложного heartbeat нет).
- Команды: renderer отправляет действие только владельцу заказа - заказы облачной ленты в
  `.../cloud/.../orders/<id>/actions`, кассы - как раньше. Портал превращает это в
  `POST /v1/kitchen/commands` с тем же `Idempotency-Key` и `expectedVersion`. Действие через
  кассу для заказа, который облако уже показало, портал отклоняет (`400`), в кассу оно не
  уходит.
- Журнал незавершённых команд в браузере отдельный для каждого владельца
  (`pickchick.kitchen.pending.v1.cloud.<scope>` для облака, прежний ключ для кассы): зависшая
  команда кассы не блокирует облачные заказы и наоборот. Повтор отправляет тот же ключ и тело.
- Лента одна: дубли по `orderId` отбрасываются (копия облака главнее), сортировка по времени.
  На билете маленькая метка источника «Касса» / «Сервер»; два индикатора «Касса: на связи /
  нет связи» и «Сервер: на связи / нет связи». Если одна лента недоступна, её последние заказы
  остаются видны, но кнопки по ним выключены. Если недоступны обе - прежнее сообщение об ошибке.
- Табло объединяет номера кассы (1-299) и облака (киоск 300-599, приложение 600-899).
- Ошибки облака (`401/403` ключа, недоступный API) показываются как «Сервер: нет связи» и
  никогда не разлогинивают повара. Разлогинивает только отказ кассы в сессии.
- `/kitchen-live/health` дополнительно отдаёт `cloudConnected` только при включённом флаге.
- Без флага портал и renderer ведут себя как раньше (тест «flag off» и прежние тесты кухни).

## Конфигурация (флаг по умолчанию выключен)

В защищённый `config.json` портала (`KITCHEN_STATE/private/config.json`, `0600`, не в Git):

```json
"cloudKitchen": {
  "enabled": true,
  "apiOrigin": "http://pickchick-api:3100",
  "branchId": "<uuid точки>",
  "keys": { "prep": "pcks_...", "assembly": "pcks_...", "display": "pcks_..." }
}
```

`apiOrigin` - только внутренний адрес (имя docker-сервиса или частный IP, без пути); три
разных ключа обязательны. Неверная конфигурация - портал не стартует (`INVALID_PORTAL_CONFIG`).
Сеть: оверлей `infra/kitchen-portal/compose.cloud.yaml` подключает портал к внутренней сети
`pickchick-kitchen_cloud`. API подключается к ней с алиасом из `apiOrigin`; сеть базы данных
API порталу не открывается. На API должны быть `CLOUD_KITCHEN_API_ENABLED=1` и не задан
`CLOUD_KITCHEN_PUBLIC` (портал не шлёт заголовков пересылки, `/v1/kitchen/*` не публикуется).

Станции облака должны быть заведены с теми же id, что станции кассы
(`provisionCloudKitchenInTransaction`), иначе облачные заказы не попадут на страницу станции.

## Шаги владельца для выпуска (не выполнялись)

Выпуск - отдельная guarded-операция по runbook с резервацией `@vps`; бэкап, проверка CI и
откат обязательны. Предварительные условия: на VPS применены cloud 053-056 и гранты
`cloud-kitchen-grants.mjs`, `channel-number-grants.mjs`, `cloud-kitchen-screen-grants.mjs`;
станции и маршрутизация облака заведены.

1. Для каждой роли создать запись и код (код печатается один раз, живёт 10 минут):

   ```sh
   node infra/staging/cloud-kitchen-screen-owner.mjs create --branch <id> --role prep \
     --station <id цеха> --name "Портал: горячий цех" --operator <имя> --reason "портал кухни"
   node infra/staging/cloud-kitchen-screen-owner.mjs create --branch <id> --role assembly \
     --station <id сборки> --name "Портал: сборка" --operator <имя> --reason "портал кухни"
   node infra/staging/cloud-kitchen-screen-owner.mjs create --branch <id> --role display \
     --name "Портал: табло" --operator <имя> --reason "портал кухни"
   ```

2. На VPS обменять каждый код на ключ внутри сети API:
   `POST /v1/kitchen/pairing {"pairingCode":"XXXX-XXXXXX"}` -> `{"screenKey":"pcks_...","screen":{...}}`. Ключ
   записать сразу в `config.json` портала (без вывода в терминал, логи, Git и чат).
3. Создать внутреннюю сеть и подключить API:
   `docker network create --internal pickchick-kitchen_cloud`,
   `docker network connect --alias pickchick-api pickchick-kitchen_cloud <контейнер API>`.
4. Включить `CLOUD_KITCHEN_API_ENABLED=1` на API, добавить блок `cloudKitchen` в `config.json`,
   обновить портал с `-f compose.yaml -f compose.cloud.yaml`; `update-deploy.py` сверяет
   SHA-256 конфигурации - передать новый `expected-config-sha256`.
5. Проверить: `/kitchen-live/health` -> `cloudConnected: true`; на странице оба индикатора;
   тестовый заказ киоска в режиме `cloud` виден на prep/assembly/табло; выключенная касса ->
   «Касса: нет связи», облачный заказ доводится до выдачи.
6. Ротация: `pairing-code --screen <id>` + обмен (старый ключ перестаёт работать при обмене),
   затем замена ключа в `config.json` и перезапуск портала. Отзыв: `revoke` (сразу; страница
   покажет «Сервер: нет связи»).

## Ограничения

- Новый вход повара требует кассы (учётные записи поваров только на кассе). Уже вошедшие
  повара продолжают работать с облачными заказами при выключенной кассе. После перезапуска
  портала при выключенной кассе подтверждения в памяти нет - облачная лента недоступна до
  возвращения кассы (или до входа на привязанное табло, которому сессия повара не нужна).
- `confirm_cancel` облачных заказов - только управляющий через BO, не портал.
- Отчётное зеркало (protocol 5, edge 022) и X/Z с облачными заказами - этап S7.
