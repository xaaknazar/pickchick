# Kaspi QR: проверка upstream и сохранение банковской identity

Дата: 8 октября 2026. Причина: владелец повторно сообщил «QR код не распознан»
и попросил перепроверить `tapter-dev/kaspi-pos-automation`.

## Проверенные исходники

На мосту закреплён `28c9167f9c72cd6758a25e254bc92bc610daa485`.
Свежий upstream main: `175577ee1b34437dba46fb9bb0c8706f57f3b311`.
Clone и сравнение этих SHA показали: QR routes, подпись тела запроса,
polling и QR demo между ними не менялись. Изменились defaults версии приложения
Kaspi (4.112.1 / 1107 -> 26.0921 / 1115) и диагностика ошибок входа.
Действующая сессия при проверке была активна; обновление версии входа само по
себе не является исправлением текущего QR.

- [Сравнение версий](https://github.com/tapter-dev/kaspi-pos-automation/compare/28c9167...175577e).
- [QR route](https://github.com/tapter-dev/kaspi-pos-automation/blob/175577ee1b34437dba46fb9bb0c8706f57f3b311/src/routes/qr.js)
  отправляет `PaymentAmount`, `DeviceInterface: Pos`, координаты в
  `/v01/qr-token/create`; подписывается то же сериализованное тело.
  Наш мост использует ту же структуру с настроенными координатами точки.
  Route сохраняет исходный token как `QrOriginalToken` и формирует отдельную
  Kaspi-only ссылку заменой `qr.kaspi.kz/` на `pay.kaspi.kz/pay/`.
- [Демо](https://github.com/tapter-dev/kaspi-pos-automation/blob/175577ee1b34437dba46fb9bb0c8706f57f3b311/public/app.js)
  рисует именно `QrOriginalToken`. Его внешний сервис генерации QR не переносим:
  PickChick кодирует ссылку локально, без передачи платёжного token третьей стороне.
- [Polling](https://github.com/tapter-dev/kaspi-pos-automation/blob/175577ee1b34437dba46fb9bb0c8706f57f3b311/src/polling.js)
  обрабатывает `Processed`; демо отдельно ожидает `Paid`. Эти примеры не заменяют
  проверку реального банковского результата и точное связывание суммы/операции.

## Наблюдения на реальном мосту

Первый диагностический create: 14:31:03 UTC. Второй, отдельно разрешённый:
18:22:30 UTC. Каждый выполнялся ровно один раз, на 100 ₸, без оплаты и без
нового заказа. Оба вернули HTTP 200 / StatusCode 0, operation ID и token,
но `Amount: 0`. Pending status вернул совпадающий `Id`, статус
`QrTokenCreated`, без `Amount` и без `QrOperationId`.

Первое изображение офлайн декодировано Apple Vision: payload совпал с банком.
Первый показ задержался, позже status стал `QrTokenDiscarded`; это могло
повлиять на результат, но не доказывает единственную причину отказа.
Второй исходный QR показан сразу, затем показана Kaspi-only ссылка из того же
token без повторного create. Владелец снова сообщил отказ распознавания.
Точное время его сканирования неизвестно. Нет оснований объявлять доказанной
ни ошибку кодировщика, ни expiry, ни требование конкретного формата ссылки.

Исходный ответ create единственного контрольного заказа не сохранился;
диагностика не доказывает, что именно он содержал Amount 0. Его попытка
остаётся unknown без identity, без подтверждённого capture. Не подставлять
в неё ID диагностических операций. Ответы с token/ID хранятся приватно,
в Git публикуются только обезличенные факты.

## Исправление адаптера

`kiosk-kaspi-qr.ts` раньше сохранял operation ID только при совпавшей сумме.
Теперь валидные ID и token сохраняются атомарно и неизменно также при
несовпадении суммы. Состояние остаётся unknown, QR пользователю не выдаётся;
worker может проверять банковский статус. Повторный create при replay или
перезапуске не выполняется, expiry не продлевается.

Status допускает `Id` или `QrOperationId`; если присутствуют оба, они должны
быть валидны и совпадать. Неверная identity, отсутствующая/нулевая/другая сумма
не дают capture. Положительный результат требует `Processed`, точной суммы
заказа и точного ID. Поддержка `Id` основана на реальном pending ответе;
финальный Processed пока проверен только синтетически, не реальной оплатой.

Локальные проверки: TypeScript build и QR PostgreSQL suite на PostgreSQL 18.6,
**14/14**. Адресные ESLint/Prettier прошли; commerce unit/bridge suite:
43 passed, 1 optional pinned-overlay test skipped. Новая проверка воспроизводит Amount 0 и pending Id без суммы,
доказывает сохранение identity, скрытие QR, отсутствие повторного create,
сохранение expiry и единственный capture при последующем точном synthetic
Processed. Расширены отрицательные случаи конфликтующих/невалидных aliases.

Правка не установлена. Она устраняет потерю данных сверки, но не объявляется
исправлением распознавания QR. Мост, сессия, сервер и iPad в этом этапе не менялись.
Реальная платёжная приёмка не пройдена. Новые QR/платёжные пробы требуют отдельного
разрешения; предыдущие два разрешения полностью использованы.

Следующий необходимый факт для продолжения: подтверждённый контракт пригодного
к сканированию QR и достоверная сумма операции. Не отключать amount guard,
не подменять банковскую сумму запрошенной, не переводить unknown в failed/paid
через SQL. Общие project-status/roadmap заняты другими задачами; онлайн-пульт
этим этапом не обновлён.

Владелец прислал изображение QR с подписью 5 000 ₸ и уточнил, что это пример
из другого источника, а не подтверждённый QR своей точки. Изображение содержит
`https://qr.kaspi.kz/` и непрозрачный hex token длиной 41 символ, без query/fragment.
Сумма 5 000 ₸ прочитана с изображения, но не подтверждена банковским status.
Платёжная ссылка не открывалась.

Для сравнения прочитаны только ранее сохранённые приватные ответы на VPS:
первый диагностический token имеет 41 символ, второй 40; оба Amount 0.
Второй token побайтно совпадает с локально сохранённым payload. Обрезки при
переносе не обнаружено. Разница длины не доказывает причину отказа, и нет
оснований добавлять префикс, дополнять token или менять полученную ссылку.
Пример подтверждает сходство формата ссылки, но не доступность QR для
нашей точки и не успешную оплату. Изображение и сами токены в Git не включены.
