# Бэк-офис BO-02: операции, дизайн и внедрение

Все 15 разделов исходного макета доступны в `apps/backoffice`. Изменения проходят
через scoped API и PostgreSQL. Данные на скриншотах синтетические. Production-ресторан,
платёжные/фискальные адаптеры и локальные серверы точек этим этапом не внедрены.

## Источник дизайна

Оригинал владельца: `Pick Chick Бэк-офис (offline).html`, SHA-256
`4cc129416b2631b86d0c26f78ec935fa63668a2d1f951696c534ee851e5b4644`.
Текстовая копия: `docs/research/Pick Chick Бэк-офис.txt`.
Сохранены Inter, тёмно-синяя палитра, оранжевые действия, 250 px sidebar, порядок
15 разделов, точка/период в шапке, карточки показателей и плотные таблицы.
Реальные неизвестные/нулевые значения не заменены числами оригинального demo.
Скриншоты и процедура сравнения: `tests/backoffice/screenshots/full/README.md`.

нужны серверная пагинация и фоновые выгрузки; границы отражены в интерфейсе/API.
CSV защищён от формул в пользовательском тексте. Контактные данные гостей не выдаются.

## Транзакции и восстановление

`POST /v1/admin/backoffice/branches/:id/commands` требует `request_id`, причину и
типизированную команду. Точная команда сохраняется в sessionStorage до отправки.
После потери ответа повторяется тот же request ID и body. Другой body с тем же ID
отклоняется. Перед сменой точки требуется разрешить неизвестный исход. Другой
управляющий не получает локальный журнал предыдущего. Утрата хранилища предотвращает
новую отправку; принудительный выход не считается отменой уже отправленного запроса.

Документы склада не редактируются задним числом. Потребление по заказу разрешено после
подтверждённого начала кухни; изменение техкарты не меняет закреплённый snapshot.
Для комбо/модификаторов нужны отдельные точные нормы; операция блокируется, если их нет.
Возврат не восстанавливает продукты на склад автоматически.

## Запуск и права

1. Собрать workspace. Применить миграции в порядке cloud001–017 и edge001–008 на
   отдельном проверочном стенде. Для существующей среды сначала backup/restore drill.
2. Включить `CATALOG_ADMIN_ENABLED=true`, `BACKOFFICE_ENABLED=true` для API.
   Последний по умолчанию false. При выключенном флаге частное API недоступно;
   публичный content API отдаёт пустую конфигурацию.
3. `infra/staging/provision.mjs` применяет runtime grants после каталог/transport grants.
   BO не получает право вставлять подтверждённые capture/refund effects или менять ключи.
   При изменении набора флагов повторно применять весь provision, а не отдельный helper:
   shared commerce permissions пересчитываются transport helper перед BO.
4. Выдать управляющему существующий приватный файл catalog access и отдельно назначить
   BO-права доверенным CLI:

```sh
node --env-file=.env scripts/backoffice-setup.mjs --actor UUID --branch UUID --role manager
```

Для чтения без изменений использовать `analyst`. Импорт файла каталога без BO grant
не даёт операционные полномочия. Отзыв catalog access блокирует также BO.
`bo_access_audit` фиксирует назначения. Токены не помещать в URL или репозиторий.

5. Запустить API и `node apps/backoffice/server.mjs`; локальный адрес
   `http://127.0.0.1:4177`. Для HTTPS-стенда собрать public bundle: новые JS включаются
   автоматически. Gateway содержит отдельный allowlist BO и public content маршрутов;
   cookie/device headers не передаются в BO, публичная лента не принимает bearer.

**Совместимость migration017:** trigger на `commerce_orders` читает `bo_records` и
вставляет `bo_order_recipes`, даже когда BO UI выключен. Любая отдельная роль создания
заказов должна получить SELECT первой таблицы и INSERT второй до запуска новых заказов.
`backofficeGrants` даёт этот минимум независимо от флага; старые отдельные commerce
runtimes надо обновить вместе с миграцией. Trigger не получает SECURITY DEFINER.

## Удалённый стоп-лист (cloud046, protocol 4)

Касса остаётся единственным источником стопов. Бэк-офис только ставит команду в
`cloud_stop_commands`; транспорт (protocol 4) доставляет её кассе, касса применяет её с
проверкой `expected_version` и возвращает результат при следующем обмене.

- `GET /v1/admin/backoffice/branches/:id/stops` — стоп-лист v2 (читает и `analyst`).
  Строка на каждый товар и опцию опубликованного каталога: `catalog_ref` (slug), хэш-id кассы
  (`localCatalogId`, как в меню кассы), имя, `stopped`, `version`, `source`, `expires_at`,
  `sales_blocked`, открытая команда `pending` и последний ответ кассы `last_result`
  (`applied`, `conflict`, `not_found`, `no_open_shift`, `expired`). Стопы вне публикации
  попадают в `unknown_stops` с именем из старых таблиц `products`. Стоп-лист v1 внутри
  `GET branches/:id` сохраняет прежнюю форму и теперь тоже называет хэш-id по публикации.
- `POST /v1/admin/backoffice/branches/:id/stops` (только `manager`, JSON до 16 KB, ответ 202):
  `{request_id, catalog_ref:{product_id, group_id?, option_id?}, stopped, duration:
manual|hour|shift, reason, expected_version}`. Повтор того же `request_id` возвращает
  тот же результат, тот же `request_id` с другим телом — `CONFLICT`. Действие пишется в
  `bo_audit` (`remote_stop:stop|unstop`).
- Ошибки несут стандартный конверт и `error.code`: `REMOTE_STOPS_DISABLED` (503),
  `CATALOG_NOT_PUBLISHED`, `EDGE_STOPS_NOT_READY` (409, нет протокола 4 у кассы),
  `CATALOG_ITEM_NOT_FOUND` (404), `STOP_COMMAND_IN_PROGRESS` (409, по позиции уже есть
  открытая команда; она закрывается ответом кассы или через 120 с + 60 с).
- Включение: `BACKOFFICE_REMOTE_STOPS_ENABLED=true` (по умолчанию false) только после
  миграции cloud046, кассы на `FULFILLMENT_TRANSPORT_PROTOCOL=4` с
  `EDGE_REMOTE_STOPS_ENABLED=true` и публикации меню на кассу. Grants:
  `backofficeStopGrants` из `infra/staging/backoffice-stop-grants.mjs` (provision.mjs
  применяет их после transport/BO grants). В публичном gateway нужно разрешить
  `GET` и `POST .../stops` в allowlist BO.

## Что ещё требуется для полного §4.6

- Доставка и подтверждение плана станций edge-узлом. `bo_delivery_outbox` хранит намерение,
  consumer/lease/receipt ещё не реализованы; надпись «опубликовано» означает cloud-версию.
- Переключение mobile/kiosk/POS на нейтральные catalog publications и полный безопасный
  цикл локальных стопов/норм. Текущий TEST-каталог автоматически не заменяется.
- Утверждённые точные нормы вариаций/комбо, межскладские перемещения, поставщики и документы
  закупок/заказов поставщику. Учёт целых g/ml/pcs реализован, дробные нормы требуют масштаба.
- Фискальные смены, кассовая дисциплина/внесение/выемка, реальные адаптеры банка/ККМ/1С.
  Управленческий журнал не открывает фискальную смену. Оплаты не называются выпиской банка,
  разность оплат и возвратов не называется чистой прибылью.
- Серверные сессии/валидация игр, применение суточных лимитов и согласованная экономика.
  `daily_attempts` пока подготовленная настройка, не действующий лимит; reward строго 0.
  Проверка доступности на клиенте не заменяет авторизацию и защиту финансовой награды.
- Push provider/token lifecycle, дедупликация доставки, frequency caps и атрибуция;
  разрешённое подключение отзывов/карт, вложения/уведомления/SLA обращений.
- Сотрудники с реальными edge-полномочиями, MFA/SSO управляющих и более детальные роли;
  зарплаты/премии/оценки производительности не рассчитываются этим журналом.
- Полная аналитика событий приложения/когорт и кухонных длительностей, серверные
  фильтры архива и фоновые выгрузки. Тесты на масштаб из ADR0007 не заменены UI-тестом.
- Публичное развёртывание этого этапа, проверка реальных устройств и приёмка на точке.

Эти пункты остаются в исходном плане и не считаются выполненными из-за наличия вкладки.

## Проверки

Временные PostgreSQL cloud/edge schemas, синтетические данные, удаление после тестов:

```sh
pnpm --filter @pickchick/backoffice-core test
pnpm --filter @pickchick/backoffice-core test:integration
BACKOFFICE_TEST_PYTHON=/path/to/playwright/python pnpm test:backoffice
pnpm test:commerce
pnpm test:fulfillment-transport
pnpm test:pos-order-sync
pnpm test:mobile
```

BO acceptance покрывает права/revoke/cross-branch, точный повтор неизвестного исхода,
конфликты и недостаток склада, сохранение стоимости полуфабриката, immutable audit,
публичную публикацию/расписание/канал, реальные commerce refund/cancel и rollback при
ошибке аудита. Браузер проверяет все 15 разделов через реальный HTTP/PostgreSQL.
Результаты текущего прогона записаны в `docs/project-status.md`.
