## Копия, восстановление и миграция

Перед изменением создана зашифрованная копия
`/opt/pickchick-staging/backups/cloud-20260906T212116Z.dump.age`.
Время копии: 6 сентября 21:21:16 UTC / 7 сентября 02:21:16 Алматы.
SHA-256: `274067970d2d3d6e93544e97a52dc09db38ad3a4bbe6e020f2db0a3fa8bd4d96`.
Проверка контрольной суммы прошла.

Копия восстановлена в отдельную временную БД. С рабочей БД совпали журнал
миграций с checksum, точки, версии меню, идентификаторы/версии/статусы
TEST-заказов и оплат, количества кухонных задач и outbox. Это проверка
восстановления с перечисленной сверкой, а не побайтовое сравнение всех таблиц.
Временная БД удалена после проверки; рабочая БД не восстанавливалась из копии.

Первый запуск provision применил только
`005_cloud_test_modifier_task_titles.sql`; повторный вернул `applied: []`.
Миграция расширяет текст TEST-задачи до 4 000 символов, не переписывая заказы
и их снимки. Новый readiness требует 004 и 005 при включённом TEST-контуре.

## Проверки после переключения

`staging_smoke_passed` подтвердил readiness, закрытую синтетическую точку,
ответ 401 без авторизации, запреты runtime DDL и изменения устройств/журнала
миграций, разрешённое чтение меню, TEST-заказ через runtime-роль, повтор
идемпотентной операции и отказ при недостаточных правах.

Приватная проверка метрик нашла HTTP admission limit 32 и метрику пула БД.
Она не является нагрузочным испытанием. Время запуска PostgreSQL, Redis
и трёх контейнеров соседнего приложения совпало до/после; совпали контрольные
суммы страницы соседнего приложения и конфигурации общего Caddy.

Полный browser-прогон `RUN_MODE=all` направлял запросы на реальный TEST API VPS:

- **T-000026:** киоск → приготовление → сборка → табло → выдача сотрудником.
  Потерянный после commit ответ восстановлен повтором прежнего ключа и тела;
  новый гостевой сеанс сохранил заказ предыдущего гостя на кухне.
- **T-000027:** неизвестный результат имитации сохранился после перезагрузки;
  новый гость и повторная оплата были недоступны. Управляющий разрешил тот же

- **T-000028:** мобильный web-клиент создал `mockup-v0.3` заказ Pick Combo

## Совместимость и откат

Новый API обслуживает старый формат `mockup-v0.2` по умолчанию и расширенный
формат по `catalog_version=mockup-v0.3`. Старые клиенты получают выбранные
опции в читаемых названиях строк/задач. PostgreSQL хранит исходный неизменяемый
снимок; новые строки содержат выбранный состав, без копии всех доступных опций.
[Контракт и происхождение каталога](../../../packages/test-order-flow/README.md).

**Возврат прежнего API `d644822` после появления v0.3-заказов несовместим:**
его строгая схема не читает новые снимки. Для исправления регрессии нужен
API, сохраняющий чтение обоих форматов, на основе текущего совместимого выпуска.
Самостоятельный откат web сохраняет новый API и миграцию 005. Сужать ограничение
текста задач обратно до 200 символов при наличии длинных составов нельзя.

Проверенная копия предназначена для восстановления после сбоя. Возврат её
поверх обслуживаемой БД удалит изменения после 21:21:16 UTC; это не обычный
способ отката приложения. Совместимый выпуск и сверка активных заказов должны
сохранять поступившие после копии данные.

Все перечисленные заказы синтетические. Банк, реальные деньги, SMS, ККМ,
iiko и локальная кухня ресторана не вызывались. КБЖУ/описания взяты из мокапа,
а не из утверждённых техкарт. Production-внедрение, автономный цикл точки,
нагрузочная приёмка и установка на физические устройства остаются отдельными
проверками. [Подтверждённый выпуск TestFlight 4](../mobile-testflight.md) прошёл
после этого API deployment; нативные Run-20/21/22 записаны в отдельном UI-протоколе.
