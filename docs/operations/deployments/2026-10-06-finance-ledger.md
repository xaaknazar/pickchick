### Остановки и контролируемое продолжение

Первый apply остановился после запуска прежнего API на проверку совместимости:
изменился только heartbeat `cloud_branch_availability` (кроме ожидаемого ledger
миграций). Finance связывает `snapshot` с полной market-реализацией, поэтому
унаследованный runtime_snapshot фактически не исключает revision/observed_at.
Ожидаемая монотонная пара heartbeat ошибочно попала в строгий digest.
Привязка branch/device и stopped_ids не менялись. Maintenance и locks оставались.

Оператор подтвердил хешом, что сохранённые row-level данные availability точно
соответствуют исходному полному snapshot; штатный verify_availability проверил
все пять полей, точный набор точек, неизменность привязок и стоп-листов,
монотонность revision/observed_at. Только после этого при сравнении runtime
нормализован heartbeat; все остальные таблицы/sequences, миграции, ACL, worker,
артефакты, окружение и ownership проверены исходными guards. Исходный код,
CI SHA, backup и артефакты не менялись; миграции повторно не применялись.
Продолжен проверенный suffix apply под первоначальным owner UUID.

После открытия verify_public остановился на ошибочном auth-probe: GET не
содержал обязательных дат, POST - обязательного JSON. Сервис сначала проверяет
схему, поэтому такие запросы дают 400, а не ожидаемые 401. Maintenance был
подтверждённо закрыт снова. При повторном продолжении проверены валидный GET
с датами и анонимный void для заранее проверенного отсутствующего UUID;
оба вернули 401. Команда ничего не записала; новые таблицы остались пустыми.
Остальные public/neighbor guards прошли, ingress открыт, locks сняты.

Локальные протоколы и точные команды продолжения защищены в
`.local/finance-release/` и `.local/finance-ledger-release/<source-sha>/`;
они не являются общей памятью. Два дефекта release tooling требуют адресной
поправки и регрессии перед следующим повторным выпуском/откатом; исходный
prepare/apply без этих исправлений не считать повторно пригодным.
