# Telegram: активация клиентского входа на VPS

## Причина недоступности

На старте этапа API `2f3c3f3` содержит identity, но runtime возвращает
`enabled:false`; переменные Telegram не переданы контейнеру. Публичный
`/v1/auth/config` возвращает 404. Проверка доставки Telegram 26.09 была отдельным
тестом транспорта, а не завершённым входом с телефона через этот VPS.

Владелец 30.09 поручил завершить подключение. Ранее согласованы оператор,
размещение Hoster.kz/Алматы, документы пилота и лимит 1000 резервирований/UTC-день.
Повторная регистрация Gateway не нужна. SMS/WhatsApp остаются выключенными.

## Выпуск

`infra/staging/release-telegram-auth.py` - отдельный профиль schema 027 без новых
миграций. Пин исходного API 2f3c3f3, public overlay bda246f и gateway af729c3.
Наследует штатные deploy/cleanup locks, закрытие ingress, остановку писателя,
зашифрованную копию и её проверку восстановлением в отдельную БД, сравнение
данных/ACL, проверку старого image и CAS указателей. Ошибка/таймаут оставляет
владение lock для диагностики; автоматического повторного применения нет.

Новые права только identity, остальные права и данные сохраняются. Запрещено
включение Kaspi pilot; банковские счета, кухня и платёжные worker не запускаются.
Реальный токен хранится только в приватном env на VPS, не в mobile/Git. Четыре
независимых ключа identity сохраняются для следующих выпусков.

Публичные маршруты: config, запрос/проверка OTP, refresh/logout и свой профиль.
Ответы `no-store`; доверенный IP берётся через два явно заданных proxy hop.
Обычные приватные панели не открываются. Условия и privacy публикуются отдельно
из защищённой папки с реквизитами владельца, не из Git и не с незаполненными полями.

Публикационная редакция сохраняет согласованный пилот и уточняет фактических
получателей: [Hoster.KZ](https://hoster.kz/oferta/),
[Telegram Gateway](https://telegram.org/tos/gateway),
[политику Telegram](https://telegram.org/privacy). Нельзя утверждать, что Telegram
обрабатывает данные только в Казахстане или что точная география Gateway проверена.
Страница описывает наблюдаемые сроки очистки и резервирования; это не заключение
о юридической достаточности для коммерческого запуска и не новая оферта продаж.

## Проверки до выпуска

73 Python release-проверки прошли, включая 5 новых: неизменность маршрутов,
отсутствие миграций/изменений данных, только identity ACL, запрет незавершённых
legal страниц и точное совпадение baseline. Полная CI и установка отмечаются
ниже только после результата.

## Откат

До открытия ingress при ошибке сохранить maintenance/cleanup locks, сверить
`before.json`, `prepared.json` и частный журнал команд. Вернуть старый API/публичный
compose и указатели штатным CAS; для прав использовать `acl_restore_sql` после
сравнения текущего ACL с сохранённым. Не откатывать всю БД и не удалять ключи.
После первых входов сохранить созданные профили; отключение авторизации не
означает удаление пользователей. Дамп поверх действующей базы не восстанавливать.

Первый прогон 36680701996 обнаружил старую guest-фикстуру Pick Man после auth v3;
исправлено разделение гостя и вошедшего пользователя, локально проверены 5 размеров.

Backup+restore в изолированной БД, неизменность данных/схемы 027, identity-only ACL,
готовность старого и нового API, hashes/mounts и сохранение соседних служб прошли.
Публичный config 200: enabled=true, channels=[telegram], consent_required=true.
Условия/privacy 200, профиль/checkout 401 без сессии. Невалидные request/verify/refresh 400,
Cache-Control=no-store, X-PickChick-Data=customer. Токен проверен с VPS запросом
checkVerificationStatus с вымышленным request_id, без отправки сообщения.

Реальные OTP автоматическим прогоном не отправлялись. После установки владелец
сам запросил код в PickChick Dev и подтвердил вход и сохранение сессии после
повторного открытия приложения. Выход, доставка на другие номера и баланс
для них этим подтверждением не проверены.
PickChick Dev manifest/bundle HTTP 200; для обновления конфигурации можно нажать
«Повторить подключение» или перезапустить приложение.

## Публикация пульта проекта

Первая попытка среза `6fab3a6` откатилась штатно: проверка manifest запрашивала
`/legal/terms.html`, хотя gateway публикует `/legal/terms`. API и вход не менялись,
SQLite не восстанавливалась поверх данных. Проверка теперь использует реальные
адреса двух legal-страниц и по-прежнему сравнивает полный SHA-256 содержимого.
Все 17 проверок roadmap deploy прошли, включая 4 регрессии маршрутов и hash.
Повторная публикация `dbfd9741b807da4cb686086718822938c92fc183` прошла после
[roadmap CI 36686932801](https://github.com/xaaknazar/pickchick/actions/runs/36686932801).
Публичный `/roadmap/health` подтвердил этот source SHA; `/v1/auth/config` после
публикации по-прежнему возвращает enabled=true, channels=[telegram]. Gateway hash
`9359358675c93db88ac13f01b68c1c919c5a4f4909a316081f4d893a911be09b` сохранился;
API, БД, кухня, Kaspi-мост и соседние службы не перезапускались.
