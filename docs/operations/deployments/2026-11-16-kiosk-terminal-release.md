# Киоск и отдельный Kaspi Smart POS - подготовка выпуска 16.11.2026

## Статус

Выпуск остановлен до изменений. Владелец разрешил выпуск ADR-0018 после слияния
PR388 и полной зелёной Foundation CI именно на коммите слияния. Разрешены новая
нативная сборка киоска во внутреннем TestFlight и сохранение прежней привязки.
Контрольную оплату выполняет владелец, не оператор выпуска.

Проверки выполнены только чтением. Резервная копия для этого выпуска ещё не
создавалась, миграции, права, провайдеры, окружение, API и шлюз не изменялись.
Новая сборка не собиралась и в TestFlight не загружалась. Реальных заказов,
попыток оплаты и команд терминалу не создавали.

## Откат

Для этой попытки не нужен: рабочие системы не менялись. После начала выпуска
использовать раздел отката `docs/operations/kiosk-kaspi-terminal.md` из принятого
коммита. Не удалять журнал 080 и не восстанавливать рабочую базу поверх заказов.

## Дальше

1. Получить точное зарегистрированное наименование и 12-значный ИИН/БИН ИП
   PEAK GROUP из реквизитов Kaspi, через приватный файл или другой защищённый
   канал. Не помещать реквизиты в Git или отчёт. Создание юрлица ещё не выполнено.
2. Дождаться исправления CI, слияния PR388 и полного PASS Foundation на
   опубликованном коммите слияния. Повторить все проверки на новом точном SHA.
3. Согласовать занятые области перед изменениями, получить штатный lock и
   повторить baseline активной работы и финансовых операций. Сейчас занята
   только область этого протокола, облачные и Apple-резервы не перехвачены.
4. До необратимого шага сообщить владельцу, создать свежую зашифрованную копию
   базы и проверить изолированное восстановление. Подготовить точный путь
   миграций от 077 до 080, без молчаливого включения посторонних возможностей.
5. Затем выполнить утверждённую установку: отдельный kaspi-pos на PEAK GROUP,
   080, права после остальных grants с фактической сверкой, ровно два новых
   параметра API, проверенный API и маршруты шлюза. Сохранить прежний PIN,
   привязки, соседние сервисы и остальные настройки.
6. Проверить без денег config, отказ 401 без ключа и доступность terminal-events.
   Для config требуется существующая идентичность киоска и гостя; не переиздавать
   ключ устройства ради проверки и не публиковать его.
7. Подготовить новую нативную сборку с разрешением локальной сети, прежними
   Bundle ID, Apple Team и SecureStore. Учесть разрешённое владельцем отключение
   фотопринтера из PR387, сохранить production API и commercial checkout.
   TestFlight не заменяет физическую проверку владельцем оплаты и кухни.

Общие статус, roadmap и онлайн-пульт не перезаписаны: они закреплены за другой
задачей и содержат независимые изменения. Этот протокол фиксирует только
подготовку и препятствия, а не состоявшийся выпуск.
