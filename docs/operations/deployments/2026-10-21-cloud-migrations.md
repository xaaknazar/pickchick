# Облачная схема 058 -> 060 -> 064/066/068

21.10.2026 владелец разрешил начать первый этап выпуска после плана в чате:
подготовка защищённого оператора, резервная копия, восстановление, миграции и
проверка. Это отдельное разрешение на схему; runtime, flags, каталог, касса,
iPad/Apple и онлайн-пульт в этот этап не входят. `204d318b` не выпускается.

## Кандидат и область

База исходников: принятый PR262, `d15bde82a87a85f1f5c4004c7c3be3c76d0977a2`.
Ветка `codex/cloud-migrations-1021`, резерв `cloud-migrations-1021`:
новые owner/release-инструменты, их проверки, этот протокол, `@vps/api`,
`@vps/postgres`. Чужие незавершённые области не менялись.

На чтение подтверждены live API `5b6f846b80785f915e9f8dd7d45fa72fd4bc13ee`,
образ `sha256:e1b4a09a3c8f2cb32ed6f7b40f8ef1a864737506868ce95329a1feb2fa3173ca`,
публичный срез `76902fa4b8403f9084c0028fa16f02b8ec155586`.
Перед действием проверяются полные ledger/checksum058, compose/gateway hashes,
все переменные среды (хеши), pointers, контейнеры, runtime ACL и readiness.

## Механизм

- `combo-rewards-owner.mjs`: только точная058 ->060 в repeatable-read транзакции
  и под штатным advisory lock724001. SQL060 закреплён SHA256, старые constraints
  проверяются; полный fingerprint старых столбцов/строк, роли, ACL и журнал
  сверяются внутри одного снимка. Никаких активаций, backfill или новых grants.
- Шаг064/066/068 использует принятый `release-fixes-1019-owner.mjs` внутри такого
  же снимка и общей блокировки. Единственные новые права - четыре операции на
  `identity_otp_failures`, только если серверная авторизация уже имеет права.
- Python-оператор допускает только diff инструментов относительно PR262,
  чистый опубликованный SHA и полную Foundation CI этого SHA. Общая серверная
  блокировка сохраняется при ошибке/неизвестном исходе и не крадётся.
- Кандидат запускает только owner-инструменты в отдельном контейнере существующего
  закреплённого API image. Runtime-контейнеры не заменяются и не перезапускаются.
- Перед apply: зашифрованный dump и manifest количества строк, checksum;
  восстановление в новый контейнер без внешней сети; обе миграции на копии,
  rollback с возвратом058, повтор с commit068, проверка отказа replay.
  Приватный age-ключ идёт только по stdin через проверенный SSH, не пишется на VPS.
  Зашифрованная копия дополнительно сохраняется на Mac.

## Команды оператора

Из чистого checkout с точными доказательствами CI и live pins в приватных файлах:

```sh
python3 infra/staging/release-cloud-migrations-1021.py prepare \
  --sha "$SOURCE_SHA" --branch codex/cloud-migrations-1021 \
  --expected-api-sha "$API_SHA" --expected-api-image "$API_IMAGE" \
  --expected-public-sha "$PUBLIC_SHA" --expected-compose-sha256 "$COMPOSE_HASH" \
  --expected-gateway-sha256 "$GATEWAY_HASH" --ssh-key "$SSH_KEY" \
  --backup-identity "$AGE_KEY" --ci-proof "$CI_PROOF"
```

Без `--apply` это проверка. После проверки та же команда с `--apply` сохраняет
неизменяемые инструменты и доказательство prepare. Далее заменить `prepare`
на `apply`: сначала проверка, затем `--apply` выполняет backup/restore/rehearsal
и последовательные транзакции060 и064/066/068. Аргументы и SHA не менять между
проверкой и выполнением. Секреты не подставлять текстом в команды/логи.

## Остановка и восстановление

Ошибка транзакции откатывает именно её. Если060 уже подтверждена, а следующий
шаг не завершён, сначала read-only сверка журнала и процесса; не выполнять весь
apply повторно. Локальный apply-attempt запрещает слепой повтор.
При разрыве SSH исход неизвестен: блокировка остаётся, не запускать конкурирующий
оператор. Успешную аддитивную схему не удалять и старый dump поверх новых продаж
не восстанавливать. Runtime остаётся прежним, отдельного runtime rollback нет.
