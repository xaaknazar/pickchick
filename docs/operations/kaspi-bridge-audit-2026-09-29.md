## Источник протокола

Прочитан публичный код [интерфейса входа Kaspi](https://entrance-pay.kaspi.kz/process/entrance/),
сборка [app.de20fd73.js](https://static.cdn-kaspi.kz/kkz/entrance-pay/process/js/app.de20fd73.js).
Копия для анализа находится только в игнорируемой `.local`; исходники банка
не включаются в наш репозиторий.

- `KPEnterLoginPasswordPage` передаёт `data.password`, `actType=Success` и
  метаданные текущего процесса. Этот формат реализован и проверен банком.
- `UniversalKaspiIdTakePhotoPage` вызывает нативные `faceCheck` / `faceCheckV2`;
  результат содержит банковский verification code. Это не обычная веб-форма
  загрузки фотографии. В мосте нативного модуля нет; замена результата на
  фиктивный Success не реализуется.
- `KPMobileCallPage` - вызов нативного приложения, а не телефонный звонок.
  Для `kpDeviceRegistration` выполняется `onRegister`. Наш адаптер допускает
  штатный upstream finish после OTP только для этого типа; неизвестные действия,
  регистрация организации и Kaspi ID не превращаются в готовую сессию.
- Парольный шаг также найден в двух из 30 просмотренных последних форков:
  [ansarakim](https://github.com/ansarakim/kaspi-pos-automation/commit/60952da9),
  [satugoi101-boop](https://github.com/satugoi101-boop/kaspi-pos-automation/commit/0726bd0e).
  Это сверка формата, не подтверждение работоспособности форков или решения Kaspi ID.

## Дальше

Следующая зависимость входа - штатная поддержка Kaspi ID для нового устройства
и получение проверяемой сессии именно выбранного продавца/точки. Обычный вход
в Kaspi Pay на телефоне не доказан как способ завершить этот серверный процесс.
Не направлять владельца по неподтверждённому обходному пути.

Независимые оставшиеся части продукта: commercial quote/create/payment/read
API для проверенного customer, серверная цена опубликованного меню с налоговой
привязкой, подтверждённый admission ресторана, мобильный экран ожидания счёта,
проверка профиля merchant, Webkassa и подтверждение чека перед кухней. Эти части
не становятся готовыми от успешного парольного запроса. TEST-заказы не помечать
оплаченными и не направлять их через боевой банковский адаптер.

Установка: вместо одного `git apply` выполнить
`node infra/payments/kaspi-bridge/install-overlays.mjs /path/to/pinned-upstream`.
Если есть старые локальные патчи, установщик останавливается на конфликте;
не сбрасывать файлы устройства и ключи ради повторного применения.

## Личное прохождение Kaspi ID и серверная сессия

Владелец поручил подготовить личное подтверждение с дальнейшим использованием
входа сервером. Проверка 29 сентября установила следующее:

- [Справка Kaspi о регистрации сотрудника](https://guide.kaspi.kz/partner/ru/profile/user/general/q3241)
  прямо называет фотоверификацию обязательным этапом регистрации пользователя.
  Предыдущая короткая SMS-инструкция не исключает этот этап. Пользователь уже
  подтвердил завершение регистрации и уточнил: приложение впустило сразу,
  проверки лица на телефоне не было. Это не подтверждает серверный процесс.
- Публичный JS модуль `a3b4` вызывает `authApi.send`; модуль `db49` берёт
  `authApi` из `window.auth`. У `UniversalKaspiIdTakePhotoPage` обработчик вызывает
  `faceCheck` / `faceCheckV2` с verificationId и получает verificationCode через
  native callback. Обычная ссылка на SPA не добавляет `window.auth` в Safari.
  Подтверждённого browser/phone handoff URL или доступного SDK для нашего процесса
  в просмотренном коде и документации не найдено. Новый UI камеры не создаём:
  он не сможет сам получить банковское подтверждение.
- [Ограничение Kaspi Pay на устройства](https://guide.kaspi.kz/partner/ru/app/settings/q1424):
  вход на другом устройстве завершает предыдущий. Нельзя считать две независимые
  авторизации на телефоне и сервере одной сессией или обещать бессрочный вход.

### Порядок дальнейшего подключения

1. Получить подтверждённый способ открыть нативную проверку **того же** процесса
   на устройстве владельца. Сейчас это незакрытая зависимость. Не создавать новый
   SMS-процесс, пока нет способа завершить следующий шаг. Отдельный вход в Kaspi Pay
   не трактуется как подтверждение сервера; token extraction из приложения не нужен.
2. После появления поддерживаемого способа - запускать вход на конечном сервере
   с постоянными ключами устройства. Владелец лично подтверждает проверку в
   официальном интерфейсе; лицо/видео в PickChick не собираются и не сохраняются.
3. Банк должен завершить процесс и вернуть настоящую сессию кассира. Проверить
   организацию и точку до включения worker. Никакой фото-callback или кнопка
   владельца сами по себе не означают готовый вход или оплату.
4. Сохранить вместе неизменную связку: `device.json`, `keypair.json`, ключ
   `TOKEN_SECRET_KEY` и `kaspi-session.env`. Секреты только в защищённых каталогах
   серверного пользователя, файлы 0600, каталоги 0700, вне Git, клиентского bundle
   и логов. Не запускать генерацию новых device/keypair при обновлении контейнера.
   Если понадобится перенос, остановить исходный экземпляр, передать всю связку
   через проверенный SSH, проверить сессию на новом узле без выставления счёта.
5. До сохранения нового файла CLI теперь требует `finished`, `isCashier===true`
   и успешный read-only `/api/session/check` через тот же мост. Запись атомарная;
   при ошибке прежний файл остаётся, временный удаляется. Это локальная подготовка,
   не подтверждение уже сохранённой настоящей сессии. Merchant/ККМ проверяются отдельно.
6. После установки проверить сессию ещё раз после перезапуска. При отзыве сессии
   остановить новые счета, сохранить незавершённые попытки для reconciliation и
   запросить повторный личный вход. Не обещать автоматическое бессрочное продление.
7. Только затем отдельный согласованный платёжный пилот через ledger, Webkassa
   и kitchen admission. Сейчас сессии/счетов нет, VPS и онлайн-пульт не менялись.

Проверки: 19 Kaspi unit-тестов, включая сохранность прежнего файла при Kaspi ID,
неподтверждённой роли, отказе/обрыве session check; атомарная запись 0600 и отсутствие
остаточного временного файла. Реальный банк на этом этапе не вызывался.

`confirm_mobile` завершает процесс через finish; обработчика личной проверки
того же verificationId нет. SignInLite обновляет уже имеющуюся сессию, а не
создаёт отсутствующую. Подменять им Kaspi ID нельзя. Рекомендация README пройти
проверку в приложении не подтверждена как способ завершить наш серверный процесс.
Новых подтверждённых решений нативного шага в изученных источниках не найдено.

Повтор init/send-phone снова запросил password. Пока владелец сохранял пароль,
десятиминутный срок процесса истёк. Перед отправкой это проверено; создан один
новый процесс с прежними ключами устройства и стандартными параметрами.
Пароль отправлен один раз: success=true, nextStep=sms. После нового SMS владельца
банк вернул success=false, nextStep=identity_verification,
errorCode=KASPI_ID_REQUIRED. Автоматических повторов OTP и finish не было.

Оба приватных файла очищены после использования, локальный мост остановлен.
Повтор подтвердил прежнее препятствие, а не устранил его. Нет сессии, счетов
и списаний; VPS и онлайн-пульт не обновлялись. Код интеграции в этом этапе
не менялся. Проверены ссылки/зависимости roadmap и формат документов;
полная CI не является подтверждённой приёмкой этого банковского сценария.

| [qrapi](https://qrapi.kz/docs/)                          | Изолированный bridge для клиента, init/send-phone/verify-otp, зашифрованная сессия                                                                                                           | Публичный контракт описывает SMS-путь, не подтверждает поддержку лица; сходство путей не доказывает общий исходный код.                                                                    |

### Что нового даёт ApiPay

В [требованиях к номеру](https://apipay.kz/guides/trebovaniya-k-nomeru-kassira)
ApiPay связывает совместимость не только с ролью номера в конкретной точке,
но и с бизнес-профилем владельца SIM. Поэтому прежний ответ «отдельный номер,
только кассир» не проверяет всю эту гипотезу. Владельцу задан вопрос только
о наличии собственного ИП/ТОО в Kaspi Pay у владельца SIM; ИИН и документы
не запрашивались. Владелец ответил: да, собственное ИП/ТОО в Kaspi Pay есть.
Это совпадает с условием ApiPay, но не подтверждает причинную связь: банковский
ответ не раскрывает причину выбора Kaspi ID и сам по себе роли не доказывает.

Нельзя утверждать, что покупка новой SIM тем же человеком устранит проблему,
что отдельный вход в приложении подтвердит наш процесс или что посредник умеет
обходить лицо. В ApiPay/Tole документирован подбор совместимого SMS-сценария,
а не опубликованная реализация прохождения биометрии. Не менять номера,
профили, устройство и банковские флаги ради подавления обязательной проверки.

В ApiPay `kyc_required` относится к одобрению анкеты бизнеса самим сервисом;
это не синоним банковского KASPI_ID_REQUIRED. Их external/self и коды ошибок -
контракт ApiPay, а не доказательство альтернативного официального входа Kaspi.
[GitHub ApiPay](https://github.com/bazarbaykz/apipay-docs) содержит документацию
к API сервиса; открытого серверного обработчика Kaspi ID там не установлено.

У Tole есть совет не входить в приложение заранее, у xpayment сказано проверить
возможность входа. Эти инструкции различаются. В нашей хронологии пароль
запрашивался до завершения регистрации на телефоне: нельзя объявлять вход
в приложение причиной первоначального запроса пароля/лица.

### Практический вывод для собственного моста

Подтверждённый путь этих сервисов - получить действительную сессию кассира,
затем создавать счета/QR, сверять статус и доставлять события своему клиенту.
Это объясняет их API и автоматизацию после входа, но не доказывает особых
банковских привилегий или общего решения любой проверки личности.

Пользователь подтвердил наличие бизнес-профиля владельца SIM. Следующий
диагностический шаг - сравнить способ первоначального подключения amoTEAM
(чей кассир, какой шаг подтверждал владелец; без секретов). Точная причина
остаётся неподтверждённой, зависимость нативного подтверждения открытой. Поддержка
счетов, финальные статусы, Webkassa и commercial checkout не становятся готовыми
от этой документационной проверки. Онлайн-пульт и VPS не обновлены.

## Новый кассир: успешная банковская сессия

29 сентября владелец предоставил другой номер и подтвердил, что он добавлен
кассиром в ИП PICK CHICK ALA AP / Pick Chick Abay Plaza и SMS доступны ему.
Номер сохранён только приватно. Init/send-phone с прежними ключами устройства
сразу вернули success=true, nextStep=sms: пароль не запрашивался.

После одного verify-otp: success=true, nextStep=finished, isCashier=true,
orgName=ИП PICK CHICK ALA AP. Обработчик saveVerifiedSession выполнил проверку
сессии банком на чтение; active=true. Только после этого записан локальный
.local/kaspi-session.env с правами 0600. После остановки и нового запуска моста
с теми же ключами сохранённая сессия снова прошла банковскую проверку active=true.

Файл OTP очищен. Дубликат секретов удалён из временного результата входа,
каноническая копия сессии осталась в приватном env. Локальный мост остановлен,
ключи устройства и ключ шифрования сохранены. На VPS ничего не перенесено.
Актуальный кассир: .local/kaspi-cashier-active.json; старый
.local/kaspi-cashier.json относится к предыдущей неуспешной попытке.

Границы результата:

- Реально подтверждены вход, роль кассира, название организации и повторное
  использование сессии после перезапуска. Это больше не только FakeBridge.
- Нативной проверки лица в этом процессе банк не запросил; никакой проверки
  не подавляли. Успех другого кассира не доказывает причину отказа предыдущего.
- Точка Abay Plaza подтверждена владельцем, но в возвращённых полях банковского
  результата название точки отсутствует; её банковская привязка ещё не сверена.
- Счета, списания, возвраты и чеки не создавались. Работа мобильной оплаты
  и прохождение заказа на кухню этим входом не подтверждены.
- До первого пилотного счёта: проверить торговую точку/merchant и Webkassa,
  установить мост с сохранением комплекта ключей и сессии по guarded runbook,
  подключить commercial checkout и проводить платёж через durable ledger.
  Полная CI/критерии выпуска обязательны перед серверной установкой.

Документационные проверки: roadmap evidence test, Prettier и staged diff.
Онлайн-пульт не обновлён; код моста в этом этапе не менялся.
