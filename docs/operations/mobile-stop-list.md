# Стоп-лист кассы в мобильном приложении

## Причина

На 1 октября Pick Combo остановлен в локальном `local_stops`, но мобильное
приложение читало каталог без этой проекции. Локальный UUID базовой позиции
отличается от строкового product ID мобильного каталога.

## Изменение

- Касса остаётся владельцем стопов. Аутентифицированный fulfillment worker
  передаёт эффективный список с монотонной ревизией в каждом цикле обмена.
  Ручные стопы, ограничения по времени и по смене сохраняют POS-семантику.
- Cloud schema030 хранит проекцию, связанную с активным устройством точки.
  Запоздалая/повторная ревизия не меняет список и не продлевает свежесть.
- Публичный read-only endpoint `/v1/customer-checkout/availability` возвращает
  только доступность товаров и вариантов. Long poll возвращается при изменении;
  персональные данные и управление стопами наружу не передаются.
- Мобильное меню показывает «Нет в наличии», запрещает добавление; корзина
  сохраняет состав и объясняет, что нужно заменить. Сервер отдельно проверяет
  стоп перед котировкой и первой попыткой оплаты, edge - перед admission.
- При отсутствии свежего снимка более 30 секунд новая оплата закрыта.
  Уже оплаченные заказы и история продолжают читаться. Это не резервирование
  последней порции и не расчёт остатков по нормам.
- Идентификаторы сопоставляются по точному алгоритму установленного локального
  каталога v1/v2 и product ID, не по названию и не по SKU.

## Проверка и установка

Подготовлены тесты монотонности, base/modifier stops, устаревания, отключения
устройства, истечения стопа, quote/pay, edge admission, мобильной корзины.
Windows обновляется без миграции schema015; worker получает SELECT только
на 7 столбцов стопов/состояния смены. Штатные backup/restore, CI и ACL guards
сохраняются. `release-mobile-stops.py` допускает только cloud030 и строго
ограниченный новый GET в gateway.

Установлен runtime `e47702add67dff3d2d37462ae51adc693ff81449`:
API и кассовые Edge/FulfillmentWorker. Полная [CI 36847858596](https://github.com/xaaknazar/pickchick/actions/runs/36847858596)
прошла 6/6. Cloud030 добавлена, edge015 не изменялась. Kaspi worker остаётся
`289da31`, его сессия и платёжная политика не менялись.

Backup и изолированное восстановление прошли для VPS и Windows. Существующие
строки, последовательности и ACL сохранены; добавлены только заявленные права.
Первая попытка VPS apply потеряла SSH до миграции. Перед повтором проверены
baseline pointers, schema029, отсутствие release-процессов и принадлежность
блокировки. Повторный штатный apply завершился успешно без ослабления guards.

На реальном VPS: свежий снимок, Pick Combo `available=false`, серверная проверка
возвращает ITEM_STOPPED. На моноблоке работают все пять служб, ошибок обмена нет.
Браузерная сборка приложения с настоящим VPS проверена на 320 и 390 px:
Pick Combo отмечен «Нет в наличии» и отключён, Master Combo можно выбрать,
ошибок JavaScript нет. Физический iPhone после этого обновления ещё не принят
владельцем. Никакие стопы пользователя для проверки не переключались.

Локально прошли pnpm check, 60 commerce, 28 edge, 52 transport, 74 release,
две Windows migration/grant проверки, мобильные и целевые браузерные сценарии.
Состояние финансового журнала при read-only проверке: 5 заказа, 5 попытки, 5 счёта, 1 capture.
Проверочные заказы, счета и списания не создавались.

Первый CI выявил три старые browser fixtures, которые считали новый read-only
GET неожиданным запросом. Fixtures дополнены конкретным отключённым ответом;
запрет остальных запросов и любых записей сохранён. Все три повторно прошли
локально на экспортированной QA-сборке. Дополнительно остановленный до admission
заказ освобождает локальный слот: исходная команда остаётся в cloud outbox без ACK,
а доступные заказы других клиентов продолжают доставляться.

Дополнены также изолированные сценарии регистрации и Kaspi: регистрация
получает отключённую проекцию, платёжный сценарий - свежую доступность каталога.
В повторном CI возник прежний SQL deadlock сценария TEST-нумерации при прямых
параллельных INSERT; отдельный повтор и повтор CI на том же SHA прошли этот
сценарий. Это известная нестабильность теста, не изменение рабочего счётчика.
