## Почему так

- Отдельный инструмент вне runtime: работает на установленной кассе уже сейчас (схема 020,
  старый runtime; Node и драйвер `pg` из фундамента), не зависит от отложенного выпуска
  020 -> 023 и после него продолжает работать без переустановки (023 в списке).
- Восстановление в отдельную базу при каждом запуске не делается: роли копии для этого
  нужны права создания баз. Полная репетиция - по edge-restore.md и
  `backup-native-service.mjs`; здесь - TOC, хеш и полное расшифрование каждой копии.
- Кабинет: хранение возраста копии в облаке требует облачной миграции (номер полосе не
  выделен) и правки центра устройств (занят другой задачей). Поэтому сигнал идёт через
  лог API в watchdog без миграции; показ в кабинете - следующий шаг.
- Блокировка обслуживания: копия держит открытым `EdgeTools\unified-menu-maintenance.lock`,
  поэтому выпускные скрипты (FileShare.None) не стартуют во время копии, а копия
  пропускается, пока идёт обслуживание.

## Флаги и значения по умолчанию

| Флаг                                         | По умолчанию | Значение                                                                        |
| -------------------------------------------- | ------------ | ------------------------------------------------------------------------------- |
| `install-edge-backup.ps1 -ReportInHeartbeat` | выключен     | касса сообщает о просроченной копии в пульсе (хранится в конфигурации и status) |
| `-MaxAgeMinutes`                             | 120          | после этого копия просрочена (60-4320)                                          |
| `-HourlyCopies` / `-DailyCopies`             | 48 / 14      | хранение                                                                        |

Новых переменных окружения нет. Облако принимает поле всегда, но пишет строку только когда
касса его прислала; без установки копии или без флага поведение пульса не меняется.

## Миграции и контракты

- Миграций нет (cloud и edge). Роль `pickchick_edge_backup` создаёт установщик.
- Контракт: в `FulfillmentTransportPullRequest` добавлено необязательное поле
  `edgeBackup` (`state` stale/failed, `ageMinutes` или null, `maxAgeMinutes`, `error`
  код или null); `packages/contracts/openapi.json` перегенерирован, `contracts:check` зелёный.
- `native-edge-backup-ledger.json` дополнен 021-023 (общий для ручной копии и
  обновления отчётов кассы, им нужен префикс до 016 - совместимо).

## Развёртывание

1. Касса (независимо от остальных шагов, можно до выпуска runtime): папка поставки с
   `install-edge-backup.ps1` и пятью файлами; `Install -DryRun`, затем Install с местом
   владельца. Сразу после - копия ключа владельцу. Проверка: Inspect, `health/status.json`,
   файл копии и паспорт на втором месте, `edge-backup-restore.mjs verify`.
2. Облако (по желанию сигнала): выпуск API с новым `@pickchick/fulfillment-transport`
   (принимает поле) и watchdog с проверкой `edge.backup`.
3. Касса: runtime с новым `native-fulfillment-worker.mjs` (следующий выпуск после 21.10).
4. Повторный Install с `-ReportInHeartbeat`.

Откат: `install-edge-backup.ps1 -Mode Uninstall` (ключ, конфигурация и копии остаются;
`-RemoveDatabaseRole` убирает роль). Облако и watchdog - прежние релизы: старый API
отклоняет поле, новый обработчик кассы сам его убирает; старый обработчик поле не
шлёт. В базу кассы, службы и настройки копия ничего не пишет.

## Что нужно от владельца

- Место: второй физический диск (NTFS) или NAS; при NAS - разрешение записи учётной
  записи компьютера кассы (SYSTEM) или домен; учётные данные NAS для SYSTEM инструмент
  не хранит.
- Окно 20-30 минут на кассе для установки и первой копии.
- Хранение копии ключа отдельно от копий (менеджер паролей или носитель в сейфе).
- Решение о `-ReportInHeartbeat` и о выпуске API/watchdog для сигнала.
- Репетиция восстановления по edge-restore.md на стенде.

## Не проверено

Windows PowerShell 5.1, Планировщик и ACL NTFS, `Get-Partition`, запуск от SYSTEM без
входа, NAS, блокировка файла обслуживания между Node и PowerShell, `pg_dump.exe` 18.6 и
длительность копии на реальной базе, перенос ключа владельцу, восстановление на стенде,
выпуск API/watchdog и нового обработчика кассы.
