# Этап 2 (24.10.2026) - линия pcs: стоп комбо на самой кассе

Ветка `codex/pos-combo-stop-1024`, база `4cc11e05`. Остаток находок аудита 19.10 1.3 / 4.2 / 6.3
(«Стоп комбо на самой кассе» в [README выпуска 19.10](../release-fixes-2026-10-19/README.md) и
[ful.md](../release-fixes-2026-10-19/ful.md)). Киоск, приложение и допуск их заказов на кассе уже
работают по правилу ПМ (решение 1). Продажа кассиром на POS проверяла только стоп самого товара и
выбранного варианта: комбо с остановленным картофелем или напитком продавалось.

## Что сделано

Правило то же, что в облачных каналах (`catalogStopView`): комбо недоступно, если остановлен любой
фиксированный компонент (вложенные комбо тоже, до 5 уровней) или все варианты обязательной группы;
вариант недоступен по своему стопу или по стопу товара, за который он стоит (`linked_product_id`,
иначе товар с тем же id, что у варианта).

Выпуск в два шага, обратно совместимый:

1. **Касса (новый runtime кассы).**
   - Контракт `MenuSnapshot` (`packages/contracts`): два необязательных поля -
     `combo_component_variant_ids` у позиции (варианты меню всех фиксированных компонентов, вложенные
     комбо уже развёрнуты; не пустой список, без повторов и без самой позиции) и `linked_variant_id`
     у варианта выбора (вариант меню товара, за который стоит напиток или соус). Меню без этих полей
     разбирается как раньше.
   - `local-orders`: расчёт (`createQuote`) и создание заказа (`createLocalOrder`) проверяют стопы
     через `menuLineStopIds` (`packages/menu-sync/src/availability.ts`): позиция, выбранные
     варианты, товары за выбранными вариантами и все фиксированные компоненты. Отказ - прежний код
     `ITEM_STOPPED`. Для меню без полей набор id ровно прежний: поведение не меняется.
   - Экран кассы (POS v2): плитка комбо со стопом части состава серая, при нажатии - причина
     («Комбо недоступно: «Фингерс, 1 шт» в стоп-листе», «Недоступно: нет доступных вариантов в
     группе «Соус»»); напиток или соус, чей товар в стопе, зачёркнут, не выбирается и не
     подставляется по умолчанию (уже выбранный можно убрать); строка корзины помечается.
     Контроллер не добавляет такое в корзину: `COMBO_STOPPED` («Комбо недоступно: часть его состава
     в стоп-листе. Выберите другое блюдо или снимите стоп.»), `CHOICE_STOPPED` («Все варианты
     обязательного выбора в стоп-листе...») и `OPTION_STOPPED` («Выбранный напиток или соус в
     стоп-листе. Выберите другой вариант.»). Текст `ITEM_STOPPED` теперь упоминает часть комбо.
     Окончательную проверку всё равно делает касса (edge).
   - Воркер меню кассы на каждом запросе меню сообщает `menu_features=combo_stops` (рядом с
     прежними `active_release_id` / `active_version`).
2. **Облако (API).**
   - Владелец включает `CATALOG_EDGE_COMBO_STOPS_ENABLED=true`: публикация каталога на кассу
     (`projectCatalogMenu`) добавляет поля. Выключено (по умолчанию) - публикация байт в байт
     прежняя, та же контрольная сумма.
   - Рукопожатие при выдаче: облако отдаёт сохранённую публикацию с полями только кассе, которая
     прислала `menu_features=combo_stops`. Любой другой кассе (установленный edge021) отдаётся тот
     же выпуск без новых полей и с контрольной суммой именно этого вида - установленная касса
     никогда не видит поле, которое её строгая схема отвергнет. Публикация без полей отдаётся без
     изменений.
   - Подтверждение (ACK) принимается с контрольной суммой сохранённой публикации или её прежнего
     вида, и только с ними; идемпотентность inbox прежняя (второй ACK другого вида - `CONFLICT`).
   - Публичный `GET /v1/branches/:id/menu` никогда не показывает новые поля.

### Почему решение при выдаче, а не при публикации

Чтобы решать при публикации, облаку нужно хранить, что касса умеет новые поля. Для этого нужна
облачная миграция, а номера cloud 070/071 закреплены за другими линиями; у pcs облачного номера
нет. Решение при выдаче не требует хранения, работает и для старой кассы, и для отката кассы:
откаченная касса перестаёт присылать признак и сразу получает прежний вид. Контрольная сумма
по-прежнему проверяется с обеих сторон: касса проверяет то, что получила, облако принимает только
две заранее вычисленные суммы одного выпуска.

## Флаги

| Переменная                         | Где                                              | По умолчанию | Смысл                                                                                                                                                                                                                     |
| ---------------------------------- | ------------------------------------------------ | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CATALOG_EDGE_COMBO_STOPS_ENABLED` | API (рядом с `CATALOG_EDGE_PUBLICATION_ENABLED`) | `false`      | публикация каталога на кассу добавляет поля стопа комбо; действует только при включённой публикации на кассу; иное значение, кроме `true`/`false`, - ошибка конфигурации `CATALOG_EDGE_COMBO_STOPS_CONFIGURATION_INVALID` |

Флага на кассе нет: новый runtime всегда сообщает `combo_stops` и применяет поля, если они есть.
Переменная не добавлена в `infra/staging/compose.yaml` и в `release-unified-menu.py` (флаги
публикации каталога пишутся в живой compose выпускающим скриптом, см.
[unified-menu-publication](../unified-menu-publication.md)); включение - отдельный шаг выпуска с
обычной проверкой окружения API.

## Миграции и контракты

- Миграций нет. Облачная не нужна (см. выше). Edge 025 не понадобилась: поля живут внутри снимка
  меню, который касса уже хранит как JSON (`menu_snapshots.payload`) вместе с контрольной суммой;
  схема базы кассы не меняется, поэтому и охраняемый инструмент обновления Windows не нужен.
- Контракты: `MenuSnapshot` (два необязательных поля), `EdgeMenuFeatureSchema` (`combo_stops`),
  ключ `menu_features`; `packages/contracts/openapi.json` пересобран, `pnpm contracts:check`
  проходит. Внутренний протокол меню: необязательный ключ запроса `menu_features`; ответ облака и
  ACK по форме прежние.

## Совместимость версий

| Облако               | Касса (edge + воркер меню)   | Что происходит                                                                               |
| -------------------- | ---------------------------- | -------------------------------------------------------------------------------------------- |
| установленное        | установленная (edge021)      | как сегодня                                                                                  |
| установленное        | новая                        | ключ `menu_features` игнорируется, меню без полей, продажа как раньше                        |
| новое, флаг выключен | любая                        | публикации байт в байт прежние, та же контрольная сумма                                      |
| новое, флаг включён  | установленная или откаченная | касса получает выпуск без полей и его контрольную сумму, ACK принимается, продажа как раньше |
| новое, флаг включён  | новая                        | касса получает поля, правило действует на расчёте, заказе и экране POS                       |

Экран POS разбирает меню по известным полям: прежний экран с новой кассой просто не показывает
причину (касса всё равно откажет с `ITEM_STOPPED`), новый экран со старым меню ведёт себя как
раньше.

## Порядок выпуска

1. Облако: API с этим кодом и выключенным флагом. Можно до или после кассы: без флага ничего не
   меняется; лишний ключ запроса от новой кассы установленный API игнорирует (читает только два
   ключа состояния меню с 08.10).
2. Касса: новый runtime (edge, воркер меню, POS) - после ожидающего выпуска runtime 022/023, в
   ночное окно, по действующему регламенту. До включения флага касса получает меню без полей и
   ведёт себя как раньше.
3. Данные владельца в кабинете (ниже).
4. Владелец включает `CATALOG_EDGE_COMBO_STOPS_ENABLED=true` в окружении API и перезапускает API.
5. Публикация меню из кабинета. Проверить: доставка «применено», в `/edge/v1/menu` кассы у комбо
   есть `combo_component_variant_ids`, на кассе стоп компонента делает комбо серым и расчёт
   отказывает.

## Откат

- Только поля: выключить флаг, опубликовать меню. Новая публикация без полей; касса применяет её.
- Откат кассы на прежний runtime: **сначала** выключить флаг и опубликовать меню, дождаться
  «применено», только потом откатывать. Причина: прежний runtime разбирает активное меню строго и
  с полями в активном меню не откроет POS. Если касса уже откачена с таким меню: опубликовать меню
  ещё раз - облако отдаст прежнему runtime вид без полей, после применения POS работает.
- Откат API на прежний образ: тоже сначала выключить флаг, опубликовать меню и дождаться
  «применено». Прежний API разбирает сохранённые выпуски строго: неподтверждённый выпуск с полями
  остановил бы выдачу меню, активный выпуск с полями сломал бы публичный `GET .../menu`.

## Что нужно от владельца

- Заполнить состав комбо (`combo_components`) в кабинете: в демонстрационном каталоге он пуст, без
  него стоп компонента (например, картофеля) комбо не закрывает. Заполнение состава меняет и
  кухонную раскладку облачных заказов (снимается признак `whole_product`): перед публикацией
  проверить `scripts/catalog-edge-parity.mjs --routing` и тестовый заказ.
- Проставить «Связанный товар» (`linked_product_id`) вариантам, чей id не совпадает с товаром:
  `cola-bottle`, `cola-can`, `cola-zero` -> `cola`; `piko-apple`, `piko-orange` -> `piko`;
  `iced-tea-sweet` / `iced-tea-unsweet` -> `iced-tea`; `fuse-*`. Варианты с тем же id, что у товара
  (`lemonade`, `water`, `piko`, `sauce`, `fingers`...), работают сразу после включения флага.
- Решение о включении флага после установки нового runtime кассы.

## Ограничения

- Стоп на товаре, который снят с публикации (нет в меню кассы), но остаётся компонентом комбо,
  тоже закрывает комбо - как в киоске и приложении. На кассе такой стоп не виден в стоп-листе
  (стоп-лист строится по меню) и снимается после повторной публикации товара. Экран кассы о нём не
  знает, отказ даёт касса при расчёте (`ITEM_STOPPED`).
- Вложенность компонентов учитывается до 5 уровней, как в облачном правиле.

### Что подтверждено

- Критерии линии выполнены: необязательные поля в снимке меню; правило на расчёте, заказе и экране
  POS; без полей набор id прежний; облачный флаг по умолчанию выключен и действует только вместе с

  обязательной группы, связанный товар, смешанные версии и неизменность контрольной суммы.
- Установленный API (`d6085655`): `edgeMenuState` читает только два ключа состояния, лишний ключ

- Старая касса не может получить поля: облако отдаёт ей вид без них. Даже если бы получила, strict
  разбор даёт `INVALID_MENU` с отклонённым ACK, а не остановку обмена.
- Повторы и смена runtime между pull и ACK: воркер сначала отправляет сохранённый ACK, потом
  делает pull, поэтому одно событие не приходит кассе в двух видах; ACK второго вида после первого -
  `CONFLICT` (inbox облака). Откаченный воркер читает активное меню без разбора JSON
  (`readActiveMenuState`) и может принять следующую публикацию: описанное восстановление работает.
- Тождества совпадают с `catalogStopView`: все товары каталога, до 5 уровней, `linked_product_id`,
  иначе товар с тем же id. Список компонентов не превышает 99 (в каталоге не больше 100 товаров),
  ограничение схемы 100 публикацию не ломает.
- Статус доставки («применено») не сравнивает контрольные суммы, поэтому работает для обоих видов.
  Публичный `GET /v1/branches/:id/menu` поля не показывает; других облачных маршрутов с телом
  выпуска нет. `/edge/v1/menu` читает только POS; установленный POS (Electron) берёт только
  известные поля, обслуживаемый экран - `v2/app.js` (`index.html`), старый `app.ts` не загружается.
- Миграций нет, гранты не меняются, секретов и реальных данных в diff нет, файлы чужих линий не
  тронуты.
