## API: подготовленный оператор

`infra/staging/release-stage2-1024.py`, отдельный коммит `2e5dd351` с тестами.

- Только API; ровно schema071 с контрольными суммами 069/070/071.
- Установленный compose проверяется по хешу; в `api` и `provision` добавляются
  три буквальных `"false"`. Все остальные строки и настройки сохраняются.
- Чистый опубликованный SHA, полная CI именно этого SHA, защищённая блокировка,
  неизменные соседи и права, зашифрованная копия, изолированное восстановление
  и запуск кандидата обязательны до переключения.
- Реальные платежи, публикация каталога, миграции и выдача прав не вызываются.
- `rollback` возвращает прежний образ и указатель, не восстанавливает рабочую БД.
  Включённые флаги этапа 2 запрещают откат; после их отдельного выключения нужно
  дождаться применения совместимого меню и только затем готовить откат.

**Предусловие до выпуска:** уже опубликованный API `c3a0fbee` с изменениями App Store
должен быть предком кандидата. Исходная ветка этапа 2 этого не содержит. Оператор
намеренно откажет до согласованной интеграции PR276 и обновления reviewed `ACCEPTED`
после проверки общего diff и CI. Нельзя обходить защиту заменой SHA без ревью.
Текущие хеши образа/compose/gateway и публичный указатель получают read-only перед
будущим разрешённым выпуском; в этом этапе сервер не проверялся и не менялся.

Шаблон команд после выполнения предусловий (параметры - из закрытого протокола):

```sh
python3 infra/staging/release-stage2-1024.py prepare \
  --sha "$SOURCE_SHA" --branch "$BRANCH" \
  --expected-api-sha c3a0fbeea69e3c94b4a0994f5cdee74ba98c77da \
  --expected-public-sha "$PUBLIC_SHA" --expected-api-image "$API_IMAGE" \
  --expected-compose-sha256 "$COMPOSE_HASH" --expected-gateway-sha256 "$GATEWAY_HASH" \
  --ssh-key "$SSH_KEY_PATH" --ci-proof "$CI_PROOF_PATH" \
  --backup-identity "$BACKUP_IDENTITY_PATH"
```

Без `--apply` только проверка. При отдельном разрешении владельца те же параметры
для `prepare --apply`, затем `apply --apply`. Откат - `rollback --apply` с теми же
закреплёнными значениями и владельцем блокировки; после сбоя сохранить receipt,
не удалять чужую блокировку. 069/070/071 выполняются отдельно по README.

## Касса: подготовленный оператор

`infra/windows/update-runtime-stage2-1024.ps1`, отдельный коммит `0923ab01` с тестами.
Охватывает четыре native-службы edge/fulfillment/menu/device-access, edge024,
аддитивное право cloud-link и копию базы в одном обслуживании.

До запуска нужны установленный runtime023 из своего кандидата, свежая проверенная
и восстановленная копия schema023, точная CI кандидата, проверенный ZIP, второй диск
или NAS. Receipt `pickchick-stage2-baseline-v1` получают при read-only инвентаризации:
`schema: 23`, `sourceCommit` установленного runtime, `branchId`, `computerName`,
`xmlHashes` четырёх служб в порядке edge/fulfillment/menu/device-access. Сам receipt
защищается NTFS ACL и закрепляется SHA-256. Он не содержит паролей.

```powershell
.\update-runtime-stage2-1024.ps1 -SourceCommit $sha `
  -RuntimeArchive $zip -RuntimeSha256 $zipHash -CiProof $ci `
  -BackupManifest $restoredBackup023 -BranchId $branch `
  -BaselineReceipt $baseline -BaselineSha256 $baselineHash `
  -BackupDestination $secondLocation
```

Без `-Apply` нет постоянных изменений. Проверяются provenance, каждый файл ZIP,
предыдущие 23 миграции и установленный runtime, конфигурации, службы, права и backup.
При отдельном разрешении повтор с `-Apply`:

1. Проверить и переустановить закреплённый backup-инструмент с поддержкой024.
   Существующие ключи, destination, retention и heartbeat сохраняются; первая
   установка оставляет heartbeat выключенным. Дождаться свежей копии023.
2. Отключить расписание, дождаться завершения активной копии, взять общий maintenance
   lock. До остановки служб повторно проверить baseline. Архив распаковать в новый
   неизменяемый каталог, исходные XML сохранить в защищённый протокол.
3. Остановить всех пяти писателей, включая KitchenLink. Проверить и применить024,
   проверить сохранение данных, применить только аддитивный cloud-link, сменить XML.
4. Запустить службы в обратном порядке, проверить readiness, процессы, ledger024,
   неизменность конфигураций/идентичностей и соседей. Возобновить расписание и проверить
   новую зашифрованную копию именно024. Только после этого записать completed.

При частичной остановке исходные службы восстанавливаются. При чужом XML службы
остаются остановленными для проверки. До запуска кандидата сбой замены XML откатывает
привязки; после запуска автоматического возврата старых читателей нет. Откат runtime
вручную по отдельному решению: флаги и совместимое меню сначала, затем закреплённые
исходные XML/образ, readiness и проверка копии. Схему024 и новый backup-инструмент оставить.

**Граница:** Electron POS v2/оболочка - отдельный пользовательский установщик
из Windows POS package того же SHA. Этот административный оператор не запускает
per-user NSIS от администратора и не закрывает кассовый сеанс. Установку оболочки
нужно включить в то же согласованное окно, сохранив userData, и проверить исходный
SHA по `verification.json`. До этого приёмка всего этапа на кассе не завершена.
Проверки PowerShell с подменённым SCM не являются установкой на настоящую Windows.
