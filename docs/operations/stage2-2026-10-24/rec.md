# Ежедневная сверка оплат - черновик для бухгалтера (этап 2, полоса rec)

Ветка `codex/daily-reconciliation-1024` от `4cc11e05`. Задача roadmap `payments-reconcile`,
критерий AC-35: у каждой суммы есть объяснение; необработанные расхождения видны и назначены
ответственному. Состояние: **реализовано и проверено локально** на свежей базе; **не установлено**
на VPS; реальная выписка банка не использовалась; приёмка владельцем и бухгалтером не проводилась.

## Что сделано

В кабинете на странице «Оплаты и чеки» сверху появился раздел «Ежедневная сверка оплат» (только при
включённом флаге; иначе страница выглядит как раньше). Один экран - один день по времени Алматы
(календарные сутки 00:00-24:00 Asia/Almaty).

1. **По способам оплаты.** Kaspi: счёт на телефон (приложение и киоск), Kaspi QR на киоске, ручные
   возвраты в Kaspi Pay, Kaspi Smart POS на кассе, TipTopPay (карта), наличные на кассе, «Kaspi:
   способ не определён» и «Другие провайдеры» (только если есть данные). Для каждого: заказов
   оплачено, оплаты, возвраты, подарки (скидка Pick Combo), ожидаемая сумма, банк/итог, разница,
   откуда данные банка. Подарочные заказы за 0 ₸ и тестовые платежи TipTopPay (песочница)
   показаны отдельно и в деньгах не участвуют.
2. **Внешние факты.**
   - Загрузка выписки CSV через **профиль колонок** (источник, кодировка UTF-8/Windows-1251,
     разделитель, строки до заголовка, колонки даты/времени/суммы/комиссии/номера операции/
     ссылки/способа/типа/описания, формат даты, десятичный разделитель, тенге или тиыны, значения
     «возврат», значения способа, пропуск строк «Итого», окно сопоставления). Формат Kaspi Pay не
     выдуман: профиль задаёт бухгалтер. Перед загрузкой - «Проверить файл»: ошибки по строкам,
     дни и суммы, первые строки, уже загруженные операции. Пример синтетического файла:
     [rec-sample-statement.csv](rec-sample-statement.csv), профиль к нему - ниже.
   - **Итог вручную** банка или ККМ за день по способу оплаты с обязательным комментарием;
     исправление отменяет прежний итог (история сохраняется).
3. **Сопоставление.** Сначала по номеру операции или номеру счёта (ссылке) внутри одного источника,
   иначе по сумме и времени (окно по умолчанию 10 минут; только если у одной из сторон нет номера).
   Состояния: совпадает, поздно/другой день, сумма отличается, нет в банке, нет в PickChick,
   повтор. Источники не смешиваются (строка TipTopPay не закроет оплату Kaspi). Номер операции
   сравнивается с учётом направления денег: строка возврата под номером исходной оплаты - это
   возврат (деньги ушли), а не повтор строки, и с оплатой в пару не встаёт.
4. **Решения.** У каждого расхождения - ответственный (сотрудник с доступом к кабинету точки),
   статус (открыто, в работе, решено, принято с причиной) и комментарий. Статусы «в работе»,
   «решено» и «принято» без ответственного не сохраняются. Решение привязано к
   состоянию и сумме: если пришли новые данные и расхождение изменилось, оно снова открыто
   (прежнее решение видно как устаревшее). Можно принять все показанные с одной причиной.
5. **Закрытие дня.** Только после окончания дня и когда все расхождения решены или приняты.
   Закрытый день неизменен: снимок отчёта хранится, любые записи на этот день отклоняются.
   Если после закрытия пришли новые данные (поздняя оплата, строка выписки), экран это показывает;
   учесть их можно только открыв день заново с причиной. Все действия - в журнале аудита кабинета.
6. **CSV для бухгалтера** - кнопка «Выгрузить CSV» (UTF-8 с BOM, разделитель `;`, открывается в
   Excel). Колонки описаны ниже.
7. **Роли.** Управляющий точки и назначенный бухгалтер изменяют; аналитик только смотрит.
   Бухгалтер - это сотрудник с доступом «аналитик», которого оператор назначил бухгалтером сверки
   (остальные разделы для него остаются только на просмотр; роли кабинета не менялись).

## Формы для бухгалтера (на утверждение владельцу)

### Таблица «По способам оплаты»

| Колонка      | Что означает                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------- |
| Способ       | Способ оплаты (см. список выше)                                                                    |
| Заказов      | Сколько разных заказов получили оплату за день этим способом                                       |
| Оплаты       | Сумма подтверждённых банком оплат за день (по времени оплаты)                                      |
| Возвраты     | Сумма подтверждённых возвратов за день; ручные возвраты Kaspi Pay - отдельной строкой              |
| Подарки      | Скидка подарком Pick Combo в оплаченных заказах (денег нет, для справки)                           |
| Ожидается    | Оплаты минус возвраты. «-» - PickChick этот способ пока не учитывает (наличные, Kaspi Smart POS)   |
| Банк / итог  | Сумма строк выписки за день (повторы строк не считаются) или итог банка/ККМ, введённый вручную     |
| Разница      | Банк (или итог) минус ожидаемое. Каждый тенге разницы объяснён строками в «Расхождения и операции» |
| Данные банка | «Выписка» - загружена выписка этого источника за день; «Итог вручную»; «Нет данных банка»          |

### Строки «Расхождения и операции» и знак разницы

| Состояние / правило                   | Разница за день                                              | Что делать                              |
| ------------------------------------- | ------------------------------------------------------------ | --------------------------------------- |
| Совпадает (по номеру / сумме-времени) | 0                                                            | Ничего                                  |
| Поздно / другой день                  | Для дня PickChick: минус сумма; для дня банка: плюс сумма    | Пояснить (обычно оплата около полуночи) |
| Сумма отличается                      | Банк минус PickChick                                         | Найти причину, решить или принять       |
| Нет в банке                           | Минус сумма PickChick                                        | Проверить выписку/банк                  |
| Нет в PickChick                       | Плюс сумма банка                                             | Например, оплата на терминале кассы     |
| Повтор строки выписки                 | 0, строка не входит в сумму банка                            | Принять как повтор                      |
| Повтор: двойная оплата заказа         | Сколько получено сверх суммы заказа                          | Сделать возврат или пояснить            |
| Нет данных банка (на весь способ)     | Минус ожидаемое                                              | Загрузить выписку или ввести итог       |
| Итог вручную                          | Итог минус ожидаемое; для неучитываемых способов - весь итог | Пояснить разницу                        |
| Закрытие кассовой смены               | Пересчёт минус ожидаемое в кассе (данные кассы)              | Пояснить недостачу/излишек              |

### CSV «Выгрузить CSV»

Одна таблица. Строки трёх типов: «Итог по способу» (по одной на способ), «Подарки без оплаты»,
«Операция» / «Итог вручную» / «Проверка дня» (по одной на каждую строку сверки, включая совпавшие).

| Колонка                                    | Содержание                                                                              |
| ------------------------------------------ | --------------------------------------------------------------------------------------- |
| День                                       | Дата сверки ГГГГ-ММ-ДД (Алматы)                                                         |
| Тип строки                                 | Итог по способу / Подарки без оплаты / Операция / Итог вручную / Проверка дня           |
| Способ оплаты                              | Название способа                                                                        |
| Состояние                                  | Для итога - откуда данные банка; для операции - состояние сверки                        |
| Правило сопоставления                      | По номеру операции, по сумме и времени, пара не найдена и т.д.                          |
| Время PickChick                            | Время оплаты/возврата по Алматы                                                         |
| Сумма PickChick, ₸                         | Для итога - ожидаемая сумма; для операции - сумма в PickChick (возврат со знаком минус) |
| Заказ                                      | Номер заказа PickChick (UUID)                                                           |
| Операция PickChick                         | Номер операции от банковского адаптера (`kaspi:` и `manual:` - служебные префиксы)      |
| Время банка                                | Время строки выписки по Алматы (для итога вручную - время ввода)                        |
| Сумма банка / итог, ₸                      | Сумма строки выписки или итог банка/ККМ                                                 |
| Операция банка, Ссылка банка               | Номер операции и номер счёта/ссылка из выписки                                          |
| Комиссия банка, ₸                          | Комиссия из выписки, если есть колонка (в сверке не участвует, для справки)             |
| Разница, ₸                                 | Разница за этот день (см. таблицу знаков выше)                                          |
| Пояснение                                  | Текст сверки, комментарий к итогу, описание из выписки (телефоны скрыты)                |
| Ответственный, Статус решения, Комментарий | Решение по расхождению; «Не решено» - решения нет или оно устарело                      |

Суммы - числа с запятой без пробелов («-3000,00»), чтобы Excel считал их числами.

## Миграции и права

- Cloud **071** `071_cloud_daily_reconciliation.sql`: только новые таблицы `bo_rec_*` (бухгалтеры
  сверки, профили, загрузки и их отмены, строки выписки, итоги и их отмены, решения, события
  закрытия, журнал команд). Денежные таблицы не меняются. Всё, кроме профилей и решений,
  только добавляется (триггер `commerce_immutable`).
- Права: `infra/staging/reconciliation-grants.mjs` (`reconciliationGrants`), подключён в
  `infra/staging/provision.mjs` **после** `customerCheckoutGrants` (тот отзывает права на
  `commerce_kaspi_invoices`). Чтение своих таблиц, добавление записей, UPDATE только колонок
  профиля и решения; по столбцам - чтение номера счёта Kaspi (`attempt_id, reference,
operation_id`) и итогов песочницы TipTopPay. Назначать бухгалтеров, менять оплаты, возвраты и
  заказы роль API не может (проверено тестом с ограниченной ролью).

## Установка и откат

1. Применить cloud 071 (охраняемой процедурой облачных миграций). **Порядок:** если вместе с этой
   веткой выпускается cloud 070 (полоса cfg), сначала 070, потом 071 - ledger миграций отклоняет
   номер меньше уже применённого.
2. Выпустить API этой ветки (контроллер `reconciliation`, лимит тела 320 KB только для
   `reconciliation/preview|commands`) и кабинет (новые файлы `reconciliation-model.js`,
   `components/ReconciliationView.js`, `server.mjs`: маршруты и ответ дня до 4 MB).
3. Выдать права `reconciliationGrants('pickchick_app', true)` после прав оформления заказов и
   поставить `BACKOFFICE_RECONCILIATION_ENABLED=true`. Отдельного охраняемого production-скрипта
   выпуска полоса не писала (скрипты выпуска - за интеграцией/владельцем).
4. Назначить бухгалтера: сотрудник получает доступ «аналитик» (`scripts/backoffice-setup.mjs
--role analyst`), затем оператор:
   `node --env-file=.env scripts/reconciliation-accountant.mjs --actor <UUID> --branch <UUID> --enabled true`.

Откат: `BACKOFFICE_RECONCILIATION_ENABLED=false` (раздел скрывается, маршруты 503) и
`reconciliationGrants(..., false)`; таблицы 071 остаются, данные не теряются. Старый кабинет и
старый API совместимы: новый кабинет со старым API раздел не показывает (404), установленные
клиенты, касса и edge не затронуты.

## Что нужно от владельца

1. Образец выписки Kaspi Pay (без персональных данных): колонки, кодировка, часовой пояс, как
   показаны возвраты, комиссия (из суммы или отдельно), попадают ли в одну выписку счета, QR и
   Smart POS, есть ли номер операции, совпадающий с номером в Kaspi.
2. Формат отчёта TipTopPay для сверки и Z-отчёта ККМ (если их будут загружать, а не вводить итог).
3. Кто бухгалтер в кабинете (учётная запись), кто ответственные по умолчанию.
4. Утвердить: бизнес-день = календарные сутки по Алматы (не кассовая смена), окно 10 минут,
   формы и колонки выше, правило «закрыть день можно только когда всё решено или принято».
5. Политика учёта наличных и Kaspi Smart POS: пока касса не передаёт оплаты, они сверяются только
   итогом вручную.

## Ревью техлида (24.10.2026)

Проверено по `git diff origin/codex/shared-development..HEAD`: критерии полосы (способы оплаты,
импорт с профилем, итог вручную, правила сопоставления и состояния, ответственный/статус/
комментарий, закрытие и повторное открытие с причиной, CSV, роли, флаг, cloud 071 + права),
гонки и повторы (блокировка на точку, журнал `request_id`, отпечаток запроса, оптимистичные
ревизии), перезапуск кабинета (неподтверждённая команда хранится и повторяется тем же номером),
старые клиенты (кабинет без API скрывает раздел, касса и edge не затронуты), время Алматы
(в PostgreSQL и Node одна и та же база часовых поясов: образ `postgres:18.3-alpine` закреплён
и в staging), инварианты денег (целые тиыны, разница по способу объяснена строками), права
(только свои таблицы, UPDATE лишь колонок профиля и решения, без записи в денежные таблицы;
отзыв столбцовых прав на `commerce_kaspi_invoices` не трогает табличное право оформления заказа),
миграция только добавляет таблицы. Факты Kaspi/ККМ не выдуманы: формат выписки задаётся профилем.

Исправлено в ревью (отдельные коммиты):

1. Строка возврата с номером исходной оплаты считалась «повтором строки выписки»: сумма 0, не
   входила в сумму банка, пояснение вводило в заблуждение; без строки оплаты такая строка
   вставала в пару с оплатой как «сумма отличается». Теперь повтор и пара по номеру - только при
   одинаковом направлении денег (unit-тест).
2. Перекрывающаяся выписка отклонялась целиком, если хотя бы одна её строка приходилась на
   закрытый день, даже когда эта строка уже была загружена и была бы пропущена. Теперь открытыми
   должны быть только дни, в которые добавляются новые строки; «Проверить файл» показывает
   новые строки по дням, кабинет блокирует загрузку только при новых строках закрытого дня
   (старый API без этого поля блокирует как раньше). Тест PostgreSQL: после закрытия дня
   перекрывающаяся выписка добавляет только строку открытого дня, дрейфа нет.
3. AC-35 («назначены ответственному»): решение «в работе», «решено» или «принято» можно было
   сохранить без ответственного. Теперь сервер отвечает `ASSIGNEE_REQUIRED`, кабинет просит
   назначить ответственного (массовое принятие и раньше ставило текущего сотрудника).

Остаётся (не блокирует черновик, решается с владельцем или интеграцией):

- Охраняемый production-скрипт выпуска cloud 071 и прав - за интеграцией; 070 (cfg) раньше 071.
- Ответ дня ограничен 4 MB в прокси: примерно 5000 строк выписки за день. Для одной точки
  достаточно; при росте нужна постраничная выдача строк.
- Итог вручную при уже загруженной выписке того же источника даёт отдельную строку сравнения
  итога с ожиданием (двойное объяснение одной разницы); бухгалтеру проще отменить лишний итог.
- Попытки оплаты с неизвестным результатом показываются по способу, но закрытие дня не
  блокируют: без выписки такая оплата не станет расхождением.
- Решения привязаны к строке выписки: после отмены загрузки и повторной загрузки файла решения
  по прежним строкам не переносятся.

## Что не проверено
