# Облако сейчас: 072-077 и раздел «Расходы» одним окном (решение владельца 11.11)

11.11 владелец попросил поставить раздел «Расходы» сразу, не дожидаясь 19.11. Ресторан пока
работает на iiko, облачный сервер в работе точки не участвует, поэтому окно можно проводить в
любое время. Порядок для исполнителя (Codex). Основа: `cloud-1-handover-1110.md` (сервер,
архив, проба), шаги 2 и 8 `cutover-2026-11-19.md`, раздел второй волны там же,
`backoffice-expenses.md`.

## 1. Зависимость

На сервере схема 071. Миграции идут строго по порядку, у каждой свой охраняемый шаг:

| Шаг      | Что ставит                       | Команда                                           |
| -------- | -------------------------------- | ------------------------------------------------- |
| 072      | восстановление очереди           | `queue-recovery-cloud-owner.mjs inspect`, `apply` |
| 073, 074 | продажи кассы, переход бэк-офиса | `cutover-cloud-owner.mjs inspect`, `deploy`       |
| 075      | бэк-офис P1                      | `inspect-075`, `deploy-075`                       |
| 076      | вторая волна бэк-офиса           | `inspect-076`, `deploy-076`                       |
| 077      | «Расходы»                        | `inspect-077`, `deploy-077`                       |

Все шаги ставят только новые таблицы и колонки с выключенными флагами; прежний API на новой
схеме работает. Полный `provision.mjs` на сервере не запускать.

## 2. Кандидат

Голова `codex/cutover-1119` после слияния PR #353 («Расходы») с зелёной полной Foundation CI.
Архив исходников для образа собирается той же командой, что в `cloud-1-handover-1110.md` §2,
на этом точном коммите. Байты 077 закреплены в `EXPENSES_CHECKSUM`
(`af585ccadaed5ea51e416a904e2e729308904a949a16ae34d88a7aee076b6988`).

## 3. Проба на копии базы

Как `cloud-1-handover-1110.md` §3, плюс после `deploy-076`:

- `node infra/staging/cutover-cloud-owner.mjs inspect-077` (ожидается `ledger: schema076`,
  `pending: [077_cloud_backoffice_expenses.sql]`), затем `deploy-077` (ожидается
  `applied: [077…]`, `expenses: false`, `privilegesAdded: []`).
- `expenses-grants on` (ожидается добавление прав только на шесть таблиц `bo_expense_*`), затем
  `expenses-grants off` (ровно обратная разница).
- API кандидата на пробной базе с `BACKOFFICE_EXPENSES_ENABLED=true` (и правами `on`):
  `GET /v1/admin/backoffice/expenses/meta` с токеном владельца отвечает 200 и ролью `director`.

## 4. Живое окно

До окна подготовить также канонический кабинет `https://pickchick.kz/backoffice/`.
Его обслуживает отдельный `pickchick-staff-login` с UI и HTTP allowlist внутри образа:
замена `public-web/backoffice` обновляет только gateway/nip.io. Использовать штатные
`infra/backoffice-login/prepare.py` и `update.py` по
[device-access-backoffice.md](device-access-backoffice.md), тот же источник и полную CI.
Prepare требует Python 3.12+, опубликованную чистую ветку и закреплённые Node/corepack pnpm.
В окне 12.11 портал обновлён до миграций, затем остановлен вместе с API. Его update-оператор
имеет собственную общую release lock: не запускать его внутри уже взятой блокировки.
Аккаунты/пароли сохраняются; после обновления потребуется повторный вход.

1. Проверить `current` и SHA-256 compose (`cloud-1-handover-1110.md` §1). Иначе стоп.
2. Свежая копия базы (`pickchick-backup.service`), сверка манифеста, пробное восстановление.
3. Блокировка выпуска и штатный cleanup flock. Закрыть наш gateway, затем остановить
   `pickchick-staff-login`, который проксирует API напрямую, и только затем API.
   Gateway maintenance не закрывает канонический кабинет: `/backoffice/` на api-домене
   перенаправляется туда через 308. Проверить закрытие обоих путей и отсутствие пишущих
   сессий перед миграциями. Внешний Caddy не менять.
4. 072 (`queue-recovery-cloud-owner.mjs inspect`, `apply`).
5. `cutover-cloud-owner.mjs`: `inspect`, `deploy`; `inspect-075`, `deploy-075`;
   `inspect-076`, `deploy-076`; `inspect-077`, `deploy-077`. Каждый ответ в протокол.
6. Окружение API, каждый раз новый файл и оба SHA-256 в протокол:
   `compose-candidate` → `compose-supply` → `compose-expenses` (добавляет
   `BACKOFFICE_EXPENSES_ENABLED: "false"` в сервис `api`).
   Установленный выпуск 6630eb0f содержит resolved JSON без `provision`. Для него нужен
   кандидат с поддержкой этого формата в тех же командах. Они сохраняют все прежние
   значения, образ и соседние сервисы; добавляют только флаги в `api`. JSON должен быть
   каноническим (отступ 2, перевод строки в конце), с сервисами `api`, `cloud-db`,
   `redis-cache`. SHA-256 сверяется до преобразования; повтор шага и неизвестная
   структура отклоняются. Полный `provision.mjs` и добавление сервиса `provision`
   не нужны. Новую ссылку на проверенный образ API устанавливает шаг 7 отдельно.
7. Релиз `releases/<sha>`, образ, переключение `current`, запуск API со всеми флагами выключенными.
   Проверки старого потока: `/health/ready`, заказ приложения и киоска, кухня, кабинет.
8. Веб-кабинет и шлюз из того же коммита: экраны «Расходы» живут в бандле `apps/backoffice`,
   маршрут `/v1/admin/backoffice/expenses/*` в `infra/public-staging/gateway.Caddyfile`. Отдельный
   выпуск `pickchick-public-gateway` по прежнему порядку web-выпусков
   (`docs/operations/operations-ui-release.md`, сборка `infra/public-staging/prepare-web.py`):
   новый public-web и точный expenses-блок из Caddyfile репозитория, добавленный к фактически
   установленному файлу. Сохранить checkout/support/legal/desktop-updates и все сети;
   полная замена шаблоном может удалить уже выпущенные маршруты. `caddy validate`, перезапуск только шлюза, проверка
   mount и static smoke. API и база этим шагом не меняются. Без этого шага статический
   кабинет gateway/nip.io остаётся прежним, а шлюз не пропускает запросы расходов.
   Канонический кабинет обновляется отдельно через staff-login, как указано выше.
9. Включение раздела: `expenses-grants on`, затем
   `compose-flag expenses true --compose <файл шага 6> --sha256 <его hash> --out <новый>`,
   перезапуск API с этим compose. В кабинете появляется «Расходы» вместо «Финансы».
   Нужен `BACKOFFICE_ENABLED=true` (он на сервере уже задан, сверить).
   Запустить подготовленный staff-login, проверить его здоровье и точные app/api/expenses
   JS/CSS на `pickchick.kz`, а также expenses/meta 200 с ролью владельца. После всех проверок
   освободить только свои блокировки. Фактический compose с включёнными расходами должен
   стать effective `compose.yaml`; сохранить выключенную копию и оба hash для отката.
10. Проверка владельцем: вход в кабинет, раздел «Расходы», ввод одной суммы, она видна в журнале.

Флаги перехода (продажи кассы, роли, склад и прочие) этим окном не включаются: только «Расходы».

## 5. Откат

- Только раздел: `compose-flag expenses false`, перезапуск API, затем `expenses-grants off`.
- Веб-кабинет: прежний Compose шлюза и прежний public pointer (порядок web-выпуска).
- Весь выпуск: `current` на прежний релиз и прежний compose. Схему не откатывать: 072-077 только
  добавляют таблицы и колонки.
