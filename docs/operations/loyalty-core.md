# Серверное ядро Чиков

`@pickchick/loyalty-core` и `010_cloud_loyalty.sql` реализуют внутренний
PostgreSQL-репозиторий бонусного кошелька. Это коммерческий контур, отдельный от
TEST actors/orders и локальных демонстрационных Чиков. HTTP, интерфейс кошелька,
игры, push и подключение финансовых событий ещё не включены. Пакет не вызывает
банки, SMS, ККМ или VPS и не создаёт программу автоматически.

## Доверие и правила

`TrustedLoyaltyContext = { organizationId, branchId, actorId, authority }`
создаётся сервером после аутентификации и проверки полномочий. `authority` —
`manager`, `checkout`, `fulfillment`, `refund` или `scheduler`. Контекст нельзя
принимать из клиентского JSON. Репозиторий проверяет принадлежность точки сети;
источник события дополнительно обязан проверить заказ, покупателя, точку,
завершение выдачи/банковской операции и допустимые суммы.

`AuthenticatedLoyaltyCustomer = { organizationId, customerId }` — порт чтения
для уже аутентифицированного покупателя. Нет поиска по телефону и списания по
номеру, введённому на киоске. Общий кошелёк принадлежит паре сеть/покупатель;
точки одной сети используют один баланс. Коммерческий `orderId` — UUID
доверенного cloud/edge-владельца. Ссылка намеренно не ссылается на TEST-таблицы
и не требует cloud-commerce order: POS/kiosk остаются edge-owned по ТЗ.

Программа создаётся только менеджером с обязательными `version`,
`approvalReference`, `reason` и всеми правилами. Создание не активирует её;
`activateProgram` записывает отдельное неизменяемое решение. Конфигурация версии
не редактируется. Исторические выдачи/возвраты используют закреплённую версию,
которая ранее действительно была активирована. Новый резерв требует текущую
активную версию.

| Обязательное правило                  | Поддерживаемое поведение                                                         |
| ------------------------------------- | -------------------------------------------------------------------------------- |
| `earnBasisPoints`                     | Начисление: `floor(eligibleMinor × bps / (10000 × pointValueMinor))`             |
| `pointValueMinor`                     | Стоимость одного целого Чика в минимальных единицах денег                        |
| `maxRedemptionBasisPoints`            | Лимит: `floor(eligibleOrderMinor × bps / (10000 × pointValueMinor))`             |
| `lotTtlDays`                          | `null` либо срок 1–3650 суток по 24 часа с момента начисления                    |
| `refundSpentExpiry: 'new_lot_ttl'`    | Возврат потраченных баллов создаёт новую партию со сроком закреплённой программы |
| `expiredEarnRefund: 'ignore_expired'` | Уже истёкшие начисления не списываются второй раз при возврате заказа            |

Последние два значения — явно поддерживаемые политики, которые нужно утвердить,
а не универсальные бизнес-правила. Иные политики сначала требуют реализации и
тестов. 7%, 300 баллов, уровни и игровые награды из макета не являются defaults.
Здесь не реализованы подарочные начисления за регистрацию/день рождения, уровни,
промо-исключения, рефералы, rounding по строкам или распределение денежного
возврата по товарам. Точное `originalEligibleMinor` формирует доверенный pricing/
financial слой с учётом утверждённых исключений и скидок; он неизменяем для заказа.

## Внутренние методы

Все изменяющие методы принимают `(context, commandKey, input)`. `commandKey` —
UUID. SHA-256 канонического тела включает операцию и весь контекст. Одинаковая
команда возвращает сохранённый результат, изменённое тело даёт `CONFLICT`.
Сохранённый ответ — снимок на момент команды; актуальный баланс получают через
`readWallet`. Отдельные уникальные ссылки дедуплицируют фактическое событие даже
при новом ключе доставки.

| Метод                                       | Полномочие и смысл                                                                                                          |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `createApprovedProgram` / `activateProgram` | manager: явное утверждение и активация версии                                                                               |
| `earnFulfilledOrder`                        | fulfillment: `{ customerId, programId, orderId, originalEligibleMinor, fulfillmentEventId }`; один reward на выданный заказ |
| `refundEarned`                              | refund: те же ссылки, `sourceRefundId`, `eligibleRefundMinor`; суммарный возврат не больше исходной базы                    |
| `reserveRedemption`                         | checkout: `{ customerId, programId, orderId, points, eligibleOrderMinor }`; атомарный резерв, ответ содержит `holdId`       |
| `captureRedemption`                         | checkout: `{ customerId, holdId, sourceCaptureId }`; доверенное окончательное списание резерва                              |
| `releaseRedemption`                         | checkout/refund/manager: `{ customerId, holdId, resolutionReference, reason }`; явное подтверждённое разрешение             |
| `refundRedemption`                          | refund: `{ customerId, holdId, sourceRefundId, points }`; возврат ранее списанного, в том числе запись до получения capture |
| `adjust`                                    | manager: `{ customerId, programId, deltaPoints, reason }`; подписанная коррекция с причиной, без удаления истории           |
| `expire`                                    | scheduler: `customerId`; истечение свободных партий                                                                         |
| `readWallet`                                | authenticated customer: баланс, резерв, доступно, долг, версия; `null`, если кошелька нет                                   |

Суммы денег и количество Чиков в JSON — десятичные строки целых чисел; внутри
используется `BigInt`, в PostgreSQL — `bigint`. Дробные значения, отрицательные
цены, экспоненциальная запись, лишние поля и суммы за пределами
9 000 000 000 000 000 отвергаются. Отрицательным может быть только adjustment/
баланс. Причины обязательны, пробелы без текста не принимаются.

`captureRedemption` не подтверждает оплату клиента. Его вызывает orchestration
после проверенного банковского/кассового события. `releaseRedemption` допускается
только после окончательного отказа/отмены до отправки, а не по таймеру или при
`unknown`. У резерва нет автоматического TTL. Поздний capture после уже
разрешённого резерва возвращает `CONFLICT`: адаптер должен отправить событие на
сверку, а не повторно тратить освобождённые баллы. Внешний финансовый inbox должен
сохранить такой конфликт и фактическое движение денег независимо от loyalty.

Один заказ получает один hold, включая завершённый hold. Нельзя переиспользовать
отменённый заказ для нового резерва. Capture ID уникален в сети; повтор фактической
операции на другом hold откатывает всю вторую транзакцию. `sourceRefundId` имеет
отдельные пространства для reversal начисления и restoration списания: один
денежный возврат может законно породить оба эффекта.

## Учёт, порядок событий и истечение

Кошелёк блокируется `FOR UPDATE`. Параллельные команды одного покупателя
сериализуются; разные кошельки не блокируют друг друга глобально. Неизменяемые
таблицы хранят ledger, команды, исходные order/refund ссылки, аллокации,
движения партий и решения по программе. Баланс, партии и hold status —
проверяемые изменяемые проекции, а не переписываемая финансовая история.

- `available = max(0, balance − reserved)`.
- Сумма ledger равна balance; сумма активных hold равна reserved.
- Для каждой партии: `initial = remaining + redeemed + expired + revoked + debtSettled`.
- Для кошелька: `balance = Σ(remaining − pendingRevocation) − debt`.
- Held allocations соответствуют held points партий. Новые аллокации — FIFO
  по монотонному `sequence` партии. Внутри одного кошелька создание сериализовано.
- Deferred SQL constraints проверяют эти равенства в финальном состоянии
  транзакции; несогласованные прямые UPDATE откатываются.

При возврате до выдачи сохраняется база/возвращённая часть заказа без начисления.
Последующая выдача начисляет только оставшуюся долю. Возвраты после выдачи
уменьшают итоговое целочисленное право, а не округляют каждый возврат отдельно.
Это даёт одинаковый результат независимо от порядка доставки событий.

При возврате начисленных Чиков сначала учитывается уже истёкшая часть без второго
дебета, затем свободные баллы, затем помечаются удержанные баллы. Потраченное
становится долгом. Новые начисления погашают долг; это движение партии без нового
дебета ledger. Поэтому последующее истечение не может списать погашенный долг
повторно.

Пример: начислили 100, удержали 80, вернули исходный заказ полностью. Баланс 0,
резерв 80. При release помеченные 80 удаляются без второго дебета: баланс 0.
При capture списание 80 создаёт долг 80: баланс −80. Если до capture уже пришло
новое начисление 100, из него погашаются эти 80, остаётся 20. Этот случай проверен
в реальном PostgreSQL, включая последующее истечение.

Истечение затрагивает только свободный остаток. Удержанная часть сохраняется до
release/capture. При release помеченное отзывается без нового дебета, оставшаяся
уже просроченная часть истекает один раз. Если одна партия обслуживает несколько
hold, её pending revocation разрешается по мере фактического разрешения hold;
суммарное право кошелька остаётся тем же. Capture удержанного разрешён даже после
срока партии. RefundRedemption до capture только записывается как pending,
блокирует release и не создаёт баллов; capture применяет его один раз атомарно.
Сумма pending + применённых возвратов не превосходит исходный hold.

Чтение и изменение кошелька делают ленивое истечение. Scheduler должен также
обходить открытые просроченные партии. Время по умолчанию приходит из PostgreSQL;
`clock` в конструкторе — внутренняя тестовая зависимость, которую production
bootstrap не передаёт. Клиент не выбирает время, TTL или сумму начисления.

После удаления identity закрыты чтение, новые резервы и начисления за новые
выдачи. Завершение capture/release/refund/expiry и документированная коррекция
существующего кошелька остаются доступны доверенным внутренним обработчикам:
удаление профиля не уничтожает финансовый долг. Новый кошелёк удалённому identity
не создаётся. Будущая integration inbox должна отдельно разрешать позднюю выдачу
удалённого профиля, не автоматически повторять запрещённое начисление.

## Внедрение и проверки

Миграция зависит от foundation и `007_cloud_customer_identity.sql`, не от TEST
и не от 008/009. В объединённом репозитории применять полный последовательный
набор миграций: **не применять 010 на сервере раньше ещё ожидающих 008/009**.
Мигратор отклоняет изменённые/пропущенные уже применённые файлы и вставку старой
версии после новой. В миграции нет активной программы и начальных балансов.

DDL выполняет migration owner. Runtime роли нужны SELECT identity/branches и
loyalty, INSERT журналов/проекций, UPDATE только active_programs/wallets/lots/
holds/rewards, USAGE sequence. Не выдавать DDL, DELETE, TRUNCATE, UPDATE identity,
владение таблицами или обход триггеров. Возможности manager следует дополнительно
разделить в серверной авторизации; SQL grants сами по себе не аутентифицируют
переданный TypeScript context. Тест проверяет работу с ограниченной ролью.

Журнал не очищается по TTL. Ошибки исправляются компенсирующими операциями с
причиной. Откат приложения оставляет новые таблицы и запрещает новые команды;
не удалять таблицы/ledger как способ rollback. Сначала совместимость старого
runtime и восстановление backup в отдельной среде, затем rollout. Production
миграция, runtime grants и backup/restore этого нового пакета ещё не выполнялись.

```sh
pnpm --filter @pickchick/database build
pnpm --filter @pickchick/loyalty-core build
pnpm --filter @pickchick/loyalty-core test
pnpm --filter @pickchick/loyalty-core test:integration
```

Интеграционные тесты используют только localhost из `LOYALTY_TEST_DATABASE_URL`
или открытый synthetic local default, каждый тест — отдельную временную schema.
В конце удаляется только созданная им schema, не строки работающего кошелька.
Не читаются private `.env`, не отправляются реальные события.

Проверено 22 PostgreSQL и 3 unit сценария: двойная трата, повтор и конфликт
команды/источника, FIFO, округление и возврат до выдачи, параллельные частичные
возвраты, debt после расхода и удержания, expiry/hold race, pending restoration,
удалённая identity, разные точки/покупатели, immutable guards, runtime grants и
откат всей транзакции после искусственного сбоя.

Остаются integration worker из commerce/edge outbox с безопасным повтором и
reconciliation очередью, серверный расчёт eligible/refund amounts, customer HTTP
и история с пагинацией, backoffice согласование программы и коррекции, сценарий
подтверждения владельца киоскового кошелька, уведомления и UI, игры AC26,
операционный scheduler, мониторинг сверки ledger/projections и нагрузочные
испытания. Проверки инвариантов сканируют историю конкретного кошелька; их
стоимость на длинной истории нужно измерить до заявлений о целевом масштабе.
При отсутствии связи с cloud новый расход Чиков запрещён; edge не создаёт
локальную копию сетевого баланса для самостоятельного списания.
