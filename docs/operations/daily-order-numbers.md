# Ежедневные номера заказа

Решение владельца 25 сентября 2026: убрать видимый префикс `T-` и ведущие нули;
начинать каждый календарный день с 1 по времени Алматы.

Новый клиент получает `1`, `2`, `3` через `number_format=daily`. Номер назначается
один раз в PostgreSQL в транзакции создания заказа. День определяется по
`created_at` сервера и `branches.timezone` (`Asia/Almaty`), граница - 00:00.
Счётчик отдельный для точки и даты. Отмена/выдача не переиспользует номер,
повтор команды возвращает прежний номер, rollback не расходует его. После
полуночи вчерашний незавершённый заказ сохраняет свой номер.

UUID остаётся идентификатором: совпадающие номера разных дат не смешивают
заказы, статусы и команды. На табло у заказа предыдущего дня показывается дата; карточки различаются по UUID.
Историю нужно различать также по дате заказа.
Миграция020 создаёт отдельные таблицы номеров/счётчиков и один раз заполняет
историю по дате и прежней глобальной последовательности. Старые заказы,
платежи, outbox и сохранённые результаты команд не переписываются.

Для установленных старых клиентов ответ без `number_format` сохраняет прежний
формат. Новый mobile, native kiosk и web operations запрашивают дневные номера.
Сохранённые результаты команд преобразуются при выдаче нового формата; это
не изменение истории. Ошибочный формат запроса отклоняется. Доступ к заказу
проверяется до преобразования, номера чужих клиентов не возвращаются.

Назначение запускает owner-функция только через INSERT trigger с закреплённым
search_path. Runtime имеет SELECT двух таблиц, без INSERT/UPDATE/DELETE.
Обычная очистка истории удаляет только привязку заказа, дневной счётчик сохраняется.
Существующие права и таблицы остаются неизменными.

`infra/staging/release-daily-numbers.py prepare|apply` принимает точные SHA API,
public и hash текущего gateway, SSH key, branch/source SHA. Apply требует полную
зелёную Foundation CI, encrypted backup и isolated restore. Сначала claim @vps
и project:check; owned locks/maintenance обязательны. База019 обновляется до020,
каждая прежняя строка/sequence сохраняется. Новые таблицы сверяются с историей,
дельта прав - только два SELECT. Старый API проверяется на совместимость.
Внешний Caddy не меняется, действующий gateway копируется побайтно; обновляется
только operations bundle. При ошибке не перехватывать lock и не восстанавливать
БД поверх live. Чеки/реальная оплата и Windows-касса этим не подключаются.

UI: адресная проверка UI/UX Pro Max (React Native accessibility labels) и
Impeccable clarify; исходная композиция/бренд сохранены. Для plain-language
подписи отдельного совпадения в базе навыка не было; применена общая ясная
формулировка «Заказ №…» и озвучивание «Заказ номер …».
