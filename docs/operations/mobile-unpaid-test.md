# Заказ из мобильного без оплаты - тестовый контур

Решение владельца 25 сентября 2026: проверить заказ из приложения, приготовление,
сборку, табло и изменение статуса без банка и фискализации.

## Реализация

`EXPO_PUBLIC_UNPAID_TEST_ORDERS=1` включает ConnectedCheckout в отдельной Dev-сборке.
Обычный выпуск по умолчанию остаётся закрытым. Сервер должен явно сообщить
`features.unpaid_test_orders=true`; прежний API не включает кнопку отправки.
Вход в тестовый аккаунт приложения сохраняется, настоящий SMS/WhatsApp не включён.

`POST /v1/test/orders` принимает `execution_mode: unpaid_test`. Это только TEST
namespace существующего staging gate, не production-платёж. Сервер считает
сумму по сохранённому quote и одной PostgreSQL-транзакцией создаёт заказ,
задания и outbox. `payment_state=not_started`, `payment_attempt_id=null`,
`fiscal_state=not_applicable` сохраняются до выдачи. Симулятор оплаты остаётся
отдельным старым сценарием; неоплаченный заказ нельзя превратить в оплату.
Миграция 019 сохраняет прежние ограничения для старых заказов и делает режим
исполнения неизменяемым. Финансовые таблицы не используются.

Мобильный журнал хранит режим вместе с ключом команды. После потери ответа
восстанавливается тот же заказ, включая перезапуск приложения. Активный статус
получается через [событийный watch](mobile-order-events.md) сразу после commit
кухни; при возвращении приложения загружается актуальный snapshot.
Ошибка связи не означает успешное выполнение и не заменяет известный статус.

Тестовые экраны:

- `/test/kitchen/prep` - одно подтверждение всего приготовления;
- `/test/kitchen/assembly` - одно подтверждение сборки после кухни, затем выдача;
- `/test/display` - готовящиеся и готовые номера.

Они используют существующие отдельные ключи TEST-ролей. Ключи не находятся в
URL, сборке или Git. Обычные `/kitchen/prep`, `/kitchen/assembly`, `/display`
по-прежнему показывают кассовый edge. Это две разные очереди. Мобильный TEST
заказ не попадёт на обычную кассовую кухню или в iiko.

Статусы приложения: «Готовится» → «На сборке» → «Можно забирать» → «Выдан».
Каждый переход основан на сохранённом подтверждении, не на таймере. Модификаторы
и количество видны на кухне. Повтор подтверждения с тем же ключом безопасен;
неверная станция и сборка до приготовления отклоняются сервером.

## Проверки и установка

Локально проверены 25 PostgreSQL сценариев TEST flow/readiness и 24 сценария
восстановления мобильного журнала, включая неоплаченную отправку, потерю ответа,
откат всей транзакции при сбое outbox, права станции и весь цикл выдачи.
Браузерный сценарий на отдельной локальной PostgreSQL прошёл: оформление с
модификаторами, перезагрузка приложения, приготовление, блокировка преждевременной
сборки, сборка, табло, статусы и выдача. Проверены ширины 320/390/430. Общая
integration: 175 прошли, 1 opt-in пропущен; историческая миграция проверена отдельно.
163 mobile JS + 30 Python, 52 operations Python и pnpm check прошли. Фактический
выпуск и проверка через публичный сервер записываются отдельно.
До подтверждённого deployment этот документ не означает установленную функцию.

`infra/staging/release-mobile-test.py` предназначен только для наблюдённого API
93b14e7/schema014. Prepare сохраняет все действующие публичные overlays и меняет
только operations bundle и три TEST alias. Apply требует зелёную CI точного SHA,
общий lock, остановку входящих запросов и cleanup, зашифрованную копию и проверку
восстановления в отдельную БД. Сохраняет старые строки, права и соседние сервисы;
новые коммерческие domains 015-018 остаются выключенными. Неопределённая ошибка
сохраняет lock, требует диагностики; live restore не выполняется.

Для этой проверки нужен интернет. Офлайн мобильный клиент не подтверждает
новый заказ. Автономная касса/кухня через edge - отдельный действующий контур;
объединение с mobile и полноценная эксплуатационная приёмка ещё не завершены.

### Проверенные остановки выпуска и продолжение

Первый apply остановился после provisioning: исходная проверка ACL требовала
полного равенства, а cloud017 закономерно добавляет `SELECT bo_records` и
`INSERT bo_order_recipes` для trigger фиксации рецептуры даже при выключенном
backoffice. Подтверждены ровно эти два добавления и отсутствие удалённых/расширенных
старых прав. Продолжение сохранило тот же release lock и cleanup lock, повторило
проверки CI, артефактов, резервной копии, старых строк, соседних сервисов и provision.

Следующая проверка обнаружила старые абсолютные bind paths в скопированном compose.
API уже был готов, gateway продолжал обслуживать прежнюю папку. Исходный failed
public release не изменяли. Создана отдельная immutable копия
`c5715e7dbca924a04b3c52988b84f257d2826cfd-web-mounts`: файлы/manifest/Caddyfile
побайтно совпали с проверенным пакетом, изменились только два read-only mount source.
После Caddy validate подтверждены реальные mounts, SHA config, три HTTP200 страницы,
API readiness, edgeConnected и прежние контейнеры. Затем переключён public pointer
и освобождены только собственные lock. Соседний idrink Caddy не менялся.

Обе причины исправлены в deployment helper и покрыты отдельными regression tests.
Это последующая правка инструмента выпуска; установленный API/operations остаётся
на зелёном c5715e7. Повторно запускать исходный apply поверх schema019 нельзя:
его guard рассчитан на первоначальный schema014 baseline. Следующий выпуск требует
актуального baseline и новой проверки. Документ/roadmap могут иметь более новый SHA,
чем API; online roadmap после публикации имеет свой sourceSha.
