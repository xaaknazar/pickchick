# Статусы мобильного заказа по событиям

Решение владельца 25 сентября 2026: получать изменения после подтверждения кухни,
без обычного опроса раз в3 секунды. Область - существующий cloud TEST-контур.

## Как работает

После изменения заказа та же транзакция сохраняет outbox и отправляет PostgreSQL
NOTIFY с UUID заказа. Сигнал доставляется только после COMMIT. Это подсказка,
не замена durable outbox/таблиц: клиент получает полную авторизованную проекцию.
Справка PostgreSQL: https://www.postgresql.org/docs/current/sql-notify.html.

`POST /v1/test/orders/watch?catalog_version=mockup-v0.3`, Bearer в заголовке,
тело `{versions:[{order_id,version}]}` (максимум20 записей). API сначала проверяет
доступ, затем подписывается **до** чтения актуального snapshot. Если версии
различаются, ответ немедленный. Иначе запрос ждёт сигнал своего заказа до20с.
Сигналы во время чтения сохраняются; после события/heartbeat доступ проверяется
ещё раз. Чужие UUID не расширяют подписку: её состав берётся из серверной выборки.
Ответ - прежний `TestOrdersSchema`, совместимый с сохранением/восстановлением заказа.

Это событийный long polling через обычный HTTPS fetch, а не WebSocket. Телефон
не делает запрос каждые3 секунды: один запрос ожидает изменение и сразу после
ответа открывается следующий. Через20с без событий соединение планово обновляется
с проверкой данных. Нативная библиотека/пересборка Dev Client не нужна.

Один отдельный LISTEN connection на API, без долгих транзакций/DB connection на
телефон. Максимум32 ожидающих HTTP-запроса и2 на TEST credential; отдельный лимит
сохраняет обычные места для команд/health. Метрика `pickchick_order_watches_in_flight`.
Disconnect, background, unmount и команды отменяют ожидание; после foreground
читается snapshot. После ошибки - backoff с jitter,401 прекращает подписку.
404 старого API сохраняет прежний polling на время поэтапного выпуска.

Gateway разрешает только POST watch и его CORS preflight; cookie/device header
удаляются, credential не передаётся в URL. Только watch имеет upstream header
limit32с на обоих шлюзах; обычные запросы сохраняют5с на внутреннем и8с на внешнем.
Во внешнем Caddy меняется только точный блок hostname PickChick, остальные байты
сохраняются. Конфигурация проверяется и передаётся через stdin graceful reload,
без перезапуска контейнера; исходник сохраняется в приватную резервную копию. Общий write deadline40с вмещает bounded wait.

## Проверка

- PostgreSQL: событие только после commit, rollback без сигнала, чужие заказы,
  гонка snapshot/событие, разрыв LISTEN и новое подключение.
- HTTP: авторизация/роль/владение, приготовление и сборка без polling tick,
  повторная проверка revoked access, освобождение отменённого ожидания.
- Mobile core: версии/AbortSignal, восстановление потерянного ответа без нового заказа.
- Реальный pinned Caddy: POST/CORS/credential forwarding, ожидание11с без старого
  таймаута, запрет GET и сохранение остальных ограничений.
- `REQUIRE_ORDER_EVENTS=1` включает в `browser_mobile_unpaid.py` проверку подписки,
  отсутствия обычного трёхсекундного опроса и доставки статуса после ответа кухни
  менее2,5с. Локально сценарий использует настоящую изолированную PostgreSQL/API.
  Скорость на физическом телефоне зависит также от сети и требует приёмки владельца.

## Выпуск

`infra/staging/release-order-events.py prepare|apply` требует чистый опубликованный
SHA, точные `--expected-api-sha`, `--expected-public-sha`, `--expected-gateway-sha256`, `--expected-front-sha256`,
`--branch`, `--ssh-key`. Для apply: `--backup-identity` и `--ci-proof`/`--ci-run`
полного зелёного Foundation CI (6 jobs). Сначала project:check и claim @vps.
Схема019/данные/ACL не изменяются, provision не запускается. Под owned deploy и
cleanup locks закрывается TEST ingress, останавливается только API, создаётся
зашифрованный backup с отдельным restore rehearsal. Новый immutable API/gateway
проверяется перед открытием; текущие edge/roadmap/assets и соседние сервисы сохраняются.
При guard failure locks остаются: изучить приватные diagnostics, не захватывать
их повторно и не восстанавливать БД поверх live. Откат - прежние API/gateway
из проверенных immutable releases, без миграции и без восстановления live БД.

Локальный полный цикл T-000003 прошёл: после ответа кухни статус менялся за24-25мс;
выдача во время обрыва сети и восстановление также проверены. Это браузерная
проверка на изолированном API, не измерение физического iPhone.

Публикация и проверка публичного заказа пока не выполнены для этого изменения.
