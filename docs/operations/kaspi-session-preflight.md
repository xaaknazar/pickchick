# Проверка Kaspi перед новым счётом

Worker перед созданием новой записи счёта выполняет существующий read-only
`GET /api/session/check` приватного bridge. Только HTTP success и строгое
`active: true` допускают отправку. Таймаут ограничен меньшим из настроенного
таймаута bridge и 10 секунд. Секреты передаются штатными заголовками сессии,
redirect запрещён; ответ банка и секреты не логируются.

Если проверка не прошла, исходная durable outbox-команда остаётся неподтверждённой,
попытка оплаты остаётся pending, новая запись счёта не создаётся. Повторная
проверка выполняется не чаще чем через 5 секунд этим worker; lease той же
команды сохраняет такую же задержку после рестарта. Сверка существующих счетов
продолжается независимо от проверки. Неопределённый результат уже отправленного
счёта по-прежнему восстанавливается по истории, без повторного создания.

Это проверка текущей сессии, а не гарантия будущей доступности банка. Штатная
проверка ответа отправки и защита от дубликатов остаются обязательными.
При подтверждённой потере сессии во время отправки сохраняется существующий
режим остановки новых отправок до повторного входа и рестарта worker.
Ресторан проверяется штатными server-side availability/admission gates.

## Проверки

- Targeted commerce dependency build, ESLint и Prettier.
- 23 Kaspi adapter unit-теста: положительный ответ, inactive, неверный тип,
  HTTP 401/503, отсутствие credentials и transport failure.
- 34 PostgreSQL integration-теста прошли на отдельном локальном экземпляре, scripted bridge;
  новая проверка покрывает отложенную команду, отсутствие нового счёта,
  восстановление той же попытки и сверку существующего оплаченного счёта.
- Запросы к реальному Kaspi и deployment не выполнялись.
