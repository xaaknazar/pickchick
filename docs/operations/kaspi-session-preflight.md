# Проверка Kaspi перед новым счётом

Worker перед созданием новой записи счёта выполняет существующий read-only
`GET /api/session/check` приватного bridge. Только HTTP success и строгое
`active: true` допускают отправку. Таймаут ограничен меньшим из настроенного
таймаута bridge и 10 секунд. Секреты передаются штатными заголовками сессии,
redirect запрещён; ответ банка и секреты не логируются.

Если проверка не прошла, исходная durable outbox-команда остаётся неподтверждённой,
попытка оплаты остаётся pending, новая запись счёта не создаётся. Повторная
проверка выполняется не чаще чем через 5 секунд этим worker; lease той же
команды сохраняет такую же задержку после рестарта. Сверка существующих счетов
продолжается независимо от проверки. Неопределённый результат уже отправленного
счёта по-прежнему восстанавливается по истории, без повторного создания.

Это проверка текущей сессии, а не гарантия будущей доступности банка. Штатная
проверка ответа отправки и защита от дубликатов остаются обязательными.
Ресторан проверяется штатными server-side availability/admission gates.

Изменения 19.10 (аудит, находки 0.0, 0.1, 5.1; подробности в
[release-fixes-2026-10-19/pay.md](release-fixes-2026-10-19/pay.md)):

- неготовый заказ откладывает только свою команду (свой lease), остальные заказы
  получают счёт в том же цикле; ресторанная проверка выполняется до и после проверки банка;
- неудачная проверка сессии - проблема банка: `sessionProblem` с кодом причины
  (`session_inactive`, `bridge_unreachable`, `session_missing`, `session_rejected`),
  событие `kaspi_remote_attention` не чаще раза в 5 минут и одно событие восстановления;
- при потере сессии во время отправки новые счета останавливаются, но worker сам
  повторяет read-only проверку (5 с, затем 10, 20, 40 и не реже раза в минуту;
  после отказа банка - через 30 с) и продолжает без рестарта, когда
  сессия снова активна; после повторного входа рестарт по-прежнему допустим;
- попытка, не отправленная в банк за `KASPI_REMOTE_PENDING_MAX_AGE_SECONDS` (600 с),
  получает failed без счёта и денег; старый заказ после восстановления сессии не
  выставляется.

## Проверки

- Targeted commerce dependency build, ESLint и Prettier.
- 23 Kaspi adapter unit-теста: положительный ответ, inactive, неверный тип,
  HTTP 401/503, отсутствие credentials и transport failure.
- 36 PostgreSQL integration-теста прошли на отдельном локальном экземпляре, scripted bridge;
  новая проверка покрывает отложенную команду, отсутствие нового счёта,
  восстановление той же попытки и сверку существующего оплаченного счёта.
- Локальные проверки использовали scripted bridge; реальные счета не создавались.

## Ресторан и установка worker

После read-only ответа Kaspi worker повторно проверяет freshness ресторана
(30 секунд), активную привязку и устройство, текущую held admission, отсутствие
отмены и остановленных позиций. Потеря readiness откладывает ту же команду;
сверка уже отправленных счетов продолжается. Worker получает только SELECT
на cloud_branch_availability, fulfillment_transport_bindings и devices.

Профиль `infra/staging/release-kaspi-session-worker.py` обновляет только worker.
Read-only проверка VPS 2 октября подтвердила исходный worker
`289da31b47915b2d5cc3bb1813a4df613eb265b2`, API `f83794ce68c10906d2924a3a04351f7550d62b40`,
public `9e2e5dcd605bd5273e23e66380a0bf8b37b36736`. Перед применением передать
точные ожидаемые API/public SHA, если другая согласованная установка изменила
указатели. Нужны полная зелёная Foundation CI точного source SHA, prepared.json
с SHA/image_id подготовленного образа и claim @vps.

Профиль проверяет отсутствие pending submissions и unsettled invoices,
сохраняет ledger/секреты/mounts/соседние контейнеры, применяет только недостающие
read-only grants, держит штатную release lock и восстанавливает старый worker
и только добавленные права при ошибке. Проверка установленного адаптера
использует fake fetch, без банковского запроса или нового счёта.
2 октября worker `b18beb08b86341e13ab2b919edd01f523cea0c23` установлен после
[Foundation CI 37012247704](https://github.com/xaaknazar/pickchick/actions/runs/37012247704), 11/11.
Installed probe подтвердил session preflight, TTL180 и читаемое сообщение.
Ledger, credentials, mounts и соседние контейнеры сохранены; новые счета не
создавались. Приватное доказательство: `kaspi-companion/<sha>/completed.json`
в `/opt/pickchick-staging`. API/public SHA при выпуске остались указанными выше.

Подготовка worker выполняется этим же профилем с `--prepare-only` и теми же
SHA/CI/ожидаемыми API/public аргументами. Профиль проверяет точные 11 зелёных
Foundation jobs, архивирует Git source SHA и собирает только Docker-образ в
отдельном `kaspi-builds/<sha>`. API/public упаковка, миграции и перезапуски
при подготовке не выполняются. Prepared proof содержит hash CI, архива,
image_id и workerOnly; последующее применение требует тот же CI proof.
