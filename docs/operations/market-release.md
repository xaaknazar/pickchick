# Выпуск API, каталога и бэк-офиса на staging

`infra/staging/release-market.py` — отдельный сценарий для перехода с API
`5d3eead08c392bdbb60eae64a0bee4e883bb0af3` и web
`00ca82896517813808568d81ed843bc815ff3635` на проверенный новый SHA.
Его нельзя использовать как универсальный deploy или повторять поверх другого
исходного состояния. Для следующего перехода с `7cd` и schema `001`–`013`
используется отдельный [maintenance-профиль транспорта](transport-release.md);
исторический apply не принимает этот профиль. Целевой сервер — `185.129.51.103`, SSH `pickchick-ops`.
Подготовка этого файла **не является доказательством выполненного выпуска**.

Выпуск добавляет миграции `007`–`013`, включает редактор каталога и сохраняет
синтетический TEST-контур. Серверный вход, SMS, реальные платежи и чеки остаются
выключенными. Мокап не становится утверждённым ресторанным каталогом:
сценарий не создаёт управляющих, черновики, публикации, заказы или бонусы.
Менеджерский credential и установка фоновой очистки — отдельные действия после
успешного выпуска, по [инструкции каталога](catalog-admin.md) и
[инструкции аккаунтов](customer-identity.md).

## Подготовка

Нужны чистый checkout полного SHA, тот же SHA в ветке канонического GitHub,
установленные зависимости для `prepare-web.py` и успешный полный Foundation CI.
`--ci-run` получает run/jobs через штатно авторизованный `gh api`; все четыре
обязательных job должны завершиться успешно для этого SHA. Альтернатива
`--ci-proof /private/path/ci.json` принимает объект `{ "run": ..., "jobs": ... }`
из ответов GitHub API, включая полный список jobs. Этот вариант помечается в
доказательствах как **предоставленный оператором снимок**, а не независимо
проверенная подпись GitHub. Источник такого файла обязан проверить оператор.

Не использовать токен или пароль в командной строке. SSH по умолчанию использует
`~/.ssh/pickchick_staging_ed25519` и существующий проверенный `known_hosts`.
Age identity для rehearsal по умолчанию находится в
`.local/vps/backup-identity.agekey`, обычный файл без symlink, права `0600`.
Его байты идут в stdin `age`, ключ не копируется на VPS. Ключ и приватные
доказательства не включаются в Git.

```sh
python3 infra/staging/release-market.py prepare FULL_COMMIT_SHA \
  --branch codex/market-readiness-core --ci-run SUCCESSFUL_CI_RUN_ID

python3 infra/staging/release-market.py apply FULL_COMMIT_SHA \
  --branch codex/market-readiness-core
```

Вместо заглушек передать фактические SHA и CI run. Каждая команда ограничена по
времени. `prepare` создаёт новый неизменяемый каталог release, Docker image с
OCI revision и отдельный web release. API-контекст берётся из `git archive` по
разрешённым путям; `apps` исключены из него. Operations/backoffice и публичные
дизайн-ресурсы собираются отдельно через `prepare-web.py` с manifest SHA-256.
Старые release, активные сервисы, БД и указатели `current` при подготовке
не меняются. Уже существующий target release/image или `prepared.json` не
перезаписывается автоматически.

Файл `release.env` создаётся с настоящими переводами строк, с сохранением
прежних остальных настроек и явными `TEST_ORDER_FLOW_ENABLED=true`,
`CATALOG_ADMIN_ENABLED=true`, `CUSTOMER_AUTH_ENABLED=false`.
Общий защищённый `secrets/staging.env` не редактируется. Перед применением
дважды сверяются image ID/OCI SHA, все подготовленные web-файлы, compose,
gateway и хеши нового/старого environment. Одной смены symlink недостаточно:
проверяется фактический запущенный контейнер и смонтированный gateway bundle.

## Применение и проверка сохранности

Нужен согласованный тихий интервал без действий в TEST-интерфейсах, ручных
миграций, cleanup и других deploy. Снимок сравнивает все прежние строки и
последовательности, поэтому даже легитимный параллельный заказ остановит выпуск.
Сценарий не отключает публичный TEST и не стирает изменения, чтобы скрыть такое
расхождение.

Обе фазы используют единственный owned lock
`/opt/pickchick-staging/.market-release.lock`, созданный эксклюзивным `mkdir`.
UUID владельца записывается в `owner.json` и приватное локальное доказательство.
Другой запуск этого сценария не может войти; автоматического захвата старого
lock нет. Иные инструменты и ручные команды должны соблюдать тот же запрет на
параллельный выпуск. Сравнения и CAS указателей дополняют lock, но не заменяют
координацию с другими операторами.

`apply` выполняет последовательность:

1. Проверяет прежний API image, оба `current`, реальный web manifest, старые
   шесть migration checksum и ограниченную runtime-роль PostgreSQL.
2. Сохраняет приватные хеши/число строк каждой прежней таблицы, параметры и
   значения последовательностей, полный direct table/column/sequence ACL
   `pickchick_app`, параметры соседних контейнеров и хеш iDrink Caddyfile.
3. Делает свежий `pg_dump --no-owner --no-acl`, шифрует `age`, проверяет хеш,
   восстанавливает в отдельную случайно названную временную БД и сравнивает
   строки/последовательности. Удаляется только эта временная БД; live-БД не
   восстанавливается из дампа. ACL проверяется отдельно, поскольку dump его
   намеренно не содержит.
4. Дважды запускает **новый** `provision --no-deps`. Старые migration checksum
   и таблицы должны остаться прежними; допускаются только семь новых записей
   ledger, ожидаемые пустые domain-таблицы и две ещё не использованные
   последовательности commerce/loyalty. Проверяются точные права CMS и
   отсутствие прав runtime на identity/commerce/loyalty при выключенных доменах.
5. Обновляет только `api` и собственный `gateway` через `up --no-deps --wait`.
   Не запускает `down`, общий restart Docker, БД, Redis или iDrink.
6. Проверяет readiness/dependencies, прежние capabilities и оба TEST-каталога
   v0.2/v0.3, выключенный private auth config, public `404` для auth/customer и
   private health, `401 UNAUTHORIZED` CMS без credential, фактический public
   asset/manifest/config/image. Старые строки/последовательности и соседние
   сервисы сравниваются повторно. Только после этого оба указателя меняются
   атомарным `os.replace` с проверкой ожидаемого прежнего target.

Доказательства находятся в `.local/market-release/FULL_COMMIT_SHA/`: JSON,
ошибки команд и исключений имеют права `0600`, каталог — `0700`.
В обычный stdout не выводятся команды с доступами, env, телефоны, токены,
содержимое дампа или необработанные ошибки. Публичный итог можно составлять
по `result.json`; приватные логи целиком публиковать нельзя.

## Ошибка и откат

При **определённой** ошибке применения/проверки сценарий сначала возвращает
точный прежний ACL одной транзакцией, включая явный отзыв column grants,
затем запускает старый API и gateway с **их** compose/release.env. Он проверяет
неизменность rollback-файлов, возвращает только собственные изменённые указатели
и снова проверяет старые API/данные/соседей. Добавленная схема и новые данные
сохраняются. Старый `provision` не запускается: его migration runner не знает
ledger `007`–`013`. Автоматический dump restore поверх live-БД запрещён.

При потере SSH, timeout или неоднозначном завершении remote-команды
(`124/125/137/255`) автоматический rollback **не начинается**: Docker daemon
может ещё исполнять действие после завершения клиента. Сохраняются
`uncertain.json` и lock; оператор сначала проверяет именно запущенный процесс,
контейнеры, ledger, ACL и фактические указатели. Deadline удалённой команды
снижает риск зависания, но не доказывает отмену операции Docker.

После любой ошибки lock остаётся даже при успешном автоматическом rollback.
Не удалять его по возрасту. Сопоставить remote owner UUID с локальным
`lock-owner-UUID.json`, убедиться, что никакая операция этого владельца не
продолжается, сохранить состояние и только затем отдельно разрешить дальнейшее
действие. Частично подготовленные каталоги не удаляются и не переиспользуются
автоматически. Если миграции уже применены, повторный `apply` данного сценария
отклонит новый baseline: нужен отдельный проверенный план продолжения.

Cleanup, который использует `current`, нельзя оставлять на старом release после
отката: прежний image может не содержать нового maintenance CLI. Таймер/cron
устанавливать отдельно после успеха, с собственной процедурой остановки или
закреплённым совместимым maintenance release. Выдачу управляющего выполнять
с долговечным приватным RW mount для результата, а не во временной файловой
системе `docker compose run --rm`.

## Проверки сценария

```sh
python3 -m py_compile infra/staging/release-market.py
python3 -m unittest discover -s tests/operations -p test_market_release.py -v
```

Offline-тесты проверяют отказы CI, подмену старых строк/последовательностей,
допустимую пустую additive schema, ACL quoting/column revoke, настоящий newline
и `0600` для `release.env`, remote uncertainty, владение lock и запрет
конкурирующего rollback. Исправленный ACL SELECT дополнительно выполнен как
read-only запрос в локальном PostgreSQL 18. Полный remote prepare/apply,
rehearsal и запуск старого API на `007`–`013` этим набором не подтверждены;
их фактические результаты фиксируются отдельно при выполнении владельцем.
