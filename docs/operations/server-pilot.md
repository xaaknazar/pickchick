# Серверный пилот: подтверждённый аккаунт и заказ

Этап 26.09.2026. Реализация проверена локально; установка на VPS этим документом
не подтверждается. Решения владельца: Telegram, общий предел1000 резервирований
кода за суткиUTC, временно бесплатная выдача еды до эквайринга. Коммерческие
платежи, чеки и бонусный финансовый учёт остаются отключены.

## Владение заказами

Миграция024 добавляет отдельное соответствие `customer_id` и TEST-актора. Она
не присваивает существующие анонимные заказы владельцам телефонных номеров.
При включённом customer auth мобильная сессия требует действующий identity
Bearer. Повторные запросы и вход на другом устройстве возвращают того же актора.
Каждое чтение/действие проверяет срок, отзыв сессии и удаление аккаунта в БД;
смена токена не создаёт новую историю. Удалённый и заново зарегистрированный
аккаунт не наследует прежнюю историю. Кухонные роли и отдельный kiosk-сценарий
сохраняют свои существующие полномочия.

Mobile хранит журналы заказа отдельно для каждого customerId. Рабочий identity
access token берётся у провайдера аккаунта для каждого запроса, не копируется в
журнал заказа. При401 выполняется один повтор после сериализованного обновления
токена. Долгое ожидание события не блокирует выход; результат проверяет владельца
повторно. При смене аккаунта старые история/карточка/отзыв сразу скрываются,
поздние ответы не применяются к новому аккаунту.

Состояния приготовления поступают через существующий bounded events watch.
Бесплатный заказ сохраняет `payment_state=not_started` и
`fiscal_state=not_applicable`: готовность кухни не выдаётся за банковскую оплату.
Публичные capabilities различают synthetic и pilot, показывают фактическое
состояние phone_auth и сохраняют отключённые checkout/payments/fiscal/loyalty.

## Проверяемый выпуск

`infra/staging/release-server-pilot.py` рассчитан на API4ee0b80/schema020:
021 сохраняет выданные номера и вводит смены;022/023 доставку и согласие;024
соответствие аккаунту. Скрипт использует существующие owned deploy/cleanup locks,
проверку опубликованного чистого SHA и полной CI, encrypted backup с пробным
восстановлением, сверку данных/ACL, совместимость старого образа и CAS pointers.
Сравниваются все прежние столбцы, новые поля проверяются отдельно. Исторические
согласия не заполняются задним числом. Старые номера не перенумеровываются.

Подготовка копирует фактический gateway целиком, сохраняя кухню и roadmap;
добавляет только точные auth/profile/legal маршруты. Заполненные HTML-документы
поступают из защищённой локальной папки, секреты - из отдельного файла0600.
Они не входят в Git или образ. Уже установленный файл ключей нельзя перезаписать
другими значениями: смена ключей требует отдельной процедуры.

Адрес непосредственного gateway фиксируется в его Docker-сети и является
единственным доверенным proxy для API. Внутренний gateway доверяет только
проверенному адресу внешнего Caddy; использует строгий разбор и нормализованный
client IP. При изменении адреса внешнего proxy требуется повторная проверка.
Основание: [официальные параметры Caddy](https://caddyserver.com/docs/caddyfile/options#trusted_proxies_strict).
Нельзя подменить этот список всеми private_ranges или доверять сырым заголовкам.

Для обращений runtime получает INSERT в bo_records даже при выключенном
административном UI; UPDATE/DELETE и дополнительные коммерческие права этим
изменением не предоставляются. Штатный install-identity-cleanup-cron.py закрепляет очистку OTP раз в15 минут
за проверенным образом; установка и первый успешный запуск проверяются отдельно.

- Workspace build/typecheck/lint/format, unit, contracts и design checks прошли.
- Общий PostgreSQL прогон192:191 прошёл,1 существующий skip. После него добавлен
  и отдельно проверен второй сценарий restricted-role/HTTP.
- Проверен путь customer→quote→unpaid order→prep→assembly→display→handoff;
  дубликаты, чужой аккаунт, logout/re-login, удаление и повторная регистрация.
- Проверены реальные SQL-права restricted role и HTTP401 для анонимного mobile.
  -176 Node +30 Python mobile tests, в том числе26 identity tests: истечение/обновление, отзыв, потеря ответа и logout
  во время ожидания события; платежи и реальные сообщения не отправлялись.
  -23 release guards (включая market/mobile/events/daily profiles); Caddy2.11.4 подтвердил
  конфигурацию, составленную из текущего gateway VPS.
- Предыдущая CI9c0c61d завершилась ошибкой browser_cart_sheet: таймер сбора кадров
  истекал до нажатия на холодном клиенте. Причина подтверждена журналом GitHub;
  измерение теперь начинается на фактическом click, критерий движения сохранён.
  Новый полный CI-прогон обязателен до apply.

подтверждены: Telegram-форма→вход→Pick Combo→корзина→отправка без оплаты→

перезагрузка сохранила заказ№1 в «Моих заказах». Gateway был заменён только
в локальной проверке; реальные сообщения и заказы ресторана не отправлялись.

## Следующее действие

1. Получить полный зелёный CI для нового SHA; устранить оставшиеся ошибки при наличии.
2. Завершить фактические сведения политики и публикационные HTML. Ранее полученное
   согласование текста сохраняется; отдельно запрошен пока не заданный срок
   хранения истории пилота/обращений. Не обещать автоматическое обезличивание,
   пока механизм не реализован и не проверен.
3. Вызвать prepare/apply с текущими baseline, локальным protected auth env,
   legal directory, off-server backup identity и CI proof. Пример формы:
   `python3 infra/staging/release-server-pilot.py prepare --help`.
4. После применения установить штатное pinned cron-задание очистки, проверить
   сохранность других заданий и первый успешный run. Проверить HTTPS policy/auth, защиту IP, лимит, доступ
   клиента; затем обновить Dev server-auth и принять поток на устройстве.
5. Опубликовать обновлённый roadmap и внести фактический SHA/проверки установки.

Перед apply заново project:check и резервирование @vps; никаких старых SHA из
документа без проверки. При неопределённом результате не снимать чужой lock и не
запускать конкурирующий rollback. Копия БД на том же VPS не заменяет независимый
backup; физическая кухня и пополнение Gateway остаются отдельной приёмкой.
