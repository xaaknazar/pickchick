# Редактор каталога: черновик и публикация

7 сентября 2026. Этот подэтап реализует PostgreSQL-домен редактирования меню,
отдельные полномочия управляющего, HTTP-контроллер и CLI выдачи/отзыва доступа.
Рабочий интерфейс бэк-офиса подключается к этому контракту отдельным коммитом.
Проверки выполняются на временных локальных схемах и синтетических организациях;
они не означают развёртывание CMS на VPS или подтверждение фактического состава блюд.

## Границы и источник данных

Новый каталог не использует `synthetic`, TEST namespace, TEST actor или TEST quote.
Для первоначального **черновика** берутся 24 позиции канонического source dataset
из `design/reference-source/mobile-v2.html.txt`, перенесённого в
`test-order-flow/complete-catalog`. Импортируется только чистый набор данных.
Исходные цены, описания, КБЖУ и группы модификаторов сохраняются. KK-переводы не
выдумываются: пустая строка означает незаполненный перевод. Состав/аллергены и
пищевая ценность мокапа не считаются подтверждёнными для продаж.

Прототип бэк-офиса B05–B11 показывает номенклатуру, блюда, цены и модификаторы.
Этот серверный этап предоставляет редактирование соответствующего каталога;
техкарты склада, налоговые признаки, реальные оплаты, кассовые смены, stop-list
на edge и полный бэк-офис сюда не включены.

Публикация создаёт активную **версию каталога**, но не включает checkout и не
меняет `branches.ordering_enabled`. Существующие `/v1/test/catalog`, цены TEST
заказов, их неизменяемые снимки, foundation `menu_releases`, edge и POS остаются
без изменений. Подключение нового каталога к доверенному серверному quote,
каналам mobile/kiosk и доставке edge требует отдельной интеграции: показ цены
из публичного меню сам по себе не разрешает продажу или платёж.

## API и подключение

Пакет `@pickchick/catalog-admin` экспортирует `CatalogAdmin`, `CATALOG_ADMIN`,
`catalogAdminOptions`, команды выдачи/отзыва и схемы. Чистый subpath `./contracts`
содержит `CatalogPayloadSchema`, `CatalogStateSchema`, связанные типы и список
`CATALOG_ASSET_KEYS`; subpath `./seed` — исходный неподтверждённый черновик.

```ts
const catalog = new CatalogAdmin(pool, catalogAdminOptions(environment));
// Nest provider: { provide: CATALOG_ADMIN, useValue: catalog }
// Nest controller: CatalogAdminController
```

`CATALOG_ADMIN_ENABLED=false` по умолчанию. Выключенный редактор возвращает 503
для административных операций и для `GET /v1/catalog/branches/{id}`. Выключение
редактора не удаляет публикацию; витрины мобильного приложения и киоска читают
её своими маршрутами.

`CATALOG_ACCESS_ROLES_ENABLED=false` по умолчанию. При `true` каждый вызов
требует строку `bo_access_grants` для точки: `analyst` только читает, `manager`
сохраняет, засевает и публикует; без строки — 403. Перед включением выдать роль
каждому действующему держателю токена каталога (`grantBackoffice`), иначе он
потеряет доступ. Staging provision выдаёт чтение и `lock_anchor` этой таблицы
через `catalog-edge-grants.mjs` после back-office grants.

Ошибка публикации 409 дополнительно содержит только код причины
`error: {code}`: `CHANNEL_PRICES_NOT_SUPPORTED`, `UNAVAILABLE_LINKED_PRODUCT`,
`EDGE_DEVICE_INACTIVE`, `EDGE_MENU_STATE_UNKNOWN`. При публикации на кассу
версия меню = max(версии облака, активная версия, о которой сообщила касса) + 1;
пока касса не сообщила своё меню (`edge_menu_state`), публикация отклоняется.
`edge_delivery` показывает `rejected` с `reject_reason`, если касса отклонила
релиз, и `edge_active_version`/`observed_at` из последнего отчёта кассы.

Контроллер/DI и флаг зарегистрированы в основном API. Staging provision выдаёт
права через `catalog-admin-grants.mjs`. Миграция 011 добавляет constrained no-op `lock_anchor`: PostgreSQL
требует UPDATE privilege даже для `FOR SHARE`. Runtime получает UPDATE только
этого всегда-true столбца на credentials/scopes и не может менять token, назначение
точки или выдавать управляющих. Проверка выполняет полный цикл под такой ролью.

Все административные маршруты требуют `Authorization: Bearer <64hex token>`.
Токен выдаётся только доверенной CLI-командой владельца. HTTP-маршрута выдачи нет.

| Метод | Путь                                              | Тело / результат                                                                                     |
| ----- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| GET   | `/v1/admin/catalog/branches`                      | `{actor:{id,name},branches:[{id,code,name}]}` только назначенные точки                               |
| GET   | `/v1/admin/catalog/branches/:branchId`            | Полный `state`                                                                                       |
| POST  | `/v1/admin/catalog/branches/:branchId/draft/seed` | `{expected_revision:0,request_id}` → `state`, только если черновика/публикации ещё нет               |
| PUT   | `/v1/admin/catalog/branches/:branchId/draft`      | `{expected_revision,request_id,payload}` → `state`                                                   |
| POST  | `/v1/admin/catalog/branches/:branchId/publish`    | `{expected_revision,expected_published_version,request_id,confirmation:'publish_catalog'}` → `state` |
| GET   | `/v1/catalog/branches/:branchId`                  | `{branch_id,version,published_at,payload}`, без Bearer; 404 до первой публикации                     |

`state` содержит `branch:{id,code,name}`, `draft` и `published`:

```text
draft = null | {revision,base_version,updated_at,updated_by,payload}
published = null | {version,published_at,published_by,payload}
```

У исходного черновика `revision=1`, `base_version=0`. Сохранение увеличивает
revision. Публикация также увеличивает revision, записывает новую immutable
publication version и устанавливает `base_version` равной опубликованной версии.
Интерфейс должен брать новые номера из ответа, не вычислять их заранее.

Добавление/удаление блюда, категории, компонентов и модификаторов выполняется
сохранением полного payload. Допустимы 1–100 блюд, 1–30 категорий, 10 групп на
блюдо, 20 опций на группу. Максимум payload — 256 KiB UTF-8. Исходные 24 позиции
занимают около 68 KB; полный state с черновиком и публикацией около 136 KB.
HTTP-хост должен разрешить для этого PUT не менее 300 KiB JSON, сохраняя строгие
лимиты остальных маршрутов; клиентскому reader/proxy нужен предел не менее
1 MiB для state. Не увеличивать глобально лимит OTP или произвольных endpoint.

Ошибки: 400 `INVALID_REQUEST`, 401 `UNAUTHORIZED`, 403 `FORBIDDEN`, 404 `NOT_FOUND`,
409 `CONFLICT`, 503 `SERVICE_UNAVAILABLE`. Контроллер передаёт безопасный код в
общий error-filter, без Bearer и сырого payload в логах. `no-store`, TLS, admission
и корректные HTTP body limits обеспечивает общий API-host.

## Данные и проверки черновика

Полный контракт находится в `packages/catalog-admin/src/contracts.ts`:

- `schema_version:1`, `currency:'KZT'`, `content_source:'mockup'|'operator'`,
  `content_reviewed:boolean`; RU/KZ категории, ETA и ссылки upsell.
- У блюда стабильные slug `id`, уникальный `sku`, RU/KZ имя, описание,
  ингредиенты и подпись порции; `weight_g`/`volume_ml` — целые значения или null.
- `price_minor` и `price_delta_minor` — десятичные строки целых минимальных
  денежных единиц, без float и округления. `419000` означает 4190 ₸.
- Фото — разрешённый локальный `image_asset_key`, а не произвольный URL или путь.
  Список включает фактически существующие source-фото и `generic-drink` как
  отсутствие подтверждённого фото; i3/i21, которых нет в source assets, не принимаются.
  Загрузка новых файлов и их CDN-публикация — отдельный подэтап.
- КБЖУ с базисом `per_serving`/`per_100_g`; `nutrition_status` остаётся
  `unverified`, пока оператор не вводит данные. `operator_entered` — происхождение
  записи, не лабораторная проверка. `allergens_status:'unknown'` отличается от
  заявленного оператором списка; пустой список не означает отсутствие аллергенов.
- `kind:'item'|'combo'|'set'`; явные `combo_components` с ID блюда и количеством;
  опции могут иметь `linked_product_id` или null. Источник не задаёт достоверную
  машинную техкарту для всех составов, поэтому seed не выдумывает component-связи.
- Группы определяют min/max количества, доступность, доплату, начальные количества,
  ограничения каждой опции и source-множитель пищевой ценности, если он был в макете.

Сервер отклоняет дубли ID/SKU/опций, отсутствующие категории, удалённые зависимости,
дубликаты upsell, циклы компонентов/ссылок модификаторов, неправильные деньги и
количества. Нельзя задать обязательную группу, которую невозможно заполнить,
или начальное количество выше допустимого/у недоступной опции. Чтобы удалить
блюдо, сначала нужно удалить ссылки на него в зависимых компонентах и upsell.

Seed всегда `content_reviewed:false`; публикация такого черновика запрещена.
Управляющий явно проверяет содержимое, сохраняет `content_reviewed:true` и нажимает
публикацию. Это его решение о размещении каталога. Флаг не объявляет достоверными
неподтверждённые КБЖУ, состав, перевод, налоговый режим или реальные продажи.

## Версии, повторы и аудит

PostgreSQL хранит каждую версию черновика, публикацию и audit-запись. Текущие
указатели обновляются атомарно; внешних вызовов в транзакции нет. Одновременные
редакторы передают ожидаемые revision/version. Проигравший получает 409 и должен
перечитать актуальную версию, показать расхождения и сохранить свои локальные
изменения для ручного решения. Last-write-wins и скрытая перезапись не применяются.

`request_id` — UUID, который клиент сохраняет до отправки команды. Повтор той же
команды с тем же ключом возвращает исходный ответ без новой версии или публикации.
Ключ действует на управляющего во всех его точках; иной payload, branch или тип
операции с этим ключом даёт 409. Отозванный токен не получает даже старый receipt.
Если после неизвестного результата сервер уже продвинул каталог другим запросом,
восстановленный receipt может содержать старую revision: UI не должен понижать
свой номер, после восстановления нужно GET актуального state.

Draft/publication/audit/command receipts запрещено UPDATE/DELETE триггерами.
Публикация должна точно совпасть с указанной исходной версией черновика и hash;
SQL-триггер проверяет это независимо от HTTP. FK не разрешают указатель на
несуществующую версию или чужую организацию. Аудит хранит actor, время, действие,
предыдущую/новую revision и hash; полные прежние значения сохраняются в immutable
`catalog_draft_versions`. Удаление истории и retention пока не реализованы:
нужны отдельный согласованный регламент, мониторинг объёма и безопасный архив.

## Доступ управляющего

В новой схеме `catalog_managers` и назначениях хранятся собственные ID и SHA-256
256-битного случайного Bearer. TEST/customer/staff токены другого домена не
принимаются. Организация и список точек проверяются и приложением, и composite FK
на foundation branches. Отзыв сериализуется с активными командами shared-lock:
команда либо завершается до отзыва, либо больше не авторизуется.

Нужен административный доступ к cloud PostgreSQL и приватный файл входа:

```json
{
  "organization_id": "00000000-0000-4000-8000-000000000001",
  "name": "Управляющий тестовой точки",
  "branch_ids": ["00000000-0000-4000-8000-000000000003"]
}
```

UUID выше — только иллюстрация, CLI требует реально существующую назначенную
организацию/точку. Из корня репозитория:

```sh
node --env-file=.env packages/catalog-admin/dist/cli.js provision \
  --input .local/catalog-manager-input.json \
  --output .local/catalog-manager-credential.json
node --env-file=.env packages/catalog-admin/dist/cli.js revoke --actor ACTOR_UUID
```

CLI использует `CLOUD_DATABASE_URL`. Выходной JSON содержит `actor_id`,
`organization_id`, `name`, `branch_ids`, `token`, `issued_at`. Файл создаётся
exclusive с правами 0600 внутри `.local`; существующий файл не перезаписывается,
переход через directory symlink наружу запрещён. Токен не печатается. Если выдача
успела завершиться, но файл не сохранился, CLI отзывает выданный доступ.
Не помещать credential/input с настоящими именами и секреты в GitHub.

У токена этого закрытого операторского контура нет календарного expiry;
отзыв выполняется CLI. Полноценные staff MFA/SSO, централизованная смена полномочий,
короткие повышенные сессии и корпоративный жизненный цикл сотрудника ещё требуют
реализации перед публичным production-доступом управляющих. Этот private Bearer
не выдаётся за выполнение всех требований безопасности staff из ТЗ.

## Миграция, grants и проверка

`009_cloud_catalog_admin.sql` добавляет 8 таблиц `catalog_*` и unique index
`branches(id,organization_id)` для привязки областей доступа. Миграция 008 другого
домена должна быть согласована до применения 009 к постоянной БД: migrator не
допускает добавление старшей пропущенной миграции задним числом. Откат старого API
оставляет новые таблицы/версии; down-миграция с удалением данных не нужна.

Runtime API требует SELECT для всех 8 таблиц, INSERT/UPDATE для
`catalog_branch_heads`, INSERT для `catalog_draft_versions`, `catalog_publications`,
`catalog_audit`, `catalog_command_receipts`; SELECT foundation branches. Команды
оператора отдельно требуют INSERT managers/scopes/manager_audit, UPDATE managers
для отзыва. Ни DELETE immutable истории, ни права на production деньги не нужны.
Readiness проверяет migration checksum/ledger и доступ к таблицам. Выпуск и grants
выполняются владельцем отдельно; этот подэтап не запускает CLI или миграции на VPS.

Проверки: unit schema/source invariants, реальные локальные PostgreSQL
create/read/save/publish, конкуренция/replay, rollback аудита, невозможность
чужих scopes, FK и immutable constraints, реальная CLI запись 0600/отзыв,
HTTP auth и публичное чтение. DB harness создаёт случайные схемы и удаляет только
их после теста. Runtime-включение CMS, реальные данные меню, перевод и физическая
работа ресторанов этими проверками не подтверждаются.
