# Локальный домен кухни: резерв, приготовление и выдача

Проверяемый этап от 7 сентября 2026: пакет `@pickchick/edge-fulfillment`,
миграция edge `005_edge_fulfillment.sql` и изолированные PostgreSQL-проверки.
Коммерческая часть заказа остаётся в cloud; локальный edge хранит исполнение.
Пакет не подключён к HTTP, KDS/POS/LED UI, worker, VPS или внешним провайдерам.

Основание: KDS-01–04 и DSP в [ТЗ](../01-technical-spec.md), ограничения
[модели данных](../02-data-and-api.md), [владение cloud/edge](../03-offline-and-reliability.md).
Он продвигает доменную часть AC-12/13/16/18/25; AC-15 с физическими кассой,
iPad, двумя экранами, банком/ККМ и восемью часами без WAN ещё не принят.
Неоплаченный `local_orders` POS остаётся `fulfillment_state=blocked`.

## Доверенные входы

`EdgeFulfillment.acceptCloud(scope, command)` — внутренний порт будущего
аутентифицированного транспорта. `scope` содержит `organizationId`, `branchId`,
`deviceId`, `producerId`; эти значения извлекаются из проверенной связи/сертификата,
а не из полей, присланных гостем. В каждой транзакции они сверяются с локальной
`fulfillment_config`. Пакет не умеет аутентифицировать сетевой запрос.
Публичную кнопку, `paid=true` или клиентскую роль к этому порту подключать нельзя.

Первые два типа принимают точный `payload` существующего commerce outbox:

| Команда                             | Условие и результат                                                                                                                                                                                                                                                           |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `edge.admission_requested`          | Точка разрешает новые заказы; owner=cloud, order/quote/branch и SHA-256 снимка совпадают. Все компоненты имеют явные маршруты. Создаёт долговечный резерв `held` и `edge.admission_reserved`. Заданий и номера на табло ещё нет.                                              |
| `edge.kitchen_admission_requested`  | Commerce выпускает событие после достаточной подтверждённой оплаты, успешно выданного фискального документа и проверок возвратов/расхождений. Edge проверяет свою reservation/device/quote/hash и состояние. В одной транзакции создаёт задания, номер и `accepted` с outbox. |
| `edge.admission_release_requested`  | Отдельная доверенная команда разрешения неопределённости: точные reservation/quote/hash и `expectedVersion`; допустима только из `held`. Оставляет терминальную запись `released`.                                                                                            |
| `edge.fulfillment_cancel_requested` | Те же идентификаторы и версия плюс причина. До начала работ отменяет queued-задачи. При начатой работе требует локального подтверждения остановки и решения управляющего. Из `ready`/`handed_over` отклоняется.                                                               |

Последние две команды — определённый этим пакетом внутренний порт, ещё не
производимый commerce worker. До его реализации нельзя обещать автоматическую
доставку отмены или возврат после остановки кухни.

Будущий мост берёт `event_id` локального `edge.admission_reserved` и поля
`orderId/reservationId/quoteDigest` и вызывает существующий
`CommerceRepository.confirmAdmission` от проверенного edge device. В проверке
такое соединение выполнено непосредственно между двумя временными БД.
Сетевого протокола, подписи сообщения, retry worker или фоновой сверки пока нет.

## Резерв и маршруты

Резерв сохраняет неизменяемые order/quote/snapshot/hash, `commercial_owner=cloud`,
`fulfillment_owner=edge`, device и `owner_hash` этих идентификаторов. Unique
`(branch_id,quote_id)` не даёт открыть два исполнения для одного расчёта.
Изменённый body под прежним event ID конфликтует; inbox и результат неизменяемы.
Повторный event ID возвращает сохранённый результат команды, который может быть
старше текущего состояния. Текущее состояние читается отдельно; replay ничего
повторно не готовит. Другой event ID с тем же order/reservation также не создаёт
новые задания. Освобождённый или отменённый резерв нельзя использовать заново.

**У резерва нет TTL.** Потеря WAN, закрытие клиента, остановка приёма новых заказов
и смена активного маршрута его не снимают. Release/cancel требуют явной команды.
Резерв этого этапа фиксирует допуск исполнения и его состав; он пока **не резервирует
склад, последнюю порцию или производственную мощность**. AC-03 требует отдельного
складского домена и общей атомарной проверки перед началом оплаты.

`provisionFulfillment` — внутренний локальный provisioner, не HTTP/CLI для
кассира. Он задаёт привязку cloud producer/устройства, станции и immutable
`routing.version`. Для каждого product ID задаются station ID и `prep` либо
`assembly_item`. Напитки/готовые SKU явно направляются на assembly; пропуск
маршрута не превращает их в автоматически готовое блюдо.

У обычного блюда создаётся задача родительского SKU, а связанные добавления
дают дополнительные задачи. Для combo/set используются leaf-компоненты
`selectedDetails.components`, уже рассчитанные `catalog-pricing`; количество
компонента умножается на количество строки. Выбранные модификаторы и описания
сохраняются в заданиях, включая исключённые ингредиенты. Для linked modifier
нужен явный маршрут; схема не угадывает станцию по названию.

Версия маршрута и план закрепляются **до оплаты**. Публикация версии 2 не
переназначает задания резерва версии 1. Станции — логические идентификаторы,
не номера мониторов. Переназначение начатого задания, blocked и временная
смена станции при отказе экрана пока не реализованы.

## Локальные действия персонала

`act(branchId, auth, command)` использует существующий `authenticateStaff`:
активный сотрудник, терминал, сессия, её срок и отзыв проверяются в PostgreSQL.
Клиент не передаёт свою роль. `grantStation` локально назначает существующему
сотруднику `kitchen` станции. `shift_manager` может выполнять действия любой
станции своей точки; `cashier` не может отмечать приготовление/выдачу.
Кухонный сотрудник без нужного назначения получает отказ.

Каждая команда несёт уникальный `commandId`, `orderId`, `expectedVersion`.
Для задачи нужны также `taskId` и `expectedTaskVersion`. Старая версия не
перезаписывает действие другого экрана. Повтор команды возвращает исходный
результат, пока полномочия сотрудника действительны; отозванная сессия не
получает доступ даже через повтор старого ключа.

| Действие         | Переход                                                                                                          |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| `start_task`     | `queued → in_progress`, только на назначенной станции                                                            |
| `complete_task`  | `in_progress → done`; само по себе не делает весь заказ готовым                                                  |
| `ready`          | Отдельное подтверждение assembly после `done` всех обязательных задач                                            |
| `handoff`        | Только из `ready`, сотрудником assembly/управляющим; одно событие выдачи                                         |
| `confirm_stop`   | Станция подтверждает остановку `cancel_requested → cancelled`                                                    |
| `confirm_cancel` | Управляющий завершает отмену только после остановки активных задач; обязательны причина и `inventoryDisposition` |

При отмене уже начатого заказа queued-задачи отменяются, in-progress ждут
подтверждения остановки, выполненные задачи остаются `done` для аудита.
Управляющий отмечает `requires_inventory_review` или `recorded_elsewhere`.
Это запись решения/необходимости разбора: склад не восстанавливается и документ
списания автоматически не создаётся. Гонка ready/cancel сериализуется на строке
заказа; победившее действие исключает несовместимое действие со старой версией.
Возврат денег и чек возврата этим пакетом не исполняются.

## Чтение и доставка событий

`readOrder` проверяет локальную сессию; `listKitchen` требует kitchen/manager и
возвращает весь заказ с компонентами. `afterOrderId` — keyset cursor; limit 1–100,
страница ограничивается также примерно 2 MiB. Клиент обязан дочитывать cursor,
затем периодически обновлять список сначала: новые UUID могут появиться до
уже прочитанной позиции. Время поступления неизменяемо и доступно для FIFO/SLA UI.
Проекция одного заказа и его задач читается под одной блокировкой.

`readDisplay` выбирает только локальный номер и `preparing/ready`, без состава,
суммы, customer ID, телефона, никнейма и имени сотрудника. Номер назначается
единственным edge через PostgreSQL sequence, уникален; пропуски после rollback
допустимы. Операционная дата хранится в Asia/Almaty. Номер пока не сбрасывается
ежедневно и не ограничен тремя цифрами. После `handed_over`/отмены запись
исчезает из публичной проекции; таймер не создаёт выдачу. Будущий display
adapter фиксирует branch по устройству, а не разрешает выбирать другую точку.

Каждое изменение fulfillment создаёт один outbox-event с
`aggregate_type=order_fulfillment`, order ID и новой aggregate version.
Снимок коммерции и PII не копируются в эти статусные события. У task-событий
есть отдельные task ID/version/state/station и ID действовавшего сотрудника
для внутреннего аудита; публичным каналом этот outbox не является.

`claimOutbox` использует `FOR UPDATE SKIP LOCKED`, batch 1–100, lease 5–300 секунд,
worker ID и случайный lease token. `acknowledgeOutbox` принимает только текущий
неистёкший lease; точный повтор успешного ACK безопасен. После обрыва lease
позволяет повторную доставку. Это **at-least-once доставка и однократные локальные
эффекты**, а не обещание однократного HTTP. Consumers должны иметь inbox,
проверку aggregate version и восстановление пропусков. Здесь workers ещё нет.

Outbox, inbox, reservation и task identities защищены ограничениями/триггерами
от переписывания. Все runtime-конфликты блокируют отдельный order/command key;
глобальной блокировки операций заказа нет. PostgreSQL sequence назначает
номера/порядок outbox, а не держит одну бизнес-транзакцию на всю точку.

## Воспроизведение проверок

После включения пакета в workspace lockfile:

```sh
pnpm --filter @pickchick/edge-fulfillment... build
pnpm --filter @pickchick/commerce-core... build
node --test packages/edge-fulfillment/tests/*.test.mjs
```

По умолчанию используются только существующие локальные Docker PostgreSQL:
edge `127.0.0.1:55433/pickchick_edge`, cloud `127.0.0.1:55432/pickchick_cloud`.
Опциональные `EDGE_FULFILLMENT_TEST_DATABASE_URL` и
`EDGE_FULFILLMENT_CLOUD_TEST_DATABASE_URL` принимают только loopback и явные
имена dev/test БД, без параметров URL. Никакой `.env` с VPS не читается.

Каждая проверка создаёт случайную schema, применяет настоящие миграции,
использует настоящие роли/сессии персонала и удаляет schema в `finally` с
проверкой отсутствия. Внешних SMS, банка, ККМ, платежей и клиентских данных нет.
В одном fault-тесте собственная PostgreSQL-сессия временной schema обрывается
через `pg_terminate_backend(pg_backend_pid())`; требуется чистый reject процесса,
полный rollback и повтор после перезапуска. Другой child намеренно завершается
сразу после commit до отдачи результата; повтор не создаёт второй ticket.

Набор проверяет admission/hash/replay, wrong branch/device/producer/station,
реальные revoked staff credentials, pinned/missing routing, combo A/B,
assembly/ready/handoff, отмену и её гонки, immutable inbox/outbox, lease expiry,
полную пагинацию и ограничение крупных KDS-страниц. Cross-domain тест применяет
**фактические** события `CommerceRepository` между двумя временными БД:
synthetic capture без fiscal issued ещё не создаёт разрешения кухни;
после synthetic fiscal issued задания создаются, а локальная выдача не меняет
облачные денежные строки.

Нагрузочный сценарий держит 1 000 resident заказов и 3 000 задач на **одном**
синтетическом edge, с bounded concurrency 16, повторной авторизацией каждого и
дочитыванием всех KDS/LED страниц после создания нового экземпляра repository.
Он отдельно удерживает блокировку одного заказа и завершает действие другого,
проверяя отсутствие глобальной блокировки. Это не 1 000 HTTP-запросов в секунду,
не десять физических кухонь и не испытание оборудования.

Финальный локальный прогон: **14/14 PASS** (3 unit + 11 PostgreSQL scenarios),
TypeScript и ESLint без ошибок. Источник доменов — `b13546a` плюс исправление
PostgreSQL disconnect `376a3ea38346808cf79b3c374b42f63644e81e28`; этот helper
обязателен для строгого clean-rejection fault-теста. Ранее fault обнаружил
необработанное событие pg Client; сценарий не ослаблен до допуска аварийного
падения процесса.

На Apple M5, 10 logical CPU, 16 GiB RAM, Node 24.16.0 и локальном Docker
PostgreSQL 18.3 arm64 (`shared_buffers=128MB`, `max_connections=100`, `fsync=on`,
`synchronous_commit=on`) 1 000 заказов / 3 000 задач сохранены без ошибок и дублей.
Измеренная цепочка reserve → authorize → replay при concurrency 16: p50 **23,21 ms**,
p95 **29,47 ms**. Общая измеренная часть с пагинацией и проверкой независимых
блокировок заняла **2,055 s**. Это один локальный прогон на общей рабочей машине,
без сетевого HTTP, внешних исполнителей и отдельного ресторанного оборудования;
по нему не менялись индексы других доменов, PostgreSQL или инфраструктурный sizing.
Временные schemas удалены и отсутствие проверено. Следующий интеграционный
прогон/CI выполняется отдельно; пакет ещё не подключает кухню ресторана.

## Следующая интеграция

1. Аутентифицированный cloud↔edge транспорт, persistent worker и versioned
   projection статусов в commerce, включая handshake отмены перед возвратом.
2. Привязка принятого складского резерва к admission и маркированные
   производственные потери без автоматического восстановления.
3. LAN API с правами персонала/устройства, затем реальные KDS/LED/POS клиенты.
4. Настройка station routing по техкартам первой точки, реальные разрешения
   банка/ККМ и физический пилот без WAN с измеренными RPO/RTO.

Нет автоматического удаления history/inbox/outbox: retention/архив с защитой
replay и долговечных резервов требует отдельной политики и maintenance job.
