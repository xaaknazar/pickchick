# Telegram и бесплатный пилот - 26 сентября 2026

## Решения владельца

- Текст клиентских документов согласован. Повторное согласование того же текста
  не требуется; дата действия и публикация ещё не выполнены.
- Лимит отправок повышен с предложенных100 до **1000 в сутки**. Это общий предел
  резервирований всех каналов в PostgreSQL за UTC-день, не1000 на каждого клиента.
  Таймер повтора и ограничения телефона, устройства и IP остаются.
- Владелец намерен пополнить Gateway на$5. Фактическое пополнение не подтверждено,
  автопополнение не включалось. При опубликованной цене$0.01 за доставленный код
  это примерно500 кодов, без учёта возможных сборов пополнения. Лимит1000 не
  гарантирует наличие такого баланса. [Источник Telegram](https://core.telegram.org/gateway).
- Пилот доступен всем; еда временно бесплатная для проверки заказа и кухни до
  подключения интернет-эквайринга. Нельзя отмечать эти заказы банковской оплатой,
  выдавать им фиктивные фискальные чеки или начислять коммерческие бонусы.
- VPS: **hoster.kz, Алматы**, подтверждено владельцем в чате. Документ из кабинета
  не проверялся. На сервере backup timer активен, последний результат службы
  успешный. Копии на том же VPS не заменяют отдельного хранилища и проверки restore.

## Подготовлено в коде и локальной конфигурации

Шаблон `.env.customer-auth.example` и защищённая ignored-копия
`.local/customer-auth-pilot.env` содержат `CUSTOMER_AUTH_DAILY_SMS_BUDGET=1000`.
Это готовая конфигурация для выпуска; **на VPS лимит этим этапом не применён**.
Секрет Telegram хранится отдельно; в приложение, Git и публичный пульт не попадает.

Перед запросом кода mobile требует отдельную отметку для номера, канала и версии
документа. При изменении этих данных согласие не переносится на новый запрос.
Смена способа доставки возвращает к выбору и согласию, не вызывает скрытый SMS.
Условия работы аккаунта принимаются отдельно при проверке кода; реклама исключена.

API требует `delivery_consent: {privacy_version, accepted: true}` и проверяет
версию до резервирования и передачи провайдеру. Миграция023 добавляет
`identity_otp_challenges.delivery_consent_version`; существующий `created_at`
фиксирует момент принятия запроса. Оба записываются до отправки. Старые записи
получают NULL, согласие задним числом не приписывается. Запись хранится в пределах
прежнего срока жизни OTP-журнала; это не отдельный бессрочный архив согласий.

В `/v1/auth/config` добавлен `delivery_consent_required`. Мобильный журнал
сохраняет принятую версию вместе с идемпотентным запросом и восстанавливает её
после потери ответа/перезапуска. Новый сервер намеренно отклоняет старые клиенты
без согласия; auth API и клиент нужно выпускать согласованно. Старые TEST-заказы
и отключённый identity не требуют нового столбца. Readiness включённого identity
блокирует обслуживание без миграции023 или самого столбца.

1. Полная зелёная CI и проверенный выпуск. На базовомbcf4fe6 два задания CI
   завершились failure. Ошибка общего PostgreSQL прогона воспроизведена и исправлена
   выше; transport локально зелёный, причина его CI-сбоя не подтверждена.
   Загрузка подробных job logs через доступную авторизацию вернулаHTTP401.
2. Выпустить API/gateway с фактического VPS020 через021/022/023, включая INSERT ACL
   в `bo_records` для обращений. Сохранить штатные backup/lock/CAS проверки;
   старый release-order-events, рассчитанный на019, не применять вслепую.
3. Опубликовать согласованные документы по HTTPS, заполнить реальную версию/URL,
   карту получателей и фактические сроки хранения. Владелец уже согласовал текст;
   открытые сведения не подменять выдуманными значениями. Подробности в
   [клиентских документах](../legal/customer-documents-draft.md).
4. Связать настоящий `customerId` с доступом к заказам на сервере. Сейчас
   `useTestOrders`/`TestCustomerClient` держат отдельную TEST-сессию, а
   `useAccount` - identity-сессию. Клиентского запрета заказа без входа недостаточно
   для владения историей после смены аккаунта. Не объединять старые demo/TEST
   заказы с реальным номером автоматически. Проверить изоляцию двух клиентов,
   logout/login, отзыв токена, потерю ответа и перезапуск.
5. Установить mobile server-auth и проверить на устройствах: Telegram-вход →
   заказ без оплаты → приготовление → сборка → готово/табло → выдача → история.
   Статусы должны приходить по существующему events watch; доставка/оплата/чек
   не имитируются. Номер заказа сбрасывается новой сменой, не полуночью.
