# К14: подготовка POS-синхронизации в общей ветке

Обычным merge сохранены оба исходных коммита PR316 (`d2eb3081`, `48ede212`).
Отчёт backlog из PR319 (`a9360d60`) перенесён отдельно; инструменты будущих
миграций 026-028 и весь cutover не включались этим переносом.

## Что входит

- POS-синхронизация использует отдельный loopback-порт 43110. Порт 43100
  остаётся за действующим `PickChickFulfillmentTunnel`. Старую настройку POS
  на 43100 установщик отвергает, автоматически не переписывает.
- На схеме 020+ общий инструмент выдачи прав запрещает сброс уже имеющихся
  прав runtime до первого REVOKE. Для cloud-link используется отдельный
  инструмент добавления прав; историческое поведение схемы 019 сохранено.
- `infra/windows/pos-sync-backlog.mjs` читает очередь в READ ONLY-транзакции
  и выдаёт количества, суммы в минимальных денежных единицах и границы времени.
  Он не подтверждает события, не удаляет заказы и не запускает отправку.
- Сборщик ZIP включает backlog и все пять файлов, требуемых нынешним
  POS-установщиком, сам установщик, диагностику и руководство. Ранее общий
  сборщик пропускал часть обязательных файлов, и проверка manifest отказывала.
- Отдельный GitHub workflow выполняет существующие проверки чистых функций
  POS-установщика под Windows PowerShell 5.1.

## Перед первой установкой на точке

Из распакованного проверенного runtime выполнить локально:

```powershell
node --env-file=<защищённый-owner.env> infra/windows/pos-sync-backlog.mjs
```

Сохранить JSON приватно вместе с протоколом окна. Первый запуск отправит
неподтверждённые события, в том числе старые тестовые продажи. При
`decision_required: true` остановиться до решения владельца по очереди.
Данных о пяти исторических POS-записях из работающей кассы в этом облачном
прогоне нет. Здесь не принималось решение об их отправке или удалении.

Только после решения по очереди выполнять Prepare/Configure/Install/Verify
по `infra/windows/native-pos-sync.md`. Не менять и не останавливать
действующий fulfillment-туннель. Установку выполнять отдельно от перехода
024→025: его оператор намеренно отказывает при уже установленной POS-службе.

## Проверки и предел результата

Локально собран весь текущий workspace; проверяются реальные PostgreSQL ACL,
отказ сброса прав, добавление cloud-link, неизменность очереди при отчёте,
состав ZIP, PowerShell-парсер и восстановление файлов состояния. Результаты
точного итогового SHA и ссылки на GitHub CI сохраняются в PR.

Отдельный тест первичной настройки службы требует PostgreSQL >=18.6,
как закреплено в `native-foundation-db.mjs`. PostgreSQL 18.3 правильно
отвергается; требования установщика ради стенда не ослабляются.

Это подготовка к установке. К14 целиком не закрыт до чтения настоящей очереди,
решения по ней, установки на Windows и проверки получения продаж облаком.
Физическая касса, рабочая база, SSH-ключи и сервер в этой работе не менялись.
