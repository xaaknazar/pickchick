# LAN-клиент кухни и табло

`apps/kitchen` — отдельный браузерный клиент настоящего локального
`/edge/v1/fulfillment`. Старый публичный TEST-интерфейс `apps/operations` не меняется.
Клиент не создаёт заказы, платежи, допуски на кухню или доступы сотрудников.
Требуются включённый LAN fulfillment API, настроенная привязка edge к точке,
опубликованная маршрутизация и назначенные сотрудникам станции.

## Запуск на рабочем месте

```sh
pnpm --filter @pickchick/kitchen build
KITCHEN_EDGE_PORT=3101 KITCHEN_PORT=4178 node apps/kitchen/server.mjs
```

Открыть `http://127.0.0.1:4178` на том же компьютере. Gateway слушает только
loopback; целевой edge также доступен по loopback. Для отдельного экрана в LAN
нужен управляемый локальный туннель до узла точки: эта сборка не открывает HTTP
с токенами в общедоступную сеть. Нельзя заменить bind на `0.0.0.0` без отдельного
решения TLS/рабочего устройства. `KITCHEN_BRANCH_LABEL` — только подпись точки.
Пакет не требует новых runtime npm-зависимостей; общий TypeScript уже есть в repo.

Импортировать JSON, выданный штатным provision CLI для роли `kitchen` или
`shift_manager`. Используются `session_id`, `staff_id`, `terminal_id`, `branch_id`,
`role`, `token`, `expires_at`. Файл не загружается на сторонние сервисы.
Сам клиент не выпускает и не продлевает доступы. Проверку роли, срока, терминала,
точки и принадлежности станции выполняет настоящий edge API.

Сессия хранится в `sessionStorage`, без cookies и URL-параметров. Повторная загрузка
страницы сохраняет вход в этом окне; закрытие вкладки требует нового импорта.
Web Locks выделяет один активный клиент на пару сотрудник/терминал/точка в пределах
данного browser origin. Если Web Locks недоступен, действия не разрешаются.
Разные браузерные профили этот механизм не координирует: конкуренцию терминалов
окончательно разрешают серверные версии и идемпотентность.

## Действия и восстановление

- Приготовление: начать / завершить только задачи выбранной станции.
- Сборка: собственные задачи плюс весь состав других станций для контекста.
  «Заказ собран» появляется только когда все задачи готовы; выдача — только
  для `ready` на станции сборки. Сервер повторно проверяет каждый переход.
- Запрос отмены: сотрудник подтверждает остановку своих задач. Итоговое
  `confirm_cancel` с причиной и учётом остатков оставлено управляющему через
  доверенный служебный инструмент; произвольной отмены в этом UI нет.
- До POST в `localStorage` записывается журнал с order/station ID, исходным телом,
  ожидаемыми версиями и UUID idempotency key. Запись проверяется чтением.
- При таймауте, 5xx или повреждённом ответе успех не рисуется. Новые команды
  заблокированы до восстановления. Повтор посылает ровно прежний body/key;
  перезапуск сам не отправляет POST. Ответ команды — квитанция; экран после него
  перечитывает текущее состояние заказа/очереди.
- Только полный strict ErrorSchema с допустимой парой HTTP status / code считается
  подтверждённым отказом. HTML/битый JSON/произвольный code на 401/403/409 остаются
  неизвестным исходом: credential и журнал сохраняются, сверка 409 не включается.
- При подтверждённом CONFLICT(409) UI перечитывает заказ, показывает его состояние и версию и ждёт явной
  сверки сотрудника. Автоматического повтора с новой версией/ключом нет.
- Logout/подтверждённые UNAUTHORIZED(401)/FORBIDDEN(403) скрывают очередь и очищают credential; журнал команды сохраняется.
  Для восстановления импортировать доступ того же сотрудника/терминала/точки.
  Нельзя очищать данные браузера или редактировать журнал при неизвестном исходе.
- Обновление и действия выполняются последовательно. Logout доступен немедленно,
  даже при ожидании сети, и меняет epoch сессии. Запоздалый GET/POST прежнего epoch
  не восстанавливает вход и не меняет состояние новой сессии. Журнал старого POST
  сохраняется: новый вход восстанавливает его и проверяет точным повтором.

## Большая очередь и табло

Каждый refresh начинает чтение API с первого cursor. Страницы по 100 дочитываются
до конца, проверяются и только затем целиком заменяют локальный перечень. Ограничения:
100 страниц, 10 000 записей, 50 MiB сериализованных символов, 20 секунд между
страницами; отдельный HTTP-ответ ограничен 3 MiB, timeout 12 секунд.
Превышение / повтор cursor / некорректный ответ / ошибка середины загрузки
оставляет последнюю целую очередь и явную ошибку. Это не транзакционный snapshot
нескольких HTTP-запросов: изменения в ходе обхода сходятся следующим refresh.

Кухня сортирует загруженные заказы по времени создания, затем ID, и показывает
явные локальные страницы по 50. Счётчики подписаны «На странице»; прокрутка
доступна, карточки и нижняя навигация не обрезаются фиксированным canvas.
Новые заказы с меньшим UUID не теряются из-за сохранённого серверного cursor.

Табло использует отдельный endpoint с только `{number,state}`; лишние поля
отклоняются валидатором. Имена, телефоны, состав, деньги и customer ID не
запрашиваются в режиме табло. Номера автоматически сменяются каждые 8 секунд:
до 6 «готовится» и до 4 «готово», с номером страницы и общим количеством.
Нет искусственного прогресса, ETA, рекламных обещаний или подсчёта бонусов.
Это служебная сессия с обычным сроком действия; отдельного бессрочного
unattended device credential этот этап не выпускает. При недоступности edge
показываются последние данные и явный статус связи, при отказе доступа — вход.

## Защитные границы gateway

Точный Host и same-origin; reject cross-site. Только фиксированный loopback upstream,
allowlist методов, маршрутов и query-параметров. JSON POST ≤16 KiB, response ≤3 MiB
проверяется при потоковом чтении. Redirects запрещены. Пересылаются только auth,
staff session, terminal и idempotency headers; cookies, CORS, Location и Set-Cookie
не пересылаются. Static files — фиксированный список, CSP self-only, no-store.
На gateway нет облачного ingress, SMS, checkout, банковских или фискальных маршрутов.

## Дизайн и доказательства

Инертные оригиналы заказчика сохранены в
`design/reference-source/kitchen.html.txt`, `display.html.txt`; точные SHA и пути
в `kitchen-display.provenance.json`. Это исходные `.dc.html`, не наш производный
прототип. Код демонстрационной генерации заказов в них не исполняется приложением.
Сохранены тёмно-синяя шапка, #0047BB / #FF671F, фон bg-blue, Montserrat/Golos,
светлые карточки, крупные номера, оранжевые действия и двухколоночное табло.
Существенные адаптации: реальные станции/статусы, журнал восстановления,
пагинация, отсутствие имён/фиктивного ETA и SLA-статистики, доступные button/select.

Исходник рассчитан на 1920×1080; рабочие размеры проверки 1280×800 и 1920×1080.
Снимки реализации не выдаются за снимки исходника. Проверка на физическом
кухонном оборудовании, масштабе Windows, сетевом туннеле и отключении WAN
остаётся отдельной приёмкой точки; локальный browser/PG тест её не заменяет.

## Воспроизводимые проверки

```sh
node apps/kitchen/build.mjs
node --test apps/kitchen/tests/*.test.mjs
PICKCHICK_BROWSER_PYTHON=.local/design-venv/bin/python node --test tests/kitchen/browser.test.mjs
```

Последняя команда требует локального PostgreSQL из dev compose и установленного
Playwright из `tests/design/requirements.txt`. Создаёт только временную schema,
настоящие короткоживущие credentials и синтетические разрешённые доменным
fixture заказы. Cleanup удаляет schema/credentials и останавливает свои HTTP servers.
Никаких live API/VPS/SMS/банков. Тест выполняет реальный prep→assembly→ready→handoff
через gateway; теряет один ответ после реального commit, затем проверяет точный
повтор после reload и итог PostgreSQL `handed_over`. Секретный fixture JSON — только
в `.local`, режим 0600, удаляется в finally; PNG не содержат credentials.
