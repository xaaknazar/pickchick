## Исправления для запуска

### Явный маршрут мобильных комбо

У закреплённого каталога 24 мобильных строковых ID, а на кассе используются
24 детерминированных UUID из `local-pos-draft.mjs`. Комбо содержат выбранные
модификаторы, но не содержат структурированной `combo_components` рецептуры.
Ранее такое комбо отклонялось до оплаты как `ROUTING_MISSING`.

Для этого каталога добавлен явный локальный параметр маршрута
`unexpandedCombo: whole_product`: кухня получает комбо целиком с количеством,
описанием и всеми выбранными напитками/соусами. Это соответствует решению
владельца об одном подтверждении чека; состав и количества рецептуры не выдумываются.
Без параметра прежний отказ сохраняется. Разрешение относится к одному product ID,
не ко всем комбо. Linked additions без раскрытого состава по-прежнему отклоняются;
у комбо с раскрытым составом сохраняется прежняя маршрутизация компонентов.

`scripts/build-mobile-kitchen-routing.mjs` только готовит новую версию. Проверяет
хеш действующего routing, сохраняет каждый старый POS-маршрут и добавляет мобильные
ID к тем же явно назначенным станциям. Неизвестная позиция, повтор ID, изменившийся
каталог или уже существующая мобильная привязка требуют рассмотрения. Скрипт не
пишет в БД. На действующем read-only снимке подготовлены 48 маршрутов version2,
SHA256 `56e0cc6bec2a91c9c2a28731e19a0d761f5cc4fb7e5f02f7c64b593be52dd43a`.
На кассе пока остаётся version1. Новая версия требует совместимого обновления
Edge и worker; старый runtime со strict routing schema её не понимает.

Проверены 4 unit и 27 PostgreSQL сценариев fulfillment, включая сохранение выбора
при admission, запрет готовить до authorize, приготовление, сборку и выдачу одним
чеком. Отдельный тест проверяет соответствие всех24 мобильных ID и сохранение
старых маршрутов. Это локальное доказательство, не реальный оплаченный заказ.

`infra/staging/checkout-grants.mjs` разделяет права API и банковского worker.
API может создать immutable quote/order/attempt, но не записать банковское
подтверждение или переписать цены. Отдельный worker может зафиксировать
подтверждение и outbox, но не менять сумму capture, создавать клиентские
сессии, редактировать аккаунт провайдера или оформлять возврат.

Provision применяет checkout grants после transport/backoffice grants,
иначе их REVOKE убирает нужные права. Флаг проверяется вместе с полным scope
существующей серверной политики. При выключении снимаются checkout INSERT
и доступ к таблице счетов; права остальных подсистем остаются их ответственностью.

`infra/payments/kaspi-bridge/worker.compose.yaml` запускает отдельный процесс
из проверенного API image. Секреты читаются из read-only файлов, порт не
публикуется; worker использует network namespace действующего моста.
Перед запуском мосту нужен доступ в private Docker network БД. При замене
контейнера моста companion требуется пересоздать, чтобы присоединить новый namespace.
