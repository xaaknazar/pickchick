# Финансы: короткий ввод и аналитика

7 октября 2026. Ветка `codex/finance-dashboard`, база `2f00491`.
Предыдущий финансовый выпуск установлен из `d6cd144`; этот документ описывает
следующее изменение, а не утверждает его установку на VPS.

## Решение владельца

Убрать выбор счёта при обычном вводе операции, сократить форму, приблизить
сводный ОПиУ к переданному Excel и добавить графики ДДС/ОПиУ.
Структура листа «Август» повторно сверена по группам и формулам. Реальные суммы,
сотрудники и контрагенты из файла не импортировались и не сохранены в Git.
Ошибки исходных формул C79 и расчёта себестоимости не перенесены.

## Реализация

- Поступление/расход сохраняются с `account_id: null`. Нет автоматического
  создания кассы, банковского счёта или выдуманного начального остатка.
  Суммы включаются в ДДС по cash_date, в ОПиУ по recognition_date.
- В основной форме тип, сумма, дата, статья, подразделение и назначение.
  Контрагент, примечание и отдельная дата признания находятся в «Дополнительно».
  По умолчанию дата ОПиУ следует за денежной датой; отдельная дата сохраняется.
- Счета и переводы сохранены в необязательных настройках. Перевод по-прежнему
  требует два разных существующих счёта. В остатках явно указано, что операции
  без счёта в них не входят; их поступления/выплаты показаны отдельно.
- Начальная вкладка «Сводка» сравнивает движение денег и результат периода.
  ДДС/ОПиУ показывают одну раскрываемую таблицу, а не отдельные карточки групп.
  ОПиУ содержит доли от выручки, валовую прибыль, результат после потерь,
  операционные расходы, операционную прибыль и итог внесённых данных.
  При нулевой выручке доля обозначается «-», а не выдуманным процентом.
- График поступлений/выплат или доходов/расходов по дням; для периода длиннее
  45 дней - по месяцам. Доступна таблица точных значений. Горизонтальные полосы
  показывают крупнейшие расходы, доли и переход к соответствующим операциям.
  Остальные статьи суммируются отдельно, поэтому общая сумма не теряется.
- Сервер агрегирует полный период в одной repeatable-read транзакции, отдельно
  по датам денег и признания. Пагинация и поиск журнала не меняют графики.
  Отменённые записи и внутренние переводы исключены. Фильтр подразделения
  действует одновременно на отчёт и динамику.
- Все финансовые суммы остаются строками минимальных единиц, SQL numeric/BigInt.
  Number используется только для ограниченной относительной ширины полос.
  CSV сохраняет точные тиыны. Пользовательский текст выводится через textContent.
- Старые записи, права и применённые миграции не меняются. Новой миграции нет.
  Нет банковских вызовов, фискализации, исторического импорта или новых доступов.

## Проверка

Адресные unit/model, настоящие HTTP/PostgreSQL и browser проверки включают:
ввод без счёта, 105 записей и полные агрегаты, два периода признания, фильтры,
повторы, отмены, права аналитика, закрытый месяц, откат при отказе аудита,
суммы больше Number.MAX_SAFE_INTEGER, отсутствие старого API timeline,
CSV и потерю ответа с восстановлением после reload. Браузер проверяет
1440/768/393, ввод и просмотр без горизонтального переполнения страницы.
Все примеры синтетические, PostgreSQL только на loopback 55442 в временных схемах.

Локально: 14/14 адресных проверок прошли, сборки backoffice/backoffice-core/API,
ESLint, Prettier и diff-check успешны. Браузерный сценарий завершился без JS ошибок.

## Выпуск и совместная работа

Нужен согласованный выпуск API и backoffice из одного проверенного коммита.
Новый интерфейс нельзя выпускать первым поверх старого API: тот отклоняет
денежную операцию без account_id. Старый API также не умеет отменять такую
новую запись, поскольку проверяет старую строгую схему. При откате интерфейса
оставить совместимый финансовый API; не восстанавливать старый dump и не удалять
новые записи. Перед переключением проверить незавершённые команды.
Если API не возвращает timeline, интерфейс явно сообщает о недоступной динамике.

На этом Mac нет разрешённого SSH-доступа. Серверные области заняты другой
задачей `kiosk-kaspi-qr`; установка этого изменения не выполнялась.
Перед релизом выпускающий Mac должен сверить свежие pointers/schema и занять
серверные области. Старый release-finance-ledger.py нельзя повторно применять
как готовый новый релиз: его baseline 850c6fa и две остановки документированы
в протоколе предыдущей установки. Нужен проверенный профиль обновления текущего
API/public без повторного применения миграций и без изменения киоска/банков.

Общие project-status/roadmap/handoff зарезервированы farm-gameplay-v2,
онлайн-roadmap - tiptoppay-test-rollout. Они не переписываются параллельно.
После освобождения включить этот результат и отдельно факт будущей установки.
