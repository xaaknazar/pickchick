# Б10: Redis-конфигурация и ротация журналов

9 ноября 2026. База работы: общий срез `eb86d392b8cb820669783fb49b7e127a0a9bee6c`.

Завершена подготовка к проверке Б10: аудит без чтения секретов, ограничение
журналов при **первой** установке staff-login и воспроизводимая проверка Docker.
**Б10 целиком не закрыт:** фактические права, пользователи и журналы на VPS
не проверены, существующие контейнеры не изменялись. Доступа к VPS в этой
облачной сессии нет. Это не серверный релиз.

## Что исправлено и почему

`infra/backoffice-login/release.py` теперь создаёт staff-login с `json-file`,
`max-size=10m`, `max-file=3`. Это примерно 30 MiB файлов журнала на контейнер,
а не жёсткая дисковая квота: Docker может превысить порог отдельной записью.
Остальные проверки установки, блокировки, CI и маршруты не менялись.

Уже созданный контейнер эти параметры автоматически не получает. Повторять
первичную установку поверх рабочего сервера нельзя. В
`infra/backoffice-login/update.py` явной политики ротации пока нет: файл
закреплён за другой задачей `restaurant-completion`. При согласованном обновлении
нужно добавить политику и туда, иначе пересоздание опять будет зависеть от
настроек daemon. Контейнеры iDrink и их исходные deployment-файлы не менялись.

`infra/staging/generate-secrets.py` намеренно выставляет Redis-файлу 0644 внутри
каталога 0700. Одна цифра 0644 ещё не означает, что любой пользователь хоста
может прочитать файл: нужно право прохода через все родительские каталоги.
При bind mount контейнер видит файл по своему пути; права родителей хоста
не защищают его от других пользователей внутри контейнера. Нужно проверить
реальный UID/GID, группы, ACL, остальные mounts, доступ к Docker и sudo.

На закреплённом образе Redis 8.2.1 подтверждено: файл 0644 внутри 0700 доступен
Redis через read-only bind, а смена только режима на 0600 при прежнем владельце
приводит к отказу запуска `Permission denied`. Генератор секретов и рабочие
права поэтому не менялись. Выбор 0600/0640 с подходящим владельцем/группой
требует отдельной проверки фактического окружения и запуска после изменения.

## Как провести фактический аудит

Запускать на Linux-хосте с нужным локальным Docker daemon, из проверенной копии
репозитория. Нужны права читать metadata файла, его родителей и Docker socket.
Сначала сверить актуальную серверную резервацию и deployment lock. Взять
фактические имена всех контейнеров staff-login и iDrink, включая БД/Redis/worker,
если они входят в iDrink. Не считать приведённые ниже имена инвентаризацией VPS.

```sh
umask 077
python3 infra/operations/server-storage-audit.py \
  --redis-conf /ABSOLUTE/ACTUAL/secrets/redis.conf \
  --redis-container ACTUAL_REDIS_CONTAINER \
  --container pickchick-staff-login \
  --container ACTUAL_IDRINK_CONTAINER > b10-audit.json
```

Повторить `--container` для каждого дополнительного контейнера. Инструмент:

- Читает только metadata файла/родителей и имена xattr; содержимое Redis-конфига
  не открывает. Символические ссылки, ACL или недоступные metadata требуют
  ручной проверки и дают `unknown`.
- Обращается только к `unix:///var/run/docker.sock`, игнорируя удалённые
  `DOCKER_HOST`, `DOCKER_CONTEXT` и TLS overrides. Не запускает SSH.
- Запрашивает у Docker только LogConfig, Mounts и Running. Не запрашивает
  environment, команду контейнера, логи или содержимое конфигураций.
- Выводит только выбранные поля: режим, UID/GID, вывод о DAC для other,
  наличие точного read-only bind и числовые ограничения логов. Не выводит
  пути mounts, неизвестные logging options или сырые ошибки Docker.
- Ничего не меняет: нет chmod/chown, рестартов, удаления журналов или контейнеров.

Код выхода 0: выбранные metadata удовлетворяют узким проверкам. Код 2:
нужна проверка/исправление, включая неизвестный результат. Код 1: недопустимое
имя контейнера. Ошибка аргументов argparse также возвращает 2.

`json-file` без положительного `max-size` считается неограниченным;
одного `max-file` недостаточно. `local` без явных параметров использует
штатные 20 MiB × 5. `journald`, внешние drivers и `none` требуют отдельной
проверки хранения/сохранности журналов, а не объявляются автоматически исправными.
Неизвестные форматы опций дают `unknown`.

Это снимок metadata выбранных контейнеров, не полная проверка безопасности:
не исключены изменения во время проверки, дополнительные mounts, доступ
через группы/привилегии и log files внутри контейнеров. Значение
`runtimeReadabilityVerified=false` остаётся явным даже при коде выхода 0.
Нет проверки Redis AUTH/health, фактического оборота файлов или полноты списка
контейнеров. Вывод с UID/GID и именами контейнеров хранить как внутренний отчёт.

## Проверки

```sh
python3 -m unittest tests/operations/test_server_storage_audit.py
python3 infra/backoffice-login/test_release.py
```

13 новых проверок: 0644/0700, доступный путь, 0600, symlinks, ACL/ошибки,
необычные пути, json-file/local/external drivers, недопустимые параметры,
локальный Docker, отсутствие утечек, недоступный контейнер, точный read-only bind
и коды выхода CLI.
5 существующих проверок первичного установщика тоже прошли.

Для изолированного Docker-стенда без daemon-level ротации json-file:

```sh
docker --host=unix:///var/run/docker.sock pull redis:8.2.1-alpine@sha256:987c376c727652f99625c7d205a1cba3cb2c53b92b0b62aade2bd48ee1593232
python3 tests/operations/server_storage_docker.py
```

Runner использует случайные имена, `--network none`, не публикует порты,
не подключается к существующим контейнерам; в `finally` удаляет только свои
контейнеры и анонимные volumes. Docker должен видеть `.local` рабочей копии.
Конфигурация содержит только публичную синтетическую строку, не настоящий ключ.
Параметры ротации извлекаются из реальной команды `release.py` и проверяются
Docker, сам установщик не выполняется. Проверены 6 условий, протокол рядом:
[docker-evidence.json](docker-evidence.json). Fixture-контейнеры удалены.

При первом прогоне Docker отклонил явно заданный `max-size=-1` при старте.
Runner исправлен: для неограниченного случая применяется штатный json-file
без max-size. Итоговый прогон прошёл полностью; провалившийся тоже убрал свои
контейнеры. Это не ошибка рабочего Redis и не изменение его конфигурации.

1. Снять этот отчёт на VPS для полного актуального списка контейнеров.
2. Проверить доступ Redis с фактическими UID/GID/ACL; любое изменение режима
   сначала испытать на копии конфигурации с тем же образом и пользователем.
3. Согласовать исправление update.py с владельцем его области, сохранить
   настройки/образы/volumes существующих staff-login и iDrink, подготовить
   обратимый план пересоздания в серверное окно. Не делать Docker prune,
   truncate журналов или массовый restart.
4. После применения проверить LogConfig, здоровье сервисов, вход в бэк-офис
   и работу iDrink, затем сохранность и фактическую ротацию журналов.
5. Сохранить обезличенные доказательства и только тогда отметить весь Б10.
