# С8: отключение TEST API с сохранением Apple Review

9 ноября 2026. Проверена общая база `f643f902de30fa07e3110b04829b50a1a7e3ca1f`
после PR #332/#333. Рабочие флаги не менялись. Плановая дата С8 - 16 ноября;
этот документ фиксирует проверку совместимости и порядок будущего переключения.

## Что проверено

Новый `tests/integration/test-mode-cutover.test.mjs` запускает настоящий `createApi`
и HTTP-сервер с полными миграциями PostgreSQL 18.3. Каждый прогон использует
изолированные схемы. Переход проходит через настоящий `loadConfig`, меняя
`TEST_ORDER_FLOW_ENABLED` между `true`, `false` и обратно, с перезапуском API.

1. При включённом TEST API создаются гостевая сессия, котировка и синтетический
   заказ. Вход Apple Review работает, но создание TEST-сессии проверяющему
   уже запрещено (403). Это положительный контроль перед отключением.
2. После отключения capabilities показывают `test_order_flow=false` и
   `unpaid_test_orders=false`, `phone_auth=true`, readiness отвечает 200.
   Каталог TEST, история, кухня/табло, сессии, котировки, неоплаченные TEST-заказы,
   симуляция оплаты и выдача отвечают 404. Проверены анонимный запрос, старый
   гостевой токен, обычный customer token и App Review token.
3. Сохранённые обычная и review-сессии продолжают работать. Новый вход
   проверяющего и refresh успешны, создание заказа и счёта возвращает 403.
   В commerce orders/payment attempts/Kaspi invoices остаётся ноль строк.
   Удаление синтетического review-аккаунта действительно отзывает его сессии,
   а сессия обычного клиента сохраняется.

До и после сравниваются полные строки TEST orders/quotes/outbox и migration
ledger. После обратного включения прежний TEST-заказ читается тем же гостем.
Ничего не удаляется для отключения флага. Итог Node runner: **4/4 PASS**
(три подэтапа и общий сценарий), без пропусков.

Коды, телефоны, ключи и данные тестовые. Внешние fetch-запросы блокируются
самим тестом; их счётчик остаётся нулевым. Для обычного клиента код выдаёт
локальный fake transport. Задержка повторного запроса OTP моделируется
сдвигом времени только challenge-строк этой фикстуры; рабочие лимиты не меняются.
DB-доступ стенда owner, поэтому это не приёмка фактических runtime grants VPS.

Дополнительно проверен завершившийся mobile job
[129105884765](https://github.com/xaaknazar/pickchick/actions/runs/42601172103/job/129105884765)
для исходника `2346a3b9c7fe813450f4fccb66ba60d33f66a470` (PR #332).
Шаг `Verify storefront, review checkout and opt-in payment presentation` - PASS.
Он собирает production-профиль с API `api.pickchick.kz`, обоими TEST-флагами `0`

## Какие настройки относятся к С8

| Область         | Условие переключения                                                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Cloud API       | Эффективный `TEST_ORDER_FLOW_ENABLED=false` у запущенного API и в сохранённой конфигурации следующего запуска                                   |
| iOS/Android     | В установленном артефакте `EXPO_PUBLIC_ORDER_SIMULATOR=0`, `EXPO_PUBLIC_UNPAID_TEST_ORDERS=0`, опубликованный каталог и утверждённый API origin |
| App Review      | Сохранить `CUSTOMER_AUTH_ENABLED=true`, `CUSTOMER_REVIEW_ACCOUNT_ENABLED=true`, прежние phone/digest и четыре ключа identity                    |
| Доставка кодов  | Сохранить действующий provider и его приватные настройки; не ставить `PHONE_DELIVERY_PROVIDER=disabled`                                         |
| POS/киоск/кухня | Отдельно проверить установленные артефакты и режимы на устройствах; выключение cloud TEST API не доказывает готовность кассы                    |

Настройки review-аккаунта независимы от TEST API. Однако `CustomerIdentity.enabled()`
требует доступный канал доставки ещё до обработки review-номера. В первоначальной
фикстуре с `PHONE_DELIVERY_PROVIDER=disabled` запрос кода вернул 503; с настроенным
Telegram transport и запретом любых исходящих запросов review-вход прошёл без
отправки сообщения. Поэтому при С8 нельзя выключать общую доставку кодов.

Оба мобильных флага закреплены в `scripts/mobile/ios_release.py`; Android
использует те же профили. Они вшиты в JS bundle: изменение VPS или переменной
на компьютере не изменит установленный бинарник.

Не менять серверный `APP_ENV` на `production`: текущий `loadConfig` допускает
`local/test/staging`, а production здесь является отдельным мобильным профилем.
Не выключать реальный Kaspi checkout или обычную customer identity под видом
отключения TEST. Демо Apple Review остаётся локальным и не является TEST API.

## Порядок в серверное окно

1. Получить свежий общий код, занять серверную область через ProjectSync и
   сохранить фактические API SHA, compose overlays, текущий флаг и release guards.
   Не заменять действующий compose шаблоном из Git: на VPS могут быть JSON и
   дополнительные overlays. Секреты не печатать и не сохранять в отчёт.
2. Сверить фактическую TEST-очередь. Незавершённые TEST-заказы отдельно завершить
   или отменить штатным путём до отключения. Историю сохранить. Реальные
   неоплаченные customer-заказы не относятся к `unpaid_test`; их не удалять.
3. По штатному процессу конфигурационного выпуска изменить только TEST gate,
   сохранить остальные runtime-настройки и backup/rollback evidence, перезапустить
   API. Проверить сохранённый флаг и эффективный флаг процесса; одного файла env
   недостаточно. Миграции, отзыв identity grants и очистка таблиц для С8 не нужны.
4. Проверить runtime readiness, capabilities, HTTP 404 TEST-маршрутов и публичный
   gateway. Затем приватно проверить App Review вход, обычную customer-сессию,
   опубликованное меню, запрет реальной оплаты для review и локальную демонстрацию.
   Удаление существующего review-аккаунта не входит в переключение: его удаление
   проверено только на синтетическом стенде.
5. На кассе, киоске и телефонах подтвердить версии установленных артефактов и
   отсутствие TEST-оформления. Если acceptance не проходит, остановить переход
   и вернуть сохранённую конфигурацию штатным rollback, не восстанавливать БД
   поверх новых данных. Вновь включённый TEST API снова допускает TEST-заказы.

После окна сохранить SHA/время, результаты до/после и подтверждение на устройствах.
Только тогда отмечать весь С8 закрытым. Сейчас завершена **стендовая проверка
совместимости отключения**. VPS, gateway и установленные приложения не изменены.
Общие status/roadmap заняты другой задачей; отчёт передаётся через PR и ProjectSync,
онлайн-пульт этим этапом не обновлён.

## Повторение

На изолированных локальных PostgreSQL/Redis с `.env` из лабораторной среды:

```sh
pnpm install --frozen-lockfile
pnpm --filter '@pickchick/api...' build
node --env-file=.env --test tests/integration/test-mode-cutover.test.mjs
```

Общий `pnpm test:integration` уже включает файл по glob. Перед выпуском нужен
полный CI точного выпускаемого SHA и проверка текущих настроек на сервере;
результаты предыдущего SHA не переносятся автоматически.
