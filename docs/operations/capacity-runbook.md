# Ёмкость и перегрузка: эксплуатация foundation

Цели сети и границы текущей реализации: [ADR 0007](../architecture/adr/0007-capacity-and-fixed-controls.md).
Рабочие million-profile / 1 000-KDS испытания ещё не проведены. Ниже — процедуры
для реализованного локального/staging foundation, без платежей и SMS.

## Конфигурация

`DB_POOL_MAX=5`, `HTTP_MAX_IN_FLIGHT=32` — текущие defaults. Compose передаёт оба
значения API. Изменять через версионируемый release env, пересоздавая только API;
не перезапускать общие PostgreSQL/Caddy или соседний сервис ради такого изменения.
Проверить нагрузку и бюджет всех реплик до повышения. Падение p95 при росте
`pickchick_db_pool_waiting` означает необходимость анализа запросов/БД, а не
автоматического увеличения очереди HTTP.

HTTP 503 с `Retry-After` означает занятость сервиса. Повтор выполняется с jitter;
если ответ на команду неизвестен, использовать прежний idempotency key и сверить
сохранённый результат. Не создавать новый платёж/заказ при каждом retry.
Промежуточный gateway timeout также не доказывает rollback БД.

## Приватный мониторинг

Scraper размещать в private network/VPN, не публиковать health/metrics наружу.
Пример job для существующей сети Compose; сам Prometheus этим файлом не запускается:

```yaml
scrape_configs:
  - job_name: pickchick-staging-api
    metrics_path: /health/metrics
    scrape_interval: 15s
    scrape_timeout: 3s
    static_configs:
      - targets: ['api:3100']
        labels:
          environment: staging
```

Предварительные сигналы для настройки после baseline:

- `up == 0` две минуты: API/scraper недоступен, сравнить private live и ready.
- `rate(pickchick_http_rejected_total[5m]) > 0` пять минут: проверить входящий пик,
  пул БД, медленные запросы и запас реплик. В planned overload это ожидаемое событие.
- `pickchick_db_pool_waiting > 0` одну минуту или occupancy > 80% пять минут:
  проверить locks, SQL plans и admission. Не снимать limiter для обхода симптома.
- Рост heap между сравнимыми quiet intervals: снять безопасный runtime profile,
  не выгружая клиентские данные в GitHub.

Метрики process-local сбрасываются при рестарте; `rate` учитывает reset.
Идентификаторы экземпляров добавляет scraper. Нет labels на каждый URL/клиента.
Histogram HTTP latency, queue age, event delivery lag, PG WAL/replication lag,
диск, backup age и алерты вне основного хоста нужны перед production Gate;
текущий endpoint не означает, что полный мониторинг уже развёрнут.

## Воспроизводимые проверки

Из корня репозитория, после локальной настройки `.env` и синтетической БД:

```sh
pnpm build
pnpm test:integration
node --env-file=.env tests/load/local-read.mjs
```

Baseline запускает отдельный API на loopback, читает 2 000 раз меню/точки с 16
параллельными клиентами и закрывает процесс. Допустимы только APP_ENV local/test;
адрес внешнего стенда не принимается. Сохраняет JSON в stdout: машина, Node,
concurrency, длительность, throughput, p95/p99, ошибки и очередь пула после теста.
Порог p95 400 мс; сравнивать результаты только на сопоставимых стендах. Этот
read-only baseline не измеряет запись заказа, банк, realtime или миллион профилей.

Integration отдельно блокирует таблицу PostgreSQL, насыщает лимит, разрывает
клиентский запрос и проверяет, что SQL остаётся учтённым до завершения; затем
проверяет восстановление без перезапуска. Нельзя воспроизводить этот LOCK-тест
на работающем ресторане или общем VPS.

## Будущий нагрузочный стенд

Создать отдельные базы/Redis/edge fixtures и пользователей без реальных телефонов.
Каждый тест маркировать run ID, сохранять начальные и конечные счётчики, сумму
платежей/возвратов/бонусов и журнал потерянных событий. Внешние провайдеры —
детерминированные адаптеры с задержками и duplicate/unknown outcome. Отдельный
согласованный sandbox-прогон проверяет реальные контракты провайдеров.

Генератор должен поддерживать открытую модель заданных arrival rates, считать
неотправленные итерации ошибкой ёмкости генератора и завершать только собственные
синтетические заказы. Продолжительность/нагрузка и stop conditions фиксируются
до старта: p99 > 5 с пять минут, неожиданные финансовые эффекты, рост диска > 80%,
отказ зависимостей вне сценария. Shared staging сейчас не является таким стендом.
