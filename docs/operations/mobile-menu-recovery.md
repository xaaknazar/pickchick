# Восстановление загрузки мобильного меню

## Наблюдение 8 сентября 2026

В PickChick Dev появилось «Нет свежего меню». На Mac в той же Wi-Fi-сети
HTTPS к публичному API завершался таймаутом. Прямое указание IP через
`curl --resolve` не помогло; имя разрешалось в ожидаемый IP. TCP 443 был
недоступен с этого подключения, тогда как TCP 22 и 80 соединялись.
HTTP 80 возвращал штатный redirect на HTTPS.

На VPS read-only проверки показали здоровые API, PostgreSQL и Redis.
Readiness и публичные capabilities, branches, menu и test catalog через
серверный HTTPS ответили HTTP 200. В текущем тестовом каталоге 24 блюда.
Владелец отключил Wi-Fi на iPhone и повторил загрузку через мобильную сеть:
**меню появилось**.

Сбой локализован до сетевого пути текущего Wi-Fi к HTTPS сервера. Причина
на уровне роутера, провайдера или фильтрации по источнику ещё не установлена.
Это не доказательство поломки самого роутера или полного отказа VPS.
Сетевые настройки и firewall не изменялись.

## Поведение клиента

После временной транспортной ошибки или HTTP 408/429/5xx мобильный клиент
повторяет только публичное чтение каталога. После первой попытки допускаются
три повтора с паузами 2, 5 и 15 секунд после завершения неудачной попытки.
Запросы имеют таймауты; одна цепочка не запускается поверх другой.
Ошибочная схема, несовместимые возможности API и остальные HTTP 4xx
не вызывают автоматический цикл повторов.

Уход приложения в фон отменяет запросы и таймеры; возврат на передний план
начинает новую ограниченную загрузку. Ручной повтор и выбор точки отменяют
предыдущую цепочку. Уже успешно загруженные блюда остаются в памяти при
ошибке обновления. Синтетический локальный каталог автоматически не подставляется,
а оформление требует актуального успешного соединения, как и раньше.
Постоянного дискового кэша меню эта правка не добавляет.

Повторы не распространяются на создание заказа, оплату, отмену, SMS или бонусы.
Это улучшение восстановления клиента, а не исправление маршрутизации Wi-Fi.
Если соединение остаётся недоступным дольше цикла повторов, нужен возврат
в приложение после смены сети либо ручная проверка доступности.

## Проверка и следующий шаг

Проверки восстановления используют локальные HTTP fixtures и не создают
настоящих заказов. Текущие результаты записаны в [состоянии проекта](../project-status.md).

Для окончательной сетевой диагностики сравнить TCP/TLS к тому же API
с повторным подключением к исходному Wi-Fi и с другой Wi-Fi-сетью.
При повторении собрать время и результат проверки без клиентских телефонов,
токенов и заказов. Эти данные позволят проверить маршрут и фильтры конкретного
подключения до изменения серверной конфигурации.

PickChick Dev получает JavaScript с Mac через Metro. Когда iPhone работает
только через мобильную сеть, не перезагружать Dev-клиент принудительно:
локальный адрес Metro может оказаться недоступен. Новая логика доступна
после получения обновлённого bundle; TestFlight обновляется отдельной сборкой.
