# Бэк-офис P1 (полоса bo-ui): включение, проверка, откат

Экраны P1 бэк-офиса за флагами, которые по умолчанию выключены (решение владельца 05.11). Дизайн:
`docs/architecture/cutover-2026-11/design-bo-ui.md`, перенос в облако: CR `bo-ui-1` (075, права, флаги)
и `bo-ui-2` («Касса»). Облачная часть перехода (продажи кассы, роли, склад v2, отчёт продаж) - в
`backoffice-cutover.md`; этот файл продолжает его. Сначала - сводка для включения и работы, потом
подробно по экранам.

Общие правила для каждого флага P1:

- флаг - переменная окружения API, по умолчанию `false`; включается только при `BACKOFFICE_ENABLED=true`;
- пока флаг выключен, ответы API и кабинет те же, что у облачной полосы (тест
  `tests/integration/backoffice-p1-flags.test.mjs`, браузерный тест «флаг выключен»);
- кабинет показывает раздел, только когда `GET .../branches/<точка>` сообщает
  `capabilities.<ключ>=true`, поэтому порядок «сначала права, потом флаг» безопасен;
- откат - флаг `false` и перезапуск API; данные не меняются.

## Коротко: флаги, порядок 13.11-19.11, роли, откат

Этот раздел - для управляющего, оператора облака и бухгалтера. Ниже по разделам - подробности
каждого экрана, его проверки и тесты.

### Что включает каждый флаг

Все флаги - env API (и `provision`, где нужны права), по умолчанию `false`. Права на таблицы 075
выдаёт только helper `infra/staging/backoffice-p1-grants.mjs` (вызов последним в `provision.mjs`,
CR `bo-ui-1` §1); ключ helper-а указан в таблице. Без прав ключ `capabilities` не появляется, и
кабинет показывает экран облачной полосы.

| Флаг                                   | Ключ helper-а P1 | Что появляется в кабинете                                                                                                                                                                                                                                           | Зависит от          |
| -------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| `BACKOFFICE_POS_DAY_ENABLED`           | `posDay`         | раздел «Касса» (смены и Z, чеки, Webkassa, три CSV), блок «Сегодня» на «Главной», колонка «Касса» в «Заказах», имена кассиров; общие исправления аудита (раздел «Исправления аудита кабинета»)                                                                      | таблицы 073         |
| `BACKOFFICE_STOCK_V2_ENABLED` (есть)   | `stockV2`        | облачная полоса: причины списаний и данные накладной; с 075 и правами - склад P1: сторно, плитки быстрого списания, «Последний подсчёт», вкладки «Списания», «Движение», «Расхождения подсчёта», «Расход по продажам», связи меню со складом, «Подсчёт на закрытии» | 074, 075            |
| `BACKOFFICE_STOCK_AUTOCONSUME_ENABLED` | `autoconsume`    | режим списания по продажам («Выключено», «Проверка без списания», «Включено с ...»), очередь, покрытие; воркер `stock-consumption-worker`                                                                                                                           | склад v2 и склад P1 |
| `BACKOFFICE_MANAGER_SHIFTS_ENABLED`    | `managerShifts`  | «Смены» → «Смена менеджера»: открытие и закрытие по чек-листу с авто-проверками, передача смены; прежний журнал только для чтения                                                                                                                                   | -                   |
| `BACKOFFICE_STAFF_POSITIONS_ENABLED`   | `staffPositions` | должности, доп. станции и доступ к кассе в карточке, «Доступы», «Выгрузить состав для кассы», список должностей                                                                                                                                                     | -                   |
| `BACKOFFICE_DISCOUNTS_ENABLED`         | `discounts`      | раздел «Скидки» (только редактор; касса скидки не применяет)                                                                                                                                                                                                        | -                   |

Права ролей в одну строку: всё читают управляющий, начальник смены, бухгалтер и аналитик (кроме
выгрузки состава - только управляющий). Сторно - управляющий и бухгалтер. Связи меню, режим
списания, чек-лист, должности и скидки - только управляющий. Смену менеджера открывают и
закрывают управляющий и начальник смены, они же повторяют и пропускают списание по продажам.
Подсчёт и списание - управляющий и начальник смены, поставку вносят ещё и бухгалтер.

### Порядок 13.11-19.11

Номера шагов - контракт §6.2. Время - Алматы.

1. **13.11 (до окна Cloud-1, без сервера).** Шеф с управляющим готовят по опубликованному меню
   (М1) таблицу связей: для каждого товара и опции - позиции склада или выход ТТК и количество на
   одну проданную позицию; комбо обычно без своей связи (по составу). Для каждой ТТК с выходом
   решают «раскладывать на сырьё» или «списывать сам выход» (заготовки партиями через
   «Производство» - только второе). Отмечают 10-20 ключевых позиций для ежедневного подсчёта
   (мясо, булки, фри, напитки) и плитки быстрого списания. Управляющий готовит должности и доступ
   к кассе для карточек сотрудников. На стенде (если есть) - пробный проход по экранам.
2. **14.11 вечер, Cloud-1.** 072-075 и права одним шагом `provision.mjs` (075 встаёт сразу после
   074), новый API со всеми флагами P1 `false`. Проверка: кабинет и ответы API прежние
   (`GET .../branches/<точка>` без новых ключей `capabilities`). 075 нужна до Т7: без неё нет
   связей и проверки без списания на продажах Т7/Т8. CR `bo-ui-1` §4 предлагал 075 в окне Cloud-2;
   перенос в Cloud-1 - CR `bo-ui-8` §1. Если 075 всё же встанет только в Cloud-2 (ночь 17→18.11),
   шаги 3-5 сдвигаются на 18.11, проверка очереди на Т7/Т8 выпадает, и режим остаётся «Проверка
   без списания» после 19.11 не меньше двух дней работы на настоящих продажах.
3. **15.11-16.11 утро (шаг 4-5).** `BACKOFFICE_ROLES_ENABLED` и назначения, затем в env API и
   `provision`: `BACKOFFICE_STAFF_POSITIONS_ENABLED=true`, `BACKOFFICE_POS_DAY_ENABLED=true`,
   `BACKOFFICE_STOCK_V2_ENABLED=true`, `BACKOFFICE_MANAGER_SHIFTS_ENABLED=true`; провижининг с
   helper-ом P1 (ключи `staffPositions`, `posDay`, `stockV2`, `managerShifts`), перезапуск API.
   Управляющий проставляет должности и доступ к кассе, выгружает состав; оператор точки -
   `staff-roster-apply.mjs` и `staff-pin-batch.mjs` (раздел «Должности и состав кассы»), чтобы
   на Т7 кассиры входили по личному PIN, а «Касса» называла их по имени.
4. **16.11 после шага 5.** Шеф с управляющим вносят связи в «Остатки» → «Списание по продажам»
   (цель - фильтр «Без связи: 0»), управляющий утверждает; в карточках ингредиентов -
   «Считать каждый день», группа и плитки; в техкартах - «Выход техкарты при продаже». Затем
   `BACKOFFICE_STOCK_AUTOCONSUME_ENABLED=true` (env API и `provision`, ключ `autoconsume`),
   перезапуск, запуск воркера (CR `bo-ui-5` §1), «Изменить режим» → «Проверка без списания» с
   16.11.2026 до начала Т7. Проверка без списания ничего не пишет в склад.
5. **Т7 (16-17.11) и Т8 (17.11).** Каждую смену:
   - «Касса»: выручка и способы оплаты закрытой смены совпадают с её Z-отчётом на кассе,
     «Итого по Webkassa» - с кабинетом Webkassa; «Заказы»: две кассы различимы;
   - «Списание по продажам»: шеф сверяет очередь («Проверено, не списано» и что списалось бы) со
     своим ожиданием, исправляет связи; покрытие за 7 дней - не ниже 95 %;
   - «Смены»: начальник смены открывает и закрывает смену менеджера по чек-листу, пробует
     «Подсчёт на закрытии»;
   - склад до 18.11 ведёт iiko: в PickChick на Т7 можно вносить только пробные документы, их
     перекроет инвентаризация 18.11.
6. **17→18.11, Cloud-2 (шаг 8).** `BACKOFFICE_SALES_REPORT_ENABLED=true` (отчёт продаж; блок
   «Сегодня» берёт из него каналы приложения и киоска).
7. **18.11 вечер (шаг 9).** Последняя смена и Z iiko, инвентаризация с 22:00 и
   `stock-opening-import.mjs --apply` до 02:00 (`backoffice-cutover.md`, «Начальные остатки»).
   Импорт - документы «Инвентаризация»: у всех позиций файла появляется «Последний подсчёт», в
   «Расхождениях подсчёта» первый ввод виден как излишек (так и должно быть). Бухгалтер сверяет
   остатки и сумму с iiko. Затем «Изменить режим»:
   - **по умолчанию** (контракт §9 в.26): «Проверка без списания» с 19.11.2026 00:00 - очередь
     показывает, что списалось бы, склад 19-26.11 сверяется ежедневным «Подсчётом на закрытии»;
   - если проверка на Т7/Т8 прошла, покрытие не ниже 95 % и владелец согласен - сразу
     «Включено с 19.11.2026 00:00».
8. **19.11 и позже - включение с догоном.** «Изменить режим» → «Включено» с тем же «с 19.11.2026
   00:00» в любой день (цель контракта - 26.11). Воркер догоняет все продажи с 19.11 00:00 по
   порядку продажи; позиции, посчитанные после продажи, он не списывает (подсчёт уже учёл расход),
   поэтому догон не списывает дважды то, что подтвердил подсчёт. Продажи до 19.11 00:00 (Т7, Т8)
   не списываются никогда. Через час после включения - проверка из раздела «Списание по продажам».
9. **Скидки** (`BACKOFFICE_DISCOUNTS_ENABLED`, ключ `discounts`) - когда владелец захочет готовить
   скидки заранее; к 19.11 не нужны (на запуске скидок нет, касса их не применяет).

### Как пользоваться: управляющий

- **Утро.** «Главная» → «Сегодня»: выручка, чеки, открытые смены кассы, не оформленные чеки
  Webkassa. «Смены» → «Открыть смену» (или открывает начальник смены): чек-лист открытия, просрочку
  списать кнопкой «Списать в «Остатки»».
- **День.** «Касса»: открытые смены и «Данные кассы получены в ...» (если время старое - касса не
  на связи); «Webkassa» - не оформленные чеки. «Остатки» → «Поставка» по накладной, «Списание» с
  причиной (плитки для частых списаний). «Списание по продажам» → фильтр «Не списано»: причина
  словами; исправить связь или провести поставку и нажать «Повторить», либо «Пропустить с
  причиной».
- **Вечер.** «Остатки» → «Подсчёт на закрытии (N)» - ключевые позиции; затем «Смены» → «Закрыть
  смену»: авто-проверки кассовых смен (закрыты, расхождение поясняется комментарием), Webkassa,
  списания, ключевые позиции («Не посчитаны ...» - посчитать или пояснить), заблокированные
  списания; передача смены обязательна.
- **Раз в неделю.** «Остатки» → «Списания» (по причинам, дням, позициям, сотрудникам),
  «Расхождения подсчёта» (недостача и излишек по позициям), «Расход по продажам» (касса,
  приложение и киоск); CSV в тенге. Ошибочный документ - «Документы» → «Движения и сторно» →
  «Сторно» (подсчёт не сторнируется - его исправляет новый подсчёт).
- **Только управляющий:** связи меню и их утверждение, режим списания по продажам, версия
  чек-листа («Чек-лист»), должности и «Выгрузить состав для кассы», «Скидки».

### Как пользоваться: начальник смены

- Открывает и закрывает смену менеджера (как управляющий выше), пишет передачу смены.
- «Остатки»: «Списание» с причиной и плитками, «Инвентаризация» и «Подсчёт на закрытии»,
  «Поставка». Сторно нет: кнопки не видно, текст «Сторно делают управляющий и бухгалтер.» -
  попросить их.
- «Списание по продажам»: «Повторить» и «Пропустить с причиной» для заблокированных продаж; связи
  и режим меняет управляющий.
- «Касса» - только чтение: проверить, что все смены кассы закрыты и Webkassa оформлен до закрытия
  смены менеджера. Финансов, ставок и начислений начальник смены не видит.

### Как пользоваться: бухгалтер

- **«Касса» за день** (выбор дня, «Все кассы» или одна): «Смены и Z» - выручка, способы оплаты,
  наличные (ожидается, пересчитано, расхождение), Kaspi терминал; сверка с выпиской банка и Kaspi.
  «Webkassa» - «Итого по Webkassa» против кабинета Webkassa, не оформленные чеки. Три CSV в тенге
  (Z-отчёты, чеки, чеки Webkassa) - для Excel и 1С.
- **«Остатки»**: «Поставка» по накладной; отчёты «Списания», «Расхождения подсчёта», «Расход по
  продажам», «Движение» с CSV («Сумма, ₸»); «Сторно» ошибочного документа (с причиной).
- **«Смены»**: смены менеджера и их замечания читаются, кнопки неактивны с объяснением.
- День - календарный день Алматы; кассовая смена и смена менеджера, закрытые после полуночи,
  относятся к дню открытия (в «Продажах» отчёта продаж чек считается по времени продажи).

### Откат

- **Любой экран P1:** его флаг `false` в env API (и `provision`), перезапуск API. Раздел исчезает,
  вид отвечает 404 как неизвестный, команды - неизвестные; данные в 075 остаются, при повторном
  включении видны снова. Порядок не важен, флаги независимы (автосписание выключается вместе со
  складом v2).
- **Остановить списание по продажам, не трогая остальное:** «Изменить режим» → «Выключено».
  Документы и очередь остаются; включение снова догонит продажи с «с ...».
- **Ошибочный документ склада** (поставка, списание, производство, автосписание заказа):
  «Сторно» - обратный документ, исходный остаётся в истории; позиция очереди остаётся «Списано».
  Ошибочный подсчёт - новым подсчётом.
- **Общие исправления аудита** уходят вместе с `BACKOFFICE_POS_DAY_ENABLED=false`.
- **Образ API на сборку облачной полосы** (075 остаётся): сначала владелец схемы переносит поля P1
  из карточек (раздел «Откат образа API»), иначе такие карточки и техкарты не сохраняются.
- Что не откатывается: документы склада (неизменяемы), учётные записи кассы, заведённые
  `staff-roster-apply.mjs`, закрытые смены менеджера, ревизии скидок.

## Касса в бэк-офисе (`BACKOFFICE_POS_DAY_ENABLED`)

Один кассовый день точки в кабинете: смены с Z-отчётом, чеки с оплатами, отменами и возвратами,
номера Webkassa, имена кассиров. Только чтение: кабинет ничего не пишет ни в облако, ни на кассу.
Данные - проекции продаж кассы 073 (`cloud_pos_*`, поток `posSales`, CC-4) и отчёты кассы 033 для
смен, у которых ещё нет Z.

### Что видит управляющий

- **«Касса»** (в меню после «Заказы»). Вверху выбор дня (календарь Алматы) и кассы, кнопка
  «Обновить» и строка свежести «Данные кассы получены в 23:41». Вкладки:
  - «Смены и Z» - выручка кассы, чеки и средний чек, «Без выручки» (питание сотрудников и
    маркетинг), «Webkassa не оформлено»; способы оплаты за день (восемь способов кассы); карточка
    каждой смены: открыта или закрыта, кто открыл, наличные (разменный фонд, внесения, изъятия,
    наличные продажи и возвраты, ожидается, пересчитано, расхождение), Kaspi терминал (по кассе,
    введено при закрытии, разница), способы оплаты по Z-отчёту. Для открытой смены - суммы по
    полученным чекам с пометкой «Это не X-отчёт кассы».
  - «Чеки» - время, номер и касса, кассир, канал и режим (зал, с собой, Яндекс Еда, Glovo), номер
    заказа агрегатора или ChocoFood, оплата, сумма, состояние, номер Webkassa или «не оформлен».
    Поиск по номеру заказа, номеру агрегатора и номеру Webkassa; фильтры: касса, способ оплаты,
    канал, состояние. Карточка чека: позиции, оплаты со сдачей, отмены и возвраты с причиной, кто
    оформил и кто подтвердил, чеки Webkassa.
  - «Webkassa» - сначала не оформленные чеки (касса, номер, вид, сумма, время, сколько ждёт), потом
    оформленные и «Чек не нужен»; «Итого по Webkassa» для сверки с кабинетом Webkassa за день.
  - Три выгрузки CSV в тенге: Z-отчёты, чеки, чеки Webkassa (UTF-8 с BOM, «;», десятичная запятая).
  - «Как считается» - правила дня ниже, тем же текстом.
- **«Главная»** - блок «Сегодня, ДД.ММ.ГГГГ»: выручка, чеки, средний чек, каналы, «Без выручки»,
  открытые смены, не оформленные чеки Webkassa, кнопка «Открыть «Кассу»». Каналы приложения и киоска
  блок берёт из отчёта продаж, если включён `BACKOFFICE_SALES_REPORT_ENABLED`; без него - «Только
  касса». Ниже, как раньше, показатели за выбранный период.
- **«Заказы»** - колонка «Касса» («Касса 1», «Касса 2»): у каждой кассы свои номера заказов, поэтому
  два «№1» разных касс различимы. Дата в одну строку, фильтр по кассе, порядок (новые, старые, по
  номеру, по сумме), «Итого по списку» с разбивкой по кассам, CSV с датой, временем, номером,
  кассой и суммой в тенге. Оплаченный на кассе заказ - «Оплачено», а не «Не начата»; карточка такого
  заказа показывает чек кассы.
- **Отчёт по кассовой смене** («Главная», выбранная смена продаж): «Оплачено на кассе», наличные
  продажи и возвраты в расчёте остатка, касса по имени, кассир по имени (CR pos-4 §2).

Пустые состояния без «нулей»: без таблиц 073 или без прав на них - «Облако ещё не получает продажи
кассы. Смены видны по отчётам кассы, чеков и сумм пока нет.»

### Как считается (тот же текст в кабинете)

- День - календарный день Алматы. Смена относится к дню открытия: смена, закрытая после полуночи,
  и её чеки остаются в дне открытия (в «Продажах» CC-7 чек считается по времени продажи, поэтому суммы
  могут отличаться). Чек без известной смены - по своей дате продажи.
- Продажи - все чеки дня, отменённые тоже, как в Z-отчёте. Выручка = продажи - отмены - возвраты,
  сделанные в сменах дня. Возврат сегодня по вчерашнему чеку уменьшает сегодняшнюю выручку, а чек
  показан в списке с пометкой даты.
- Питание сотрудников и маркетинг не входят в выручку и средний чек («Без выручки»).
- Чек Webkassa продажи - в дне продажи, чек возврата - в дне возврата.
- Список чеков - не больше 2000 за день (и до 200 более ранних чеков с возвратом в этот день). Если
  чеков больше, кабинет пишет, что список неполный; итоги дня всё равно по всем чекам.

### Имена кассиров: `scripts/edge-staff-id.mjs`

Касса и облако знают кассира только по uuid. Чтобы «Касса» показывала имя, учётная запись кассы
создаётся с номером, который выводит этот скрипт из карточки сотрудника бэк-офиса («Сотрудники»).
Скрипт ничего не пишет; номер - чистое вычисление (`edgeStaffId`, тот же код в
`packages/backoffice-core/src/edge-staff.ts`, закреплён вектором).

```sh
# карточки сотрудников точки и их три номера для кассы (только чтение, один SELECT)
CLOUD_DATABASE_URL=... node scripts/edge-staff-id.mjs --list --branch <точка>

# номер одного сотрудника для роли кассы: cashier | shift_manager | kitchen
node scripts/edge-staff-id.mjs --employee <карточка> --role cashier

# готовый файл для scripts/staff-setup.mjs (staff_id, terminal_id, name, role)
node scripts/edge-staff-id.mjs --employee <карточка> --role cashier \
  --terminal <касса> --name "<имя как на кассе>" > /secure/staff-<карточка>.json
```

Файл для `staff-setup.mjs` передаётся на сервер точки так же, как другие файлы учётных записей
(без копий в чатах и тикетах), и удаляется после настройки. Одна роль - один номер: если человек
работает и кассиром, и начальником смены, у него две учётные записи кассы с разными номерами, и
обе показывают одно имя. Учётные записи, созданные раньше со случайным номером, не меняются:
кабинет показывает их как «Сотрудник 1a2b3c4d (нет карточки)». Чтобы появилось имя, нужна новая
учётная запись кассы с номером из скрипта (решение владельца кассы, вне смены).

### Названия касс

«Касса 1», «Касса 2» - по порядку первой смены каждой кассы (Z-отчёты и отчёты кассы точки), кассы
только с продажами - после них. Новая касса получает следующий номер; номер кассы не меняется, пока
не удалены её смены (в облаке смены не удаляются).

### Сторно

Окно «Сторно документа»: «Сторно создаст обратный документ. Исходный останется в истории.»,
таблица «Сейчас - Изменение - После сторно - Стоимость» по сегодняшним остаткам, причина изменения
(обязательна), кнопка «Провести сторно». Обратный документ - вид «Сторно», тот же номер, движения
ровно противоположные исходным (количество и стоимость). Нельзя:

- инвентаризацию и само сторно («Инвентаризацию не сторнируют: исправьте остаток новой
  инвентаризацией»);
- второй раз («Документ уже сторнирован»);
- если после документа по его позициям провели инвентаризацию: она уже учла фактический остаток
  (исправлять новой инвентаризацией или списанием);
- если остатка или его стоимости уже меньше, чем добавил документ (поставка, из которой часть уже
  списана или израсходована): кабинет пишет «остаток или его стоимость уже меньше... Сторно
  невозможно», сервер отвечает `INSUFFICIENT_STOCK`. Остаток не уходит ниже нуля, и не бывает нуля
  штук с ненулевой стоимостью.

Если пока окно открыто другой документ изменил остатки этих позиций, кабинет перечитывает их,
показывает новую таблицу и просит провести сторно ещё раз. Повтор того же запроса (потеря ответа)
не создаёт второго сторно. В журнале аудита - «Склад: Сторно документа».

- Документы сторно и `counted_at` остаются: документы неизменяемы, ошибку исправляет следующий
  документ.

  обычно: поля, отправленные обратно без изменений, сервер не отклоняет, а сохранение без них их не
  стирает (как поля должностей сотрудника). Изменить их можно только после повторного включения.
- Отчёт «Списания» облачной полосы не знает сторно: после отката сторнированное списание снова
  считается в причинах полностью, сторно видно только как документ. Итоги списаний за дни после
  первого сторно сверяйте после повторного включения склада P1.
- Откат самого образа API на сборку облачной полосы - раздел «Откат образа API» ниже: перед ним
  владелец схемы убирает поля P1 из карточек.

## Списание по продажам (шаг 5 полосы, `BACKOFFICE_STOCK_AUTOCONSUME_ENABLED`)

Продажи кассы (таблицы 073) и заказы приложения и киоска списываются со склада по связям «позиция
меню - склад». Связи заводит управляющий, шеф проверяет их, управляющий утверждает. Один документ
«По техкарте» на заказ, его не бывает дважды (уникальный индекс 075). Дизайн: `design-bo-ui.md`
§5.3, §5.5; перенос: CR `bo-ui-5`.

### Что видит управляющий

Вкладка «Остатки» → «Списание по продажам»:

- **Связи меню со складом** (есть уже при складе P1, без флага автосписания): все товары и опции
  опубликованного меню. Статус словами: «Утверждено», «Черновик», «Нет связи», «Из состава комбо»
  (комбо и наборы без своей связи списываются по составу), «Из товара: ...» (опция, которая
  означает товар меню). Фильтры «Без связи: N» и «Черновики: N». В связи - строки склада:
  «Склад: ...» списывает позицию как есть, «По ТТК: ...» раскладывает выход техкарты на сырьё
  (если у техкарты учёт запасом - списывает сам выход). «Без списания» - для опций вроде «без лука».
  Количество - на одну проданную позицию, в г, мл или шт. Любое изменение возвращает связь в
  черновик.
- **Режим** (только с флагом): «Списание по продажам: Выключено | Проверка без списания | Включено
  с ДД.ММ.ГГГГ ЧЧ:ММ». Окно смены режима пишет, что произойдёт, и предупреждает, если покрытие
  меньше 95 %.
- **Покрытие за 7 дней**: доля строк продаж, у которых все связи утверждены, и самые частые позиции
  без связи.
- **Очередь**: каждая продажа с состоянием («Списано», «Не списано», «Проверено, не списано»,
  «Ждёт списания», «Пропущено», «Списывать не нужно»), причиной словами («нет связи: Бургер Острый
  · не хватает: Булка (нужно 2 шт, есть 0 шт)»), тем, что списано, и документом. Кнопки
  «Повторить» (управляющий и начальник смены, попытка сразу) и «Пропустить с причиной».
- Плашка над вкладками: «Продажи списываются со склада автоматически с ...» при «Включено»,
  «...режиме проверки...» при проверке.

### Как считается (тот же текст в кабинете)

- Продажа кассы берётся, когда кухня начала заказ (в работе, готов, выдан), остальные - проходом
  в 03:00 Алматы следующего дня. Заказ приложения и киоска - по первой оплате, так же.
- Учитываются только продажи с момента «с ДД.ММ ЧЧ:ММ»; при включении позже воркер догоняет их по
  порядку продажи.
- Меню продажи - та версия каталога, по которой продавали: касса - через выпуск меню
  (`catalog_menu_deliveries`), приложение - по версии в заказе. Связи - текущие утверждённые.
- Комбо без своей связи раскладывается по составу до 5 уровней; опция - своя связь, иначе товар, на
  который она указывает. Выход ТТК раскладывается на сырьё до 6 уровней; округление одно, до целой
  единицы (г, мл, шт) на ингредиент на заказ.
- Нет связи, черновик, неизвестная позиция, ошибка ТТК: заказ «Не списано» целиком, причина видна,
  другие заказы идут дальше. Не хватает остатка - тоже «Не списано», со списком нехватки.
  Повтор - сам: через 1, 2, 5, 15, 30, 60 минут и сразу после поставки, инвентаризации, сторно,
  изменения связи или техкарты.
- Отмена или полный возврат до начала приготовления - «Списывать не нужно». Возврат после начала -
  остаётся списанным, в очереди это видно; ошибочное списание исправляют сторно документа (позиция
  очереди остаётся «Списано», документ «Списано, затем сторно»).
- Позиция, подсчитанная после продажи (инвентаризация позже времени продажи), не списывается: подсчёт
  уже учёл расход («учтено подсчётом»).
- «Проверка без списания» ничего не пишет в склад: в очереди видно, что списалось бы.
- Ручное «списание по техкартам заказа» в режимах проверки и включено отклоняется
  (`AUTOCONSUME_ACTIVE`): иначе заказ списался бы дважды.
- Документ автосписания создаётся от имени того, кто последним менял режим (после «Повторить» -
  от имени нажавшего); в «Документах» он
  подписан «Автоматически по продаже кассы» или «... по заказу приложения или киоска».

### Включение

Порядок по `design-backoffice.md` §7: связи → проверка без списания → инвентаризация → включено.

1. Склад P1 уже работает (раздел выше). Шеф с управляющим заводят и утверждают связи всех товаров
   и опций меню; комбо обычно не нужны (идут по составу). Цель: фильтр «Без связи: 0».
2. В env `provision` и API: `BACKOFFICE_STOCK_AUTOCONSUME_ENABLED=true` (нужен
   `BACKOFFICE_STOCK_V2_ENABLED=true`, иначе API не стартует). Провижининг вызывает helper P1 с
   `autoconsume: true`: права на `bo_stock_settings`, `bo_consumption_items` и чтение
   `cloud_pos_sales`, `cloud_pos_refunds`, `catalog_menu_deliveries`, `catalog_publications`.
   Перезапуск API. В `GET .../branches/<точка>` - `capabilities.stock_autoconsume=true`.
3. Запустить воркер (CR `bo-ui-5` §1): отдельный процесс
   `node services/api/dist/stock-consumption-worker.js` с env API. Проверка до запуска:
   `node services/api/dist/stock-consumption-worker.js --once` печатает одну строку
   `{"event":"stock_consumption_tick",...}` (только числа, без заказов и имён).
4. Управляющий: «Изменить режим» → «Проверка без списания» с 13.11 (или сейчас). 1-3 дня сверять
   очередь с ожиданием шефа (Т7/Т8), добирать связи до покрытия не ниже 95 %.
5. 18.11 вечером: инвентаризация и `stock-opening-import.mjs`, проверка остатков с бухгалтером.
6. 19.11 00:00 (или время окончания ввода остатков): «Изменить режим» → «Включено с 19.11.2026
   00:00». Продажи раньше этого момента не списываются никогда.
7. Проверка через час (управляющий, 5 минут): очередь - «Списано» у продаж с начатой кухней;
   «Не списано» - открыть причину, исправить связь или провести поставку, нажать «Повторить»;
   в «Документах» - документы «По техкарте» с подписью «Автоматически ...»; остатки уменьшаются.
   Телефон 390 px: очередь - карточки, кнопки видны.

- Ошибочно списанный заказ: сторно его документа в «Документах»; позиция очереди остаётся
  «Списано».

## Отчёты склада и подсчёт на закрытии (шаг 8 полосы)

Тот же склад P1 (`BACKOFFICE_STOCK_V2_ENABLED`, 075 и права helper-а со `stockV2`), новых флагов,
таблиц и прав нет. Без склада P1 ничего из этого не видно, а `ops/stock` с новыми видами отвечает
как раньше (склад v2 выключен - 404 `STOCK_V2_DISABLED`, без 075 - `INVALID_REQUEST`).

### Что видит управляющий

- **«Остатки» → «Расхождения подсчёта»** (период до 92 дней): итог «Подсчётов, позиций, с
  расхождением, недостача, излишек, итого»; «По позициям» - сколько раз считали, «Ожидалось» и
  «Посчитано» последнего подсчёта, «Разница» и «Сумма» всех подсчётов периода (минус -
  недостача, самые большие недостачи сверху); «По дням»; документы; «CSV итогов» и «CSV строк
  документов» в тенге.
- **«Остатки» → «Расход по продажам»**: документы «По техкарте» периода по источникам («Касса»,
  «Приложение и киоск», «Вручную по техкартам заказа»), по дням и позициям, со сторно (сторно
  уменьшает день, в который его провели); CSV в тенге. Вкладка «Списание по продажам» (связи,
  режим, очередь) - прежняя; разные названия, чтобы не путать отчёт и очередь.
- **Карточка ингредиента**: «Считать каждый день (подсчёт на закрытии)» и «Группа» (сырьё,
  полуфабрикаты, упаковка, напитки, хозтовары, другое).
- **«Подсчёт на закрытии (N)»** на панели «Остатков» (управляющий и начальник смены, если есть
  хотя бы одна такая позиция): окно инвентаризации сразу со строками этих позиций (по группам) и
  номером «Подсчёт на закрытии ДД.ММ.ГГГГ». Документ - обычная «Инвентаризация» этих позиций.
- **Смена менеджера** → авто-проверка «Подсчёт ключевых позиций»: с отмеченными позициями -
  «Ключевые позиции посчитаны: 3 из 3, последний подсчёт в 22:30» или «Не посчитаны ключевые
  позиции: 1 из 3 (Мясо). Проведите «Подсчёт на закрытии» в «Остатки» или поясните.» (тогда
  комментарий обязателен). Без отмеченных позиций - как в шаге 6 (есть ли подсчёт за день).
- **Техкарта** → «Выход техкарты при продаже»: «По умолчанию: раскладывать на сырьё»,
  «Раскладывать на сырьё (производство недоступно)», «Списывать сам выход (заготовка партиями)».
  Явное «Раскладывать на сырьё» запрещает «Производство» этой техкарты
  (`RECIPE_POLICY_EXPLODE`, текст: «...выберите в техкарте «Списывать сам выход»»): иначе партия
  списала бы сырьё, а продажи - то же сырьё ещё раз. Без выбора производство разрешено, как
  раньше; шеф выбирает «Списывать сам выход» для всех заготовок, которые делают партиями (соусы,
  маринад), до включения списания по продажам.

### Как считается

- Расхождение подсчёта - движение документа «Инвентаризация»: «Ожидалось» - остаток по учёту в
  момент подсчёта, «Посчитано» - введённое количество, сумма - по средней себестоимости. Первый
  ввод остатков 18.11 (`stock-opening-import`) - тоже подсчёт: весь начальный остаток в нём
  излишек; смотрите период с 19.11.
- Расход по продажам - документы `consumption`: источник по `source_ref` (`pos:` - касса,
  `cloud:` - приложение и киоск, без него - ручное списание по техкартам заказа).
- Ключевые позиции дня - используемые ингредиенты с «Считать каждый день», посчитанные любым
  документом «Инвентаризация» дня смены (день открытия по Алматы).

### Включение и откат

Ничего отдельно: появляется со складом P1. Откат - как у склада P1. Поля карточки
(`count_daily`, `group`) и `stock_policy` остаются в записях; пока склад P1 выключен, карточка и
техкарта сохраняются как обычно, поля не теряются (раздел «Откат» склада P1). Откат образа API -
раздел «Откат образа API».

### Откат образа API (сборка облачной полосы при оставшейся 075)

Сборка облачной полосы проверяет карточки ингредиента, техкарты и сотрудника строгими схемами
(сохранение, «Производство»). Карточка с полем P1 (`quick_waste`, `count_daily`, `group`,
`stock_policy`, `position_code`, `extra_position_codes`, `pos_access`) у неё не сохранится и не
произведётся. Поэтому **перед** откатом образа владелец схемы (не роль API) в одной транзакции
переносит эти поля в отдельную таблицу `bo_p1_payload_stash` (только владелец, у роли API прав
нет) и поднимает ревизию карточки на 1 (открытый редактор получит «Данные изменились» вместо
перезаписи). Повторный запуск ничего не меняет.

```sql
BEGIN;
CREATE TABLE IF NOT EXISTS bo_p1_payload_stash (
  branch_id uuid NOT NULL,
  kind text NOT NULL CHECK (kind IN ('ingredient','recipe','employee')),
  record_id uuid NOT NULL,
  stashed_revision integer NOT NULL,
  fields jsonb NOT NULL CHECK (jsonb_typeof(fields) = 'object'),
  stashed_at timestamptz NOT NULL DEFAULT clock_timestamp(),
  restored_at timestamptz NULL,
  PRIMARY KEY (branch_id, kind, record_id, stashed_revision)
);
REVOKE ALL ON bo_p1_payload_stash FROM PUBLIC;
WITH p1 AS (
  SELECT r.branch_id, r.kind, r.id, r.revision,
    (SELECT coalesce(jsonb_object_agg(k, r.payload->k), '{}'::jsonb)
       FROM unnest(CASE r.kind
         WHEN 'ingredient' THEN ARRAY['quick_waste','count_daily','group']
         WHEN 'recipe' THEN ARRAY['stock_policy']
         ELSE ARRAY['position_code','extra_position_codes','pos_access'] END) k
      WHERE r.payload ? k) AS fields
  FROM bo_records r WHERE r.kind IN ('ingredient','recipe','employee')
  FOR UPDATE OF r
), moved AS (
  INSERT INTO bo_p1_payload_stash (branch_id, kind, record_id, stashed_revision, fields)
  SELECT branch_id, kind, id, revision + 1, fields FROM p1 WHERE fields <> '{}'::jsonb
  RETURNING branch_id, kind, record_id, fields
)
UPDATE bo_records r
   SET payload = r.payload - ARRAY(SELECT jsonb_object_keys(m.fields)),
       revision = r.revision + 1, updated_at = clock_timestamp()
  FROM moved m
 WHERE r.branch_id = m.branch_id AND r.kind = m.kind AND r.id = m.record_id;
COMMIT;
```

Выполнять так (файл `p1-stash.sql` - ровно этот блок, `p1-restore.sql` - блок ниже; тот же
способ, что в `backup-offsite.md`):

```
docker exec -i pickchick-staging-cloud-db-1 psql -X -q -v ON_ERROR_STOP=1 -U postgres -d pickchick_cloud < p1-stash.sql
docker exec pickchick-staging-cloud-db-1 psql -X -U postgres -d pickchick_cloud -c "SELECT kind,count(*) FROM bo_p1_payload_stash WHERE restored_at IS NULL GROUP BY kind"
```

Когда снова работает сборка bo-ui, владелец возвращает последние перенесённые поля (поля, которые
карточка за это время получила сама, не перезаписываются; ревизия +1). Повторный запуск ничего не
меняет.

```sql
BEGIN;
WITH s AS (
  SELECT DISTINCT ON (branch_id, kind, record_id) branch_id, kind, record_id, stashed_revision, fields
    FROM bo_p1_payload_stash WHERE restored_at IS NULL
   ORDER BY branch_id, kind, record_id, stashed_revision DESC
), back AS (
  UPDATE bo_records r
     SET payload = s.fields || r.payload, revision = r.revision + 1, updated_at = clock_timestamp()
    FROM s
   WHERE r.branch_id = s.branch_id AND r.kind = s.kind AND r.id = s.record_id
  RETURNING r.branch_id, r.kind, r.id
)
UPDATE bo_p1_payload_stash t SET restored_at = clock_timestamp()
  FROM s
 WHERE t.restored_at IS NULL AND t.branch_id = s.branch_id AND t.kind = s.kind
   AND t.record_id = s.record_id AND t.stashed_revision <= s.stashed_revision
   AND EXISTS (SELECT 1 FROM back b WHERE b.branch_id = s.branch_id AND b.kind = s.kind AND b.id = s.record_id);
COMMIT;
```

списание полностью), «Касса», «Смена менеджера», «Скидки», «Списание по продажам» недоступны;

## Смена менеджера (шаг 6 полосы, `BACKOFFICE_MANAGER_SHIFTS_ENABLED`)

Открытие и закрытие смены менеджера по чек-листу (А10, А11, Ск7) с авто-проверками по данным кассы
и склада. Пишет только таблицы 075 `bo_manager_shifts` и `bo_branch_templates` (версии чек-листа);
кассу и склад не трогает. Дизайн: `design-bo-ui.md` §5.6, перенос: CR `bo-ui-6`.

### Что видит управляющий и начальник смены

- **«Смены» → «Смена менеджера»** (вверху страницы):
  - «Смена не открыта» и кнопка «Открыть смену» → чек-лист открытия: явка по графику, мясо и
    заготовки по срокам (кнопка «Списать в «Остатки»»: ответы сохраняются черновиком во вкладке),
    оборудование, касса и экраны, разменный фонд, стоп-лист; выбор «Менеджер смены»;
  - у каждого пункта «Готово | Есть проблема | Не применимо»; для двух последних комментарий
    обязателен (минимум 3 символа); пункт с авто-проверкой «Есть проблема» тоже требует
    комментария - это пояснение (например, расхождения кассы);
  - открытая смена - карточка «Смена открыта · менеджер ...» с авто-проверками к закрытию:
    «Кассовые смены: 2 из 2 закрыты, расхождение -500 ₸. Поясните в комментарии.», «Не оформлено в
    Webkassa: 1 чек на 11 670 ₸», «Данные кассы не поступают с 21:10. Подтвердите вручную.»,
    списания и подсчёт за день, заблокированные списания по продажам; замечания открытия;
  - «Закрыть смену» - мастер из двух шагов: чек-лист закрытия (кнопка «Сохранить черновик» хранит
    ответы на сервере), затем «Передача смены» (обязательна) и «Закрыть смену»;
  - «Смены за день» - смены выбранного дня с числом замечаний и передачей; «Подробнее» - все ответы,
    комментарии и авто-проверки на момент ответа;
  - «Чек-лист» (только управляющий) - тексты пунктов, «Обязательный», новые пункты, «Убрать» (пункты
    с авто-проверкой не убираются); сохранение создаёт новую версию, она действует для смен,
    открытых после сохранения.
- **«Кассовые смены и прежний журнал»**: «Управленческий журнал» только для чтения (кнопок
  «Добавить» и «Изменить» нет, сервер отказывает `LEGACY_JOURNAL_READ_ONLY`), показаны последние
  200 записей. Старые записи не меняются.
- Права: открывают, сохраняют и закрывают - управляющий и начальник смены
  (`manager_shifts.write`); чек-лист - управляющий (`manager_shifts.template`); бухгалтер и
  аналитик видят всё, кнопки неактивны с текстом «Открывают и закрывают смену управляющий и
  начальник смены.».

### Как считается

- День смены - календарный день Алматы её открытия. Смена, закрытая после полуночи, остаётся в дне
  открытия; авто-проверки открытой смены считаются за её день (как кассовые смены в «Кассе»).
- Одна открытая смена на точку (`MANAGER_SHIFT_OPEN`); закрытая смена не меняется (триггер 075).
- «Кассовые смены»: смены кассы дня из `ops/pos-day` (Z и отчёты кассы): сколько закрыто, сумма
  расхождений наличных и Kaspi терминала. Открытая касса или расхождение - «Есть проблема». Нет
  данных или касса открыта, а данных нет 10 минут - «Нет данных», ответ вручную.
- «Webkassa»: чеки дня, ожидающие номера Webkassa. «Списания», «Подсчёт»: документы склада дня.
  «Заблокированные списания»: продажи дня в состоянии «Не списано» (только при автосписании, иначе
  пункт необязателен). «Явка»: опубликованные смены графика на день. «Стоп-лист»: последнее
  сообщение кассы.
- Ответ хранит текст пункта и авто-проверку как они были, поэтому закрытая смена читается так же
  после смены шаблона.

### Включение

1. 075 (с разделом 8) и helper P1 уже стоят.
2. В env `provision` и API: `BACKOFFICE_MANAGER_SHIFTS_ENABLED=true`. Helper P1 с
   `managerShifts: true` выдаёт роли API `SELECT, INSERT, UPDATE` на `bo_manager_shifts` и
   `SELECT, INSERT` на `bo_branch_templates`. Перезапуск API; в `GET .../branches/<точка>` -
   `capabilities.manager_shifts=true`.
3. Проверка (управляющий, 5 минут): «Смены» → «Открыть смену», ответить на пункты, открыть;
   карточка показывает авто-проверки; «Закрыть смену» → передача → «Закрыть смену»; смена в списке
   дня. Телефон 390 px: начальник смены открывает смену, кнопки и тексты видны без прокрутки вбок.

### Откат

`BACKOFFICE_MANAGER_SHIFTS_ENABLED=false` в env API и `provision`, перезапуск API. Блок исчезает,
«Управленческий журнал» снова пишется, смены и версии чек-листа остаются в 075 (при повторном
включении открытая смена снова видна).

### Состав на кассе: операторские скрипты на сервере точки

Файл выгрузки передаётся оператору точки (не по почте и не в мессенджер: имена сотрудников).

```bash
# 1. План (ничего не пишет): кого завести, кого отозвать, что заблокировано, sha256 плана
node scripts/staff-roster-apply.mjs --file PickChick-состав-кассы-18.11.2026.json --terminal <id кассы>
# 2. Применить ровно этот план (отказ, если база или файл изменились)
node scripts/staff-roster-apply.mjs --file PickChick-состав-кассы-18.11.2026.json --terminal <id кассы> \
  --apply --expected-plan <sha256 плана>
# 3. PIN по одному: на экране имя, сотрудник сам вводит PIN дважды (скрыто); пустой ввод - пропуск
node scripts/staff-pin-batch.mjs --file PickChick-состав-кассы-18.11.2026.json [--digits 4|6]
```

- Скрипт заводит учётную запись кассы с номером `edgeStaffId` (те же номера «Касса» в кабинете
  показывает именами), выдаёт сессию на `--terminal` (активный терминал точки) и пишет файл входа
  `.local/staff-<id>.json` (0600, не печатается). Сессия действует 8 часов: PIN нужно задать в тот
  же день.
- Роль на кассе не меняется на месте: кассир, ставший начальником смены, получает новую учётную
  запись, старая отзывается. Уволенные, неработающие и без доступа - отзываются.
- «Заблокировано: revoked_earlier» - учётная запись этого человека в этой роли уже отзывалась;
  операторские функции кассы её не восстанавливают (CR `bo-ui-6` §3). Пока - вручную через
  оператора кассы.
- Общий вход кухни и учётные записи, заведённые вручную, скрипт не трогает (список «unmanaged»).
- PIN не печатается, не пишется в лог и в файлы. Занятый PIN - «Этот PIN не подходит. Введите
  другой.» Повторный запуск пропускает тех, у кого PIN уже есть (`--replace` - заменить, нужен
  новый файл входа через `staff-setup.mjs --renew`).

### Включение

1. В env API: `BACKOFFICE_STAFF_POSITIONS_ENABLED=true`, в `provision` - helper P1 с
   `staffPositions: true` (CR `bo-ui-6` §1, права `SELECT, INSERT` на `bo_branch_templates` для списка

3. Оператор точки: план, применение, PIN по одному (выше). Проверка: каждый кассир входит по PIN на
   своей кассе; в «Касса» в кабинете смена называет кассира по имени.

  - название (его увидит кассир, 1-80 символов, без повтора среди живых скидок);
  - «Процент от суммы» (1-100, до двух знаков: «12,5») или «Сумма в тенге» (до 1 000 000 ₸);
  - «Где действует»: Зал, Яндекс Еда, Glovo, ChocoFood (чек зала с оплатой ChocoFood), Приложение,
    Киоск - хотя бы один;
  - «На что»: «Всё меню» или категории целиком и отдельные позиции опубликованного меню;
  - «Когда»: «С даты», «По дату включительно» (по Алматы; пусто - без срока), дни недели, до
    четырёх промежутков часов («До 24:00» - до конца дня; без часов - весь день);
  - «Условия»: «Нужен PIN начальника смены на кассе» (включено по умолчанию), «Можно вместе с
    другими скидками» (выключено по умолчанию);
  - «Причина или комментарий для журнала»;
  - ошибки - словами до отправки; ввод хранится во вкладке, перезагрузка его не теряет, «Закрыть» и
    Esc спрашивают.
- Сохранённая скидка - **черновик**. «Включить» делает её включённой; «Выключить» - снова черновик;
  «В архив» - навсегда (название освобождается). **Изменение включённой скидки возвращает её в
  черновик**: включите её снова после проверки. Закончившийся период не включается.
- **«История»** - все версии скидки: когда, кто, что было.
- Начальник смены, бухгалтер и аналитик видят список и историю; кнопок нет, текст «Скидки создаёт и
  меняет только управляющий точки.»

### Включение

1. 075 и helper P1 с `discounts: true` (CR `bo-ui-1` §1) уже стоят: роли API выданы
   `SELECT, INSERT, UPDATE` на `bo_discounts` и `SELECT` на `bo_discount_revisions`.
2. В env API (и `provision`): `BACKOFFICE_DISCOUNTS_ENABLED=true`, перезапуск API. В
   `GET .../branches/<точка>` - `capabilities.discounts=true`, у управляющего в `permissions[]` -
   `discounts.write`.
3. Проверка (управляющий, 5 минут): «Скидки» → плашка видна; «Новая скидка» → «Проверка 1 %», 1 %,
   зал, всё меню → «Сохранить черновик»; в списке «Черновик»; «История» - одна версия; «В архив».
   В «Журнал аудита» - «Скидка: создание или изменение» и «Скидка: включение, выключение или архив».
   Касса не меняется: в `bo_publications` и `bo_delivery_outbox` новых строк нет.

Включать не обязательно к 19.11: скидок на запуске нет. Флаг можно включить, когда владелец захочет
готовить скидки заранее.

### Откат

`BACKOFFICE_DISCOUNTS_ENABLED=false` и перезапуск API: раздел исчезает, `ops/discounts` отвечает 404,
команды скидок - неизвестные. Скидки и история остаются в 075; касса их и так не получала.

### Чего пока нет

- Касса скидки не применяет и не получает (P1 полосы pos, CR `bo-ui-7` §2): нет публикации набора
  скидок на edge, approval `discount` на кассе, `discount_minor` в продаже.
- Отчёт продаж и «Касса» не разбивают выручку по скидкам (`discount_minor` чеков в «Кассе» уже
  виден, пока он всегда 0).
- Приложение и киоск скидки не применяют (каналы `mobile`, `kiosk` только хранятся).
