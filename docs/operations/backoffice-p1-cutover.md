# Бэк-офис P1 (полоса bo-ui): включение, проверка, откат

Экраны P1 бэк-офиса за флагами, которые по умолчанию выключены (решение владельца 05.11). Дизайн:
`docs/architecture/cutover-2026-11/design-bo-ui.md`, перенос в облако: CR `bo-ui-1` (075, права, флаги)
и `bo-ui-2` («Касса»). Облачная часть перехода (продажи кассы, роли, склад v2, отчёт продаж) - в
`backoffice-cutover.md`; этот файл продолжает его и дополняется на шагах 3-8 полосы.

Общие правила для каждого флага P1:

- флаг - переменная окружения API, по умолчанию `false`; включается только при `BACKOFFICE_ENABLED=true`;
- пока флаг выключен, ответы API и кабинет те же, что у облачной полосы (тест
  `tests/integration/backoffice-p1-flags.test.mjs`, браузерный тест «флаг выключен»);
- кабинет показывает раздел, только когда `GET .../branches/<точка>` сообщает
  `capabilities.<ключ>=true`, поэтому порядок «сначала права, потом флаг» безопасен;
- откат - флаг `false` и перезапуск API; данные не меняются.

## Касса в бэк-офисе (`BACKOFFICE_POS_DAY_ENABLED`)

Один кассовый день точки в кабинете: смены с Z-отчётом, чеки с оплатами, отменами и возвратами,
номера Webkassa, имена кассиров. Только чтение: кабинет ничего не пишет ни в облако, ни на кассу.
Данные - проекции продаж кассы 073 (`cloud_pos_*`, поток `posSales`, CC-4) и отчёты кассы 033 для
смен, у которых ещё нет Z.

### Что видит управляющий

- **«Касса»** (в меню после «Заказы»). Вверху выбор дня (календарь Алматы) и кассы, кнопка
  «Обновить» и строка свежести «Данные кассы получены в 23:41». Вкладки:
  - «Смены и Z» - выручка кассы, чеки и средний чек, «Без выручки» (питание сотрудников и
    маркетинг), «Webkassa не оформлено»; способы оплаты за день (восемь способов кассы); карточка
    каждой смены: открыта или закрыта, кто открыл, наличные (разменный фонд, внесения, изъятия,
    наличные продажи и возвраты, ожидается, пересчитано, расхождение), Kaspi терминал (по кассе,
    введено при закрытии, разница), способы оплаты по Z-отчёту. Для открытой смены - суммы по
    полученным чекам с пометкой «Это не X-отчёт кассы».
  - «Чеки» - время, номер и касса, кассир, канал и режим (зал, с собой, Яндекс Еда, Glovo), номер
    заказа агрегатора или ChocoFood, оплата, сумма, состояние, номер Webkassa или «не оформлен».
    Поиск по номеру заказа, номеру агрегатора и номеру Webkassa; фильтры: касса, способ оплаты,
    канал, состояние. Карточка чека: позиции, оплаты со сдачей, отмены и возвраты с причиной, кто
    оформил и кто подтвердил, чеки Webkassa.
  - «Webkassa» - сначала не оформленные чеки (касса, номер, вид, сумма, время, сколько ждёт), потом
    оформленные и «Чек не нужен»; «Итого по Webkassa» для сверки с кабинетом Webkassa за день.
  - Три выгрузки CSV в тенге: Z-отчёты, чеки, чеки Webkassa (UTF-8 с BOM, «;», десятичная запятая).
  - «Как считается» - правила дня ниже, тем же текстом.
- **«Главная»** - блок «Сегодня, ДД.ММ.ГГГГ»: выручка, чеки, средний чек, каналы, «Без выручки»,
  открытые смены, не оформленные чеки Webkassa, кнопка «Открыть «Кассу»». Каналы приложения и киоска
  блок берёт из отчёта продаж, если включён `BACKOFFICE_SALES_REPORT_ENABLED`; без него - «Только
  касса». Ниже, как раньше, показатели за выбранный период.
- **«Заказы»** - колонка «Касса» («Касса 1», «Касса 2»): у каждой кассы свои номера заказов, поэтому
  два «№1» разных касс различимы. Дата в одну строку, фильтр по кассе, порядок (новые, старые, по
  номеру, по сумме), «Итого по списку» с разбивкой по кассам, CSV с датой, временем, номером,
  кассой и суммой в тенге. Оплаченный на кассе заказ - «Оплачено», а не «Не начата»; карточка такого
  заказа показывает чек кассы.
- **Отчёт по кассовой смене** («Главная», выбранная смена продаж): «Оплачено на кассе», наличные
  продажи и возвраты в расчёте остатка, касса по имени, кассир по имени (CR pos-4 §2).

Пустые состояния без «нулей»: без таблиц 073 или без прав на них - «Облако ещё не получает продажи
кассы. Смены видны по отчётам кассы, чеков и сумм пока нет.»

### Как считается (тот же текст в кабинете)

- День - календарный день Алматы. Смена относится к дню открытия: смена, закрытая после полуночи,
  и её чеки остаются в дне открытия (в «Продажах» CC-7 чек считается по времени продажи, поэтому суммы
  могут отличаться). Чек без известной смены - по своей дате продажи.
- Продажи - все чеки дня, отменённые тоже, как в Z-отчёте. Выручка = продажи - отмены - возвраты,
  сделанные в сменах дня. Возврат сегодня по вчерашнему чеку уменьшает сегодняшнюю выручку, а чек
  показан в списке с пометкой даты.
- Питание сотрудников и маркетинг не входят в выручку и средний чек («Без выручки»).
- Чек Webkassa продажи - в дне продажи, чек возврата - в дне возврата.
- Список чеков - не больше 2000 за день (и до 200 более ранних чеков с возвратом в этот день). Если
  чеков больше, кабинет пишет, что список неполный; итоги дня всё равно по всем чекам.

### Имена кассиров: `scripts/edge-staff-id.mjs`

Касса и облако знают кассира только по uuid. Чтобы «Касса» показывала имя, учётная запись кассы
создаётся с номером, который выводит этот скрипт из карточки сотрудника бэк-офиса («Сотрудники»).
Скрипт ничего не пишет; номер - чистое вычисление (`edgeStaffId`, тот же код в
`packages/backoffice-core/src/edge-staff.ts`, закреплён вектором).

```sh
# карточки сотрудников точки и их три номера для кассы (только чтение, один SELECT)
CLOUD_DATABASE_URL=... node scripts/edge-staff-id.mjs --list --branch <точка>

# номер одного сотрудника для роли кассы: cashier | shift_manager | kitchen
node scripts/edge-staff-id.mjs --employee <карточка> --role cashier

# готовый файл для scripts/staff-setup.mjs (staff_id, terminal_id, name, role)
node scripts/edge-staff-id.mjs --employee <карточка> --role cashier \
  --terminal <касса> --name "<имя как на кассе>" > /secure/staff-<карточка>.json
```

Файл для `staff-setup.mjs` передаётся на сервер точки так же, как другие файлы учётных записей
(без копий в чатах и тикетах), и удаляется после настройки. Одна роль - один номер: если человек
работает и кассиром, и начальником смены, у него две учётные записи кассы с разными номерами, и
обе показывают одно имя. Учётные записи, созданные раньше со случайным номером, не меняются:
кабинет показывает их как «Сотрудник 1a2b3c4d (нет карточки)». Чтобы появилось имя, нужна новая
учётная запись кассы с номером из скрипта (решение владельца кассы, вне смены).

### Названия касс

«Касса 1», «Касса 2» - по порядку первой смены каждой кассы (Z-отчёты и отчёты кассы точки), кассы
только с продажами - после них. Новая касса получает следующий номер; номер кассы не меняется, пока
не удалены её смены (в облаке смены не удаляются).

### Включение (после Cloud-2: 075 и права уже стоят)

1. Права на чтение 073. Helper `infra/staging/backoffice-p1-grants.mjs` с `posDay: true` добавляет
   SELECT на шесть таблиц `cloud_pos_sales`, `cloud_pos_tenders`, `cloud_pos_refunds`,
   `cloud_pos_refund_tenders`, `cloud_pos_fiscal_receipts`, `cloud_pos_shift_reports` (тот же набор,
   что `cloudPosSalesGrants(role, {backoffice: true})` полосы pos). Вызов в `provision.mjs` - CR
   `bo-ui-1` §1: `BACKOFFICE_POS_DAY_ENABLED=true` в env `provision`, затем провижининг. Проверка -
   `assertBackofficeP1Privileges(client, 'pickchick_app', {..., posDay: true})` в том же шаге.
2. Имена: для каждого кассира и начальника смены точки - учётная запись кассы с номером из
   `edge-staff-id.mjs` (раздел выше). Можно позже: без этого видны короткие коды.
3. `BACKOFFICE_POS_DAY_ENABLED=true` в env API, перезапуск API.
4. Проверка (управляющий, затем бухгалтер и начальник смены):
   - в меню есть «Касса»; день Т7 или первый день продаж; строка «Данные кассы получены в ...»
     со временем последней продажи;
   - выручка и способы оплаты закрытой смены совпадают с её Z-отчётом на кассе;
   - «Webkassa»: «Итого по Webkassa» совпадает с кабинетом Webkassa за день, не оформленные
     совпадают с вкладкой Webkassa на кассе;
   - «Заказы»: у двух касс «№1» с разными «Касса 1» и «Касса 2»; CSV открывается в Excel;
   - телефон: «Касса» на 390 px, суммы и кнопки видны.

Права ролей (контракт §5.10, `reports.read`): управляющий, начальник смены, бухгалтер, аналитик
читают день; прочие роли и чужая точка - 403.

### Откат

- `BACKOFFICE_POS_DAY_ENABLED=false` и перезапуск API: `GET .../ops/pos-day` отвечает 404 как
  неизвестный вид, раздела «Касса» и блока «Сегодня» нет, реестр заказов и отчёт смены - как до
  полосы, ответ `GET .../branches/<точка>` без `pos_terminals`, `pos_staff`,
  `cashier_metrics.paid_total_minor`. Данные не меняются: раздел ничего не пишет.
- Права на чтение 073 остаются: тот же набор выдаёт `cloudPosSalesGrants(role, {backoffice: true})`
  полосы pos, и сбрасывает их только он.
- Учётные записи кассы с номерами из скрипта не откатываются: это обычные учётные записи кассы.

`auditFixes` (`apps/backoffice/src/operations-model.ts`); если интеграция решит иначе (без флага или
свой флаг), меняется только она (CR `bo-ui-3`).

## Склад P1: сторно, быстрое списание, отчёт списаний (шаг 4 полосы)

Флаг - существующий `BACKOFFICE_STOCK_V2_ENABLED` (дополнение контракта, `design-bo-ui.md` §2 и §8
в.5). Склад P1 включается сам, когда на базе есть 075 и helper `backoffice-p1-grants.mjs` выдал роли
API права склада (`stockV2: true`, CR `bo-ui-1` §1). Тогда `GET .../branches/<точка>` сообщает
`capabilities.stock_p1=true`. Без 075 или без прав ключа нет, и склад работает ровно как у облачной
полосы (причины списаний и данные накладной - `backoffice-cutover.md`). Подробности для интеграции -
CR `bo-ui-4`.

### Что видит управляющий

- **«Остатки»** - плашка «Продажи пока не списываются со склада автоматически. Остаток верен только
  сразу после инвентаризации...» (до автосписания, шаг 5) и колонка «Последний подсчёт» у каждой
  позиции (время последней инвентаризации позиции или «Подсчёта не было»).
- **«Списание»** - плитки быстрого списания вверху окна («Булки из шкафа +2 шт», «Мясо +0,5 кг»).
  Одно нажатие добавляет количество плитки в строку позиции; причина списания по-прежнему
  обязательна. Плитку задают в карточке ингредиента («Ингредиенты» - «Изменить»): «Название плитки»
  (до 40 символов) и «Количество за одно нажатие» (целое число в учётной единице: штуки, граммы,
  миллилитры). Оба поля пустые - плитки нет.
- **«Документы»** - у каждого документа «Причина или поставщик» и «Сторно» («Сторнирован 20.11.2026
  09:30» или «-»); в «Движения и сторно» - кнопка «Сторно» для управляющего и бухгалтера. Остальные
  видят «Сторно делают управляющий и бухгалтер.».
- **«Списания»** - период (до 92 дней): итог, по причинам (с колонкой «Сторно»), по дням, по
  позициям, по сотрудникам, список документов; старые списания без кода - строкой «Без кода причины
  (до включения склада v2)». «CSV итогов» и «CSV строк документов» в тенге («Сумма, ₸»).
- **«Движение»** - все документы периода по видам (поставка, списание, инвентаризация, производство,
  сторно), «CSV строк документов».

### Сторно

Окно «Сторно документа»: «Сторно создаст обратный документ. Исходный останется в истории.»,
таблица «Сейчас - Изменение - После сторно - Стоимость» по сегодняшним остаткам, причина изменения
(обязательна), кнопка «Провести сторно». Обратный документ - вид «Сторно», тот же номер, движения
ровно противоположные исходным (количество и стоимость). Нельзя:

- инвентаризацию и само сторно («Инвентаризацию не сторнируют: исправьте остаток новой
  инвентаризацией»);
- второй раз («Документ уже сторнирован»);
- если после документа по его позициям провели инвентаризацию: она уже учла фактический остаток
  (исправлять новой инвентаризацией или списанием);
- если остатка или его стоимости уже меньше, чем добавил документ (поставка, из которой часть уже
  списана или израсходована): кабинет пишет «остаток или его стоимость уже меньше... Сторно
  невозможно», сервер отвечает `INSUFFICIENT_STOCK`. Остаток не уходит ниже нуля, и не бывает нуля
  штук с ненулевой стоимостью.

Если пока окно открыто другой документ изменил остатки этих позиций, кабинет перечитывает их,
показывает новую таблицу и просит провести сторно ещё раз. Повтор того же запроса (потеря ответа)
не создаёт второго сторно. В журнале аудита - «Склад: Сторно документа».

### Как считается (тот же текст в кабинете)

Дни - по времени Алматы. Сумма списания - стоимость по средней себестоимости на момент документа.
Сторно списания уменьшает итоги дня, в который его провели, под причиной и автором исходного
списания: закрытые дни не меняются, а дни периода складываются в период. «Документов» - число
списаний, «Сторно» - число сторно, «Сумма» - нетто.

## Списание по продажам (шаг 5 полосы, `BACKOFFICE_STOCK_AUTOCONSUME_ENABLED`)

Продажи кассы (таблицы 073) и заказы приложения и киоска списываются со склада по связям «позиция
меню - склад». Связи заводит управляющий, шеф проверяет их, управляющий утверждает. Один документ
«По техкарте» на заказ, его не бывает дважды (уникальный индекс 075). Дизайн: `design-bo-ui.md`
§5.3, §5.5; перенос: CR `bo-ui-5`.

### Что видит управляющий

Вкладка «Остатки» → «Списание по продажам»:

- **Связи меню со складом** (есть уже при складе P1, без флага автосписания): все товары и опции
  опубликованного меню. Статус словами: «Утверждено», «Черновик», «Нет связи», «Из состава комбо»
  (комбо и наборы без своей связи списываются по составу), «Из товара: ...» (опция, которая
  означает товар меню). Фильтры «Без связи: N» и «Черновики: N». В связи - строки склада:
  «Склад: ...» списывает позицию как есть, «По ТТК: ...» раскладывает выход техкарты на сырьё
  (если у техкарты учёт запасом - списывает сам выход). «Без списания» - для опций вроде «без лука».
  Количество - на одну проданную позицию, в г, мл или шт. Любое изменение возвращает связь в
  черновик.
- **Режим** (только с флагом): «Списание по продажам: Выключено | Проверка без списания | Включено
  с ДД.ММ.ГГГГ ЧЧ:ММ». Окно смены режима пишет, что произойдёт, и предупреждает, если покрытие
  меньше 95 %.
- **Покрытие за 7 дней**: доля строк продаж, у которых все связи утверждены, и самые частые позиции
  без связи.
- **Очередь**: каждая продажа с состоянием («Списано», «Не списано», «Проверено, не списано»,
  «Ждёт списания», «Пропущено», «Списывать не нужно»), причиной словами («нет связи: Бургер Острый
  · не хватает: Булка (нужно 2 шт, есть 0 шт)»), тем, что списано, и документом. Кнопки
  «Повторить» (управляющий и начальник смены, попытка сразу) и «Пропустить с причиной».
- Плашка над вкладками: «Продажи списываются со склада автоматически с ...» при «Включено»,
  «...режиме проверки...» при проверке.

### Как считается (тот же текст в кабинете)

- Продажа кассы берётся, когда кухня начала заказ (в работе, готов, выдан), остальные - проходом
  в 03:00 Алматы следующего дня. Заказ приложения и киоска - по первой оплате, так же.
- Учитываются только продажи с момента «с ДД.ММ ЧЧ:ММ»; при включении позже воркер догоняет их по
  порядку продажи.
- Меню продажи - та версия каталога, по которой продавали: касса - через выпуск меню
  (`catalog_menu_deliveries`), приложение - по версии в заказе. Связи - текущие утверждённые.
- Комбо без своей связи раскладывается по составу до 5 уровней; опция - своя связь, иначе товар, на
  который она указывает. Выход ТТК раскладывается на сырьё до 6 уровней; округление одно, до целой
  единицы (г, мл, шт) на ингредиент на заказ.
- Нет связи, черновик, неизвестная позиция, ошибка ТТК: заказ «Не списано» целиком, причина видна,
  другие заказы идут дальше. Не хватает остатка - тоже «Не списано», со списком нехватки.
  Повтор - сам: через 1, 2, 5, 15, 30, 60 минут и сразу после поставки, инвентаризации, сторно,
  изменения связи или техкарты.
- Отмена или полный возврат до начала приготовления - «Списывать не нужно». Возврат после начала -
  остаётся списанным, в очереди это видно; ошибочное списание исправляют сторно документа (позиция
  очереди остаётся «Списано», документ «Списано, затем сторно»).
- Позиция, подсчитанная после продажи (инвентаризация позже времени продажи), не списывается: подсчёт
  уже учёл расход («учтено подсчётом»).
- «Проверка без списания» ничего не пишет в склад: в очереди видно, что списалось бы.
- Ручное «списание по техкартам заказа» в режимах проверки и включено отклоняется
  (`AUTOCONSUME_ACTIVE`): иначе заказ списался бы дважды.
- Документ автосписания создаётся от имени того, кто последним менял режим (после «Повторить» -
  от имени нажавшего); в «Документах» он
  подписан «Автоматически по продаже кассы» или «... по заказу приложения или киоска».

### Включение

Порядок по `design-backoffice.md` §7: связи → проверка без списания → инвентаризация → включено.

1. Склад P1 уже работает (раздел выше). Шеф с управляющим заводят и утверждают связи всех товаров

3. Запустить воркер (CR `bo-ui-5` §1): отдельный процесс

4. Управляющий: «Изменить режим» → «Проверка без списания» с 13.11 (или сейчас). 1-3 дня сверять

    комментария - это пояснение (например, расхождения кассы);
  - открытая смена - карточка «Смена открыта · менеджер ...» с авто-проверками к закрытию:
    «Кассовые смены: 2 из 2 закрыты, расхождение -500 ₸. Поясните в комментарии.», «Не оформлено в
    Webkassa: 1 чек на 11 670 ₸», «Данные кассы не поступают с 21:10. Подтвердите вручную.»,
    списания и подсчёт за день, заблокированные списания по продажам; замечания открытия;
  - «Закрыть смену» - мастер из двух шагов: чек-лист закрытия (кнопка «Сохранить черновик» хранит
    ответы на сервере), затем «Передача смены» (обязательна) и «Закрыть смену»;
  - «Смены за день» - смены выбранного дня с числом замечаний и передачей; «Подробнее» - все ответы,
    комментарии и авто-проверки на момент ответа;
  - «Чек-лист» (только управляющий) - тексты пунктов, «Обязательный», новые пункты, «Убрать» (пункты
    с авто-проверкой не убираются); сохранение создаёт новую версию, она действует для смен,
    открытых после сохранения.
- **«Кассовые смены и прежний журнал»**: «Управленческий журнал» только для чтения (кнопок
  «Добавить» и «Изменить» нет, сервер отказывает `LEGACY_JOURNAL_READ_ONLY`), показаны последние
  200 записей. Старые записи не меняются.
- Права: открывают, сохраняют и закрывают - управляющий и начальник смены
  (`manager_shifts.write`); чек-лист - управляющий (`manager_shifts.template`); бухгалтер и
  аналитик видят всё, кнопки неактивны с текстом «Открывают и закрывают смену управляющий и
  начальник смены.».

### Как считается

- День смены - календарный день Алматы её открытия. Смена, закрытая после полуночи, остаётся в дне
  открытия; авто-проверки открытой смены считаются за её день (как кассовые смены в «Кассе»).
- Одна открытая смена на точку (`MANAGER_SHIFT_OPEN`); закрытая смена не меняется (триггер 075).
- «Кассовые смены»: смены кассы дня из `ops/pos-day` (Z и отчёты кассы): сколько закрыто, сумма
  расхождений наличных и Kaspi терминала. Открытая касса или расхождение - «Есть проблема». Нет
  данных или касса открыта, а данных нет 10 минут - «Нет данных», ответ вручную.
- «Webkassa»: чеки дня, ожидающие номера Webkassa. «Списания», «Подсчёт»: документы склада дня.
  «Заблокированные списания»: продажи дня в состоянии «Не списано» (только при автосписании, иначе
  пункт необязателен). «Явка»: опубликованные смены графика на день. «Стоп-лист»: последнее
  сообщение кассы.
- Ответ хранит текст пункта и авто-проверку как они были, поэтому закрытая смена читается так же
  после смены шаблона.

### Включение

1. Cloud-2 (075 с разделом 8 и helper P1) уже стоит.
2. В env `provision` и API: `BACKOFFICE_MANAGER_SHIFTS_ENABLED=true`. Helper P1 с
   `managerShifts: true` выдаёт роли API `SELECT, INSERT, UPDATE` на `bo_manager_shifts` и
   `SELECT, INSERT` на `bo_branch_templates`. Перезапуск API; в `GET .../branches/<точка>` -
   `capabilities.manager_shifts=true`.
3. Проверка (управляющий, 5 минут): «Смены» → «Открыть смену», ответить на пункты, открыть;
   карточка показывает авто-проверки; «Закрыть смену» → передача → «Закрыть смену»; смена в списке
   дня. Телефон 390 px: начальник смены открывает смену, кнопки и тексты видны без прокрутки вбок.

### Откат

`BACKOFFICE_MANAGER_SHIFTS_ENABLED=false` в env API и `provision`, перезапуск API. Блок исчезает,
«Управленческий журнал» снова пишется, смены и версии чек-листа остаются в 075 (при повторном
включении открытая смена снова видна).

### Проверки (тесты полосы)

- `packages/backoffice-core/tests/manager-shifts.test.mjs` (PostgreSQL): правила чек-листа, схемы,
  флаг выключен (нет вида и команд, журнал пишется), одна открытая смена, точный повтор и конфликт
  повтора, черновик, неполный чек-лист и пустая передача, закрытая неизменна (команда и SQL), смена
  после полуночи, авто-проверки кассы (расхождение, Webkassa, нет данных), версии чек-листа, роли,
  журнал только для чтения и 200 его записей не вытесняют станции.
- `tests/integration/backoffice-p1-flags.test.mjs` (флаги выключены - прежние ответы, HTTP 404),
  `tests/backoffice/manager-shift-ui.test.mjs`, `manager-shift-browser.test.mjs` и
  `manager_shift_ui.py` (Chromium 1440x900 и 390x844, режимы «выключено» и «включено»).

### Чего смена менеджера пока не делает

- Подсчёт ключевых позиций проверяется по документам подсчёта дня, а не по списку позиций
  `count_daily` (поля у ингредиента пока нет).
- «Инциденты курьеров» - ручной пункт: события кухни (`kds_edge_events`) в облако не приходят.
- Пояснение расхождения из кассы в облако не приходит (CR `bo-ui-2` §2): его пишут комментарием к
  пункту «Кассовые смены».

## Должности и состав кассы (шаг 6 полосы, `BACKOFFICE_STAFF_POSITIONS_ENABLED`)

Должности сотрудников (А8, Д3), доступ к кассе и перенос состава на кассу точки с личными PIN.
Карточка сотрудника получает поля без DDL; список должностей точки - версии в
`bo_branch_templates`. Дизайн: `design-bo-ui.md` §5.7, перенос: CR `bo-ui-6`.

### Что видит управляющий

- **«Смены» → «Сотрудники»**: колонки «Должность», «Доп. станции», «Доступ к кассе», «Доступы»
  («Касса (PIN), экраны 2, 4 общим входом кухни» или «Нет»). В карточке: «Должность» из списка
  (11 должностей: кассир 1, выдача 2, выдача доставки 3, сборщик 4, тосты/бургеры/фри 5, панировщик 6,
  жарщик 7, заготовщик 8, раннер 9, менеджер смены, управляющий), «Доп. станции» до трёх,
  «Доступ к кассе: Нет | Кассир | Начальник смены» (подставляется по должности, можно изменить).
- **«Выгрузить состав для кассы»** - файл `PickChick-состав-кассы-ДД.ММ.ГГГГ.json` (все карточки,
  роль кассы и номер для кассы по `edgeStaffId`, sha256 содержимого) и строка «В выгрузке N
  карточек: кассиров ..., начальников смены ...».
- **«Должности»** - список точки: название, станция, доступ по умолчанию, «Действует»,
  «Добавить должность». Должность не удаляется, только выключается: у сотрудников она остаётся.
- Только управляющий (`staff.positions`); бухгалтер и аналитик видят колонки.

### Состав на кассе: операторские скрипты на сервере точки

Файл выгрузки передаётся оператору точки (не по почте и не в мессенджер: имена сотрудников).

```bash
# 1. План (ничего не пишет): кого завести, кого отозвать, что заблокировано, sha256 плана
node scripts/staff-roster-apply.mjs --file PickChick-состав-кассы-18.11.2026.json --terminal <id кассы>
# 2. Применить ровно этот план (отказ, если база или файл изменились)
node scripts/staff-roster-apply.mjs --file PickChick-состав-кассы-18.11.2026.json --terminal <id кассы> \
  --apply --expected-plan <sha256 плана>
# 3. PIN по одному: на экране имя, сотрудник сам вводит PIN дважды (скрыто); пустой ввод - пропуск
node scripts/staff-pin-batch.mjs --file PickChick-состав-кассы-18.11.2026.json [--digits 4|6]
```

- Скрипт заводит учётную запись кассы с номером `edgeStaffId` (те же номера «Касса» в кабинете
  показывает именами), выдаёт сессию на `--terminal` (активный терминал точки) и пишет файл входа
  `.local/staff-<id>.json` (0600, не печатается). Сессия действует 8 часов: PIN нужно задать в тот
  же день.
- Роль на кассе не меняется на месте: кассир, ставший начальником смены, получает новую учётную
  запись, старая отзывается. Уволенные, неработающие и без доступа - отзываются.
- «Заблокировано: revoked_earlier» - учётная запись этого человека в этой роли уже отзывалась;
  операторские функции кассы её не восстанавливают (CR `bo-ui-6` §3). Пока - вручную через
  оператора кассы.
- Общий вход кухни и учётные записи, заведённые вручную, скрипт не трогает (список «unmanaged»).
- PIN не печатается, не пишется в лог и в файлы. Занятый PIN - «Этот PIN не подходит. Введите
  другой.» Повторный запуск пропускает тех, у кого PIN уже есть (`--replace` - заменить, нужен
  новый файл входа через `staff-setup.mjs --renew`).

### Включение

1. В env API: `BACKOFFICE_STAFF_POSITIONS_ENABLED=true`, в `provision` - helper P1 с
   `staffPositions: true` (CR `bo-ui-6` §1, права `SELECT, INSERT` на `bo_branch_templates` для списка
   должностей). Перезапуск API; `capabilities.staff_positions=true`.
2. Управляющий проставляет должности и доступ к кассе 68 карточкам (сначала кассирам и начальникам
   смены), выгружает состав 18.11.
3. Оператор точки: план, применение, PIN по одному (выше). Проверка: каждый кассир входит по PIN на
   своей кассе; в «Касса» в кабинете смена называет кассира по имени.

### Откат

`BACKOFFICE_STAFF_POSITIONS_ENABLED=false` и перезапуск API: колонки и кнопки исчезают. Поля в
карточках остаются: сохранение карточки без них их не стирает (и при выключенном флаге), прежний
редактор, отправивший их без изменений, не получает отказа. Учётные записи кассы не меняются.

### Проверки (тесты полосы)

- `packages/backoffice-core/tests/staff-positions.test.mjs` (PostgreSQL): 11 должностей, схемы,
  старые карточки, флаг выключен, поля карточки и их сохранение, список точки (версии, выключение,
  `POSITION_IN_USE`), выгрузка (все карточки, роль, номер, sha256), роли, откат.
- `tests/integration/backoffice-p1-staff-roster.test.mjs` (облако и касса, синтетика): выгрузка →

  месте → заблокированная запись → PIN по одному, вход по PIN, PIN нигде не показан.
- `tests/backoffice/manager-shift-ui.test.mjs`, `manager-shift-browser.test.mjs`.

### Чего пока нет

- Имя на кассе не обновляется скриптом (операторской функции нет): план показывает
  `name_differs`.
- Расстановка по станциям (А9) и CSV-импорт должностей - не в этой полосе.
