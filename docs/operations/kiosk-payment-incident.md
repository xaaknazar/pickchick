# Киоск: передача неизвестного платежа сотруднику

Задача `kiosk-payment-incident`, 9 октября 2026. Решение владельца: вариант A,
освободить установленный iPad build 10 без новой сборки.

## Проблема

Контрольный заказ киоска на 100 ₸ от 8 октября ожидает оплату. Его QR-попытка
находится в `unknown` без банковского ID (`operation_id IS NULL`): ответ create
потерян, сверить результат с банком нечем. Пока такая попытка открыта:

- сервер отдаёт заказу фазу `checking`, и iPad показывает «Уточняем результат оплаты»;
- `KioskSessions.end()` отвечает `CONFLICT`, поэтому новый гость невозможен.

Объявлять попытку `failed` или `paid` через SQL, удалять приложение или
подставлять ID диагностических QR запрещено ([блокеры](payment-blockers-2026-10-09.md)).

## Решение

Ответственный менеджер точки принимает инцидент. Запись создаётся атомарно
и не меняет ни попытку, ни QR-строку, ни заказ.

- Миграция `050_cloud_kiosk_payment_incidents.sql` добавляет append-only таблицу
  `commerce_kiosk_payment_incidents`: кто принял, когда, причину, заметку и
  наблюдённое состояние. Триггер БД допускает запись только для заказа киоска,
  у которого:
  - единственная открытая QR-попытка `issuing`/`unknown`, начатая не менее 15 минут назад;
  - нет captures и возвратов, нет других открытых попыток и счетов.

  `UPDATE` и `DELETE` таблица запрещает.

- `KioskSessions.end()` пропускает такой заказ, пока его единственный открытый
  пункт - эта попытка. Если появился capture, возврат, внимание кухни или вторая
  попытка, снова действует прежний `CONFLICT`.
- `KioskCheckout.read()` только в ответе устройству отдаёт `phase: 'failed'`
  вместо `checking`. Это единственный путь выхода из сохранённого заказа в
  установленных сборках. Мобильный клиент, бэк-офис, `readKioskQrPayment` и
  финансовые проекции по-прежнему видят `checking`/`unknown`.
- QR worker продолжает сверку этой строки. Повторного create нет. Поздний
  `Processed` с точной суммой привязывается только к исходному заказу; после
  capture подмена фазы прекращается.

**Компромисс варианта A.** На iPad появится «Оплата отклонена» и строка
«Обратитесь к сотруднику». Это неточный текст для неизвестного результата.
Его видит сотрудник: гость ушёл 8 октября. Честный текст требует новой сборки
iPad с отдельной фазой.

## API и операция

`/v1/admin/backoffice/branches/:id/kiosk-payment-incidents`
(`services/api/src/kiosk-incident-controller.ts`,
`packages/backoffice-core/src/kiosk-incidents.ts`):

- `GET` - кандидаты и уже принятые инциденты. Роль `manager` или `analyst`.
- `POST` - принятие инцидента, только `manager` этой точки. Тело:
  `request_id`, `order_id`, `attempt_id`,
  `reason` (`bank_identity_lost`/`bank_result_unknown`), `note` 3-500 символов и
  `confirm: "payment_result_remains_unknown"`. Повтор с тем же `request_id`
  возвращает прежний результат, с другим телом - `CONFLICT`. Запись дублируется
  в `bo_audit` (`action = kiosk_payment_incident`) и `bo_commands`.

Маршрут не опубликован в gateway и портале. Оператор вызывает loopback API на VPS:

```sh
python3 infra/staging/kiosk-payment-incident.py preview --branch-id <id> --token-file <0600>
python3 infra/staging/kiosk-payment-incident.py accept --branch-id <id> --token-file <0600> \
  --order-id <id> --attempt-id <id> --note-file <txt>
```

Токен - собственный back-office токен ответственного менеджера в файле 0600.
Он передаётся через stdin SSH, в аргументах не появляется. Банк не вызывается.

После принятия iPad при опросе или по кнопке «Проверить статус» переходит на экран
заказа. Сотрудник нажимает «Новый заказ»: `/sessions/end` отвечает успешно, и iPad
возвращается на стартовый экран.

## Права и выпуск

Роли API нужны `SELECT,INSERT` на новую таблицу (`infra/staging/kiosk-incident-grants.mjs`).
`SELECT` обязателен до запуска нового API: его читают `end()` и `read()`.

Выпуск: миграция 050 и образ API с полной зелёной CI, блокировкой, зашифрованным
backup и проверкой восстановления. `@vps/api` и `@vps/db` сейчас заняты задачей
Codex `unified-menu-release`, поэтому выпуск согласуется с ней. Нельзя применять
проверку «0 нерешённых QR» из `release-kiosk-qr-recovery.py`: эта строка
по замыслу остаётся на сверке.

- новый `packages/backoffice-core/tests/kiosk-incidents.test.mjs`, 5/5, три прогона подряд:
  - блокировка до 15 минут и до принятия;
  - запись неизменна;
  - деньги и попытка байт-в-байт прежние;
  - iPad получает `failed`, `end()` проходит;
  - worker не создаёт QR повторно;
  - analyst, чужой токен, чужая точка и выключенный сервис отклоняются;
  - триггер БД;

  - точные права роли.
- Существующие kiosk sessions/checkout/QR suites 39/39. В двух тестах
  ограниченной роли к модели прав добавлено `SELECT` на новую таблицу.
