# Единое реальное меню: подготовка и блокеры

Дата: 25 сентября 2026. База: `8a93c06` из `codex/shared-development`.
Работа ведётся по поручению владельца перенести фактическое меню iiko и подключить
одну опубликованную версию к mobile/POS/kiosk/edge. **Этап целиком не завершён:**
машинная выгрузка блокируется недостающей авторизацией приложения iiko,
а источник цен ещё требует решения владельца. Рабочее меню не опубликовано,
клиенты не переключены. iiko и существующие каналы продаж не изменялись.

## Почему API пока не выгрузил меню

Действующий ключ проверен без изменения настроек. Старый
`POST /api/1/access_token` вернул HTTP 403 с требованием использовать
`/api/v2/access_token`. Пробный запрос нового метода без реквизитов приложения
вернул HTTP 400, отсутствует `clientSecret`. Токен не получен; организации
и меню через защищённые методы API ещё не читались.

После этого прочитана актуальная официальная
[документация авторизации](https://api-ru.iiko.services/docs#tag/Authorization)
и её [OpenAPI](https://api-ru.iiko.services/api-docs/docs).
Правильный v2 запрос содержит **apiKey, appId, clientSecret** (не apiLogin).
App ID и секрет выдаёт приложение на [портале разработчика iiko](https://api.iiko.help/).
Старый ключ ресторана не заменяет эти два реквизита. В карточке Analytics
виден активный доступ, но реквизиты приложения в просмотренном разделе не указаны.

У владельца запрошено, существует ли зарегистрированное приложение.
Новый доступ/договор не оформлялся, действующие ключи не пересоздавались.
Секреты в переписку или Git не передавать: подготовить приватный env-файл
на нужном Mac. На этом Mac создан `.local/iiko-import/credentials.env` (0600)
с ранее переданным ключом; appId/clientSecret пустые. Эта папка исключена из Git.

## Подготовленный инструмент

[`scripts/iiko-menu-export.mjs`](../../scripts/iiko-menu-export.mjs) использует
v2 авторизацию и актуальное чтение меню `/api/menu/v3/by_id`. Старые методы
выгрузки помечены deprecated в актуальной спецификации и не выбраны для нового кода.

Экспортёр:

- разрешает только фиксированный HTTPS-host iiko, авторизацию и три метода
  чтения: организации, список меню/ценовых категорий, меню по ID;
- запрещает редиректы и произвольные пути, ограничивает время и размер ответа;
- не выводит ключи, токен и тела ошибок провайдера; токен остаётся в памяти;
- требует явную организацию, проверяет доступность выбранных меню/ценовой категории
  и точное совпадение ID ответа. Не переключается молча на другую точку/прайс;
- сохраняет исходные ответы меню с SHA-256 в новой приватной папке `.local`.
  Завершающий manifest записывается последним; повтор создаёт новый снимок;
- формирует review с количествами, размещениями блюд, ценами, скрытыми позициями,
  отсутствующими ссылками и полями, требующими решения;
- различает отсутствующую цену и явный ноль, не округляет суб-тиыны;
- сохраняет исходные правила модификаторов/комбо в JSON. Не объявляет их
  совместимыми с PickChick автоматически. `publishable` всегда false;
- не подключается к БД PickChick, не меняет настройки iiko, не отправляет заказы,
  не скачивает изображения и не публикует меню.

Запуск после безопасного заполнения недостающих реквизитов:

```sh
node --env-file=.local/iiko-import/credentials.env scripts/iiko-menu-export.mjs --discover
```

В выводе выбрать подтверждённый ID организации; затем:

```sh
node --env-file=.local/iiko-import/credentials.env scripts/iiko-menu-export.mjs \
  --organization ORGANIZATION_UUID
```

Без `--menu` выгружаются все доступные по ключу внешние меню выбранной
организации (не вся номенклатура iiko и не весь ресторанный архив).
Повторяемый `--menu ID` ограничивает выбор; `--price-category UUID` задаёт
конкретную доступную ценовую категорию. По умолчанию она null: цены меню.
Raw JSON и review с фактическими данными остаются локально, в Git идут код,
синтетические тесты и этот обезличенный отчёт.

## Известные различия контрактов перед импортом

`CatalogPayloadSchema` требует slug-ID, ограниченный набор локальных изображений,
целый вес, фиксированный состав комбо и default choices не ниже минимума группы.
iiko допускает отсутствие дефолта при обязательном выборе (подтверждено карточкой),
дробный вес, freeQuantity/минимумы отдельных модификаторов и цены компонентов комбо.
Для edge используется отдельный `MenuSnapshot` с UUID; mobile/kiosk TEST-контур
не является читателем этого коммерческого каталога.

Следовательно, перенос через простую замену массива блюд теряет бизнес-правила.
После получения исходного JSON требуется явный mapping ID/артикулов, проверка
совместимости или версионированное расширение контрактов, локальный импорт
черновика, контрольные корзины с владельцем и только затем публикация/receipt
одной версии для каналов. Нельзя выставить `content_reviewed=true`, придумать
налоги/RU-KZ/КБЖУ, обнулить доплаты или включить оформление на основе таблицы браузера.

## Проверки и точка продолжения

На Mac установлены зависимости через pnpm 11.19.0 с frozen lockfile, Node 24.16.0.
Полная сборка монорепозитория прошла. Прошли 105 unit-тестов, включая 11 новых
проверок экспортёра, 7 roadmap-тестов, targeted ESLint/Prettier и diff check.
Проверены ограничения методов/организации, отсутствие секретов в ошибках,
обрыв/размер ответа, точность цены, отсутствующие ссылки, приватные права,
новый снимок при повторе и отказ от symlink-папки.

Это контрактные проверки с синтетическими ответами, не успешная реальная
API-выгрузка и не проверка PostgreSQL-импорта. Полная Foundation CI базы имеет
ранее описанные RUN/kitchen ошибки. Docker/БД на этом Mac, импорт, подключение
клиентов, серверная публикация, обновление онлайн-roadmap и приёмка не выполнены.

Продолжение после ответа владельца: appId/clientSecret через приватный файл,
подтверждение прайса, read-only export, проверка исходных правил и недостающих
данных, импорт в изолированную БД, согласование корзин, интеграция каналов,
CI и отдельный guarded deploy с разрешённого компьютера. Текущий терминал,
iiko, Яндекс и Glovo до приёмки сохраняют действующую работу.
