# PickChick: домен, TipTopPay и Webkassa

Решение владельца от 28 сентября 2026: домен **pickchick.kz** куплен в PS.kz;
первоначально названный piktik.kz был исправлен владельцем. Текущий VPS
185.129.51.103 (Hoster.kz, Алматы, по подтверждению владельца) используется
временно. Мобильный клиент после приёмки будет обращаться к
https://api.pickchick.kz; смена IP выполняется через DNS и перенос сервера,
без зашитого IP в новой сборке. Старые адреса сохраняются на время перехода.

Пилот предполагает реальные списания малой суммы и настоящие чеки; размер суммы
ещё не утверждён. Переданный терминал TipTopPay находится в TEST. Статус
«Активный» не означает LIVE. Его кабинет оформлен на другую компанию:
merchant/legal entity для PickChick ещё согласуются с провайдером.

## Сделано в коде

- `packages/commerce-core/src/tiptoppay.ts`: проверка Content-HMAC SHA256 по
  исходным URL-encoded байтам, ограничение 16 KiB, запрет дублей параметров,
  точные целые тиыны, проверка KZT/Payment/Completed/TestMode=0.
- `InvoiceId` для будущего checkout должен быть UUID **попытки оплаты**,
  `AccountId` - неприватный UUID клиента, не телефон. Сверяются сохранённые
  попытка, сумма, customer, provider account/Public ID и юридическое лицо
  платёжного и фискального аккаунтов. Поля из приложения не задают сумму.
- HTTP `POST /v1/integrations/tiptoppay/check` и `/pay` принимают только
  `application/x-www-form-urlencoded`, используют отдельный raw parser.
  JSON/GET/плохая подпись/TEST/неверная привязка отклоняются.
- Pay передаёт результат в существующий transactional inbox/ledger/outbox.
  Ответ code=0 отправляется только после commit. Поздние повторы для отключённого
  аккаунта остаются допустимы. Сырой payload, телефон и карточный токен не хранятся.
- Приём по умолчанию выключен. Даже при включённом приёме LIVE подтверждений
  Check возвращает code=13: новый checkout этим этапом **не открывается**.
  TEST capture не записывается в коммерческий ledger и не создаёт реальный чек.
- Приватный шаблон `infra/payments/tiptoppay.env.example` и безопасная проверка
  `/test`: `node --env-file=.local/tiptoppay.env infra/payments/check-tiptoppay.mjs`.
  Этот запрос не проводит платежей и не доказывает LIVE/готовность кошельков.
- Подготовлены DNS manifest и дополнительный Caddy site block в `infra/domains`.
  Существующий Caddyfile соседнего проекта не заменяется. Cookie/auth/Origin,
  приватные маршруты, TLS и mobile transport проверяются до переключения клиента.

## Что пока не подключено

Владелец сохранил ключ в приватном файле. 28 сентября запрос POST /test к
api.tiptoppay.kz вернул Success=true: доступ подтверждён без списания.
Секрет не выводился, не включался в Git и не переносился на VPS. Это не проверка LIVE.
Новые HTTP-обработчики
ещё не выпущены на VPS и не открыты allowlist публичного gateway.
**Адреса в кабинете TipTopPay пока не заполнять.** Локальный HTTP-ответ не
является доступностью внешнего webhook.

Нет исходящего charge/3DS/wallet адаптера, серверного commercial checkout
и reconcile worker TipTopPay. Fail/Confirm/Refund/Cancel/Recurrent/Receipt
не подтверждаются кодом 0; их нельзя включать до реализации и приёмки.
Проверки неизвестного результата, возвратов и повторов коммерческого ядра
не заменяют испытаний с настоящим провайдером.

Apple Pay: Merchant ID/processing certificate/entitlements и новый native build.
Google Pay: регистрация/одобрение приложения и production-access по требованиям
TipTopPay. Эти доступы пока не проверены. Переход на другой merchant account
требует новых привязок, проверки сертификатов и работы возвратов по старым
операциям; сохранённые карты нельзя считать автоматически переносимыми.

## Webkassa - единственный исполнитель фискализации mobile

Владелец подтвердил действующую Webkassa точки и желание использовать ту же
кассу для приложения. Вход в кабинет теперь проверен, но API-доступ и совместная работа с iiko требуют уточнения.
Предоставленные ККМ принадлежат ИП Peak Group; владелец подтвердил продавцом mobile
ИП «PICK CHICK ALA AP». [Отчёт о доступе и несовпадении реквизитов](../integrations/webkassa-live-access-2026-09-28.md).
Не включать параллельно автоматические чеки TipTopPay/Kassir и нашего адаптера:
это может создать два чека на одну покупку.

От Webkassa нужны актуальная документация/Postman, тестовая касса/API-KEY,
порядок допуска в рабочую среду, разрешённый способ работы с существующей кассой,
роли и владение открытием/закрытием смены, поиск исходного чека после таймаута,
внешний уникальный ID, продажа/частичный возврат, налоговые ставки и тип оплаты.
Подтвердить отсутствие повторной фискализации этих же mobile заказов через iiko.
Секреты передаются вне Git/чата. Производственные чеки и смены не изменялись.

Серверный путь после завершения интеграций: неизменяемая рассчитанная корзина →
TipTopPay → проверенное банковское подтверждение → очередь Webkassa → настоящий
чек и путь допуска на кухню из commerce-core. При сбое кассы показывать ожидание,
выполнять сверку, не повторять вслепую продажу и не придумывать чек. Политика
ожидания/возврата при недоступной фискализации требует проверки до первого списания.

## Проверки и выпуск

28 сентября локально прошли 10 новых проверок (включая реальный HTTP),
6 unit коммерческого ядра и 23 PostgreSQL integration. Пять одновременных
подписанных Pay дают один capture, один inbox и один fiscal document;
документ остаётся queued, не выдаётся за выпущенный чек. Проверены неверные
customer/amount/currency/TestMode и повтор после отключения аккаунта.
Typecheck API/commerce, адресные ESLint/Prettier и Caddy validate прошли.

Базовый Foundation CI 36393740158 не зелёный: упал шаг
«Browser recovery regressions (isolated HTTP fixtures)», остальные пять jobs
успешны. Логи получены на следующем этапе: устаревшие ожидания UI исправляются,
см. [подготовку HTTPS](deployments/2026-09-28-domain.md). Roadmap CI зелёный.
До полного зелёного выпуска не менять API/gateway на VPS и онлайн-roadmap.
Read-only SSH подтвердил healthy API, gateway, kitchen portal и roadmap.

DNS-зона создана в PS.kz и включена: apex A 185.129.51.103 (TTL 3600),
api A 185.129.51.103 (TTL 300), www CNAME pickchick.kz (TTL по умолчанию).
Авторитетный ns1.ps.kz подтвердил оба A; локальный resolver подтвердил apex,
на следующем этапе 1.1.1.1 и 8.8.8.8 также подтвердили api A.
NS: ns1/ns2/ns3.ps.kz. HTTPS для новых имён ещё не настроен, приложение не переключено.
Мастер PS.kz автоматически создал mail A, MX и SPF; почтовый сервис не настроен.
Эти записи нельзя считать работающей почтой; перед её подключением согласовать
почтового провайдера и заменить шаблонные записи.

Учтён [аудит второго Mac](../integrations/webkassa-access-audit-2026-09-28.md),
коммит 67160b3: DN.WebKassaPlugin 1.4.4 есть у обеих касс; интерфейс iikoWeb
не предоставил API-ключи. SWK-регистрационные идентификаторы не являются API-доступом.
