# С4: транзакционный шаг cloud 071 -> 072

`infra/staging/queue-recovery-cloud-owner.mjs` выполняет только шаг базы.
Он не обновляет API, не меняет compose/флаги, не запускает общий `provision.mjs`
и не выдаёт подтверждение готовности облачного выпуска для Windows-оператора.
На рабочем VPS этот код ещё не запускался.

## Условия применения

Ответственный за серверное окно предварительно проверяет точный исходник и
полную CI, свежую зашифрованную копию с восстановлением, установленный API и
конфигурацию. Должны быть удержана штатная серверная maintenance lease и
остановлены писатели. PostgreSQL advisory lock и блокировки таблиц внутри
этого шага не заменяют внешнюю блокировку всего серверного выпуска.

Команда запускается из проверенного дерева с **ровно исходниками до 072**,
через существующее защищённое owner-подключение к `pickchick_cloud`.
`CLOUD_DATABASE_URL` не передаётся аргументом и не печатается. CLI требует
роль подключения `pickchick_owner`; роль приложения - `pickchick_app`.

```text
node infra/staging/queue-recovery-cloud-owner.mjs inspect <branch-uuid> <pos-sync-boolean> <backoffice-boolean>
node infra/staging/queue-recovery-cloud-owner.mjs apply   <branch-uuid> <pos-sync-boolean> <backoffice-boolean>
```

Оба boolean - фактически проверенные текущие значения POS order sync и
бэк-офиса, только `true`/`false`; значений по умолчанию нет. Их соответствие
существующим правам проверяется по INSERT-маркерам `pos_order_sync_inbox`
и `bo_commands`. Это проверка согласованности с БД, **не чтение текущего
окружения работающего API**. Окружение отдельно сверяет оператор выпуска.

## Что проверяет и меняет шаг

- Точный ledger 071 с хешами всех исторических миграций; существование точки.
- Проверенные байты 072:
  `d222ea9bf0aeebcaaeea96bc119c9b8aa3e1d9f032a1af7914aefe5c8981c5e2`.
- Существующую непривилегированную роль приложения без владения объектами
  и членства в других ролях. Новые роли и пароли не создаются.
- После общей migration advisory lock берёт эксклюзивные блокировки таблиц,
  сохраняет отпечатки старых строк, последовательностей и табличных/колоночных ACL.
- В одной транзакции добавляет 072 и запись ledger. Права выдаются только
  двум новым таблицам, согласно уже существующему состоянию функций:

| Существующее состояние         | Новые права                                       |
| ------------------------------ | ------------------------------------------------- |
| POS sync выключен, BO выключен | Нет                                               |
| POS sync включён               | SELECT, INSERT на `pos_kitchen_restore_conflicts` |
| BO включён                     | SELECT на конфликты; SELECT, INSERT на решения    |

UPDATE/DELETE и grant option не выдаются. Новая trigger-функция закрыта от
PUBLIC. Неожиданные default grants другой роли, PUBLIC или дополнительные
права приводят к откату всей транзакции, включая DDL, ledger и уже выданные
права. Старые права сохраняются; общий сброс прав приложения не выполняется.

После применения сверяются прежние данные, последовательности, ACL и полный
ledger. Новые таблицы должны остаться пустыми: миграция не решает конфликты
старых заказов и не переписывает канонические продажи. Повторное применение
отклоняется; частично выполненное состояние не «исправляется» автоматически.

`inspect` откатывает транзакцию без постоянных изменений, но на время проверки
берёт блокировки: его тоже нужно запускать в согласованное окно.

## Что остаётся в облачном окне

Успешный JSON этого шага содержит `apiDeployed: false`, `flagsChanged: false`
и `releaseReady: false`. После него ещё нужны запуск точного проверенного API,
проверки readiness, совместимости старых кассовых схем 023/024, маршрутов и
фактических прав API. Только их результаты могут стать основанием для
`pickchick-queue-recovery-cloud-v1` Windows-оператора.

При последующем изменении POS/BO флагов права таблиц 072 нужно пересмотреть
в том же согласованном процессе. Этот однократный шаг не является инструментом
переключения флагов; старые общие grant-скрипты сами по себе не подтверждают
новые права 072. Не перезапускать `apply` ради изменения прав.

API-откат не откатывает схему и не восстанавливает старый дамп поверх новых
заказов. Для него требуется заранее проверенный совместимый предыдущий API.
Миграции 073–076 и кассовые 026–028 относятся к последующим этапам.

## Проверки

`tests/integration/queue-recovery-cloud-owner.test.mjs` входит в существующий
`pnpm test:integration`. На PostgreSQL 18 проверяются все четыре сочетания
функций, отсутствие изменений в inspect, чужая точка/роль/флаги, изменение SQL,
откат при посторонних default grants таблиц и функций, точные новые права,
сохранность старого bigint-значения денег, последовательности и ACL, отказ
повторного применения. Используются только случайные тестовые схемы и роли.
