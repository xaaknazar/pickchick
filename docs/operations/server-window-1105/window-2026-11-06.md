С1 и С3 последовательно, без параллельных серверных изменений.

1. В 15:00: свежие refs/claims, точный baseline, наборы 73/18 и отсутствие
   новых активных оплат/заказов. Чужой lock или дрейф - стоп.
2. С1: timestamp-копия установленного compose 0600 и SHA-256.
   auth-links-release.py меняет ровно две строки на pickchick.kz.
   Проверить config --quiet, атомарную замену, пересоздать только api.
   Health/readiness, auth/config, domain gate, snapshot обоих адресов,
   long-poll nip.io и неизменность соседей. Сохранить новый compose hash.
3. С3: свежая зашифрованная копия schema068 штатным backup.sh; проверить
   новое lastSuccessAt, SHA, копию на Mac и restore-drill --require-manifest
   в изолированном контейнере. Репетиция owner 069-071 и запуск кандидата
   на восстановленной копии без исходящего доступа. Не использовать старую
   копию вместо свежей.
4. Повтор baseline и активной работы, затем штатный owner inspect --with-069,
   один deploy --with-069. Ожидается ровно schema071. При потере ответа
   сначала read-only ledger; повторный deploy вслепую запрещён.
5. release-stage2-1024.py из чистого runtime: prepare, prepare --apply,
   apply --apply со всеми точными pins, proof Foundation и Offline,
   приватным backup identity и compose hash после С1.
6. Проверить image/revision/pointer, ledger071/checksum/ACL, readiness,
