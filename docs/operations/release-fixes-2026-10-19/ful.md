## 1.0 - один отказ кассы больше не блокирует точку

Было: если касса отказывала команде допуска (закрыт приём, конфликт, нет брони), воркер держал её
как единственную «ожидающую» и больше ничего не забирал из облака; пульс при этом шёл, и киоск с
приложением продолжали продавать.

Стало (`packages/fulfillment-transport/src/worker.ts`):

- Детерминированный отказ кассы (`NOT_READY`, `ITEM_STOPPED`, `CONFLICT`, `INVALID`, `NOT_FOUND`,
  `FORBIDDEN`) откладывает только эту команду: результат хода `deferred`, ожидание очищается.
  Команда в облаке остаётся неподтверждённой и надёжной, возвращается после аренды (30 с) позади
  команд с меньшим числом попыток. Ошибки базы и сети по-прежнему повторяются с той же командой.
  `ROUTING_MISSING` по-прежнему паркуется в `fulfillment_transport_failures`.
- Облако выдаёт сначала допуски на кухню оплаченных заказов, потом новые брони
  (`packages/fulfillment-transport/src/cloud.ts`).
- Воркер сообщает облаку об отказе (`admissionRefusals`) и о закрытом приёме кассы
  (`availability.orderingEnabled=false`). Поля отправляются только когда есть что сказать; старое
  облако отвечает 400, и тот же запрос сразу уходит без них (10 минут они не отправляются).
- Облако: отказ по оплаченному заказу сразу создаёт проблему сверки `KITCHEN_ADMISSION_REFUSED`
  (видна в кабинете в «Проблемах сверки», заказ в состоянии `attention_required`) и такой заказ
  больше не уходит на кухню сам. Отказ по неоплаченному заказу ничего не меняет.
- Страховка для старых касс и офлайна: оплаченный заказ, который касса не приняла через
  `FULFILLMENT_ADMISSION_REVIEW_MINUTES` (по умолчанию 15) минут после оплаты, уходит на разбор
  (`KITCHEN_ADMISSION_OVERDUE`) вместо позднего попадания в очередь кухни (например, утром).
  Проверка выполняется перед выдачей команды кассе, не чаще раза в 30 с на точку.
- События для мониторинга (интерфейс ops): воркер кассы пишет
  `{"event":"fulfillment_transport_attention","deferred":N,"parked":N,"reasons":{...},"unresolvedFailures":N}`
  при первом отказе и далее не чаще раза в 5 минут, и одну строку `{"recovered":true}` после 2 минут
  без отказов. Только счётчики, без заказов, гостей и денег. Если облачная проверка просрочки не
  смогла выполниться: `fulfillment_admission_review_failed`.

Тесты: `packages/fulfillment-transport/tests/admission-health.test.mjs`,
`packages/fulfillment-transport/tests/cloud-admission.test.mjs`, unit `TransportAttention` и
схема полей в `packages/fulfillment-transport/tests/unit.test.mjs`. Два старых теста закрепляли
прежнее поведение и обновлены: закрытый приём теперь откладывается (а не держится ожидающим), а
константа «устаревшей ревизии» поднята выше ревизии по часам.

## 1.1 - киоск проверяет кассу до QR

- Закрытый на кассе приём делает кассу «не свежей» (`cloud064 ordering_closed`): мобильное
  приложение и киоск перестают принимать деньги (`AVAILABILITY_STALE`), конфигурация киоска
  отвечает `enabled:false` (тихий `NOT_ACCEPTING`), QR не выдаётся. Свежий пульс и стоп-лист
  проверялись и раньше; правило стопов комбо - см. 1.3.
- Если касса всё же отказала оплаченному заказу киоска, сервер показывает установленным сборкам
  киоска `phase:'failed'` при оплаченном QR: это существующий экран «Результат оплаты уточняется.
  Сотрудник проверяет оплату. Не оплачивайте повторно. Если нужна помощь, обратитесь к сотруднику»
  с автосбросом, вместо номера «-». Только представление для устройства: заказ остаётся у
  менеджера как проблема сверки (нужен возврат или ручной заказ).
- Решение владельца 08.10 (QR до брони кассы) сохранено.

Тесты: `packages/commerce-core/tests/kiosk-admission.postgres.test.mjs` (закрытая касса, экран
помощи), worker-тесты 1.0.

## 1.2 - облачная кухня (режим выключен в production)

`packages/cloud-kitchen/src/repository.ts`, `services/api/src/index.ts`:

- Догоняющий допуск на опросе ленты (`admitPendingPaid`) теперь делает ту же проверку режима, что и
  путь в транзакции оплаты: заказ, оплаченный через воркер Kaspi после переключения точки в `edge`,
  получает `CLOUD_MODE_CHANGED_BEFORE_ADMISSION`.
- Заказ, который никогда не допустится сам (неверный снимок, нет маршрута, конфликт), получает
  `CLOUD_KITCHEN_ADMISSION_FAILED` и выходит из выборки. Окно выборки своё для каждого канала;
  закончившиеся номера пропускают только свой канал. Сбойные заказы больше не держат новые.
- Снимок облачной кухни принимает заказ 0 ₸ (подарочное комбо) и любое число строк, как цены.
- Защита: кабинет и скрипт владельца (`infra/staging/cloud-kitchen-release-owner.mjs`) не включают
  режим `cloud`, пока есть оплаченные облачные заказы без кухни и без разбора, или живые заказы
  кассы с номерами 300-899 (см. 1.4).

Тесты: `tests/integration/cloud-kitchen-payment.test.mjs` (три новых теста).

## 1.3 / 4.2 / 6.3 - стоп-лист и комбо (решение ПМ 1)

Одно правило в `packages/menu-sync/src/availability.ts` (`catalogStopView`, `lineStopIds`):

- комбо/дуо/сет недоступен, если остановлен любой фиксированный компонент (вложенные комбо
  учитываются) или остановлены все варианты обязательной группы выбора;
- вариант выбора остановлен своим стопом или стопом товара, на который он указывает:
  `linked_product_id`, а если его нет - товар, чей id совпадает с id варианта (напитки и соусы
  комбо повторяют id отдельных товаров: `lemonade`, `water`, `piko`, `sauce`, `fingers`...). Id
  варианта, не совпадающий ни с одним товаром, ничего не задевает;
- остановленный вариант показывается «Нет в наличии» и не может быть выбран.

Где работает: доступность киоска и приложения (форма ответа прежняя), quote/создание/оплата
киоска и приложения (после расчёта цены проверяются и связанные товары, и компоненты), допуск
заказов киоска/приложения на кассе (`packages/edge-fulfillment/src/repository.ts`).

Не сделано (частично): продажа комбо на самой кассе (POS, `local-orders checkStops`). Меню кассы
(`MenuSnapshot` в `packages/contracts`, строгая схема) не несёт связи «вариант -> товар» и
компонентов, а установленная касса отвергает меню с новыми полями. Нужно: решение ПМ/владельца на
расширение контракта меню двумя шагами (сначала касса, принимающая новые необязательные поля,
потом облако, которое их отправляет) или команда «стоп везде» в кабинете. До этого кассир видит
стоп товара в стоп-листе и не продаёт его в комбо вручную.

Данные: для вариантов, чей id не совпадает с товаром (`cola-bottle`, `cola-can`, `cola-zero` ->
`cola`; `piko-apple`, `piko-orange` -> `piko`; `iced-tea-sweet/unsweet` -> `iced-tea`; `fuse-*`),
владельцу нужно проставить «Связанный товар» в кабинете (поле `linked_product_id`).

Тесты: `tests/unit/combo-stop-rule.test.mjs` (компонент, вложенное комбо, вариант, все варианты
группы, связь по id), `packages/edge-fulfillment/tests/combo-stops.test.mjs` (касса отказывает
комбо с остановленным компонентом/напитком; на базе тест падает),
`packages/commerce-core/tests/kiosk-admission.postgres.test.mjs` (доступность, quote, оплата),
`packages/commerce-core/tests/storefront-availability.postgres.test.mjs` (киоск и приложение
отдают одинаковую картину для стопа компонента, связанного товара и всех вариантов группы).

Важно про данные: в демонстрационном каталоге (seed) у комбо пустые `combo_components` -
фиксированные компоненты не заведены, поэтому правило «стоп компонента» начнёт работать для
этих комбо, когда владелец заполнит состав комбо в кабинете. Правило для вариантов (напитки,
соусы) работает сразу.

## 1.4 - номера кассы

- Миграция edge `022_edge_display_numbers.sql`: функция `fulfillment_display_allocate` выдаёт
  номера 1-299, с 1 на каждой открытой смене (без смены - каждый день по Алматы), пропуская номера
  живых заказов. Живой: заказ в кухонном статусе, менявшийся за 12 часов, или неоплаченная бронь
  младше 6 часов - забытые заказы не блокируют нумерацию навсегда. Если заняты все 299 номеров,
  допуск отказывается (облачная команда откладывается как `NOT_READY`, POS -
  `KITCHEN_UNAVAILABLE`), а не уходит в диапазон киоска 300-599 и приложения 600-899.
- Ограничения уникальности, запрещавшие повтор номера, сняты (уникальность среди живых заказов
  обеспечивает функция). Старая последовательность осталась для отката и для ролей без нового
  права: такой код работает как раньше.
- Табло кассы не показывает заказы, не менявшиеся 12 часов. Приложение кухни показывает два живых
  заказа с одним номером (редкий случай: бронь, оплаченная через много часов), а не уводит табло в
  офлайн.
- Облачный режим не включается, пока живые заказы кассы имеют старые номера 300-899.

Тесты: `packages/edge-fulfillment/tests/display-numbers.test.mjs` (с 1 на смене, пропуск живых,
299 занятых -> отказ, освобождение старого), `tests/operations/windows-display-numbers.test.mjs`
(обновление 021->022 сохраняет данные/права/последовательности), `apps/kitchen/tests/cloud-stream.test.mjs`.
Тест «1000 resident orders» теперь идёт на старой последовательности: 1000 живых заказов больше
299 номеров кассы по замыслу.

## 1.5 - номера облачной кухни

На каждом опросе ленты (`sweepStale`): заказ с возвратом или отменой в коммерции отменяется на
кухне (нетронутый - сразу, номер свободен; начатый - `cancel_requested`, кухня подтверждает);
заказ «готов», не выданный за `CLOUD_KITCHEN_STALE_READY_MINUTES` (по умолчанию 180), закрывается
системой (`stale_ready_sweep` в событии) и освобождает номер. При остатке меньше 30 свободных
номеров в канале API пишет `cloud_kitchen_numbers_low` (не чаще раза в 5 минут на точку).

## 1.6 - восстановление базы кассы

Ревизия пульса кассы теперь `max(счётчик+1, время в микросекундах)`: восстановление базы из копии
не отматывает её, облако принимает пульс сразу. Облако принимает строку доступности от новой
привязанной кассы (замена устройства), даже если у прежней ревизия больше. Защита от повторов
сохранена: старый запрос той же кассы с меньшей ревизией отбрасывается.

До обновления воркера кассы (старая сборка): после восстановления базы кассы выполнить на облаке
`UPDATE cloud_branch_availability SET revision=1 WHERE branch_id='<точка>';`.

## Решения, принятые в линии (владелец может изменить)

- Оплаченный заказ, которому касса отказала, сразу становится делом менеджера и сам на кухню не
  попадает (даже если стоп сняли через минуту): гость уже ждёт без номера.
- Срок разбора неполученного кассой оплаченного заказа - 15 минут; закрытие забытого «готов» в
  облачной кухне - 3 часа; окна «живого» номера кассы - 12 часов (кухня) и 6 часов (бронь).
- Неявная связь варианта с товаром по совпадению id (кроме явного `linked_product_id`).

## Миграции и переменные

- cloud `064_cloud_cashier_ordering_state.sql` - колонка `cloud_branch_availability.ordering_closed`
  (по умолчанию false, существующие права таблицы покрывают её).
- edge `022_edge_display_numbers.sql` - таблица `fulfillment_display_counters`, функция
  `fulfillment_display_allocate`, снятие уникальности номера. Права EXECUTE выдают
  `infra/windows/fulfillment-worker-grants.mjs`, `infra/windows/edge-runtime-grants.mjs` (если
  функция есть) и скрипт обновления.
- `FULFILLMENT_ADMISSION_REVIEW_MINUTES` (облачный API, 0-1440, по умолчанию 15, 0 - выключено).
- `CLOUD_KITCHEN_STALE_READY_MINUTES` (облачный API с облачной кухней, 0-1440, по умолчанию 180).
- Обе переменные не добавлены в `infra/staging/compose.yaml` (чтобы не конфликтовать с другими
  линиями): API берёт значения по умолчанию. Чтобы менять их без релиза, интеграция или владелец
  добавляет в `environment` сервиса `api` строки
  `FULFILLMENT_ADMISSION_REVIEW_MINUTES: ${FULFILLMENT_ADMISSION_REVIEW_MINUTES:-15}` и
  `CLOUD_KITCHEN_STALE_READY_MINUTES: ${CLOUD_KITCHEN_STALE_READY_MINUTES:-180}`.
- Протокол кассы: необязательные `availability.orderingEnabled` и `admissionRefusals` в pull;
  ответ облака не менялся. Исходники `packages/contracts/src` не менялись; сгенерированный
  `packages/contracts/openapi.json` пересобран `node scripts/contracts.mjs` (два необязательных
  поля внутреннего маршрута кассы), `pnpm contracts:check` проходит.

## Порядок развёртывания

1. Облако: миграции (064 вместе с остальными), затем API. Старые кассы продолжают работать:
   поля не приходят, поведение облака прежнее, кроме выдачи оплаченных допусков первыми и
   проверки просрочки 15 минут.
2. Касса Windows (ночное окно, все службы остановлены, свежая проверенная копия базы):
   `node infra/windows/display-numbers-upgrade-db.mjs inspect <tools> <app> <branch>`, затем
   `apply` от владельца базы `pickchick_edge_owner` (проверяет точную схему 021, данные, права и
   последовательности; выдаёт EXECUTE ролям `pickchick_edge_runtime` и
   `pickchick_fulfillment_sync`). Затем новый релиз edge/воркера. Если линия pos поставляет edge
   023-024, их скрипт идёт после 022.
3. Киоск и приложение пересборки не требуют.

Откат: API - предыдущий образ (колонка 064 ему не мешает). Касса - предыдущий релиз работает на
схеме 022 (функцию не вызывает, использует старую последовательность). Откат только воркера кассы
ручного шага не требует: новый воркер хранит ревизию по часам в той же колонке `attempts`, и
старый продолжает её с +1, облако принимает пульс. Ручной шаг нужен только если базу кассы
восстановили из копии, снятой до обновления (или откатили 022 восстановлением копии): тогда на
облаке выполнить `UPDATE cloud_branch_availability SET revision=1 WHERE branch_id='<точка>';`.
