# Первый шаг после merge PR262: только миграции облака

Подготовлено 21.10.2026 для отдельного решения владельца. **Не выполнялось.**
Разрешение на merge PR262 не разрешает этот шаг. API, workers, касса и клиентские
сборки остаются прежними; `204d318b` до приёмки финансовым Mac не выпускать.

## Что подтверждено чтением

- Журнал VPS заканчивается `058_cloud_device_center.sql`; 060 отсутствует.
- Кандидат PR262 содержит 060, затем 064/066/068, без миграции 059.
- `release-fixes-1019-owner.mjs` требует точное совпадение всей базы до 060,
  включая checksum, и отклонит нынешнюю 058. Он применяет только 064/066/068.
- Миграция уведомлений 059 пока только в несоединённой ветке l10n. Перед её
  будущим выпуском нужен свободный номер после 068 и обновление ссылок/тестов.
  Нельзя применить 068, а затем добавить 059 задним числом. Первый шаг следует
  закрепить за принятым SHA PR262, без ещё не принятых веток l10n/cart-lines.

## До разрешения на выполнение

1. Зафиксировать merge SHA, полную зелёную Foundation CI и SHA256 всех четырёх
   SQL-файлов. Сверить live ledger/checksum, образы, конфигурацию и права.
2. Подготовить отсутствующий сейчас охраняемый оператор **058 -> 060**.
   Он должен проверять точную базу, отсутствие объектов 060, флаг акции false,
   deployment lock и подтверждение backup/restore; применять только 060 в
   транзакции с проверкой неизменности старых данных/прав/журнала. Общий
   `db:migrate` или текущий provision вместо этого оператора не запускать.
3. Проверить этот оператор и имеющийся 064/066/068 на отдельной восстановленной
   копии: успешный путь, неверная база/checksum, повторный запуск, rollback при
   ошибке, отказ без нужного разрешения. Не использовать рабочую БД как стенд.
4. Получить отдельное разрешение владельца на шаг, согласовать резервы
   `@vps/api`, `@vps/postgres` и штатную блокировку. Не забирать их принудительно.

Оператор 058 -> 060 ещё не готов. Поэтому разрешать применение сейчас рано;
после подготовки его точная команда и неизменяемый пакет должны быть добавлены
в этот план и пройти проверку. Неизвестные значения ниже не подставлять наугад.

## Выполнение после подготовки и отдельного разрешения

Команды подготовки из чистой копии принятого SHA:

```sh
node scripts/project-sync.mjs check
node scripts/project-sync.mjs status
git status --porcelain
git rev-parse HEAD
corepack pnpm install --frozen-lockfile
shasum -a 256 db/cloud/migrations/060_cloud_combo_rewards.sql \
  db/cloud/migrations/064_cloud_cashier_ordering_state.sql \
  db/cloud/migrations/066_cloud_edge_identity_rotation.sql \
  db/cloud/migrations/068_cloud_identity_abuse_limits.sql
```

На VPS через существующий SSH с `StrictHostKeyChecking=yes`, без вывода env:

1. Снять свежую зашифрованную копию штатным установленным `backup.sh`.
   Скопировать шифрованный архив, checksum и manifest на доверенную машину.
   Проверить восстановление в изолированном контейнере:

   ```sh
   python3 infra/staging/restore-drill.py dump \
     --dump "$ENCRYPTED_DUMP" --manifest "$ENCRYPTED_MANIFEST" \
     --identity "$PRIVATE_AGE_IDENTITY"
   ```

   Требуются exit 0, совпавший checksum, ledger058 и допустимые количества строк.
   Приватный age-ключ не хранить на VPS и не печатать. Отчёт не содержит строк БД.

2. Охраняемым оператором применить **только 060**, сохраняя
   `CUSTOMER_COMBO_REWARDS_ENABLED=false`. Его команда будет закреплена после
   разработки/проверки из предыдущего раздела. Проверить ledger060, checksum,
   отсутствие начислений/подарков и изменений существующих заказов.

3. Из того же подготовленного кандидата, с приватным owner env:

   ```sh
   node --env-file=/run/pickchick/release-owner.env \
     infra/staging/release-fixes-1019-owner.mjs inspect
   node --env-file=/run/pickchick/release-owner.env \
     infra/staging/release-fixes-1019-owner.mjs deploy
   ```

   Это CLI существующего owner-инструмента, не установка нового API. Его
   упаковка/доступ к БД должны входить в охраняемый оператор, а не в ручной обход.

## После

- Ledger дополнен ровно 060/064/066/068, старые checksum сохранены.
- Проверки owner-инструмента: старые данные, роли и прежние права сохранены;
  новые права только на `identity_otp_failures` при уже включённой авторизации.
- Ротация по флагу остаётся выключенной, автоначисления комбо не включены.
- Проверить readiness прежнего API, свежий heartbeat кассы и состояния очередей
  чтением. Новые счета, QR, оплаты и заказы не создавать.
- Сохранить SHA, CI, checksum, backup/restore receipt, до/после ledger и результат
  проверок в GitHub. Онлайн-пульт пока не публиковать.

## Откат и остановка

- При ошибке внутри транзакции инструмент выполняет rollback; проверить ledger
  и состояние чтением перед повтором. Частично применённую базу не «догонять».
- Успешную аддитивную миграцию вниз не удалять. На этом шаге runtime не меняется,
  поэтому переключать его назад не требуется; флаги остаются выключены.
- Между 060 и 064/066/068 безопасно остановиться на подтверждённой 060 и заново
  проверить базу. Снимок до миграции не восстанавливать поверх новых продаж.
- Если нужна аварийная реставрация данных, сначала отдельное окно/решение
  владельца, остановка writers и сверка новых операций. Это не автооткат.
