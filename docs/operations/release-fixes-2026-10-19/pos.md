### 6.1 Касса блокировалась после 409 CONFLICT

`apps/pos/src/model.ts`: edge сохраняет результат команды только при коммите и отдаёт его
повторно по тому же ключу, поэтому 409 CONFLICT для этого ключа - окончательный отказ.
Теперь для отмены, стопа, открытия/закрытия приёма и создания заказа (как раньше для
смен) запись журнала снимается до чтения нового состояния, затем перечитываются заказ,
стоп, `ordering` или смена, а сотрудник видит «Состояние изменилось, операция не
выполнена...». Неопределённые ошибки (сеть, 5xx) по-прежнему остаются pending.
Тест на реальном edge: `tests/pos/core.test.mjs` (отмена с другой кассы, стоп с другой
кассы, устаревший `ordering`, использованный расчёт; повтор и перезапуск не возвращают
pending, работа продолжается).

### 6.2 Неверный PIN в закрытии смены

`apps/pos-desktop/protocol.mjs`: прокси помнит сессию, которой `GET /session` выдал доступ к
журналу. Отзывают его только новая аутентификация, вход по паролю, выход этой сессии и
401/403 на запросе этой сессии (или без сессии). Проверка PIN (`staff/pin`) и выход чужого
credential (PIN не начальника) журнал не трогают. 403 на собственной сессии по-прежнему
отзывает доступ (edge отвечает 403 и при отключённом или чужом терминале): защиту не
ослабляли. Тест на настоящих `createProtocolHandler` и `createJournalStore`:
`tests/pos-desktop/protocol.test.mjs`.

### 6.4 Восстановление edge из бэкапа

- Edge-миграция `023_edge_restore_fence.sql`: журнал `edge_database_epochs` (только
  добавление) с паспортом базы (system identifier кластера + OID базы) и функция
  `edge_restore_fence()` с правами владельца. На восстановленной копии она один раз сдвигает
  `local_order_streams`, `cashier_report_outbox` и `fulfillment_outbox` на 1 000 000 000
  (облако принимает пропуски, но не повторный номер) и разрешает меню один прыжок вперёд к
  самой ранней неподтверждённой публикации облака. Повторно занятый номер с другим
  содержимым облако по-прежнему отклоняет: воспроизведения нет.
- Путь поиска функции закреплён как у облачных функций с правами владельца
  (`pg_catalog, <схема>, pg_temp`): временная таблица вызывающей роли не может подменить
  журнал и заставить функцию сдвигать счётчики при каждом вызове (воспроизведено тестом до
  исправления). Параллельные вызовы сериализуются блокировкой таблицы журнала.
- Fence вызывает служба Edge при старте и FulfillmentWorker на первом цикле (если роли
  выдано право). Для файлового восстановления или `pg_restore --clean` в ту же базу -
  `SELECT * FROM edge_restore_fence(true)` от владельца.
- Процедура оператора и ручная сверка: [edge-restore.md](../edge-restore.md).
- Не сделано (владелец): автоматический бэкап по расписанию во второе место. Скрипты
  `backup-native-edge.ps1`/`backup-native-service.mjs` есть, но они привязаны к SID
  оператора, пиннингу схемы до 020 и делают тяжёлую репетицию восстановления; задача
  SYSTEM требует отдельной роли и защищённых учётных данных. Писать это без запуска на
  Windows небезопасно. Рекомендация: ежечасный `pg_dump -Fc` + `pg_restore --list` +
  SHA-256, копия на второй физический диск или NAS, хранение 48 часовых и 14 дневных копий,
  алерт при возрасте последней копии больше 2 часов.
- Остаётся ручной сверкой (см. edge-restore.md): данные между бэкапом и сбоем, заказы из
  облака, принятые после бэкапа, конфликт одного заказа на двух отрезках.

### 6.5 PIN-вход

- `packages/local-orders/src/staff-passwords.ts`: PIN одновременно логин, поэтому
  неверный PIN нельзя отнести к сотруднику (счётчик по сотруднику остаётся для входа по
  паролю). Введена блокировка по терминалу: 5 бесплатных ошибок, затем 30 с, 1, 2, 4, 8 и
  15 минут; успешный вход не сбрасывает счётчик (нельзя чередовать со своим PIN), сброс -
  через 30 минут без ошибок. Во время блокировки правильный и неправильный PIN получают
  одинаковый 429 без поиска и scrypt; неизвестные терминалы состояния не создают. Каждая
  ошибка пишется в лог edge `staff_pin_failed` (терминал, счётчик, секунды блокировки, без
  PIN). Состояние хранится в процессе edge, как и существующий ограничитель параллельных
  входов: перезапуск службы (администратор Windows) его сбрасывает.
- 429 несёт настоящий остаток блокировки в `Retry-After` (оба прокси кассы его уже
  пропускают), экран PIN пишет «Вход по PIN временно заблокирован после неверных попыток.
  Повторите через N мин.» вместо «Подождите минуту». Для лимита попыток в минуту и
  параллельных входов остаётся 60 с.
- 6-значные PIN: вход и выпуск принимают 4 или 6 цифр, `staff-pin-setup.mjs` по умолчанию
  требует 6 (`--digits 4` - только пока касса в режиме 4). Касса: `pinLength` (4 или 6, по
  умолчанию 4) в `config.json` десктопа и в конфигурации web POS.

## Решения PM

Решения PM 1-5 (комбо, срок попытки Kaspi, возвраты, фискальный флаг, домен) этой
полосы не касаются. Межполосный интерфейс pos -> ops соблюдён: срок ключа читается из
`device_credentials.expires_at`.

## Миграции

- Облако: `066_cloud_edge_identity_rotation.sql` (аддитивно). Readiness API требует колонок
  066: миграцию применять до нового образа API. Должна идти после 061-065.
- Edge: `023_edge_restore_fence.sql` (аддитивно, функция закрыта от PUBLIC). Номер 024 не
  использован. Охраняемые Windows-инструменты (`menu-sync-upgrade-db.mjs`,
  `remote-stops-upgrade-db.mjs`) требуют непрерывной нумерации edge-миграций: до слияния с
  022 полосы ful в этой ветке падают 2 unit- и 4 интеграционных теста этих инструментов
  (с временной 022 все проходят, см. «Проверки»). Если ful не выпустит 022, интеграции нужно
  перенумеровать 023 -> 022.
- Контракты (`packages/contracts`) не менялись.

## Выпуск и откат

1. Облако: миграция 066, затем образ API (флаг выключен). Проверить `/health/ready` и
   метрики `pickchick_edge_identity_*`. Включение продления - по edge-identity-rotation.md.
2. Касса, новый edge-релиз: edge-миграция 023 штатным охраняемым обновлением (инструменты
   выпуска нужно расширить на 022-023 вместе с полосой ful), затем повторно применить права
   (`edge-runtime-grants` сам выдаст `EXECUTE` на fence; для FulfillmentWorker передать
   `restoreFence: true`). Новый runtime содержит блокировку PIN и 6-значные PIN.
3. Касса, новый POS (десктоп): исправления 6.1, 6.2, `pinLength` и сообщение о блокировке.
4. Переход на 6 цифр (после закрытия): перевыпустить PIN всех сотрудников
   `staff-pin-setup.mjs` (6 цифр), затем `pinLength: 6` и перезапуск POS.

Откат: флаги `false` (облако снова 404, задача кассы `disabled`); 066 и 023 аддитивны и
остаются. Откат образа API - только без неподтверждённых ротаций (см. runbook). Старый
edge runtime не знает 6-значных PIN: перед откатом вернуть 4-значные. Старая сборка POS не
запустится с `pinLength` в config.json: удалить ключ.

«Таймаут очистки» - это `canceling statement due to statement timeout` (57014) на
`DROP SCHEMA ... CASCADE` в `finally` тестовых фикстур (`statement_timeout` пула 5 с) на
перегруженном сервере, а не в теле теста. Для проверки тел тестов таймаут этой одной
команды временно поднимался локально (`SET statement_timeout = 120000; DROP SCHEMA`),
изменение откатано и не закоммичено. Первый полный прогон интеграции прервался (процесс
был остановлен) после 117 тестов; его падения - те же таймауты и порты по умолчанию,
файлы перепроверены отдельно. `database.test.mjs` «fresh migrations serialize concurrent
runners» падал по таймауту ожидания `pg_advisory_xact_lock` второго мигратора (первый
применяет все облачные миграции дольше 5 с под нагрузкой); на тихой машине не
перепроверено.

Новые тесты этой сессии: подмена журнала fence временной таблицей (воспроизведено до
исправления, `restore.test.mjs`), `Retry-After` с реальным остатком блокировки PIN по
HTTP (`pos-workspace.test.mjs`), сообщение о блокировке на экране PIN
(`pin-readiness.test.mjs`).
