# Исправления к релизу 19.10.2026: мобильное приложение (линия mob)

Ветка `codex/fix-mob-1019`, база `76902fa4`. Аудит: `release-fixes-1019/findings.json`,
находки 0.2 (+2.0), 2.1 (клиент), 2.2 (+7.3, мобильная часть), 2.4, 2.5, 2.7, 2.8, 7.7 и
код-пункты аудита App Store от 14.10. Миграций нет, серверных флагов нет.

## Что изменено по находкам

### 0.2 / 2.0. Оформление больше не «запирает» покупателя

- Новый модуль `apps/mobile/src/checkout-resume.ts` решает, когда прежний заказ держит
  оформление. Блокирует только заказ, по которому банк ещё может списать деньги:
  `sending`, `awaiting_payment`, `checking` - до срока счёта плюс 2 минуты, а без срока -
  15 минут от последнего изменения. Заказы в `attention`, неоплаченные без счёта, оплаченные
  и проваленные новый заказ не блокируют.
- Сохранённое намерение оплаты (AsyncStorage) удаляется, когда заказ окончателен: оплачен,
  не оплачен (`failed`), `attention`, а для заказа без счёта - если намерению больше 5 минут.
  У новых намерений есть `createdAt`; намерения сборки 20 без времени считаются старыми.
- Лист оформления блокируется только пока идёт команда, есть свежее намерение или банк ещё
  может списать деньги. На каждом экране оплаты есть «Закрыть»: сразу, если банковского
  действия нет (`attention`, `ready_to_pay`, `awaiting_restaurant`, просроченный счёт), и
  через 90 секунд, если банк ещё может ответить. Рядом - контакт поддержки.
- Закрытие не трогает заказ и банк. Для заказа без счёта оно отменяет и автоматическую
  отправку счёта; для заказа со счётом намерение сохраняется (восстановление при следующем
  запуске), но `PaymentRecovery` в этой сессии экран обратно не открывает.
- Текст `attention`: «Ресторан проверяет этот заказ: его могли отменить или оформить возврат.
  Новый заказ можно сделать сразу. Если деньги списались, а заказ не выдан, свяжитесь с
  поддержкой.»
- Восстановление оплаченного или оплачиваемого заказа после перезапуска работает как раньше
  (проверено `browser_kaspi_checkout.py`).

### 2.1 (клиент). Отказ ресторана на шаге оплаты

- `/payment` с `ITEM_STOPPED`, `RESTAURANT_CLOSED`, `NOT_READY` или `KITCHEN_OFFLINE`:
  намерение удаляется, покупатель возвращается к корзине с понятной причиной, меню
  обновляется, команда оплаты сама не повторяется (политика `PAYMENT_COMMAND` в
  `checkout-preflight.ts`). Для `NOT_READY` новый текст: «Ресторан не смог принять этот заказ.
  Счёт не отправлен, деньги не списаны. Проверьте корзину и оформите заказ снова.»
- Счёт отправляется автоматически только в течение 5 минут после нажатия «Оплатить».
- Повторное нажатие не подхватывает старый неоплаченный заказ из `GET /orders`: он остаётся
  в «Заказах», корзина оформляется заново. При запуске со старым намерением показывается
  «Прошлый заказ не оплачен: счёт не отправлялся, деньги не списаны. Он остаётся в «Заказах».»
- Работает и со старым сервером (заказ остаётся `ready_to_pay`), и с исправлением линии pay
  (заказ становится отменённым, то есть `failed`).

### 2.2 / 7.3. Адрес API из конфигурации сборки

- `apps/mobile/src/build-config.ts` + `app.config.ts`: `EXPO_PUBLIC_PICKCHICK_ENV`
  (`staging` по умолчанию - nip.io как сейчас; `production` - `https://api.pickchick.kz`),
  необязательные `EXPO_PUBLIC_API_URL` (только голый `https://` origin) и
  `EXPO_PUBLIC_SUPPORT_URL` (`https:`, `tel:` или `mailto:`). Неверное значение
  останавливает сборку. `extra.environment/apiUrl` в манифесте совпадают с бандлом.
- `parseCapabilities` больше не падает на `production`, новых флагах и новых режимах данных.
  TEST-флаги читаются только из схемы 1. Оплата по-прежнему решается
  `/v1/customer-checkout/config`.
- `scripts/mobile/ios_release.py`: новый профиль `production` (флаги storefront +
  `production`). Все профили закрепляют свой сервер, `EXPO_PUBLIC_API_URL` из оболочки в архив
  не попадает; в `release.json` пишутся `environment` и `supportUrl`. Профиль по умолчанию
  остаётся `storefront` (staging).
- Юридические ссылки приходят с сервера (`/v1/auth/config`); их адрес меняется настройкой
  сервера, приложение пересобирать не нужно.
- Живой сервер не менялся.

Как собрать:

```sh
# staging (как TestFlight сейчас)
python3 scripts/mobile/ios_release.py archive --release <метка>
# production (App Store) - только после того, как api.pickchick.kz отвечает с валидным TLS
EXPO_PUBLIC_SUPPORT_URL='tel:+7XXXXXXXXXX' \
  python3 scripts/mobile/ios_release.py archive --feature-profile production --release <метка>
```

### 2.4. Вкладка «Заказы»

Из любого экрана оплаты, открытого из списка (`attention`, неоплаченный, счёт в Kaspi),
кнопка «К списку заказов» доступна сразу: вкладка не модальная, возврат ничего не отправляет.

### 2.5. KITCHEN_OFFLINE

- `KITCHEN_OFFLINE` добавлен в общий `ErrorSchema` (`packages/contracts`, openapi
  перегенерирован).
- Фильтр ошибок (`packages/platform/src/http.ts`) отдаёт этот код только клиентам, которые
  указали профиль `application/json; profile=pickchick.checkout-errors-v2`. Сборка 20
  (только v1) и киоск (обычный JSON) получают прежний `SERVICE_UNAVAILABLE`: их встроенная
  схема ошибок нового кода не знает.
- Новое приложение отправляет v2, показывает «Кухня сейчас не на связи - заказ оформить
  нельзя. Попробуйте чуть позже.» сразу, без минуты ожидания. Состояние паузы без заказа
  подписано «Повторить попытку», а не «Проверить оплату».
- HTTP-тест через настоящий стек API: `tests/integration/checkout-error-http.test.mjs`.

### 2.7. Вход только через Telegram

- Если вход возможен только через Telegram (нет WhatsApp-резерва и SMS), ответ 503 на
  `/otp/request` показывается честно: «Не удалось отправить код в Telegram на этот номер.
  Сейчас вход работает только через Telegram: установите Telegram на этот номер и попробуйте
  снова. Если Telegram нет, обратитесь в поддержку.» Ниже - контакт поддержки или «Сотрудник
  ресторана поможет оформить заказ на месте.»
- Отклонённый `request_id` сбрасывается: после установки Telegram новая попытка - новый
  запрос, а не повтор отказа. С включённым WhatsApp-резервом поведение прежнее.
- Подсказка на экране телефона: «Пришлём код в Telegram», если резерва нет.
- Сервер не менялся (код identity правит линия sec). WhatsApp/SMS - задача владельца.

### 2.8. Long-poll статуса заказа

- `packages/commerce-core/src/checkout-watch.ts`: `checkoutOrderMark()` - одна запись без
  блокировок по всем строкам, из которых строится вид заказа (заказ, попытки, захваты,
  возвраты, фискальные документы, счёт Kaspi, проекция и задачи кухни, намерения отмены,
  облачная кухня, если таблицы доступны). `watchCheckoutOrder()` берёт отметку перед каждым
  полным чтением и сравнивает её раз в секунду; полное чтение (с `FOR UPDATE`) - только при
  изменении.
- Контроллер: тот же маршрут, тот же ответ, то же окно 20 с.
- Измерено на тестовой БД: простаивающий watch - 18 запросов за 3,2 с вместо 91; изменение
  доходит в пределах одного интервала.
- Не сделано: полностью неблокирующее чтение в `repository.readOrder` (метод общий с
  платежами, его правит линия pay) и нагрузочный тест на сотни наблюдателей.

### 7.7. Пол необязателен

- Сервер: `CustomerPatchSchema.gender` принимает `null` (снять значение); профиль считается
  заполненным при сохранении любого поля профиля. Существующие значения не меняются.
- Приложение: подпись «ПОЛ · ПО ЖЕЛАНИЮ», кнопка «Не указывать пол», сохранение без пола.
  Неуказанный пол не отправляется (старый сервер принимает форму); снятие сохранённого
  отправляет `null` (нужен новый сервер).
- Решение PM по полосе: пол необязателен, как в документах о персональных данных. Владелец
  может вернуть обязательность, но тогда нужно описать её цель в политике и в App Privacy.

## Выкладка и откат

1. Сначала сервер (API): фильтр ошибок, watch, identity. Совместим со сборкой 20 и киоском
   (они не отправляют v2 и всегда присылают пол). Откат - предыдущий образ API; данных и схемы
   не меняется. Профили, заполненные без пола на новом сервере, после отката останутся
   заполненными.
2. Затем новая сборка приложения: сначала staging-профиль (TestFlight), production-профиль -
   после готовности домена. Откат приложения - предыдущая сборка в TestFlight/App Store.

## Что должен сделать владелец

1. Контакт поддержки: телефон, WhatsApp-ссылка, почта или страница. Передать для
   `EXPO_PUBLIC_SUPPORT_URL` и для поля Support URL в App Store Connect.
2. Второй канал входа: подключить провайдера WhatsApp (резерв в коде есть,
   `whatsapp_fallback_enabled`) или SMS. Без этого покупатели без Telegram войти не могут
   (приложение теперь честно об этом говорит).
3. Домен: DNS и TLS для `api.pickchick.kz` на API; nip.io оставить работающим для
   установленных сборок; юридические страницы перенести на `pickchick.kz` и поменять ссылки в
   настройках сервера; затем собрать профиль `production`.
4. App Store Connect: принять новое соглашение, номер версии, тексты, скриншоты, анкета App
   Privacy (пол теперь добровольный), категория, права на контент, возрастной рейтинг,
   цена и страны, доступ для проверяющего (линия sec), ручной выпуск, предупреждение о dSYM.
5. Решить, какие экраны «скоро будет» оставить в первой версии (казахский язык, push,
   другие способы оплаты); push и локализация - ветка `mac/codex/mobile-l10n-push-1014`.
6. Цены, коммерческие условия, возвраты и фискальные чеки - решение владельца и бухгалтера.
7. Приёмка окончательной сборки на iPhone по чек-листу аудита 14.10.

## Что не проверено

- Нативная сборка iOS/Android и реальное устройство (по правилам спринта не собирались);
  проверены web-экспорт и браузерные тесты.
- Реальные Kaspi, Telegram Gateway и кухня - только локальные фикстуры.
- Нагрузка watch на сотни покупателей - только подсчёт запросов на одном наблюдателе.
- `browser_account_required.py` и `browser_demo_account.py` (другие экспорты) не запускались;
  изменение пола там не убирает ни одного шага.
