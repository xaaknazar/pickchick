## 4.0 / 5.5 - вход в кабинет (`apps/backoffice/staff-auth.mjs`)

Было: один общий массив попыток на процесс (30 за 15 минут), запись попытки до проверки тела,
успешные входы тоже считались, глобальный флаг `verifying` давал 429 второму управляющему.

Стало:

- до проверки пароля (scrypt) ничего не считается: пустые тела, `text/plain`, битый JSON дают
  400 и никого не блокируют;
- неудачная проверка пароля считается по адресу клиента и по логину. Первые 5 ошибок с адреса
  (10 по логину) за 15 минут бесплатны, дальше блокировка 30 с, 60 с, 120 с ... до 15 минут для
  адреса и до 5 минут для логина. Заблокированный ключ отклоняется до scrypt и не продлевает
  себе блокировку; `Retry-After` - реальное оставшееся время. Успешный вход очищает оба ключа (вход знакомого
  браузера - только ключ адреса, см. ниже),
  неизвестные логины ограничиваются так же, как настоящие (429 не раскрывает аккаунты);
- адрес клиента: правое значение `X-Forwarded-For`, только если соединение пришло с частного
  адреса (внешний Caddy в Docker-сети; у контейнера нет опубликованного порта). Публичный пир
  считается самим клиентом. IPv6 - по /64;
- вместо `verifying` два одновременных scrypt и очередь на 8, затем 429 с `Retry-After: 5`
  (scrypt N=2^17 держит 128 МиБ, у контейнера лимит 512 МиБ). Отдельный глобальный счётчик не
  нужен: CPU ограничен этими двумя слотами;
- знакомый браузер (cookie устройства, приём OWASP «device cookie»). Без него злоумышленник с
  тремя-четырьмя адресами мог бесконечно держать заблокированным известный логин (например
  `ceo`): одна ошибка раз в несколько минут продлевала блокировку логина. Теперь успешный вход
  ставит вторую cookie `__Host-pickchick_staff_device` (HttpOnly, Secure, SameSite=Strict,
  90 дней). Её подпись - HMAC от времени выдачи и логина на ключе, равном scrypt-хешу пароля
  этого аккаунта: смена пароля аннулирует все такие cookie, сама cookie ничего не открывает и
  не раскрывает. Браузер с действующей cookie своего логина не останавливается блокировкой
  логина, его ошибки считаются только по адресу (5 бесплатно, затем удвоение), а его успешный
  вход не снимает блокировку логина для остальных. Сессионная cookie по-прежнему первая в
  `Set-Cookie`, выход из кабинета cookie устройства не удаляет.

Тесты: `tests/backoffice/staff-login-limits.test.mjs` (новый, 9 сценариев: 40 мусорных запросов
и вход проходит, три одновременных входа [200, 200, 200], 31 успешный вход подряд, блокировка
адреса с удвоением, распределённый перебор одного логина, знакомый браузер входит при
заблокированном логине (а чужой логин, подделка и cookie старше 90 дней - нет), смена пароля
аннулирует cookie, окно 15 минут, правила `X-Forwarded-For`). На базе воспроизведено: 429 вместо
400, [200, 429, 429]. Обновлён старый тест `bounded rate limit` в `staff-login.test.mjs` под новое
поведение.

## 5.0 - kitchen portal (`infra/kitchen-portal/server.mjs`, `remote-deploy.py`)

- маршрут gateway передаёт `header_up X-PickChick-Client-IP {client_ip}` (адрес, разрешённый
  через `trusted_proxies`), а не `{remote_host}` (всегда внешний Caddy). В коде это шаблон
  первой установки `remote-deploy.py`; живой gateway переключает релиз
  `infra/public-staging/client-ip-gateway.py` (см. 5.6). Хеш `remote-deploy.py` в
  `activate-device-access.py` обновлён на новый (изменена только эта строка);
- портал игнорирует заголовок, если это не IP-адрес (иначе каждое случайное значение давало
  новый бюджет), IPv6 считается по /64;
- экран, предъявивший cookie, запечатанную ключом портала (облачный экран
  `pickchick_cloud_screen_*` своего филиала или терминал `pickchick_terminal_*` в режиме
  terminalAccess), получает свой бюджет (360 чтений и 12 входов повара в минуту на экран) в
  отдельной таблице. Анонимный трафик, даже с того же адреса и даже заполнив свою таблицу ключей
  (2048), не останавливает опрос очереди и вход повара на сопряжённом экране. В старом режиме без
  terminalAccess проверяемой cookie нет - там лимит по реальному адресу клиента.

Тесты: `tests/kitchen-portal/rate-limit.test.mjs` (4 сценария, на базе все 4 падают),
`tests/kitchen-portal/test_deploy.py` проверяет `{client_ip}`. Весь набор kitchen-portal зелёный,
включая браузерные тесты.

## 5.6 - доверенный прокси (`infra/public-staging/client-ip-gateway.py`)

Было: релизный скрипт пилота записал в gateway `trusted_proxies static <текущий IP
deploy-caddy-1>`. Этот контейнер принадлежит другому проекту (idrink), его адрес не закреплён;
после пересоздания все клиенты превращаются в один адрес прокси, и общий лимит OTP
(30 в час на IP) блокирует вход всем.

Стало: новый охраняемый релиз gateway по образцу `device-center-gateway.py` (CI-доказательство,
CAS-пины, общий lock, резервная копия, откат):

- читает из Docker подсеть сети `deploy_default` и текущий адрес `deploy-caddy-1`; отказывается
  (понятное сообщение, ничего не меняя), если у сети не ровно одна IPv4-подсеть RFC 1918 размера
  /16../28 или адрес прокси вне её;
- меняет ровно две строки: `trusted_proxies static <подсеть>` и `{remote_host}` -> `{client_ip}`
  в маршруте кухни; любое другое отличие - отказ. `caddy validate` в контейнере без сети, затем
  `up` только gateway, проверка публичных файлов, health и того, что соседи не тронуты;
- `--check` - только чтение, без lock и CI: печатает JSON-событие `gateway_client_ip_check` и
  возвращает 1, если gateway не доверяет текущему адресу внешнего Caddy или маршрут передаёт
  адрес прокси. Его может периодически вызывать watchdog линии ops.

Доверие подсети шире одного адреса: в `deploy_default` также сидят контейнеры idrink и
`pickchick-staff-login`. Это компромисс, предложенный аудитом; полностью свою сеть можно сделать
только подключив чужой контейнер к сети PickChick (см. список владельца).

Тесты: `tests/operations/test_client_ip_gateway.py` - статические проверки на фикстуре живого
gateway и проверка в два прыжка на закреплённом Caddy 2.11.4 (тот же digest, что в compose):
клиент 127.0.0.20 -> внешний Caddy -> gateway -> эхо. Устаревший одиночный IP даёт адрес прокси
(воспроизведение находки), кандидат релиза даёт реальный адрес клиента; прямое обращение к
gateway с поддельным `X-Forwarded-For` клиента не меняет.

## 5.3 / 2.6 - бюджет кодов и общие адреса (`packages/customer-identity`)

- новые номера (без аккаунта) могут занять не больше 80% дневного бюджета
  (`CUSTOMER_AUTH_NEW_PHONE_BUDGET_PERCENT`), остальное остаётся постоянным клиентам: атака
  случайными номерами больше не закрывает вход тем, кто уже покупал;
- лимиты по адресу считают только запросы, код которых никто не подтвердил: 20 в час и 60 в
  сутки с адреса (IPv6 /64), 60 в час и 200 в сутки с подсети /24 (IPv6 /48). Подтверждённые
  входы за одним адресом оператора (CGNAT, Wi-Fi ТРЦ) не ограничиваются этими лимитами, только
  санитарный потолок 300 в час / 2000 в сутки. Лимиты по номеру (5 в час, 10 в сутки, 60 с между
  запросами) проверяются первыми, как и раньше;
- с адреса, где за сутки накопилось 40 неверных кодов (по запрошенным с него кодам), новые коды
  не выдаются;
- если Telegram однозначно ответил, что номер не может получить код (`recipient_unavailable`,
  `PHONE_NUMBER_NOT_SUPPORTED`) или адаптер отклонил номер до отправки (`invalid_input`), и
  WhatsApp не пробовали, резерв возвращается в бюджет дня. Другие отказы (конфигурация, баланс,
  отказ провайдера) по-прежнему тратят резерв;
- при достижении 50, 80 и 100% бюджета (и 80/100% доли новых номеров) API пишет JSON-событие
  `customer_otp_budget_attention` (`pool`, `percent`, `budget`, без номеров) в stderr - его может
  читать watchdog линии ops.

Что это даёт: исчерпать долю новых номеров (800 при бюджете 1000) теперь нужно минимум 14 разных
подсетей /24 на сутки, а постоянные клиенты при этом продолжают входить. Проверки до отправки
(captcha, App Attest / DeviceCheck) в приложении нет - это работа для будущей сборки (список
владельца).

Не проверено вживую: тарифицирует ли Telegram Gateway ответ `PHONE_NUMBER_NOT_SUPPORTED`. Мы
возвращаем только свой внутренний резерв; владельцу стоит сверить историю баланса Gateway.

## 5.4 - 4-значный код Telegram

Сборка 20 (TestFlight 0.2.0) для канала `auto` отклоняет ответ с `code_length` не равным 4
(`apps/mobile/src/customer-session.ts`, проверка есть с 07.10, сборка 20 - 14.10). Поэтому длина
кода не меняется: установленные приложения продолжают работать. Вместо этого:

- на один 4-значный код - 3 попытки (6-значный код SMS - по-прежнему 5);
- неверные коды считаются по номеру через все коды, долговечно (таблица
  `identity_otp_failures`, часовые корзины по ключевому HMAC номера, удаляются через 31 день):
  6 ошибок за 24 часа или 12 за 30 дней блокируют для этого номера и выдачу новых кодов, и
  проверку кода (ответ 429, приложение показывает «Подождите перед повторным запросом»).
  Уже открытые сессии на устройствах владельца номера продолжают работать;
- блокировка не действует на устройство, на котором у клиента с этим номером уже была сессия
  (в том числе завершённая выходом или по сроку 5.7). Его `device_id` - случайный UUID,
  который приложение хранит у себя и никому не показывает, так что подобрать его злоумышленник
  не может. Ошибки этого устройства тоже считаются, лимиты номера (5 в час, 10 в сутки, 60 с) и
  3 попытки на код действуют как обычно; для всех остальных устройств номер остаётся
  заблокированным.

Вероятность угадать код целевого номера: было до 50 попыток в сутки (0,5% в сутки, 13,9% за
30 дней, 36% за 90 дней), стало не больше 12 попыток за 30 дней (0,12% за 30 дней, около 1,5% в
год). Цена: злоумышленник может на сутки-месяц заблокировать вход с нового устройства (новый
телефон, переустановка приложения) для известного ему номера; существующие сессии и повторный
вход на прежнем телефоне не страдают. Полностью риск снимает только 6-значный код в будущей
сборке приложения (список владельца).

## 5.7 - refresh-токены клиента

- абсолютный срок сессии 90 дней от входа (`CUSTOMER_AUTH_SESSION_MAX_DAYS`), простой 30 дней
  без обновления (`CUSTOMER_AUTH_SESSION_IDLE_DAYS`). Истёкшая сессия при обновлении отзывается
  и отвечает 401; установленное приложение на авторитетный 401 очищает токены и показывает вход
  (`CustomerSessionCore.refresh`), то есть клиент просто входит заново. Пилот идёт с 26.09, так
  что в момент выката массового выхода не будет;
- в сессии хранятся хеши 64 последних «отслуживших» refresh-токенов (`retired_refresh_hashes`,
  GIN-индекс). Если предъявлен уже заменённый токен (не точный повтор потерянного ответа) - это
  кража или клон, сессия отзывается целиком, включая текущий access-токен. Повтор только что
  заменённого токена в течение 60 секунд (параллельные запросы одного устройства) по-прежнему
  даёт 409 без отзыва; точный повтор потерянного ответа (тот же токен и `request_id`) по-прежнему
  восстанавливает сессию.

Изменён старый тест `concurrent refresh ...`: восстановление после «400 дней офлайн» больше
невозможно по определению; теперь 20 дней офлайн, а повтор токена двухшаговой давности закрывает
сессию.

## 2.3 - вход для App Review

Флаги (по умолчанию выключено, хранить в защищённом `customer-auth.env`):

- `CUSTOMER_REVIEW_ACCOUNT_ENABLED=true`;
- `CUSTOMER_REVIEW_ACCOUNT_PHONE=+77XXXXXXXXX` - один номер Казахстана;
- `CUSTOMER_REVIEW_ACCOUNT_CODE_SHA256` - только digest 4-значного кода:
  `printf 'pickchick-review-code-v1:%s' <код> | sha256sum`.

Поведение: на этот номер код не отправляется и бюджет не тратится, ответ - «код отправлен в
Telegram», длина 4. Проверка кода идёт обычным путём: 3 попытки на код, лимиты номера и
блокировка 5.4 действуют. Создаётся обычный клиент; удаление аккаунта в приложении работает,
повторный вход создаёт новый аккаунт. Этот клиент:

- получает 403 `FORBIDDEN` на создание заказа и на оплату (`/v1/customer-checkout/orders`,
  `/orders/:id/payment`); установленное приложение показывает «Оплата Kaspi ещё не открыта для
  вашего аккаунта». Меню, корзина, расчёт заказа, профиль, игры, удаление доступны;
- не получает TEST-сессию (`/v1/test/sessions`, `/sessions/continue` -> 403), значит не может
  отправить TEST-заказ на кухню;
- не получает телефон для Kaspi-счёта (`readCustomerPaymentPhone` -> null): даже если попытка
  оплаты как-то появится, счёт не будет выставлен, попытка завершится ошибкой без денег.

Запрет на оплату действует, пока задан `CUSTOMER_REVIEW_ACCOUNT_PHONE`, даже при
`ENABLED=false`. После проверки Apple: выключить флаг, номер оставить (или удалить аккаунт
ревьюера в приложении).

| `CUSTOMER_REVIEW_ACCOUNT_CODE_SHA256`    | пусто        | digest кода (обязателен при ENABLED=true)                          |

Все шесть приняты строгим валидатором защищённого `customer-auth.env`

формата; любые другие поля (например `TEST_PHONE`) по-прежнему отклоняются. Заглушки - в
`.env.example`. Новых флагов для кабинета и kitchen portal нет: это исправления, включены всегда.
