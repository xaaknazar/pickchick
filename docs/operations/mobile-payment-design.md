# Страница оплаты без тестового сценария

По прямому поручению владельца от 8 сентября 2026 обычный путь
**Корзина → Оплата** больше не открывает ConnectedCheckout и кнопки симулятора.
Экран показывает ресторан, «Заберу сам / В зале», выбранные блюда и модификаторы,
сумму, редактирование корзины и фиксированную нижнюю панель.

Визуальный источник - `design/reference-source/mobile-v2.html.txt`, строки
925-990: скруглённый выбор способа, отдельная сумма справа, широкая нижняя кнопка,
лист выбора с отмеченным способом. Использованы фирменные Jost/Manrope и текущая
тёмная тема. Логотип скопирован без изменения из предоставленного владельцем
`Logo_of_Kaspi_bank.png` в `apps/mobile/assets/payments/kaspi.png`; это тот же
файл, на который ссылается оригинал. Он показан в корзине, оплате и листе выбора.

Просмотрены скриншоты [оплаты на 393](../../tests/operations/screenshots/mobile-payment/payment-393.png),
[на 320](../../tests/operations/screenshots/mobile-payment/payment-320.png),
[способов оплаты на 393](../../tests/operations/screenshots/mobile-payment/methods-393.png)
и [на 320](../../tests/operations/screenshots/mobile-payment/methods-320.png).

Кнопка оплаты отключена, рядом короткое «Онлайн-оплата скоро появится».
Подтверждённого remote Kaspi-адаптера пока нет. Дизайн не выполняет списания,
не открывает выдуманный deeplink, не выдаёт симуляцию за оплату и не обещает
неподключённые Чики. Суммы берутся из корзины в целых минимальных единицах.

## Граница обычного клиента и QA

`EXPO_PUBLIC_ORDER_SIMULATOR` не задан по умолчанию. В этом режиме M12 использует
новый Checkout, M13-M22 не показывают тестовые заказы и команды. `useTestOrders`
не читает старые тестовые сеансы по сети и не выполняет команды симулятора.
Сохранённые корзина, тестовый сеанс и незавершённые операции не удаляются.
Публичное чтение текущего меню не изменено.

Для внутренней проверки прежнего сквозного сценария нужен отдельный запуск:

```sh
EXPO_PUBLIC_ORDER_SIMULATOR=1 pnpm --filter @pickchick/mobile exec expo export --platform web --clear
```

Это флаг сборки, а не URL или переключатель пользователя. Также сохраняются
серверные capabilities, вход, идемпотентность и защита неизвестного результата.
По завершении QA обычный web export выполняется без флага и с `--clear`.
Настройки Metro для PickChick Dev не переключались.

## Проверка

```sh
pnpm test:mobile
pnpm --filter @pickchick/mobile typecheck
pnpm --filter @pickchick/mobile exec expo export --platform web --clear
MOBILE_RECOVERY_URL=http://127.0.0.1:4182 .local/design-venv/bin/python tests/mobile/browser_checkout.py
```

Новый browser-сценарий проверяет обычную сборку на 320/393/430: логотип,
выбор Kaspi/карты и сохранение выбора, правильную сумму, закреплённую кнопку,
переход назад, пустую корзину, отсутствие тестовых действий на прямых ссылках
и сохранность старых QA-данных. Все API перехвачены; записи запрещены.
Существующие `browser_catalog_recovery.py` и `browser_complete_catalog.py`
запускаются отдельно с явным QA export. CI проверяет обе конфигурации.

Выпуск не включает банковскую интеграцию, VPS или TestFlight. Следующий шаг -
оценка страницы владельцем в PickChick Dev на физическом iPhone.

## 29 сентября: отдельный экран коммерческого пилота Kaspi

Новый экран включается только сборкой `EXPO_PUBLIC_KASPI_CHECKOUT=1` вместе с
`EXPO_PUBLIC_CUSTOMER_AUTH=server`. Без флага старые пути не меняются. Коммерческие
заказы не преобразуются в TEST-заказы; история пилота показывает только commerce.

Оформление сохраняет существующую высоту листа, Jost/Manrope, синий фон и оранжевое
основное действие. Клиент выбирает «С собой» или «В зале». Блок Kaspi показывает
маскированный номер его аккаунта. Цена в итоге и деталях - серверная; изменение
относительно корзины поясняется до нажатия. «Продолжить» сохраняет заказ и запрашивает
приём рестораном; «Отправить счёт» доступно после admission. Данные карты и
несуществующие Apple Pay/Google Pay не запрашиваются.

Состояния: связываемся с рестораном → можно отправить счёт → отправляем → счёт
подтверждён банком → ожидание оплаты → деньги подтверждены → кухня → готов → выдан.
Неизвестный ответ и отсутствие сети не считаются отказом или оплатой. После обрыва
восстанавливается исходный command UUID. После оплаты очищается только та корзина,
чьи блюда, количества, модификаторы и способ получения совпадают с отправленными.
На заказе появляется `№` только с подтверждённым номером edge. Крестик слева.
Изображения позиций используют белые menuPhotos; фискальный чек показан отдельно.

Статусы клиента получают изменения через 20-секундный long poll (сервер читает
локальную проекцию каждые 500 ms). Это не банковский polling; мобильный клиент не
обращается к мосту. В фоне новые запросы прекращаются. При сетевой ошибке автоматическая
петля останавливается до явной проверки связи. Банк проверяет только existing worker.

Серверные настройки (секретные значения сюда не вставлять):

- `CUSTOMER_KASPI_PILOT_ENABLED=true`, organization/branch UUID;
- `KASPI_REMOTE_ACCOUNT_ID` - существующий enabled payment account той же legal entity;
- `CUSTOMER_KASPI_PILOT_CUSTOMER_IDS` - UUID допущенных клиентов, для первого счёта только владелец;
- `CUSTOMER_KASPI_PILOT_MAX_MINOR=10000` - предел 100 ₸, не подмена цены блюда;
- `CUSTOMER_KASPI_FISCAL_DEFERRAL_REFERENCE` - ссылка на решение владельца отложить Webkassa.

Все параметры задаются сервером. Один deferred order на клиента допускается под
транзакционной блокировкой; повтор того же заказа не расходует лимит снова.
Увеличение лимитов требует нового согласованного этапа, а не изменения клиента.
Недоступный каталог, закрытая точка, выключенный провайдер или отсутствующая
привязка кухни делают config.enabled=false. Default остаётся закрытым.

### Доказательства и границы

`packages/commerce-core/tests/{postgres,kaspi-remote.postgres}.test.mjs` проверяют
48 сценариев с PostgreSQL, включая владение, цену, неизменяемость политики и защиту
обычной фискализации. `packages/fulfillment-transport/tests/cloud.test.mjs` проверяет
15 сценариев, включая реальную доставку команды synthetic edge после capture.
`tests/mobile/browser_kaspi_checkout.py` проверяет 320/393/768 px, размеры кнопок,
потерю первого ответа create, повтор одного UUID, счёт и обновление paid.
Приватные снимки проверки: `.local/kaspi-checkout-ui/`; это HTTP fixtures, не банк.

Новый API/экран пока не выпущен на VPS/телефоны. Нужны отдельный guarded release
schema020→027, grants для API/worker, опубликованный коммерческий каталог и штатный
edge transport. TEST kitchen portal сам по себе не подтверждает commercial admission.
Первый probe 100 ₸ не отправлен. Пилот не заменяет окончательную Webkassa-интеграцию,
единый production список заказов и приёмку на физическом iPhone.

## 29 сентября: PickChick Dev запущен с Kaspi checkout

На основном Mac запущен LAN Metro с `EXPO_PUBLIC_KASPI_CHECKOUT=1`,
`EXPO_PUBLIC_CUSTOMER_AUTH=server`, `EXPO_PUBLIC_UNPAID_TEST_ORDERS=0` и Fast Refresh.
Проверка `node scripts/mobile/check-dev-bundle.mjs`: iOS manifest/bundle HTTP 200,
11 280 089 байт. Автоматическое открытие на iPhone не выполнено: devicectl вернул
`kAMDMobileImageMounterDeviceLocked`. Нужны разблокировка и открытие PickChick Dev
в одной LAN с Mac. Запуск Metro не означает установку нового нативного клиента.

Публичный `/v1/customer-checkout/config` пока возвращает HTTP 404: backend checkout
не выложен, счёт отправить нельзя. Банковских запросов/списаний не было.
Приёмка экрана на телефоне и онлайн-публикация roadmap ещё не выполнены.

## 30 сентября: передача дизайнеру и единый статус оплаченного заказа

Подготовлено [задание дизайнеру](../design/mobile-designer-brief-2026-09-30.md): папки,
маршруты M01-M35, компоненты, бренд, состояния, критерии переноса текущего приложения
в Figma без самостоятельного редизайна. Сами новые макеты в Figma ещё не создавались.

Kaspi после одной явной команды «Получить счёт» ждёт admission ресторана и автоматически
отправляет прежнюю идемпотентную попытку. Согласие сохраняется на устройстве до запроса;
просмотр истории без этого согласия не отправляет счёт. После trusted capture используется
тот же OrderStatusView/OrderChef, что и существующий экран: кухня, сборка, выдача в зале
или с собой. Коммерческий заказ не превращается в TEST-объект. Фото белые, номер с №;
суммы, модификаторы и время приходят из сохранённого заказа. Поддержка/отзыв коммерческого
заказа пока не подключены, нельзя направлять его в TEST-обработчик.

Установлен guarded выпуск API/schema020→027: `2f3c3f3`, Foundation CI36673841187
полностью зелёная. Backup+restore прошли, прежние данные/права и соседние службы
проверены; checkout вместо 404 возвращает 401 без авторизации. Customer auth и
выставление счетов оставлены выключенными; банк и worker не вызывались.
Кассовый моноблок выключен. Для активации остаются legal/identity, коммерческий
каталог, provider account, runtime grants, owner allowlist и действующий edge.
Подробности и границы: [протокол установки](deployments/2026-09-30-kaspi-checkout.md).
Онлайн-пульт опубликован из `70298fa`; `/roadmap/health` подтвердил sourceSha.
Бизнес-API, БД, мост и кухонный портал при обновлении пульта не менялись.

Проверено локально: 48 PostgreSQL commerce сценариев, 50 Python release guards,
mobile typecheck/lint; браузер 320/393/768 - потеря первого ответа, тот же UUID, одна
команда счёта, paid→сборка→выдача и прежний герой. Банковские ответы в этих проверках
подставные. Приёмка на физическом телефоне ещё требуется.
