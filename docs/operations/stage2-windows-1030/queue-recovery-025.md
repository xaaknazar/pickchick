# С4: оператор Windows 024 -> 025

`infra/windows/update-runtime-queue-recovery-025.ps1` подготавливает отдельный
переход с установленной 024 на ровно 025 и переключение четырёх native-служб.
По умолчанию выполняется проверка; изменения требуют `-Apply`. На рабочей
кассе этот оператор ещё не запускался. Облачный выпуск 072, реальная репетиция
и приёмка оборудования остаются отдельными обязательными этапами С4.

## Границы

- Не применять к 020/023, не передавать архив 026–028 и не удалять из архива
  лишние миграции: проверяются полный manifest, SHA и все 25 закреплённых SQL.
- Предшественник задаётся полным SHA `-PredecessorCommit`, кандидат - полным
  `-SourceCommit`. Требуются полная успешная Foundation CI точного кандидата
  и отдельно точного установленного облачного исходника `-CloudSourceCommit`.
- Существующий POS-sync запрещает этот переход: он устанавливается отдельно
  после исправления очереди и решения по остатку. Службы PostgreSQL и
  действующего fulfillment-туннеля остаются запущенными с прежними PID.
- Пароли, identity, конфигурации, флаги, меню и POS-приложение не меняются.
  Миграция добавляет только 025 и её ограниченные права; общий provision не
  запускается. Автоматический fence и решение по старым заказам запрещены.
- Резервная копия должна быть восстановлена и проверена не более шести часов
  назад; её точка, кластер, ledger, размер и SHA должны совпадать. Автокопии
  требуют другого физического локального диска. Раздел D на том же диске,
  что C, не подходит. Этот оператор не принимает UNC/NAS как локальный диск.

## Входные доказательства

Все файлы ниже хранятся приватно с административным ACL, вне Git и чата.
Их нельзя создавать с положительными отметками без фактических проверок.

1. `-BaselineReceipt` и `-BaselineSha256`: JSON формата
   `pickchick-queue-recovery-baseline-v1`, `schema: 24`, фактические
   `branchId`, `computerName`, `systemIdentifier`, `sourceCommit` и массив
   `xmlHashes` из четырёх SHA256 **исходных UTF-8 байтов** XML в порядке:
   Edge, FulfillmentWorker, MenuSyncWorker, DeviceAccessWorker. Файл составляется
   по осмотру установленного 024 после предыдущего перехода; итог 020/023
   или старый receipt от другого компьютера не подходит.
2. `-RuntimeArchive`, `-RuntimeSha256`, `-CiProof`: неизменяемый архив 025
   и полная CI его точного исходника в существующем формате `run`/`jobs`.
3. `-BackupManifest`: существующий `pickchick-native-service-backup-v1` от
   проверки восстановления 024; рядом должен быть проверенный `pickchick_edge.dump`.
4. `-CloudReleaseReceipt`, `-CloudReceiptSha256`, `-CloudCiProof`:
   проверенный протокол **уже выполненного** отдельного облачного окна.
   Формат receipt - `pickchick-queue-recovery-cloud-v1`; поля:
   `sourceCommit`, `apiSourceCommit` (оба равны `CloudSourceCommit`), `branchId`,
   фактический `apiImageId` вида `sha256:...`, `observedAt` в UTC, объект
   `migration` с `version: 072_cloud_kitchen_restore_review.sql` и checksum
   `d222ea9bf0aeebcaaeea96bc119c9b8aa3e1d9f032a1af7914aefe5c8981c5e2`.
   `databaseVerified`, `grantsVerified`, `apiReady`, `schema023Compatible`,
   `schema024Compatible`, `flagsPreserved` должны быть JSON boolean `true`
   только после соответствующих серверных проверок. Строка `"true"` не принимается.
   Протокол не старше часа и не из будущего, проверяется повторно перед переключением.
   **Это проверяемое заявление ответственного за облачное окно, а не живая
   проверка VPS этим Windows-скриптом и не автоматически сформированный отчёт.**
   Пока нет подтверждённого облачного выпуска и этих доказательств, `Apply`
   не допускается. Существующий выпуск 069–071 не удовлетворяет этому условию.
5. `-BranchId` и `-BackupDestination`: фактическая точка и проверенный отдельный диск.

Сначала выполнить команду без `-Apply` с этими входами. Затем, в согласованное
окно после закрытия смены, повторить те же проверенные входы с `-Apply`.
Наличие зелёной CI не заменяет проверку восстановленной реальной базы.

## Порядок и отказы

Оператор проверяет архив, CI, установленный runtime/XML, кластер и копию,
получает новую зашифрованную автокопию 024, приостанавливает задачу копирования
и берёт существующую общую maintenance lease. Снова проверяет диск, кластер,
облачный протокол и конфигурации, извлекает неизменяемый runtime и сохраняет
исходные XML в приватный каталог состояния.

Все пять писателей останавливаются до SQL: fulfillment, menu sync, device
access, kitchen link и edge. Helper проверяет 024, выполняет 025 одной
транзакцией и доказывает сохранность данных и прав. Затем заменяются четыре XML.

- При отказе остановки возвращаются все ранее запущенные службы.
- При отказе SQL без переключения XML возвращаются прежние службы только
  после подтверждения точного ledger 024 либо совместимого аддитивного 025.
- При частичной замене XML сначала восстанавливаются все исходные привязки.
  Смешанный или посторонний набор запрещает запуск всех служб.
- Новый runtime нельзя запустить с ledger 024. Несовпадение доказательства
  сохранности данных оставляет писателей остановленными для разбора.
- После начала запуска нового runtime старые бинарники автоматически не
  возвращаются: новый процесс уже мог записать данные. Проверяются readiness,
  дочерние процессы, неизменность соседних служб/конфигурации и ledger.
- После успешной проверки запускается свежая копия 025. Ошибка копии не
  объявляет переход готовым. Планировщик копирования восстанавливается в `finally`.
- Существующий каталог попытки запрещает автоматический повтор. После потери
  питания/принудительного завершения сохранить состояние и проверить БД,
  все четыре XML и службы; не удалять каталог ради повторного `Apply`.
  Восстановление БД поверх новых продаж не выполняется этим скриптом.

## Проверки кода

`test_windows_queue_recovery_release.py` исполняет функции нового оператора,
имитируя SCM/SQL и используя временные XML. Проверяются свежесть/состав
облачного протокола, отдельный физический диск, частичные остановки, отказ SQL
до/после commit, несовпадение proof, частичная замена и отказ восстановления XML,
неверный ledger и отказ запуска. Отдельно выполняется реальный Node-код драйвера
с подставным модулем pg: чужой адрес/порт/роль/БД и параметры URL отвергаются
до загрузки драйвера, секрет не печатается.

С 12.11 тот же набор проверяет правило набора миграций (`Assert-QueueMigrationSet`) на
настоящем закреплённом журнале `native-edge-backup-ledger.json`, лежащем рядом со скриптом, как
на сервере: кандидат 025 должен равняться первым 25 строкам журнала; кандидаты 024, 026 и 028,
изменённая миграция и журнал без строки 025 отвергаются. До 12.11 правило требовало файл ровно
из 25 строк, а `Assert-Stage2ToolPins` закрепляет файл этой ветки из 28 строк (001-028, его
принимает инструмент копий), поэтому оператор с головы `codex/cutover-1119` останавливался на
осмотре со словами `Reviewed queue ledger required.` при любом верном кандидате (воспроизведено
в Windows PowerShell 5.1, прогон 43205243396). Сервер при таком отказе не меняется: он
происходит до `-Apply`. Архив оператора, собранный до этого исправления с головы cutover,
собирают заново.

В Windows CI проверки запускаются именно Windows PowerShell 5.1. Транзакционный
helper дополнительно проверяется существующим PostgreSQL-набором
`tests/operations/queue-recovery-upgrade.test.mjs`. Эти проверки не заменяют
репетицию полного оператора на восстановленной реальной Windows-кассе.
