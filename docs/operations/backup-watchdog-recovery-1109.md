# С5 / С6: обрывы ответов и безопасное получение резервных копий

9 ноября 2026. База `2420cdc8a76d2e70d0ca9bfddcf5a288549a10bb`, общий срез
после исправления отмены оформления. Рабочий VPS, Telegram-группа и внешнее
хранилище не использовались; секретов и серверного доступа в облачной среде нет.

## С6: получение копии из хранилища

Выявлены и воспроизведены два дефекта `backup-offsite.py fetch`:

- Файл назначения открывался с `wb` до ответа S3. Повторная команда могла
  уничтожить ранее скачанную копию, даже если новая загрузка затем не удалась.
- Чтение HTTPResponse блоками могло завершиться без исключения при обрыве
  ответа раньше объявленного Content-Length. Частичный файл считался скачанным.

Теперь данные сначала попадают в отдельный временный файл 0600 в выбранном
каталоге. Оборванный ответ повторяется с начала в пределах прежнего лимита
попыток. Ответ 206 без запрошенного Range отвергается. Финальное имя появляется
только после полного ответа, flush/fsync и атомарного создания ссылки без
замены существующего файла. Временный файл удаляется при обычном завершении
и исключениях. При аварийном завершении процесса может остаться скрытый `.tmp`,
но он не выдаётся за готовую копию.

Существующий файл или symlink отклоняются до сетевого запроса. Если другой
процесс успел создать файл во время загрузки, его результат тоже сохраняется.
Публикация требует файловой системы с поддержкой hard link; при отсутствии
поддержки команда завершается ошибкой, без запасного пути с перезаписью.

Для каждого учения скачивать файлы в новый закрытый каталог. Повторять `fetch`
на уже существующий файл теперь нельзя; предыдущую проверенную копию сохранять.
Далее нужны прежние `.sha256`, зашифрованный manifest и `restore-drill.py`:
завершённая HTTP-передача сама по себе не доказывает пригодность базы для восстановления.
При отсутствии Content-Length полноту framing проверяет HTTP-клиент; контрольная
сумма копии остаётся обязательной отдельной проверкой.

Пять новых сценариев на старом коде падали: существующий файл/symlink, обрыв
всех попыток, успешный повтор после обрыва, ошибки 404/206 и конкурирующая
загрузка. После исправления полный набор `test_backup_offsite.py` прошёл:
**21/21, без пропусков**, с настоящим age и loopback S3-двойником, проверяющим
SigV4 и Content-MD5.

## С7: повторная проверка PITR при получении через S3-клиент

В Docker-тесте базовая копия и WAL теперь действительно скачиваются методом
`get_file`, а не записываются напрямую из памяти S3-двойника. Полный набор
`test_restore_drill_docker.py`: **2/2 PASS** на закреплённом PostgreSQL 18.3,
который используется cloud-конфигурацией. Это не кассовая проверка PostgreSQL 18.6.

Проверены обычное восстановление с манифестом, отказ при неправильном числе
строк и повреждённом файле, затем PITR из скачанных base/WAL. До целевого времени
восстановлены 28 строк; две более поздние вставки отсутствуют. Источник не менялся
при восстановлении, временные контейнеры/тома удалены. Весь набор занял 82,7 с;
это длительность тестов, **не RTO рабочей базы**.

## С5: ошибки после получения HTTP-заголовков

API probe раньше поглощал ошибку чтения тела и показывал обычный неготовый
HTTP 200. Telegram sender также превращал прерванное чтение тела в
`TELEGRAM_HTTP_200`. Теперь обрыв и timeout сохраняют правильные категории
`unreachable`/`timeout` и `TELEGRAM_UNREACHABLE`/`TELEGRAM_TIMEOUT`.

Полный, но неверный JSON по-прежнему не считается успешным ответом.
Токен, URL Telegram и исходный текст сетевой ошибки не попадают в диагностику.
Неудавшаяся отправка не продвигает состояние уведомления: следующий запуск
повторяет отправку. Режимы Telegram/shadow/dry-run и их настройки не менялись.

На старом коде новый тест воспроизвёл неверную классификацию. После исправления
**39/39** watchdog-тестов прошли. В том числе настоящий локальный HTTP-сервер
отправляет заголовки 200 и часть JSON, затем задерживает тело до timeout;
проверены обе ветки, отсутствие утечки токена, сохранение состояния и повтор.
Ни одного обращения к настоящему Telegram не было.

## Повторение проверок

```sh
python3 -m unittest tests/operations/test_backup_offsite.py
python3 -m unittest tests/operations/test_restore_drill_docker.py
node --test tests/unit/ops-watchdog.test.mjs
pnpm exec eslint infra/staging/watchdog/api-probe.mjs infra/staging/watchdog/telegram.mjs tests/unit/ops-watchdog.test.mjs
```

Для Python-тестов нужны age/age-keygen; для Docker-набора - локальный daemon
и уже загруженный закреплённый образ из `restore-drill.py`. Тесты без этих
возможностей пропускаются, поэтому результат с `skipped` не засчитывать.
В этой сессии все 21+2 проверки выполнены без пропусков; Docker явно направлен
на локальный Unix socket, не на удалённый context.
