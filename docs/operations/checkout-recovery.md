# Восстановление оформления после rollout Kaspi

Дата: 1 октября 2026. Задача: checkout-menu-conflict.

## Причина и исправление

На «Оформление» приложение повторяет сохранённый create command. После перехода
от разрешения владельцу к allVerifiedCustomers сервер включал новый
fiscal_deferral_reference в digest старого запроса. CONFLICT ошибочно показывался
как изменение меню/цены. Воспроизведено на двух существующих заказах без новых
финансовых эффектов; меню проверено отдельно (244 варианта и quote Pick Combo).

CustomerCheckout ищет заказ только по quote текущего клиента/организации/точки
и использует его неизменяемое разрешение для повтора. Репозиторий по-прежнему
проверяет ключ и digest. Для новых заказов используется текущее разрешение.
Чужие заказы недоступны, другой quote с прежним ключом остаётся конфликтом.

## Проверка и установка

Добавлены PostgreSQL regression tests: параллельное восстановление, неизменность
команды, отсутствие дополнительных заказов/платежей, изоляция клиентов, новое
разрешение для нового заказа, повтор под ограниченной runtime ролью.

Профиль release-checkout-recovery.py фиксирует API8ecdc13/public7fbf759/schema028,
требует полную CI точного commit, backup/restore, сохранение данных/ACL и точного
действующего all-customer environment. Банковский worker e560e0f не меняется.
Установка пока не выполнена. Контроль после установки: повтор двух имеющихся
create commands, тот же orderId, неизменные количества order/attempt/invoice/capture.
