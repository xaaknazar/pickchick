# Отдельный выпуск статических рабочих экранов

## Область применения

8 сентября 2026 владелец поручил убрать общий тестовый баннер и переходы
между рабочими экранами, а публичное табло привести к исходному макету.
Для этого изменения выбран отдельный manual staging UI-only профиль.
Это явное узкое исключение из общего требования зелёного CI перед deploy
в [порядке VPS-выпуска](staging-vps.md). Причина: GitHub Actions отказывает
до запуска jobs из-за оплаты аккаунта либо spending limit; локальные проверки
не называются успешным удалённым CI.

Исключение действует только на статический `apps/operations` этого поручения.
Оно требует завершённых локальных проверок ниже, review изменений, опубликованного
source SHA и готового возврата. Общий API/schema release, зависимости/миграции,
feature flags, банковские адаптеры и публичный ресторанный запуск по этому
профилю запрещены. Их прежние CI/приёмочные условия сохраняются.

## Подготовка

1. Зафиксировать исходный commit, собрать TypeScript и Vite operations.
   Проверить ESLint/формат, восстановление киоска, вход и разделение staff-ролей,
   источник номеров табло, stale-режим, очереди длиннее экрана, отсутствие
   удалённых баннера/ссылок. Сравнить скриншоты 1920×1080 и 1280×720 с оригиналом.
   Сценарии используют локальные HTTP fixtures, не настоящие заказы.
2. Read-only проверить оба действующих pointers, image/starttime API/БД/Redis
   и соседних сервисов, конфигурацию только нашего gateway, полный web manifest.
   Сверить каждый из базовых public runtime-файлов с его SHA-256, в том числе
   локальную копию. Не выводить секреты или содержимое заказов.
3. Из чистой рабочей копии того же commit упаковать уже проверенный dist:

   ```sh
   python3 infra/public-staging/package-operations-overlay.py \
     --source-sha <FULL_SOURCE_SHA> \
     --base-web <VERIFIED_CURRENT_PUBLIC_WEB> \
     --expected-base-source-sha <CURRENT_WEB_SHA> \
     --expected-base-manifest-sha256 <CURRENT_MANIFEST_SHA256> \
     --output <NEW_EMPTY_RELEASE>/public-web
   ```

   Packager проверяет source SHA/чистоту и базовые hashes, но не заменяет
   сборку и проверку dist. Он сохраняет остальные приложения побайтно,
   добавляет новый operations и сохраняет старые hashed assets для открытых
   вкладок. Составной manifest указывает новый `source_sha`, прежний
   `base_source_sha` и отдельные `component_sources`.

## Переключение и проверка

В новом immutable release находятся public-web и точные прежние gateway
Compose/Caddyfile. Проверяются readable mode 0644/0755 для публичных файлов,
все hashes и hardened Caddy validate. Внутренние manifests/docs не публикуются.

Перед переключением повторно сверить текущий gateway mount и pointer с
исходной версией; при конкурирующем выпуске остановиться. Удерживать общий
deployment lock и освобождать только собственный lock. Identity cleanup
и API/БД не останавливаются: этот профиль не выполняет снимки, миграции
или записи заказов. Перезапускается только `pickchick-public-gateway` через
его новый Compose `up -d --no-deps --wait gateway`, после чего проверяется
фактический mount. Общий Caddy соседнего приложения не изменяется.

После переключения выполнить существующие ingress/static smoke, проверить
пять SPA-маршрутов и запреты private static paths, а затем read-only вход
в рабочие роли и фактическое оформление опубликованного табло. Ошибки
авторизации/данных не скрывать. Сверить неизменность API/БД/Redis/соседних
контейнеров, runtime flags и всех не-operations web hashes. Только после
успеха атомарно переключить public-https/current; API current остаётся прежним.

При ошибке web/UI/hash/health запустить сохранённый прежний Compose для
одного gateway, проверить прежние mounts/static/ingress и вернуть только
собственный public pointer. Не восстанавливать БД для отката UI.
Точные source/base SHA и выполненные проверки фиксируются отдельным протоколом
в `docs/operations/deployments/`; неудавшуюся попытку не выдавать за выпуск.
