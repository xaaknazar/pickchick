# Лимит ошибок при восстановлении подтверждённого входа

7 сентября 2026 добавлен отдельный счётчик `receipt_failed_attempts` в
`identity_otp_challenges`, миграция `013_cloud_identity_receipt_limits.sql`.
Он ограничивает перебор шестизначного кода при восстановлении уже выполненного
`otp/verify`, если ответ с credentials потерялся до сохранения на устройстве.

Для такой попытки нужны непубличные `challenge_id`, исходный verify `request_id`
и `device_id` успешно подтверждённого устройства. Знания номера телефона
недостаточно. Лимит закрывает дополнительный сценарий утечки локального
pending-envelope в окне потерянного ответа; он не заменяет SecureStore, TLS,
ограничения отправок SMS и отсутствие чувствительных данных в логах.

Поведение сервера:

- Первичная проверка OTP сохраняет прежний лимит пяти попыток за три минуты.
  Её `attempts` не сбрасывается и не используется как счётчик recovery.
- В состоянии `consumed` только совпавшие устройство и **исходный** request UUID
  могут расходовать recovery-бюджет. Чужой device или другой request UUID его
  не меняют. Неверный код или изменённые согласия считаются несовпадением
  исходного input hash и увеличивают `receipt_failed_attempts`.
- После пяти таких ошибок receipt больше не выдаёт credentials, даже при
  последующем правильном коде. Ответ остаётся `409 CONFLICT`, без подсказки кода,
  количества оставшихся попыток или содержимого сохранённого receipt.
- Правильный exact replay счётчик не увеличивает. Две опечатки и затем верный
  повтор восстанавливают прежнюю сессию. Успешная пятая **первичная** попытка
  также допускает восстановление потерянного ответа: recovery-счётчик ещё нулевой.
- Проверка и увеличение выполняются под существующей блокировкой строки и
  phone advisory lock. Ошибка возвращается после commit, поэтому перезапуск
  сервиса и параллельные запросы не сбрасывают счётчик и не превышают пять.
- Заблокированный receipt не отзывает уже сохранённые access/refresh устройства.
  Пользователь без сохранённых credentials может явно запросить новую SMS с
  новым request ID, соблюдая прежние cooldown и бюджеты. Автоматической отправки нет.
  Прежний receipt не восстанавливается новым запросом.

Общий срок verify receipt остаётся 24 часа, только пока начальный refresh ещё
актуален. Истёкший/удалённый receipt не получает новый срок. Одно корректное
восстановление не создаёт вторую сессию и не принимает новые редакции согласий.
Идемпотентный refresh и его отдельный механизм восстановления не изменены.

Миграция аддитивна: существующие строки получают нулевой счётчик, без изменения
OTP attempts, профиля, токенов, сессии или encrypted receipt. Новый столбец
NOT NULL, CHECK 0–5. Применять миграцию до нового API; старый API без этого лимита
не должен снова обслуживать включённый auth после security rollback.
Readiness должна требовать миграцию 013 при включённом customer auth.
Имеющихся SELECT/UPDATE прав на `identity_otp_challenges` достаточно;
новых ключей, HTTP-полей и provider-настроек не требуется.

Проверки используют только временные PostgreSQL-схемы и in-memory delivery:
сохранность при миграции, две опечатки с успешным replay, пятая свежая попытка,
20 параллельных ошибочных повторов, независимость от чужих device/request UUID,
изменённые согласия и явный новый OTP после исчерпания recovery-бюджета.
Коды не печатаются в логах. VPS, реальные SMS и пользовательские устройства
в этом этапе не используются.
