# Бэк-офис: вкладка «Устройства»

Задача `devices`, октябрь 2026. Решение и границы:
[ADR-0013](../architecture/adr/0013-device-registry-pairing.md).
Пока выпуск не выполнен, на VPS работает прежняя вкладка `cf25cb9e`.

## Что делает MVP

| Устройство              | В бэк-офисе                                                   | Где меняется доступ                                                      |
| ----------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Касса и моноблок (edge) | Карточка, последняя связь, срок ключа облака                  | Отключать нельзя. Замена - по процедуре `docs/operations/menu-sync.md`   |
| iPad-киоск              | Подключение по логину и паролю (30 минут), отключение, журнал | Бэк-офис, роль `manager`                                                 |
| Кухня - приём и сборка  | Только чтение                                                 | Пароль сотрудника на кассе: `scripts/staff-password-setup.mjs --replace` |
| Табло                   | Только чтение                                                 | Этап 2: код подключения через edge                                       |

- Роль `analyst` только смотрит. Действия доступны `manager` этой точки.
- Каждое действие требует причину 3-500 символов и пишется в `device_events`
  и `bo_audit`. Для отключения нужно ввести имя устройства.
- Киоск подключается только для точки `KIOSK_CHECKOUT_BRANCH_ID` установленного
  API. Для других точек вкладка пишет «киоск для этой точки пока не настроен».
- Отключение киоска с незавершённой Kaspi-оплатой блокируется, пока платёж не
  закрыт (миграции 046 и 050).

## Подключение iPad

1. «Подключить устройство» → «Киоск iPad» → имя → причина.
2. Экран показывает логин и пароль один раз и обратный отсчёт 30 минут.
   Пароль нельзя записывать в чат, тикет или фото; закрыли окно - выпускайте
   новый.
3. На iPad ввести логин и пароль на экране регистрации текущей сборки.
4. Карточка переходит в «На связи» после первой сессии киоска.

**Сброс киоска** = «Отключить» + новое подключение. Установленная сборка хранит
прежнюю регистрацию: до новой сборки приложение на iPad придётся переустановить
(`docs/operations/kiosk-v3-launch.md`, раздел про установку без удаления).
Это отдельная операция с устройством, только по поручению владельца.

## Секрет `DEVICE_PAIRING_PEPPER`

Код подключения хранится в БД только как HMAC с pepper. Pepper живёт вне БД:
в приватном `release.env` API на VPS (0600), как `KIOSK_ENROLLMENT_KEY`.

Подготовка (делает владелец, один раз, на своём Mac):

- файл `.local/vps/device-registry.env.json`, права `0600`, не в Git;
- содержимое - ровно `{"DEVICE_PAIRING_PEPPER": "<64 hex>"}`;
- значение - 32 байта из криптостойкого генератора (например вывод
  `openssl rand -hex 32`), отдельное от всех других секретов;
- копия - в менеджере паролей владельца. Значение не печатать, не вставлять в
  чат, логи, тикеты и Git.

Агенты и скрипты значение не создают. Профиль выпуска проверяет формат, права
файла и что значение не совпадает ни с одним секретом API (сравнение по SHA-256),
передаёт его на VPS только через stdin ssh и сверяет с контейнером по SHA-256.

Потеря pepper делает недействительными только открытые коды (не больше 15 минут).
Смена pepper этим профилем не поддерживается: он требует, чтобы ключа ещё не было.

## Выпуск API: `infra/staging/release-device-registry.py`

Перед выпуском:

- `pnpm project:check`, свежий `project:tasks`; занять `@vps/api` и `@vps/db`;
- установлен `cf25cb9e` (выпуск `release-kiosk-incident.py` завершён, схема 050);
- кандидат содержит `051_cloud_device_registry.sql`,
  `infra/staging/device-registry-grants.mjs`, контроллер устройств и
  полностью зелёную CI на точном SHA;
- `--base-image` и `--expected-compose-sha256` - `image_id` и
  `compose_sha256` из `phase-deploy.json` выпуска kiosk-incident
  (`.local/kiosk-incident-release/cf25cb9e.../`). Если этот файл есть на Mac,
  профиль сверяет аргументы с ним;
- согласие владельца на выпуск.

Preflight только читает и печатает план:

```sh
python3 infra/staging/release-device-registry.py <sha> \
  --branch <ветка> --branch-id <uuid точки> \
  --base-image sha256:<id> --expected-compose-sha256 <hash> \
  --environment .local/vps/device-registry.env.json \
  --ci-run <id>
```

Применение - та же команда с `--apply`. Профиль:

1. проверяет чистое опубликованное дерево, точную CI всех заданий,
   неизменность миграций 001-050 относительно `cf25cb9e`;
2. проверяет живую базу: образ и указатель `current` на `cf25cb9e`, образ отката,
   хеш compose, ledger 001-040, 042-050 с теми же checksum, ограничения роли
   `pickchick_app`, отсутствие pepper в окружении API;
3. берёт общую блокировку выпуска, делает зашифрованный backup и проверяет
   восстановление в изоляции;
4. готовит кандидата: compose - живой байт в байт плюс одна строка
   `DEVICE_PAIRING_PEPPER: ${DEVICE_PAIRING_PEPPER:?...}` в `api.environment`;
   `release.env` - прежний с новым `RELEASE_SHA` и добавленным pepper (0600);
5. шаг владельца `infra/staging/device-registry-owner.mjs deploy` в одной
   транзакции REPEATABLE READ: применяет только 051 и гранты, доказывает, что
   колонки и строки прежних таблиц не изменились (у `devices` добавлены только
   8 колонок), новые таблицы пусты, ни одно право не снято, добавлены только
   права из `REGISTRY_PRIVILEGES`;
6. прежний API продолжает работать на аддитивной схеме, затем запускается новый;
7. проверяет: образ, ревизию, окружение (изменились только `RELEASE_SHA` и
   добавлен pepper с ожидаемым SHA-256), прежние capabilities, маршрут
   `/v1/admin/backoffice/branches/<id>/devices` отвечает 401 без токена;
8. переключает `current`; соседние контейнеры (QR worker, банковский мост,
   мобильный worker, БД) и gateway должны остаться как были.

При сбое после запуска нового API возвращается `cf25cb9e` (его compose и
`release.env` pepper не содержат); схема 051 остаётся. При неизвестном исходе
блокировка остаётся до ручной проверки. Доказательства - в
`.local/device-registry-release/<sha>/`.

Профиль не создаёт устройств, кодов, alias, платежей, QR и заказов и не трогает
gateway, публичные файлы и прокси `infra/backoffice-login`.

## После выпуска API

1. Отдельно выпустить allowlist маршрутов: `apps/backoffice/src/api.ts`,
   `apps/backoffice/server.mjs`, `infra/public-staging/gateway.Caddyfile`.
   До этого вкладка показывает прежние данные.
2. Обновить `docs/project-status.md`, `docs/roadmap/project.json` и онлайн-пульт.
3. Проверка только чтением: вкладка под `analyst`, кнопок нет; под `manager`
   у edge нет «Отключить». Подключать тестовый киоск - только по поручению
   владельца.

## Проверки в репозитории

```sh
python3 -m unittest tests/operations/test_device_registry_release.py
node --env-file=.env --test --test-concurrency=1 tests/integration/device-registry-release.test.mjs
```

Интеграционный тест прогоняет шаг владельца на синтетической 051 той же формы
и, когда настоящая 051 и модуль грантов появятся в ветке, на них.

## Не входит в MVP

- коды для кухни, табло и POS (transport протокол 5, edge 020);
- короткий код и QR на iPad (новая сборка);
- сброс пароля сотрудника из облака, самоповорот ключа edge, замена моноблока;
- MFA и повторный ввод пароля перед опасными действиями.
