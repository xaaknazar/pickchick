# Kaspi: счёт на номер телефона (kaspi-remote)

Решение и риски: [ADR 0012](../architecture/adr/0012-kaspi-remote-bridge.md).
Актуальный результат входа 29 сентября: парольный шаг добавлен, реальный банк
принял пароль и SMS, затем потребовал Kaspi ID. Сессии пока нет. Подробный
[аудит](kaspi-bridge-audit-2026-09-29.md) заменяет прежний вывод «пароль не поддерживается».
Для установки применять оба патча через install-overlays.mjs, не один старый hardening patch.

Это адаптер финансового ядра. Реальных счетов из PickChick ещё не выставлялось.

## Как это работает

1. Целевой путь: mobile создаёт заказ и попытку оплаты с аккаунтом `kaspi-remote`
   (`startPaymentAttempt`, событие `payment.submit_requested`). Сейчас это доступно
   только через внутреннее ядро: commercial checkout и mobile UI не реализованы.
2. Worker забирает событие, записывает `commerce_kaspi_invoices` в состоянии
   `issuing` с случайной ссылкой `PickChick XXXXXXXXXX` **до** обращения к Kaspi,
   берёт подтверждённый телефон клиента из `identity_customers` и выставляет
   счёт на целые тенге. Дополнительная копия телефона в таблице счетов не создаётся;
   он остаётся зашифрованным в identity. В логи worker телефон не попадает.
3. Клиенту приходит пуш Kaspi. Worker проверяет статус: первые 2 минуты каждые
   3 с, до срока счёта каждые 10 с. Подписанный вебхук моста (если включён)
   только ускоряет проверку; сумма и статус всегда перечитываются из Kaspi.
4. `Processed` → `observePayment(captured)` с суммой из Kaspi → ядро записывает
   capture, ставит чек в очередь, после чека - допуск на кухню.
   Разная сумма фиксируется как есть и уходит на сверку.
5. Через `KASPI_INVOICE_TTL_SECONDS` неоплаченный счёт отменяется один раз.
   Оплата, успевшая до отмены, всё равно засчитывается.

| Ситуация                                                                        | Результат                                                                 |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Kaspi вернул код ошибки при создании, нет сессии, нет телефона, сумма с тиынами | попытка `failed`, счёта нет                                               |
| Таймаут/обрыв/ошибка моста при создании                                         | `unknown`; счёт ищется в истории по ссылке, иначе ручная сверка           |
| Worker упал после отправки                                                      | повторный запуск не выставляет второй счёт, ищет его по ссылке            |
| Незнакомый статус                                                               | ожидание, не отказ                                                        |
| Сессия вытеснена (`-101001`)                                                    | новые счета не выставляются, лог `session_rejected`, нужен повторный вход |

Одна попытка - не более одного счёта, один `operation_id` - одна попытка
(уникальные ключи в БД). Повторы наблюдений идемпотентны через provider inbox.

## Что проверено

- Unit: конфигурация только loopback, форматы телефона/сумм/статусов, HMAC по
  исходным байтам, разбор ответов моста (не отправлено/неизвестно/сессия/отказ),
  чтение телефона клиента, помощник входа.
- Исходные PostgreSQL-сценарии (15): оплата → один capture; отказ и истечение;
  незнакомый статус и отмена по сроку; оплата наперегонки с отменой; потерянный
  ответ и восстановление из истории; падение после отправки; неизвестный без
  истории и сигнал через 5 минут; немедленные отказы; параллельные worker - один
  счёт; другая сумма; отмена отправляется один раз; сбой одного счёта не
  останавливает остальные; вебхук не снимает аренду проверки.
- Присланный отчёт о независимом ревью не заменяет проверку текущего кода;
  повторная проверка и исправления описаны ниже.
- HTTP: вебхук принимает только подписанные исходные байты JSON.
- Мост и Kaspi **не** вызывались: протокол моста взят из его исходников. Поля
  ответа истории (`findByReference`) и точные статусы нужно подтвердить на
  пробном счёте.

## Установка (после зелёной CI, выполняет владелец/ответственный за VPS)

1. Kaspi Pay владельца: добавить сотрудника-кассира на **отдельный** номер,
   который больше нигде не входит в Kaspi Pay.
2. Мост: `git clone https://github.com/tapter-dev/kaspi-pos-automation
/opt/pickchick-staging/kaspi-bridge && git -C ... checkout 28c9167 &&
node .../install-overlays.mjs /opt/pickchick-staging/kaspi-bridge && npm ci --omit=dev --ignore-scripts`, пользователь
   `pickchick-kaspi`, `secrets/kaspi-bridge.env` по примеру (0600),
   unit `pickchick-kaspi-bridge.service`. Порт наружу не открывать.
3. Миграция `026_cloud_kaspi_remote.sql`. Строка `commerce_provider_accounts`:
   `kind='payment'`, `provider='kaspi-remote'`, юрлицо продавца mobile,
   `enabled=false` до приёмки. Runtime-роль: `SELECT,INSERT,UPDATE` на
   `commerce_kaspi_invoices`, `SELECT` на `identity_customers`.
4. `secrets/kaspi-remote.env` по `kaspi-remote.env.example`.
5. Вход кассира на сервере: `node infra/payments/kaspi-bridge/kaspi-login.mjs`
   (номер кассира и код из SMS вводит владелец).
6. `kaspi-check.mjs` проверяет только сессию. Команда создания реального счёта
   удалена: она обходила ledger и Webkassa. Первый денежный пилот проводить
   через коммерческий заказ после готовности чека, согласования суммы и
   реквизитов. Фиксировать обезличенный формат статусов/истории, не сырые данные.
7. Unit `pickchick-kaspi-worker.service` (шаблон путей сверить с релизом).
8. Вебхук `/v1/integrations/kaspi-remote/webhook` нужен только при
   `BRIDGE_POLLING=on` и вызывается мостом по 127.0.0.1; в публичный gateway его
   не добавлять.

## Перепроверка 29 сентября 2026

Архив владельца содержит 27 обычных файлов, побайтно совпадающих с `e71ef81`.
В локальной ветке дополнительно есть изменение CI, которого нет в архиве.
Исходники моста по SHA `28c9167f9c72cd6758a25e254bc92bc610daa485` прочитаны;
совмещённый патч проверен на применение. Сам мост не запускался; соединений
с банковскими API и счетов не было.

Исправлены найденные при повторной проверке ошибки:

- `paid/failed` теперь имеют подтверждение доставки в ledger. Сбой между двумя
  транзакциями не теряет результат; повтор использует исходный idempotency key.
- Отсутствующая/невалидная сумма не заменяется суммой заказа. Чужой operation ID
  отклоняется; восстановление из истории требует точной метки и суммы.
- Отмена сохраняется до внешнего вызова. После потери ответа повторного запроса
  нет. Это не гарантия, что отмена состоялась: неизвестный результат сверяется.
- Worker берёт одну запись перед обработкой, а не пачку с истекающими в очереди
  lease. Токен lease не позволяет старому worker переписать результат нового.
- Восстановление из истории не продлевает десятиминутный срок счёта.
- Потерянная сессия останавливает новые отправки до повторного входа и рестарта.
- Подписанные `null`/массив не дают внутреннюю ошибку вебхука. Проверка сессии
  upstream больше не принимает пустой ответ за успешный вход.

Локально: 22 Kaspi PostgreSQL-сценария + 23 прежних интеграционных сценария ядра
прошли; 8 Kaspi unit + 1 HTTP прошли; 4 проверки ограничений pilot release прошли.
База одноразовая на loopback, банк заменён FakeBridge. Это не банковская приёмка.
Предыдущая Foundation CI 36404546441 на базе 6891e41 завершилась failure в browser
recovery, остальные 5 jobs прошли. Новый выпуск VPS/онлайн-пульта не выполнялся.

## Коммерческий mobile checkout (реализован 29 сентября, выключен)

По поручению владельца сделана сторона приложения: корзина - счёт Kaspi на номер
из аккаунта - ожидание - оплачено. Живой банк не вызывался: сессии кассира нет
(KASPI_ID_REQUIRED, см. аудит). Всё проверено с FakeBridge.

API `v1/customer/checkout` (`services/api/src/customer-checkout-controller.ts`,
логика `packages/commerce-core/src/customer-checkout.ts`):

- `GET /` - `{enabled:false}` или `{enabled:true, payment_method:'kaspi', phone_masked}`;
  номер только владельцу токена и только маской `+7 701 ••• •• 67`.
- `POST /quotes` (`Idempotency-Key`) - корзина `{service_mode, items:[{sku,quantity,selections}]}`.
  Цена только из опубликованного каталога ветки (`CatalogPricing` + `issueQuote`
  с налоговой привязкой из настроек); сумма от клиента не принимается.
- `POST /orders` (`Idempotency-Key`) - заказ по quote, фискальный счёт из настроек.
- `POST /orders/:id/kaspi-payment` (`Idempotency-Key`) - попытка оплаты
  `startPaymentAttempt`, только после admission ресторана и если нет открытого или
  неизвестного счёта; повтор с тем же ключом ничего не создаёт.
- `GET /orders/:id` - только свой заказ (principal = customer id), без id операций банка.

Стадии для клиента выводятся только из фактов ledger (`customerCheckoutStage`):
`accepting` (ресторан принимает), `sending_invoice` («Отправляем счёт»),
`invoice_sent` («Счёт отправлен в Kaspi», срок до), `checking` («Проверяем оплату»,
в том числе первые 10 минут неизвестного результата), `paid` (только по capture),
`invoice_closed` (истёк/отменён/отклонён/не выставлен, можно новый счёт новым
ключом), `unconfirmed` (результат не установлен - новый счёт не создаётся),
`attention` (нужен сотрудник). Выставляет и проверяет счёт по-прежнему только worker.

Mobile (`apps/mobile/src/kaspi-checkout.ts`, `useKaspiCheckout.ts`,
`components/KaspiPayment.tsx`, экран M12): кнопка «Оплатить через Kaspi» и маска
номера на оформлении, затем экран «Оплата» со статусом, опросом (пауза в фоне,
обновление при возврате; возврат из Kaspi оплату не подтверждает), «Отправить
новый счёт» только после закрытого счёта. Ключи идемпотентности и id заказа
сохраняются до запроса: потерянный ответ и перезапуск не создают второй заказ.
Корзину очищает только статус «Оплачено».

Включение (после входа кассира, CI и отдельного согласования пилота):

1. Сборка mobile с `EXPO_PUBLIC_KASPI_CHECKOUT=1` и серверным аккаунтом
   (`EXPO_PUBLIC_CUSTOMER_AUTH=server`).
2. API env (только сервер, не `EXPO_PUBLIC_*`):
   `CUSTOMER_KASPI_CHECKOUT_ENABLED=true`, `CUSTOMER_CHECKOUT_ORGANIZATION_ID`,
   `CUSTOMER_CHECKOUT_BRANCH_ID`, `CUSTOMER_CHECKOUT_FISCAL_ACCOUNT_ID`,
   `KASPI_REMOTE_ACCOUNT_ID` (тот же, что у worker),
   `CUSTOMER_CHECKOUT_TAX_APPROVAL_REFERENCE`, `CUSTOMER_CHECKOUT_TAX_VERSION`,
   `CUSTOMER_CHECKOUT_TAX_CODE`. Налоговые значения - только утверждённые
   бухгалтером; значений по умолчанию нет. При `true` и неверных значениях API
   не стартует.
3. Права роли API: `infra/staging/customer-checkout-grants.mjs` (подключено в
   `provision.mjs`, при выключенном флаге снимаются только его INSERT). Прав на
   capture, возврат и изменение provider account нет - деньги пишет только worker.
4. В ветке опубликован каталог (`catalog_branch_heads`), `ordering_enabled=true`,
   работает admission ресторана (fulfillment transport), включён fiscal-счёт и
   Kaspi-счёт `commerce_provider_accounts.enabled=true`.

Проверки: 4 PostgreSQL-сценария commerce-core (цена из публикации, телефон из
identity, оплата только capture, истёкший/отклонённый счёт, неизвестный результат,
чужой заказ, идемпотентность), 3 unit, 3 HTTP/integration (полный путь через
API с настоящей identity, выключенный режим, ограниченная роль с grants),
7 mobile unit (повтор ключей после потери ответа/перезапуска, истёкший quote,
блок второго заказа, тексты без «Оплачено» до capture), mobile typecheck, lint,
prettier.

Не сделано и остаётся зависимостью:

- Сессия кассира Kaspi (KASPI_ID_REQUIRED) - без неё счёт не выставится.
- Кухня после оплаты: kitchen admission ждёт выданный чек, а Webkassa-адаптера нет.
  Клиент видит «Оплачено. Передаём заказ на кухню», кухонных статусов для
  коммерческого заказа пока нет.
- Меню приложения: SKU корзины = id позиции. Сейчас это совпадает, потому что
  опубликованный каталог создан из того же макета (`catalog-admin` seed). Перевод
  витрины на `v1/catalog/branches/:id` - отдельная задача (`catalog-unified`).
- Браузерный сценарий экрана и приёмка на телефоне не выполнялись.
