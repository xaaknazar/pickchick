# LAN-клиенты точки: две кассы, кухня и табло (переход 19.11)

Runbook полосы client (CL-4, CL-5). Основание: контракт перехода, §00 п. 3-4, §5.5, §6.1, §6.2
шаги 1 и 4, §10 риск 11. Всё новое выключено до явных шагов ниже: старый конфиг шлюза
работает как раньше, iiko не меняется. Автозапуск PickChick включает сам установщик программы
(решение владельца 12.11.2026), скрипты этой полосы его не включают.

## Схема

Сервер точки - отдельный моноблок PickChick **192.168.2.69**: edge, PostgreSQL, службы и шлюз
`PickChickKitchenLAN` (HTTPS, порт 3443, закреплённый сертификат). PostgreSQL и edge слушают
только loopback, в локальную сеть смотрит только шлюз. Шлюз выбирает профиль маршрутов по IPv4
клиента; адрес, которого нет в списке, получает 403 на любой запрос.

| Устройство                       | Профиль   | Что ставится                                                         | Что доступно через шлюз                                                                             |
| -------------------------------- | --------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Касса 1, касса 2 (моноблоки)     | `pos`     | PickChick POS 0.5.0+, `install-pos-client.ps1`                       | ровно маршруты pos-desktop: вход, меню, заказы, смена, продажи, чеки Webkassa, X/Z, фото меню       |
| Кухонные моноблоки (станции)     | `kitchen` | PickChick Kitchen 0.4.0+, `install-kitchen-client.ps1`               | вход сотрудника, привязка экрана, станции, очередь, действия, KDS (раскладка, панировка, инциденты) |
| Табло                            | `display` | PickChick Kitchen 0.4.0+, `install-kitchen-client.ps1 -Mode display` | привязка, сессия терминала, `fulfillment/config`, табло; без очереди кухни, входа и заказов         |
| Резервная касса на самом сервере | -         | PickChick POS без `edgeHost`                                         | шлюз не нужен: касса ходит на `127.0.0.1:3101`                                                      |

Если табло подключено к самому серверу 192.168.2.69 (второй монитор), оно работает по loopback
без `edgeHost` и в список клиентов не вносится. Собственный адрес сервера всегда имеет профиль
`kitchen` (на нём работает проверка шлюза) и в файл клиентов не вносится.

Профиль `pos` - точное зеркало allowlist pos-desktop (`apps/pos-desktop/protocol.mjs`), плюс
`/health/ready` и `media/{sha256}.webp`; лимиты те же, что у кассы: тело PIN-запросов 2 КиБ,
остальные команды 64 000 байт, ответ 4 МБ. Тест сравнивает регулярные выражения и сами
пересылаемые запросы. Профиль `kitchen` - прежний список плюс маршруты CR kds-5 и
`orders/{uuid}/restore-review`. Профиль `display` пересылает только заголовки терминала.
Любой новый маршрут кассы или кухни сначала добавляется в клиент, затем в профиль (CR в client).

## Подготовка (до 15.11)

1. **К3.** Закрепить в DHCP роутера адреса сервера, обеих касс, всех кухонных моноблоков и табло.
   Без резерва адресов список шлюза перестанет совпадать с устройствами. Адреса хранятся в
   приватной карточке монтажа, не в репозитории.
2. Для каждой кассы завести терминал в `local_terminals` (§6.2 шаг 4) и записать его UUID в
   карточку монтажа. Кухонные экраны и табло привязываются в «Устройствах» (нужен WAN).
3. Файл клиентов шлюза `clients.json` (UTF-8, массив, до 32 записей; `label` необязателен, до 60
   символов, видят только операторы):

   ```json
   [
     { "address": "<IP кассы 1>", "profile": "pos", "label": "Касса 1" },
     { "address": "<IP кассы 2>", "profile": "pos", "label": "Касса 2" },
     { "address": "<IP экрана панировки>", "profile": "kitchen", "label": "Панировка 6" },
     { "address": "<IP экрана тостов>", "profile": "kitchen", "label": "Тосты 5" },
     { "address": "<IP стола 1>", "profile": "kitchen", "label": "Сборка - зал" },
     { "address": "<IP стола 2>", "profile": "kitchen", "label": "Сборка - доставка" },
     { "address": "<IP выдачи>", "profile": "kitchen", "label": "Выдача" },
     { "address": "<IP табло>", "profile": "display", "label": "Табло" }
   ]
   ```

   Адрес - канонический частный IPv4 (10.x, 172.16-31.x, 192.168.x, без ведущих нулей), каждый
   один раз, адрес сервера не указывается.

4. Файлы поставки из RC-клиента (manifest с SHA-256 выдаёт интеграция):
   `kitchen-lan-gateway.mjs`, `lan-route-profiles.mjs`, `kitchen-lan-check.mjs`,
   `install-native-foundation.ps1` (проверенная версия, хеш закреплён в скриптах),
   `update-kitchen-lan-clients.ps1`, `install-kitchen-client.ps1`, `install-pos-client.ps1`.
   Хеш каждого файла сверить с manifest: `Get-FileHash -Algorithm SHA256 <файл>`.
5. SHA-256 сертификата шлюза - из `C:\ProgramData\PickChick\KitchenLAN\installation.json`
   (`certificateSha256`) или из строки `KITCHEN_LAN_VERIFIED certificateSha256=...` установки.
   Его передают на кассы и кухню отдельно от публичного файла (карточка монтажа): скрипты
   клиентов сверяют сертификат из файла с этим хешем.
   Сертификат должен разрешать keyCertSign, иначе кухня и касса (Electron) его не принимают
   (14.11, тестовая касса: 504 `EDGE_TIMEOUT`, «Код не принят»). Шлюз, установленный
   установщиком до 14.11 (`4df0d495…`), переустанавливают:
   [Сертификат и переустановка шлюза](../../infra/windows/kitchen-lan.md#сертификат-и-переустановка-шлюза).

## Шаг 1. К7, 10-11.11: все кухонные экраны на прежнем шлюзе

Адрес каждого моноблока для списка клиентов написан в заголовке окна PickChick POS и
PickChick Kitchen начиная со сборок 11.11 ([`desktop-updates.md`](desktop-updates.md),
«Заголовок окна»); на прежних сборках его смотрят в параметрах сети Windows.

Если шлюз ещё не установлен - сначала `install-kitchen-lan.ps1` по `infra/windows/kitchen-lan.md`
(один кухонный адрес). Затем на сервере, в повышенном Windows PowerShell 5.1 x64 под той же
учётной записью администратора, что и установка:

```powershell
.\update-kitchen-lan-clients.ps1 -ClientsFile .\clients-kitchen.json -Legacy
```

`-Legacy` не меняет код шлюза и пишет прежний формат `clientAddresses`: в файле только
`"profile": "kitchen"`, не больше 20 адресов. Табло и кассы в этом режиме не принимаются - они
появляются на шаге 2 вместе с профилями.

## Шаг 2. Окно С4 / 15-16.11: шлюз с профилями

```powershell
.\update-kitchen-lan-clients.ps1 -ClientsFile .\clients.json -GatewaySha256 <хеш> -ProfilesSha256 <хеш> -CheckSha256 <хеш>
```

Что делает скрипт по порядку:

1. Проверяет установку и ничего не меняет при отличии: служба `PickChickKitchenLAN` под
   LocalService с автозапуском, защищённые ACL папок, приватного конфига и PFX, хеши
   установленных файлов совпадают с `installation.json`, аргументы службы, правило firewall.
2. Проверяет файл клиентов теми же правилами, что и шлюз.
3. Проверяет новые файлы по хешам и запускает новый шлюз в режиме `--check` на новом конфиге:
   конфиг и пароль PFX верны, число клиентов по профилям совпадает. Служба ещё работает.
4. Сохраняет прежние файлы в `private\backup-<UTC>`, останавливает службу, заменяет конфиг на
   месте (ACL сохраняется и проверяется), ставит новый код, задаёт правилу firewall ровно эти
   адреса, запускает службу, проверяет listener и выполняет `kitchen-lan-check.mjs`.
5. Любая ошибка после остановки службы возвращает прежние конфиг, код и firewall и запускает
   службу снова (`The previous client list is restored...`). Сообщение `ROLLBACK INCOMPLETE`
   значит, что службу надо поднять вручную из `private\backup-<UTC>`.
6. Пишет `installation.json` v2 (прежний - в backup) и `public-lan-config.json` - публичный
   файл для клиентов: адрес сервера, порт 3443, сертификат, подпись точки. Секретов в нём нет.

Повторный запуск с исправленным списком безопасен: каждый запуск делает свой backup.

## Шаг 3. Кухонные моноблоки и табло (14-16.11, рядом с iiko)

На каждом устройстве под учётной записью Windows, в которой работает кухня (без повышения):

1. Установить PickChick Kitchen 0.4.0 или новее (установщик NSIS для текущего пользователя).
2. Скопировать `public-lan-config.json` и `install-kitchen-client.ps1` (сверить хеш).
3. Запустить:

   ```powershell
   .\install-kitchen-client.ps1 -PublicConfig .\public-lan-config.json -CertificateSha256 <хеш сертификата> -Mode prep
   ```

   `-Mode`: `prep` или `assembly` - экран станции, привязывается в «Устройствах»;
   `display` - табло; `staff` - вход сотрудника на фиксированном терминале
   (`-TerminalId <UUID>`, если привязка без WAN невозможна).

4. Скрипт проверяет сертификат (хеш, IP сервера в сертификате, срок), затем с этого моноблока
   по закреплённому TLS: `healthz`, маршрут своего профиля (кухня - `/edge/v1/session` даёт 401,
   табло - `fulfillment/config` даёт 200) и чужой маршрут (404 от шлюза). Так доказано, что
   сервер дал этому IP именно этот профиль. Только после этого пишется
   `%APPDATA%\PickChickKitchen\config.json`; прежний остаётся как `config.json.bak-<UTC>`.
5. Смена режима или терминала у уже настроенного экрана - только с `-Replace` (после неё экран
   привязывается заново). Предупреждение про порт 4178 значит, что локальный порт кухни занят
   другой программой - кухня не запустится, пока его не освободить.
6. Перезапустить PickChick Kitchen, привязать экран в «Устройствах», войти общим логином
   `kitchen` (табло - без входа).

## Шаг 4. Две кассы (14-16.11, рядом с iiko)

На каждом кассовом моноблоке под учётной записью кассира (без повышения):

1. Установить PickChick POS **0.5.0** или новее: прежние сборки не знают `edgeHost` и с таким
   конфигом не запускаются. Скрипт проверяет версию.
2. Скопировать `public-lan-config.json` и `install-pos-client.ps1` (сверить хеш).
3. Запустить:

   ```powershell
   .\install-pos-client.ps1 -PublicConfig .\public-lan-config.json -CertificateSha256 <хеш сертификата> -TerminalId <UUID терминала кассы>
   ```

   Печать (необязательно, без неё продажа не блокируется - «Печать не настроена»):
   `-PrinterQueue "<имя очереди Windows>"` (драйвер; ящик - настройкой драйвера или ключом) или
   `-PrinterAddress <частный IPv4> [-PrinterPort 9100] [-DrawerKick]` (сетевой ESC/POS, ящик
   импульсом через принтер). Без этих параметров ключ `printer` остаётся прежним.

4. Скрипт проверяет сертификат и профиль `pos` этого IP (`/edge/v1/session` - 401 от edge,
   `fulfillment/stations` - 404 от шлюза), затем дописывает в `%APPDATA%\PickChickPOS\config.json`
   `edgeHost`, `edgePort`, `edgeCertificatePem`, `terminalId` (и `printer`). Остальные ключи
   (`categories`, `pinLength`, `branchLabel`) сохраняются; прежний файл - `config.json.bak-<UTC>`.
5. Другой `terminalId` у уже настроенной кассы - только с `-Replace`: неотправленный журнал
   команд привязан к терминалу. Перед заменой убедиться, что журнал пуст.
6. Перезапустить PickChick POS, войти по PIN. До `pos-sales-setup.mjs enable` касса работает
   в прежнем режиме без оплаты; `GET pos/config` с каждой кассы - предусловие включения (§6.2 шаг 6).
   Касса сама называет в этом запросе свою сборку (`client_version=pos-desktop-<версия>`, CR pos-2
   §1.1): в `pos-sales-setup.mjs status` у каждой кассы видно `client_version`. Пустое значение -
   касса старше 0.5.0 или запрос шёл не из pos-desktop.
7. Журнал неотправленных команд кассы (продажа, отмена, возврат, номер чека Webkassa, закрытие
   смены) хранится в `%APPDATA%\PickChickPOS\journal-v1`. Не очищать его: команда с кнопкой
   «Проверить результат» досылается только с этой кассы и только с тем же ключом.

## iiko рядом и автозапуск

- Скрипты не останавливают, не удаляют и не настраивают iiko: его файлы, службы, автозапуск,
  принтеры и firewall не трогаются. Найденный процесс iiko только упоминается в выводе.
- Автозапуск PickChick включает установщик программы (кассы с 0.5.2, кухни с 0.4.2): он пишет
  значение `PickChickPOS` / `PickChickKitchen` в `HKCU\...\CurrentVersion\Run` текущего
  пользователя Windows и кладёт ярлык на рабочий стол, в том числе при повторной установке и при
  самообновлении. Другие значения `Run` (iiko) не читаются и не меняются. Удаление программы
  убирает значение; удаление старой версии во время обновления его оставляет. До 19.11 iiko
  остаётся рабочей программой: окно PickChick, открывшееся при входе в Windows, закрывают.
  Скрипты этой полосы автозапуск не меняют, кроме явной команды под тем же пользователем:

  ```powershell
  .\install-pos-client.ps1 -Autostart Off   # или On
  .\install-kitchen-client.ps1 -Autostart Off
  ```

  `-Autostart Off` действует до следующей установки или самообновления программы.

- Если касса и iiko печатают на один принтер, PickChick печатает только по нажатию кассира.

## Что проверено и что нет

Проверено в контейнере разработки (Linux, Node 24, PowerShell 7.4):

- профили шлюза: `pos` равен allowlist pos-desktop (регулярные выражения и пересылаемые
  запросы), `kitchen` равен allowlist приложения кухни плюс маршруты CR kds-5, табло не видит
  `/kitchen`; старый `clientAddresses` = профиль `kitchen` с прежними лимитами;
- настоящий TLS шлюза с тремя профилями, настоящий транспорт pos-desktop через шлюз (продажа,
  фото меню, лимиты, выход сотрудника без тела, сборка кассы в `GET pos/config`), `--check`;
- журнал pos-desktop принимает каждую команду оплаты ровно в том виде, в каком её пишет касса
  (все тесты кассы в режиме оплаты сохраняют журнал через проверку main), и переживает
  перезапуск;
- функции всех трёх скриптов под PowerShell 7: файлы клиентов, конфиг шлюза (его принимает
  `--check`), конфиги касс и кухни (их принимают валидаторы pos-desktop и kitchen-desktop),
  сертификат и SAN, проба профиля по закреплённому TLS, атомарная запись, отказ автозапуска
  без установленной программы.

Проверено на настоящем Windows (runner GitHub `windows-2022`, Windows PowerShell 5.1, NTFS;
`tests/operations/kitchen-lan-files.test.ps1`, задание «Windows KitchenLAN guards»):

- запись нового файла и замена существующего функциями `Write-LanNewFile` и `Set-LanFile` из
  `update-kitchen-lan-clients.ps1`, замена конфига шлюза той самой строкой, которая стоит в
  скрипте сразу после остановки службы, откат через ту же функцию;
- замена сохраняет права доступа файла (у конфига шлюза есть своё правило для учётной записи
  службы), не оставляет временных и резервных файлов, отказывает пути с потоком данных;
- ни один скрипт `infra/windows` не передаёт `$null` как путь резервной копии в `File.Replace`.

До 12.11 `update-kitchen-lan-clients.ps1` передавал именно `$null`. В PowerShell 7 это работает,
поэтому проверки на Linux были зелёными. В Windows PowerShell 5.1 `$null` для строкового
параметра .NET становится пустой строкой, `File.Replace` отвечает «The path is not of a legal
form», и шаг остановил бы шлюз, не записал бы новый конфиг и не смог бы вернуть прежний
(`ROLLBACK INCOMPLETE`). Ошибка воспроизведена на том же runner до исправления (прогон
