# Бэк-офис, вторая волна (полоса bo-ui2): закупки - включение, работа, проверка, откат

Вторая волна бэк-офиса за флагами, которые по умолчанию выключены (решение владельца 06.11).
Дизайн: `docs/architecture/cutover-2026-11/design-bo-ui.md`, раздел 9 «Вторая волна»; перенос в
облако: CR `bo-ui2-1` (миграция 076, права, флаги). Этот файл пополняется по шагам полосы; сейчас в
нём шаг 2 - «Закупки»: поставщики и их цены, заявки и приём поставки по заявке, шаг 3 - импорт
поставщиков и цен закупки из выгрузки iiko (§5), шаг 4 - отчёты склада «Остатки», «Движение» по
позициям и «К заказу» (§8) - и шаг 5 - «Расстановка», кто на какой станции (§9).

Общие правила, как у P1 (`backoffice-p1-cutover.md`):

- флаг - переменная окружения API, по умолчанию `false`, только при `BACKOFFICE_ENABLED=true`;
- пока флаг выключен, ответы API и кабинет те же, что у итога bo-ui (эталон
  `tests/integration/backoffice-p2-golden.test.mjs`, браузерный тест «supply off»);
- кабинет показывает раздел, только когда `GET .../branches/<точка>` сообщает
  `capabilities.supply=true`; порядок «сначала права, потом флаг» безопасен;
- откат - флаг `false` и перезапуск API; поставщики, цены и заявки остаются в базе.

## 1. Что включает `BACKOFFICE_SUPPLY_ENABLED`

| Что нужно                     | Где                                                                                       |
| ----------------------------- | ----------------------------------------------------------------------------------------- |
| миграция 076                  | облако, окно Cloud-2 (CR `bo-ui2-1` §4), сразу после 075                                  |
| права роли API на таблицы 076 | `infra/staging/backoffice-supply-grants.mjs`, ключ `supply` (вызов в `provision.mjs`)     |
| склад v2                      | `BACKOFFICE_STOCK_V2_ENABLED=true` (без него `loadConfig` не запускает API с этим флагом) |
| флаг                          | `BACKOFFICE_SUPPLY_ENABLED=true` в env `api` и `provision`                                |

Ключ `capabilities.supply` равен `true`, только когда роль API имеет права 076 и пишет столбцы
прихода 074 (приём заявки - это приход склада v2). Иначе ключ `false`, раздела нет, виды отвечают
`NOT_READY`.

В кабинете появляется раздел «Закупки» сразу после «Остатки», с вкладками «Заявки» и «Поставщики и
цены».

## 2. Кто что делает

| Действие                                          | Управляющий | Начальник смены | Бухгалтер | Аналитик |
| ------------------------------------------------- | ----------- | --------------- | --------- | -------- |
| смотреть заявки, поставщиков, цены, импорты цен   | да          | да              | да        | да       |
| создать и изменить черновик заявки, подать заявку | да          | да              | -         | -        |
| принять поставку по заявке, отменить заявку       | да          | -               | -         | -        |
| завести, изменить, отправить в архив поставщика   | да          | -               | да        | -        |
| ввести и исправить цену поставщика                | да          | -               | да        | -        |
| загрузить цены из выгрузки iiko (доступ скрипта)  | да          | -               | да        | -        |

Кнопки, которых роль не может, видны неактивными, и под ними написано, кто это делает. Обычная
«Поставка» на странице «Остатки» не меняется: её проводят управляющий, начальник смены и бухгалтер.
Если поставку по заявке привезли вечером без управляющего, начальник смены проводит обычную
«Поставку», а заявку потом отменяет управляющий с причиной «Принято обычной поставкой № ...» (вопрос
владельцу - `design-bo-ui.md` §9.6 в.5).

## 3. Работа: заявка от черновика до поставки

1. «Закупки» → «Заявки» → «Новая заявка». Выбрать, куда: «В цех», «В пекарню», «Хозтовары» или
   «Поставщику». Для «Поставщику» обязателен поставщик, для остальных - по желанию (только поставщик
   своего вида: цех - для цеха, пекарня - для пекарни, поставщик - для хозтоваров и поставщику).
2. Добавить строки. Под каждой строкой: остаток по учёту, минимальный запас позиции и подсказка
   «минимум - остаток» (если минимума у позиции нет, подсказки нет). «Подставить подсказку» ставит
   её в количество; «Добавить всё ниже минимума» добавляет все позиции ниже минимума. С поставщиком
   видна его цена в силе и сумма строки по ней.
3. «Сохранить черновик» или «Сохранить и подать». Незаконченный ввод переживает перезагрузку
   страницы. После подачи строки не меняются, а остаток и подсказка фиксируются на момент подачи.
4. Карточка заявки: «Скопировать текст» и «Печать». Система ничего никому не отправляет: текст
   отправляют в мессенджере вручную. В тексте нет цен - цену называет поставщик.
5. Привезли: управляющий открывает заявку → «Принять поставку». Откуда и поставщик взяты из заявки;
   ввести номер и дату накладной, фактическое количество и стоимость каждой строки по накладной.
   Не пришло - «Не пришло»; пришло лишнее - «Добавить строку». До проведения видна проверка
   документа (остаток до и после) и разница с заявкой. Проведение создаёт обычный приход склада
   (видно в «Остатки» → «Документы») и закрывает заявку; ошибочный приход исправляют сторно, как
   любой приход.
6. Не нужна: «Отменить заявку» с причиной (обязательно). Отменённая и принятая заявки больше не
   меняются.

Список заявок - по датам создания (до 92 дней), состоянию и виду; если вне выбранных дат есть
открытые черновики или поданные заявки, страница об этом пишет. «Скачать CSV» - список в тенге, столбец
«Сумма, ₸» - ожидаемая сумма по ценам.

## 4. Поставщики и цены

- «Новый поставщик»: название (одно на точку без учёта регистра и лишних пробелов) и вид: поставщик,
  цех или пекарня. Вид потом не меняется. Поставщика не удаляют: «В архив» убирает его из новых
  заявок и цен, его цены и заявки остаются; «Вернуть из архива» - обратно.
- «Цены»: цена за одну закупочную единицу (кг, л или шт; для граммовых позиций можно и за г) с
  указанного дня до следующей цены той же позиции и единицы. «В силе» - цена на сегодня, «Будет» -
  с будущего дня, «Прошлая» - история. Ошибку в цене исправляют кнопкой «Исправить» (версия
  растёт, прежняя цена - в журнале аудита).
- Настоящий список поставщиков и цен загружают из выгрузки iiko владельца скриптом
  `scripts/supplier-prices-import.mjs` (§5); вручную - то, чего нет в выгрузке. В коде, тестах и
  документах - только синтетические названия («Поставщик 1»).

## 5. Импорт поставщиков и цен закупки из выгрузки iiko (Д6)

Скрипт `scripts/supplier-prices-import.mjs` читает файл с ценами закупки, сверяет каждую строку с
точкой и загружает новых поставщиков и новые цены. Он ничего не удаляет и не меняет уже введённые
цены и поставщиков. Нужны: флаг закупок (§1, `capabilities.supply=true`) и файл доступа
управляющего или бухгалтера (право `suppliers.write`; тот же JSON-файл доступа каталога с правами
600, что у `stock-opening-import.mjs`). Запускает оператор на своём компьютере из корня
репозитория; адрес API - `--api https://<API>` (по умолчанию `http://127.0.0.1:3100`, HTTP - только
к самому компьютеру).

### 5.1 Что выгрузить из iiko

Нужна таблица, где одна строка - цена одной позиции у одного поставщика:

- поставщик (контрагент) - название;
- товар (номенклатура) - название, как в карточке позиции PickChick. Сырьё в PickChick заведено
  из ТТК iiko (`docs/operations/ttk-import-2026-10-20.md`), поэтому названия обычно совпадают;
- единица измерения: кг, г, л, мл или шт;
- цена за эту единицу в тенге;
- дата, с которой действует цена: дата приходной накладной или прайс-листа.

Где это в iiko - уточнить в iiko: названия отчётов и меню зависят от версии и настроек точки.
Подходят два вида выгрузки:

- прайс-лист поставщика (если поставщики в iiko заведены с ценами) - одна цена на позицию;
- отчёт по приходным накладным за период, например за последние 1-3 месяца, с колонками
  поставщика, товара, единицы, цены и даты накладной - тогда в PickChick попадёт и история цен
  (каждая цена действует до следующей).

Выгрузку открыть в Excel и сохранить как «CSV UTF-8» («Файл» - «Сохранить как» - тип «CSV UTF-8»).
Лишние колонки (артикул, группа, количество, сумма, НДС) удалять не нужно: скрипт их не использует
и перечисляет в отчёте. Если в выгрузке нет даты, дату указывают один раз ключом
`--valid-from ГГГГ-ММ-ДД` (только для файла без колонки даты).

До загрузки решить с бухгалтером (уточнить в iiko, что именно в выгрузке):

- цена с НДС или без: PickChick хранит цену из файла как есть, одну и ту же договорённость держать
  во всех загрузках и при ручном вводе;
- за какую единицу цена: за кг, л или шт подходят; за упаковку, порцию, бутылку - нет (строка
  попадёт в отчёт «Единица не подходит»), такие цены пересчитать в кг, л или шт в файле;
- цена за 1 г или 1 мл с дробью мельче тиына (например 0,4523 ₸) не округляется - указать цену
  за 1 кг или 1 л.

### 5.2 Колонки файла и профили

Заголовки сравниваются без учёта регистра, лишних пробелов и «ё». Профиль `iiko` (по умолчанию)
понимает русские заголовки, профиль `csv` (`--profile csv`) - короткие английские:

| Поле                       | Профиль `iiko`                                                               | Профиль `csv`   |
| -------------------------- | ---------------------------------------------------------------------------- | --------------- |
| поставщик (обязательно)    | «Поставщик», «Контрагент»                                                    | `supplier`      |
| позиция по названию        | «Товар», «Наименование», «Номенклатура», «Название», «Наименование товара»   | `name`          |
| позиция по коду PickChick  | «ingredient_id», «Код PickChick»                                             | `ingredient_id` |
| единица (обязательно)      | «Ед. изм.», «Ед.изм.», «Ед изм», «Ед.», «Ед», «Единица», «Единица измерения» | `unit`          |
| цена, ₸ (обязательно)      | «Цена», «Цена за единицу», «Цена за ед.», «Цена, тг», «Цена, ₸»              | `price_tenge`   |
| дата                       | «Дата», «Дата документа», «Дата накладной», «Действует с», «Дата цены»       | `valid_from`    |
| вид поставщика (по выбору) | «Вид поставщика»: поставщик, цех или пекарня                                 | `supplier_kind` |

Нужна хотя бы одна из колонок позиции. Код позиции - это код PickChick (uuid из плана импорта или
карточки), а не артикул iiko: артикулы iiko в PickChick не хранятся. Если к одному полю подходят две
колонки (например «Цена» и «Цена за ед.»), скрипт останавливается и просит свой профиль. Свой
профиль - JSON-файл с названиями колонок вашей выгрузки, например:

```json
{
  "source": "iiko_export",
  "columns": {
    "supplier": "Контрагент",
    "name": "Номенклатура",
    "unit": "Ед. изм.",
    "price": "Цена без НДС",
    "date": "Дата накладной"
  }
}
```

и ключ `--profile профиль.json`.

### 5.3 Как сопоставляются строки

Ничего не угадывается: всё, что нельзя сопоставить однозначно, уходит в отчёт и не загружается.

- Поставщик - по названию (регистр, пробелы и «ё» не важны). Новое название - новый поставщик
  вида «поставщик» (или вида из колонки «Вид поставщика»; вид потом не меняется). Поставщик в архиве
  цен не получает. Два поставщика PickChick с одним названием - строка в отчёт.
- Позиция - сначала по коду PickChick, если он есть в строке (код и название вместе должны
  совпадать), иначе по точному названию. Название, которое подходит к нескольким позициям, и
  выключенная позиция - в отчёт.
- Единица должна подходить позиции: кг и г - для позиций в граммах, л и мл - в миллилитрах, шт -
  в штуках.
- Цена - тенге за одну единицу, до 2 знаков после запятой, без округления. Дата - ДД.ММ.ГГГГ (или
  ГГГГ-ММ-ДД; время после даты не учитывается), 2024-2099. Дата через косую черту (05/11/2026)
  не принимается: день и месяц можно перепутать.
- Одна и та же строка (поставщик, позиция, единица, день) дважды с одной ценой - загружается один
  раз, с разными ценами - ни одна.
- Если в PickChick на этот день уже есть цена: та же - «без изменений», другая - в отчёт; импорт её
  не меняет. Если права выгрузка, цену исправляют вручную кнопкой «Исправить» (§4).

### 5.4 Порядок

1. Проверка, в PickChick ничего не пишется:

   ```text
   node scripts/supplier-prices-import.mjs --file prices.csv --branch <точка> --token-file <доступ.json> --api https://<API>
   ```

   Скрипт печатает отчёт по-русски: сопоставлено строк (новые цены и цены, которые уже есть), новые
   поставщики, итоги по каждому поставщику, сколько строк не загрузится и почему (позиция не
   найдена, неоднозначно, единица не подходит, повторы в файле, на этот день уже другая цена,
   позиция выключена или поставщик в архиве, ошибка в строке) и сами эти строки с номером строки
   файла. Пишет файл плана `prices.csv.plan.json` (права 600) и его SHA-256.

2. Исправить файл, если нужно (названия позиций как в PickChick, единицы, даты), и повторить
   проверку. Строки, которые не нужно загружать, можно оставить: они просто останутся в отчёте.
3. Управляющий (или бухгалтер) читает отчёт и подтверждает загрузку.
4. Загрузка - та же команда с `--apply --expected-plan <SHA-256 плана>`. Отправляется ровно
   проверенный план; файл должен быть теми же байтами. Загрузка идёт частями до 500 цен (API
   принимает не больше 100 КБ на команду); после неё скрипт читает цены обратно и сверяет каждую.
5. Оборвалась связь - повторить ту же команду: части, которые уже прошли, второй раз не
   отправляются.
6. Тот же файл ещё раз: проверка скажет «Загружать нечего: все сопоставленные цены уже есть в
   PickChick» - ничего не меняется.

Ключ `--json` выводит итог одной строкой JSON (для журнала оператора). Отказы скрипта (код - в
последней строке вывода ошибок):

| Код                                                                             | Что значит и что делать                                                                                                                 |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `PLAN_MISMATCH`                                                                 | SHA-256 не тот, план другой точки или файл изменён после плана: построить план заново                                                   |
| `PLAN_INVALID`                                                                  | файл плана изменён после построения: построить план заново                                                                              |
| `PLAN_EMPTY`                                                                    | в плане нечего загружать                                                                                                                |
| `STALE_PLAN`                                                                    | после плана в PickChick ввели цену, поставщика или выключили позицию: ничего не отправлено, план заново                                 |
| `API_REFUSED .../IMPORT_STALE`                                                  | то же, обнаружено сервером: эта часть не записана; построить план заново                                                                |
| `API_REFUSED .../IMPORT_ALREADY_APPLIED`                                        | эта часть уже загружена другой командой; повторный запуск с `--apply` её пропустит                                                      |
| `API_UNREACHABLE`                                                               | API не ответил: повторить ту же команду                                                                                                 |
| `SUPPLY_OFF`, `FORBIDDEN`                                                       | закупки выключены на сервере или у доступа нет права (нужен управляющий или бухгалтер)                                                  |
| `FILE_HEADER`, `FILE_INVALID`, `FILE_ENCODING`, `VALID_FROM`, `PROFILE_INVALID` | заголовки, пустой файл или больше 5000 строк, кодировка (нужен CSV UTF-8), дата или профиль: исправить файл или ключи                   |
| `TRUNCATED`                                                                     | у точки больше 500 поставщиков или у поставщика больше 1000 цен: скрипт не проверит их все, разделить загрузку и сообщить разработчикам |

### 5.5 Проверка результата

- «Закупки» - «Поставщики и цены» - блок «Импорт цен из iiko» внизу: дата и кто загружал, файл,
  «Загружен полностью», сколько новых цен и поставщиков загружено, отчёт по категориям, строки,
  которые не загрузились (с причиной словами и фильтром по причине), поставщики этого импорта и
  сколько цен исправлено вручную после импорта. Видят все роли; на странице ничего не меняется.
  В выпадающем списке - последние 20 импортов. В отчёте хранятся первые строки с замечаниями
  (сколько всего - написано); полный список - в файле плана.
- «Цены» у поставщика: у загруженных цен в колонке «Откуда цена» - «Импорт».
- «Загружен не полностью: частей 1 из 3» - повторить ту же команду с `--apply`.

### 5.6 Если импорт ошибочный

Импорт не удаляет и не отменяется целиком (как и ручной ввод). Неверную цену исправляют кнопкой
«Исправить» в ценах поставщика: она становится ручной, прежняя остаётся в журнале аудита; лишнего
поставщика отправляют в архив. Поэтому сначала всегда проверка и отчёт.

## 6. Проверка после включения

1. `GET .../branches/<точка>` под управляющим: `capabilities.supply=true`, в `permissions[]` в конце
   `suppliers.write`, `supply.write`, `supply.close`.
2. В кабинете: раздел «Закупки» после «Остатки», вкладки «Заявки» и «Поставщики и цены». Запись
   (поставщик, заявка, приём) проверяют на синтетической точке стенда, не на рабочей.
3. Под начальником смены: «Новая заявка» активна, «Принять поставку» и «Отменить заявку» неактивны с
   объяснением.

## 8. Отчёты склада: «Остатки», «Движение», «К заказу» (`BACKOFFICE_STOCK_REPORTS_ENABLED`)

Шаг 4 второй волны. Отдельного раздела нет: это вкладки страницы «Остатки». Отчёты только читают
склад; миграции и прав сверх тех, что уже даёт `backofficeGrants`, не нужно (076 не участвует).

### 8.1 Включение

| Что нужно | Где                                                                                                      |
| --------- | -------------------------------------------------------------------------------------------------------- |
| склад v2  | `BACKOFFICE_STOCK_V2_ENABLED=true` (без него `loadConfig` не запускает API с этим флагом)                |
| флаг      | `BACKOFFICE_STOCK_REPORTS_ENABLED=true` в env `api` (и `provision`, если он читает те же переменные)     |
| кабинет   | новая сборка кабинета и прокси (allowlist `ops/stock?view=balances` и `?view=reorder`); шлюз уже пускает |

Ключ `capabilities.stock_reports` равен `true`, когда API видит склад v2 (столбцы 074). Тогда на
странице «Остатки» вкладка «Остатки» строится сервером, во «Движении» появляется «Движение по
позициям», а после «Движения» - вкладка «К заказу». В карточке ингредиента появляется флажок «Мясо:
заказывать на 3 дня среднего расхода», а при включённых «Закупках» - «Откуда обычно приходит».

### 8.2 Что на экранах

- **«Остатки»**: по каждой позиции остаток, минимум, состояние словами («Ниже минимума», «Нет
  запаса», «В наличии», «Не используется»), последний подсчёт, последнее движение, стоимость по
  средней себестоимости и по цене последней поставки (без сторнированных поставок; без поставки -
  «нет закупки»). Фильтры и CSV.
- **«Движение»** за период до 92 дней: блок «Движение по позициям» - на начало, пришло, ушло, на конец
  и из чего (поставки, выпуск производства, списано по продажам, списания, в производство,
  инвентаризация, сторно). На начало + пришло - ушло = на конец по количеству и по сумме; если у
  позиции конец не сходится с историей документов, экран пишет «не сходится» и просит сообщить
  владельцу (в норме этого не бывает). CSV «движения по позициям» и прежний CSV строк документов.
- **«К заказу»**: позиции ниже цели или рядом с ней, средний расход в день за 7 и 14 дней, «хватит на»,
  цель, «заказать» с суммой по последней цене, состояние. Правило написано под таблицей:
  - цель - минимальный запас из карточки; у позиции с флажком «Мясо» - 3 дня среднего расхода
    (больший из средних за 7 и 14 дней), но не меньше минимума;
  - заказать = цель - остаток, если остаток меньше цели; «рядом с минимумом» - остаток не больше цели
    плюс 20 %;
  - расход - списание по продажам и расход в производство за полные дни до сегодняшнего; списания и
    инвентаризации расходом не считаются.
- **«Создать заявку»** (при включённых «Закупках», управляющий и начальник смены): открывает новую
  заявку с отмеченными строками и предложенными количествами; ничего не сохраняется, пока человек не
  нажмёт «Сохранить черновик» или «Сохранить и подать». Вид заявки - общий «Откуда» отмеченных
  позиций, иначе «Поставщику» (экран говорит об этом). Бухгалтер и аналитик видят кнопку неактивной
  с объяснением.

### 8.3 Честность цифр

Пока продажи не списываются со склада автоматически (автосписание выключено, в режиме проверки или
его служба отстаёт), каждая вкладка пишет: «Продажи не списываются со склада автоматически: остатки,
движение и расход здесь - без продаж» (или «Списание по продажам не работает: N продаж не обработаны
с ЧЧ:ММ ...»). Тогда в «К заказу» расход - только производство, и цель мяса может быть занижена:
заказывайте по минимуму и по факту подсчёта. После включения автосписания средний расход считается с
первого полного дня после старта (`start_at`), под правилом это написано.

### 8.4 Проверка после включения

1. `GET .../branches/<точка>` под управляющим: `capabilities.stock_reports=true` последним ключом
   второй волны; `permissions[]` не меняется.
2. Кабинет: вкладки «Остатки», «Движение», «К заказу»; в «Движении» за неделю у каждой позиции на
   начало + пришло - ушло = на конец, нет пометок «не сходится»; конец сегодняшнего дня равен
   остатку во вкладке «Остатки».
3. Отметить у мяса «Мясо» в карточке (управляющий), открыть «К заказу» и сверить цель с правилом.
4. Под бухгалтером: «Создать заявку» неактивна с объяснением; отчёты видны.

Автотесты: `packages/backoffice-core/tests/stock-reports.test.mjs` (PostgreSQL: сверка движения по
позициям и итогам, соседние периоды, конец = остатки, цена последней закупки, правило «К заказу» на
7 и 14 днях со сторно, настоящий воркер автосписания и режимы, все роли, флаг выключен, роль API с
правами облачной полосы), `stock-reports-unit.test.mjs` (правило и периоды),
`tests/backoffice/stock-reports-p2-ui.test.mjs` (allowlist, тексты, CSV, заявка из «К заказу»),
`tests/backoffice/stock-reports-p2-browser.test.mjs` (Chromium, 1440 и 390 px, четыре роли, флаг
выключен и включён), `tests/integration/backoffice-p2-flags.test.mjs`,
`backoffice-p2-golden.test.mjs`.

### 8.5 Откат

`BACKOFFICE_STOCK_REPORTS_ENABLED=false` и перезапуск API: вкладка «К заказу» и блок «Движение по
позициям» пропадают, «Остатки» строятся по-старому, `view=balances|reorder` - `INVALID_REQUEST`.
Флажки «Мясо» и «Откуда» в карточках остаются; кабинет без флага их не показывает и при сохранении
карточки не стирает.

## 9. Расстановка (`BACKOFFICE_STAFF_ASSIGNMENT_ENABLED`)

Шаг 5 второй волны (А9): кто из сотрудников на какой станции с ЧЧ:ММ, перестановки в час пик,
история дня. Расстановка видна в «Табеле» и в чек-листе закрытия смены менеджера. Дизайн и схемы -
`design-bo-ui.md` §9.4 «Сделано в шаге 5»; там же чтение для будущей статистики ошибок кухни (КД9).

### 9.1 Включение

| Что нужно                     | Где                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| миграция 076                  | облако, окно Cloud-2 (CR `bo-ui2-1` §4), сразу после 075                                         |
| права роли API на таблицу 076 | `infra/staging/backoffice-supply-grants.mjs`, ключ `staffAssignment` (вызов в `provision.mjs`)   |
| должности                     | `BACKOFFICE_STAFF_POSITIONS_ENABLED=true` (без него `loadConfig` не запускает API с этим флагом) |
| флаг                          | `BACKOFFICE_STAFF_ASSIGNMENT_ENABLED=true` в env `api` и `provision`                             |
| кабинет                       | новая сборка кабинета и прокси, шлюз стенда с видом `staff-assignments` (иначе 404 от шлюза)     |

Порядок: сначала `provision` с флагом (права `SELECT, INSERT, UPDATE` на `bo_staff_assignments`),
потом API с флагом. Ключ `capabilities.staff_assignment` равен `true`, только когда включены
должности и у роли API есть эти права; иначе ключ `false`, раздела нет, вид отвечает `NOT_READY`.

Станции берутся из списка должностей точки - те же коды, что у экранов кухни: «Выдача (2)»,
«Выдача доставки (3)», «Сборка - зал (стол 1)», «Сборка - доставка (стол 2)», «Тосты и бургеры
(5)», «Панировка (6)», и станции без экрана: «Кассир (1)», «Жарщик (7)», «Заготовщик (8)», «Раннер
(9)». У менеджеров станции нет. Станция выключенной должности новых назначений не принимает.

### 9.2 Кто что делает

| Действие                                              | Управляющий | Начальник смены | Бухгалтер | Аналитик |
| ----------------------------------------------------- | ----------- | --------------- | --------- | -------- |
| смотреть расстановку дня, историю, станции в «Табеле» | да          | да              | да        | да       |
| поставить на станцию, переставить, закончить          | да          | да              | -         | -        |
| поставить на станцию не по должности (с причиной)     | да          | -               | -         | -        |

Права: `staff.assign` (управляющий, начальник смены) и `staff.assign_override` (только
управляющий). Кому действие недоступно, тот видит кнопку неактивной с объяснением: «Расстановку
ведут управляющий и начальник смены.» или «Поставить сотрудника не по должности может только
управляющий.».

### 9.3 Работа

Раздел «Расстановка» - в меню сразу после «Смены».

1. Утром страница открывается на текущем дне смены. Если с прошлого дня остался открытый интервал,
   сверху написано, кто и где: «Закончить» у этого интервала (время - того дня смены).
2. «Поставить на станцию»: сотрудник, станция, время ЧЧ:ММ (по умолчанию - сейчас). Сначала в
   списке станции его должности и доп. станций из карточки. Сотрудники без станции - в списке
   «Без станции» с кнопкой «Поставить».
3. «Переставить» у человека на станции: новая станция и время. Прежний интервал закрывается в это
   же время, новый открывается; на карточке старой станции остаётся «Было: ...».
4. «Закончить» - человек ушёл со станции (перерыв, конец смены).
5. Не по должности: если станция не из должности сотрудника, управляющий пишет причину (от 3
   символов), она видна в истории («Не по должности: ...»). Начальник смены так поставить не может:
   он ставит по должности или просит управляющего добавить доп. станцию в карточке.
6. «История дня» внизу - все интервалы дня: станция, время, кто поставил, кто закончил, причина.

Правила, которые проверяет сервер:

- у сотрудника один открытый интервал; интервалы одного сотрудника не пересекаются;
- новое время не раньше начала текущего интервала и не позже, чем через 5 минут от текущего
  времени; конец - не раньше начала;
- перестановка - в том же дне смены; интервал прошлого дня сначала заканчивают;
- если два человека изменили расстановку одновременно, второй получает «Расстановку изменили в
  другом окне», страница обновляется.

### 9.4 Ночь и день смены

День смены начинается в 06:00. Время с 00:00 до 05:59 - ночь после дня смены: расстановка в 01:30
в ночь на 19.11 относится ко дню 18.11, в истории - с пометкой «(ночь)». Интервал, начатый ночью,
заканчивают тоже до 06:00 того же утра. Страница открывается на текущем дне смены по этому же
правилу (до 06:00 - ещё вчерашний день); другой день выбирают в поле «День смены», кнопка «К
сегодняшнему дню» возвращает на текущий.

### 9.5 Чек-лист смены и «Табель»

- **Чек-лист.** При закрытии смены менеджера последним пунктом идёт «Расстановка заполнена»
  (обязательный, с автопроверкой «Расставлено: ...»). Проверка - проблема, если за день никого не
  ставили, если кто-то из опубликованного графика дня без интервала (до 10 имён) или если открыт
  интервал прошлого дня. Как у других пунктов с автопроверкой: при проблеме ответ без комментария
  (от 3 символов) не принимается. Шаблон чек-листа точки этот пункт не содержит и не меняется.
- **«Табель».** Во вкладке «Табель» раздела «Смены» в списках «День» и «Неделя» колонка «Станции»
  («Сборка - зал (стол 1) 10:00 - 13:30; Выдача (2) с 13:30»), в сетке месяца - точка после часов и
  станции в подсказке ячейки. Если по «Расстановке» человек работал, а записи в табеле нет, это
  написано под таблицей. Часы табеля расстановка не меняет.

### 9.6 Проверка после включения

1. `GET .../branches/<точка>` под управляющим: `capabilities.staff_assignment=true` последним
   ключом второй волны; в конце `permissions[]` - `staff.assign`, `staff.assign_override` (у
   начальника смены - только `staff.assign`).
2. Кабинет: «Расстановка» после «Смены», сетка станций дня. Запись (поставить, переставить, не по
   должности, закончить) проверяют на синтетической точке стенда, не на рабочей.
3. Под начальником смены: «Поставить на станцию» активна; станция не по должности - с объяснением,
   «Сохранить» неактивна.
4. Под бухгалтером и аналитиком: все кнопки неактивны с объяснением, история видна.
5. Закрытие смены менеджера: последний пункт «Расстановка заполнена» с проверкой. «Табель»:
   колонка «Станции».

Автотесты: `packages/backoffice-core/tests/staff-assignments.test.mjs` (PostgreSQL: флаг выключен,
станции, поставить и переставить в одной транзакции, закончить, ревизии и повтор запроса,

helper-а), `staff-assignments-unit.test.mjs`, `tests/backoffice/assignment-ui.test.mjs` (модель,

`backoffice-p2-golden.test.mjs`.

### 9.7 Откат

`BACKOFFICE_STAFF_ASSIGNMENT_ENABLED=false` и перезапуск API: раздел и колонка «Станции» в
«Табеле» пропадают, вид отвечает 404, команды - `INVALID_REQUEST`, в чек-листе закрытия нет пункта
