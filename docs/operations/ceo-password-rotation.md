# Смена пароля существующего CEO

Офлайн-оператор `infra/backoffice-login/accounts.mjs rotate` готовит новый файл
на Mac/Linux. Он не обращается к серверу и не меняет работающий кабинет.
Самостоятельной смены пароля в интерфейсе бэк-офиса пока нет.

Пароль выбирает и вводит владелец в локальном Terminal. Не передавать его в чат,
аргументы команд, environment или clipboard агента. Существующий файл выдачи
с прежним паролем читать не требуется. Генератор `provision.mjs` для ротации
не использовать: он создаёт одноаккаунтный v1 и может потерять другие аккаунты.

## Подготовка владельцем

Оператор заранее создаёт приватный локальный каталог вне Git/общих облачных папок
и передаёт владельцу только путь. Владелец сам выполняет следующий ввод в своём
Terminal (вместо пути ниже - согласованный приватный каталог):

```sh
python3 - /private/path/ceo-new-password.txt <<'PY'
import getpass, os, sys, warnings
warnings.simplefilter('error', getpass.GetPassWarning)
password = getpass.getpass('Новый пароль CEO (16-256 символов): ')
confirmation = getpass.getpass('Повторите новый пароль: ')
if password != confirmation or not 16 <= len(password) <= 256:
    raise SystemExit('Пароли должны совпадать и содержать 16-256 символов')
fd = os.open(sys.argv[1], os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, 'w', encoding='utf-8') as file:
    file.write(password)
    file.flush()
    os.fsync(file.fileno())
print('Приватный файл сохранён; пароль не напечатан')
PY
```

`getpass` отключает эхо; при невозможности безопасного ввода команда завершается.
Существующий файл не перезаписывается. Сохранить пароль в личном менеджере паролей.

## Офлайн-ротация

До применения получить текущий server accounts file по доверенному доступу
в приватную локальную копию 0600, не печатая содержимое. Зафиксировать его SHA-256
для последующей проверки неизменности установленного файла. Выполнить:

```sh
node infra/backoffice-login/accounts.mjs rotate \
  /private/path/current-accounts.json ceo \
  /private/path/ceo-new-password.txt /private/path/next-accounts.json
```

Меняются только `salt` и `hash` выбранного аккаунта. `username`, `token`, `actor_id`,
`origin`, формат v1/v2, порядок и все поля остальных аккаунтов сохраняются.
Роль `manager` остаётся в API; этот оператор роли не меняет. Существующий пароль
повторно выбрать нельзя. Пробелы в пароле сохраняются; допустим только один
завершающий LF/CRLF, добавленный текстовым редактором.

Входные файлы должны принадлежать текущему пользователю, быть обычными файлами
0600 без symlink/hardlink; проверяется открытый descriptor, UTF-8 и размер.
Выход создаётся эксклюзивно 0600. Любая ошибка оставляет исходные файлы прежними;
новый файл сам по себе ничего не включает. Тесты используют только синтетические
секреты и настоящую проверку входа: старый CEO-пароль отклоняется, новый и пароль
другого сотрудника работают, идентичность и права сохранены.

## Отдельное применение

После полной CI и согласованного окна оператор берёт штатный release lock,
сверяет текущий SHA-256 с сохранённым baseline и сохраняет приватную резервную
копию. При несовпадении остановиться и подготовить файл от свежего baseline;
не перетирать параллельные изменения аккаунтов.

Отдельный `infra/backoffice-login/rotate.py` выполняется из проверенного immutable
архива `prepare.py`; по умолчанию только проверяет. Он принимает полную зелёную CI
исходника оператора, точные source/image текущего staff-login, API/public pointers,
front/gateway hashes и SHA-256 двух приватных конфигураций. Новая конфигурация
передаётся на VPS отдельным файлом 0600; самого пароля в ней нет, только хеш.

```sh
python3 "$INCOMING/infra/backoffice-login/rotate.py" \
  --source-sha "$OPERATOR_SHA" --ci-proof "$CI_PROOF" \
  --expected-portal-sha "$STAFF_SHA" --expected-portal-image "$STAFF_IMAGE" \
  --expected-api-sha "$API_SHA" --expected-public-sha "$PUBLIC_SHA" \
  --expected-front-hash "$FRONT_HASH" --expected-gateway-hash "$GATEWAY_HASH" \
  --expected-private-sha256 "$CURRENT_CONFIG_HASH" \
  --candidate "$NEXT_CONFIG_FILE" --candidate-sha256 "$NEXT_CONFIG_HASH"
```

После просмотренного preflight повторяется та же команда с `--apply`. Проверка
JSON допускает только новую уникальную соль и хеш существующего `ceo`; изменение
любого другого поля блокируется до остановки. Оператор закрепляет исходные
inode/device файла, проверяет резервную копию и её восстановление в отдельный
файл. Останавливает только staff-login, сохраняет inode bind mount при точечной
CAS-записи и запускает **тот же** контейнер. Image, Config, HostConfig, Mounts,
все соседи и ingress сравниваются; новые образы/службы/сети не создаются.

Простой atomic rename исходного файла не обновляет уже открытый Docker bind mount.
Штатный `update.py` по-прежнему запрещает изменение credentials; новый оператор
его проверку не обходит. До отправки stop сохраняется уникальный attempt. Любой
незавершённый apply оставляет lock и доказательства, без автоматического возврата
раскрытого старого пароля. После успешного apply нужна отдельная приёмка входа
владельцем; HTTP health не объявляется подтверждением его пароля.

Локально прошли реальные file/inode/CAS проверки, отказ salt-collision и изменения
других аккаунтов, default read-only, штатный stop/start и потерянный ответ start
с сохранением нового файла/lock/attempt без отката. Это не факт живой ротации.

После замены завершатся все сессии портала. Владелец входит как `ceo` на
`https://pickchick.kz/backoffice/`, проверяется прежняя роль manager; остальные
аккаунты сохраняют свои пароли. API/БД/Kaspi/Windows/iPad не изменяются.
Не откатывать раскрытый старый пароль автоматически при неизвестном результате:
сохранить блокировку и проверить состояние. После приёмки владелец удаляет
приватный файл нового пароля; резервные конфигурации остаются защищёнными.
