# Автоматическая копия базы кассы (edge)

Аудит 19.10, пункт 6.4, действие владельца 16. Задача Windows каждый час делает
зашифрованную проверенную копию базы `pickchick_edge` во второе место (второй физический
диск или папку NAS) и хранит 48 часовых и 14 дневных копий. Восстановление - по
[docs/operations/edge-restore.md](../../docs/operations/edge-restore.md).

Статус: код и тесты готовы, на реальной кассе не устанавливалось и не запускалось.

## Что нужно от владельца

1. Второе место: отдельный физический диск кассы (NTFS, внутренний или постоянно
   подключённый USB) или папка на NAS вида `\\nas\share\pickchick-cashier`. Раздел того же
   диска (`D:` на одном диске с `C:`) установщик не принимает: при отказе диска копия
   пропадёт вместе с базой.
2. Окно 20-30 минут на кассе для установки и первой копии (продажи не останавливаются).
3. Место, где будет храниться копия ключа шифрования (менеджер паролей владельца или
   USB-носитель в сейфе), отдельно от копий. Без ключа копии восстановить нельзя; с ключом
   любой, у кого есть копии, может их прочитать.
4. Решение, включать ли сигнал в пульсе кассы (`-ReportInHeartbeat`), чтобы мониторинг VPS
   предупреждал о просроченной копии. Требует обновлённых API и обработчика кассы (ниже).

## Установка

Файлы поставки лежат в одной папке: `install-edge-backup.ps1`, `edge-backup-lib.mjs`,
`edge-backup-task.mjs`, `edge-backup-setup.mjs`, `edge-backup-restore.mjs`,
`native-edge-backup-ledger.json`. Установщик сверяет их SHA-256 с закреплёнными в нём
значениями и копирует в защищённую папку `C:\Program Files\PickChick\EdgeBackup\tool-<id>`
до запуска. Запускать в повышенном x64 Windows PowerShell 5.1.

```powershell
# 1. Только чтение: состояние задачи, последний результат, возраст копии.
.\install-edge-backup.ps1

# 2. Проверка без изменений: пути, закрепления, фундамент, схема, роль, план задачи.
.\install-edge-backup.ps1 -Mode Install -BranchId <uuid точки> -Destination 'E:\PickChickBackup' -DryRun

# 3. Установка и первая копия (ждёт до 20 минут и печатает результат).
.\install-edge-backup.ps1 -Mode Install -BranchId <uuid точки> -Destination 'E:\PickChickBackup'
```

Параметры: `-HourlyCopies` (по умолчанию 48, 1-168), `-DailyCopies` (14, 1-90),
`-MaxAgeMinutes` (120, 60-4320: после этого копия считается просроченной),
`-ReportInHeartbeat` (выключен), `-FoundationReleaseName` (`edge-0186902`),
`-PostgresRelease` (`18.6-3`). Повторный Install меняет место и хранение; ключ и пароль
роли при этом не меняются никогда.

Install делает:

- папки `C:\ProgramData\PickChick\EdgeBackup\{private,staging,logs,health}` с
  защищёнными правами (только SYSTEM и Администраторы; `health` дополнительно читает
  LocalService - только запись о здоровье, без секретов);
- для диска - папку назначения с теми же правами; для NAS права задаются на самом NAS;
- ключ архива `private\backup-key.json` (256 бит, создаётся один раз);
- роль PostgreSQL `pickchick_edge_backup` и её пароль `private\backup-db.json` (один раз;
  у существующей роли пароль не сбрасывается);
- конфигурацию `private\edge-backup.json` (место, хранение, лимит, часовой пояс точки);
- задачу `\PickChick\PickChickEdgeBackup`: учётная запись SYSTEM (работает без входа
  оператора), каждый час в :37 и через 10 минут после включения ПК, пропущенный запуск
  выполняется при первой возможности, не более одного запуска одновременно, лимит
  50 минут, работает и от батареи/ИБП. Аргументы задачи: только путь к инструменту и к
  конфигурации, без пароля и ключа.

## Ключ

Сразу после установки скопируйте `C:\ProgramData\PickChick\EdgeBackup\private\backup-key.json`
в место хранения владельца и проверьте, что копия открывается. В файле есть `keyId`; тот же
`keyId` записан у каждой копии (`*.pcbak.json`) и в `Inspect`. Если диск кассы откажет, ключ
есть только у владельца. Ключ не заменяется повторной установкой; новый ключ означает
удаление старого файла вручную и новую установку, после этого старые копии читаются только
старым ключом.

## Как устроен один запуск

1. Блокировка запуска (`staging\run.lock`; старше 3 часов - остаток сбоя). Пока открыт
   общий файл обслуживания `EdgeTools\unified-menu-maintenance.lock`, копия пропускается
   (`MAINTENANCE`); пока идёт копия, скрипты обслуживания не получают этот файл и ждут.
2. Место назначения должно быть доступно, иначе база не читается вообще.
3. Вход ролью `pickchick_edge_backup`, одна транзакция REPEATABLE READ: идентификатор
   кластера PostgreSQL из фундамента, журнал миграций точно равен проверенной схеме
   020, 021, 022 или 023 (имя и SHA-256 каждого файла), ровно одна точка с заданным id,
   число строк каждой таблицы, экспорт снимка.
4. `pg_dump --format=custom --snapshot=...` того же снимка в `staging` (пароль - во
   временном pgpass-файле, удаляется сразу после дампа), `pg_restore --list`: в архиве
   есть данные каждой таблицы.
5. Шифрование AES-256-GCM (отдельный подключ HKDF на каждую копию) сразу во временный
   файл на втором месте, сброс на диск, переименование, полное чтение копии с проверкой
   подлинности и SHA-256, затем файл-паспорт `*.pcbak.json`. Только копия с паспортом
   считается готовой. Внутри архива зашифрованы также журнал миграций и число строк
   каждой таблицы - по ним проверяется восстановление.
6. Только после успешной копии - хранение: самая новая копия каждого из 48 последних
   часов с копиями и каждого из 14 последних дней (часовой пояс точки); самая новая
   всегда остаётся. Остатки прерванных запусков старше 6 часов удаляются. Файлы других
   касс, ссылки и чужие файлы не трогаются никогда.
7. Незашифрованный дамп удаляется из `staging` при любом исходе; остатки сбоев удаляются
   в начале следующего запуска.

Проверка копии - список архива, SHA-256 и полное расшифрование. Восстановление в
отдельную базу при каждом запуске не делается (для этого роли копии нужны права на
создание баз); полную репетицию делать по edge-restore.md и периодически
`backup-native-service.mjs`.

## Схемы

Разрешены только проверенные схемы 020-023 (`native-edge-backup-ledger.json`). Касса
сейчас на 020; 021-023 придут с выпуском runtime 21.10. Любая другая схема (например,
новая миграция 024) останавливает копию с кодом `UNREVIEWED_SCHEMA`, мониторинг это
показывает. Каждая новая edge-миграция требует добавить её в ledger, проверить и заново
выполнить Install этой папкой поставки (новые закрепления).

## Права

- Роль `pickchick_edge_backup`: LOGIN, NOINHERIT, без SUPERUSER/CREATEDB/CREATEROLE/
  REPLICATION/BYPASSRLS, не более 3 соединений; CONNECT только к `pickchick_edge`;
  членство только в `pg_read_all_data` с INHERIT TRUE и SET FALSE. Права таблиц других
  ролей не меняются. Установщик доказывает, что роль читает каждую таблицу и
  последовательность и не может писать, двигать последовательности, создавать объекты,
  выполнять функции владельца (`edge_restore_fence`, `fulfillment_display_allocate`) и
  создавать временные таблицы.
- Пароль роли передаётся PostgreSQL только как SCRAM-хеш; в аргументах, выводе и журнале
  его нет. Журнал `logs\edge-backup.log` и `health\status.json` содержат только коды,
  время и счётчики.

## Сигнал здоровья

- `health\status.json`: `state` (`ok`, `failed`, `skipped`), код ошибки, время последней
  попытки и последней успешной проверенной копии, схема, число копий, `keyId`.
- `.\install-edge-backup.ps1` (Inspect) показывает возраст копии в минутах и `stale`.
- Результат последнего запуска в Планировщике: 0 - копия сделана или пропущена из-за
  обслуживания, 1 - нужна проверка.
- С `-ReportInHeartbeat` обработчик кассы (FulfillmentWorker) добавляет в пульс поле
  `edgeBackup`, но только пока последняя проверенная копия старше `-MaxAgeMinutes` или её
  не было, и не раньше чем через 30 минут после своего запуска: касса, выключенная на
  ночь, утром ждёт копию, которую задача делает через 10 минут после включения ПК.
  API пишет строку `edge_backup_attention` (не чаще раза в 4 минуты на точку),
  watchdog VPS поднимает проверку `edge.backup` (warning; critical, если копии нет
  24 часа и дольше) и закрывает её, когда строки прекращаются. Старый API отклоняет поле:
  обработчик сразу повторяет пульс без него (сигнал закрытой кассы сохраняется) и час не
  отправляет его снова. Нужны новый API (облако) и новый runtime кассы; до этого флаг ни на
  что не влияет.
- В кабинете возраст копии не показывается: для этого нужна облачная миграция (номер этой
  полосе не выделен) и правка центра устройств, который занят другой задачей.

## NAS

Задача работает от SYSTEM, к сетевой папке она обращается как учётная запись компьютера
кассы (`<домен>\<имя-ПК>$`). В рабочей группе без домена NAS обычно не пускает такую
учётную запись. На месте проверить: Install c папкой NAS, затем результат первого
запуска; при `DESTINATION_UNAVAILABLE` - разрешить на NAS запись учётной записи
компьютера (домен) или выбрать второй диск. Хранение учётных данных NAS для SYSTEM этим
инструментом не реализовано; это отдельное решение после выбора NAS.

## Удаление и откат

```powershell
.\install-edge-backup.ps1 -Mode Uninstall -DryRun
.\install-edge-backup.ps1 -Mode Uninstall                       # только задача
.\install-edge-backup.ps1 -Mode Uninstall -RemoveDatabaseRole -BranchId <uuid>
```

Удаление снимает задачу (и при `-RemoveDatabaseRole` роль с её паролем). Ключ,
конфигурация, журнал, запись о здоровье и все копии остаются. Задача ничего не меняет в
базе, службах и настройках кассы, поэтому для отката достаточно Uninstall.

## Коды

| Код                                                            | Что значит                                                   |
| -------------------------------------------------------------- | ------------------------------------------------------------ |
| `DESTINATION_UNAVAILABLE`                                      | второе место не найдено или не читается                      |
| `DESTINATION_FULL`                                             | на втором месте меньше размера дампа + 64 МБ                 |
| `DESTINATION_WRITE_FAILED`, `VERIFY_FAILED`                    | запись или проверка копии не удалась; файл копии удалён      |
| `UNREVIEWED_SCHEMA`                                            | схема базы не входит в 020-023                               |
| `CLUSTER_MISMATCH`, `BRANCH_MISMATCH`                          | другой кластер PostgreSQL или другая точка                   |
| `DATABASE_UNAVAILABLE`, `SNAPSHOT_FAILED`                      | роль не вошла или не прочитала снимок                        |
| `DUMP_FAILED`, `ARCHIVE_INCOMPLETE`                            | pg_dump не завершился или в архиве нет данных таблицы        |
| `KEY_INVALID`, `CREDENTIAL_INVALID`, `CONFIG_INVALID`          | повреждён файл ключа, пароля или конфигурации                |
| `MAINTENANCE`, `LOCKED`                                        | пропуск: идёт обслуживание или другой запуск (не ошибка)     |
| `RETENTION_FAILED`, `CLEANUP_FAILED` (предупреждения при `ok`) | копия готова, но старые копии или временные файлы не удалены |

## Проверено и не проверено

Проверено локально (Linux, PostgreSQL 18): роль и её права, запуск с поддельными
`pg_dump`/`pg_restore`, читающими через экспортированный снимок, отказы и хранение,
формат и шифрование, и отдельно настоящие `pg_dump`/`pg_restore` 18 под этой ролью с
полным восстановлением копии в новую базу и сверкой строк. Установщик проверен разбором
PowerShell, закреплениями и проверками функций в PowerShell 7 на Linux.

Не проверено (только на кассе): Windows PowerShell 5.1 и Планировщик, ACL NTFS,
`Get-Partition`, запуск от SYSTEM без входа оператора, NAS, блокировка файла
обслуживания между Node и PowerShell, `pg_dump.exe` 18.6, длительность копии на
реальной базе, копия ключа у владельца, восстановление на стенде по edge-restore.md.
